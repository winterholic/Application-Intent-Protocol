# DD-07. 같은 동작을 여러 건에 한 번에 적용하다 일부가 안 되면 어떻게 하는가

> 결정 상태: **검증 필요** (새 기준: [B §5](../alignment/B-decision-reclassification.md#5-dd-문서의-현재-처리-상태))
> 기존 에이전트 리뷰·추천은 이전 지침 아래 작성된 검토 이력이다. 제안 본문은 보존하되 새 원문과 B의 확정 기준에 충돌하면 그 기준을 우선한다.
> 범위: DD-02의 **bulk capability**(같은 capability를 여러 대상에 적용)의 성공 단위. DD-02 W-I4·W-I7이 "T11 `[미정]`"으로 넘긴 질문이다. **C'(묶음)는 범위 밖**이다. C'의 성공 단위는 DD-02가 이미 "함께 성공 또는 함께 실패"로 정의했다. "실행 전에 미리 확인하는 기능"도 이 문서에서 뺐다(C.4, 후속 후보).
> 이전 지침 토론 기록: `../reviews/DD-07-sonnet-r1.md`, `../reviews/DD-07-sonnet-r2.md` (이전 지침 아래 에이전트 검토 이력; 새 기준은 위 B §5)
> 관련: `DD-02-write-scope.md` C.3, `DD-01-read-composition.md` I5, `../topics/T11-transaction-effects.md`

## A. 지금 결정할 문제

관리자가 지원자 30명을 한 번에 승인했는데 그중 1명이 이미 동아리 회원이라 승인할 수 없다. 이때 AIP의 **기본** 동작은

- 아무도 승인하지 않고, 안 되는 사람과 이유를 **한 번에 모두** 알려 줄까(전체 단위),
- 되는 29명은 승인하고 안 된 1명만 알려 줄까(항목별 단위).

기본은 하나만 정한다. 업무에 따라 다른 쪽이 꼭 필요하면 **그 업무에만 서버가 미리 정해 두고**, 앱 개발자나 AI가 요청마다 고르지 않게 한다.

## B. 실제 개발 시나리오: 아리아리 지원자 일괄 승인

### B.1 기존 코드 (`기존 코드`)

`ariari-backend/.../domain/recruitment/apply/ApplyService.java` 94~124행 `approveApplies`(요약):

```java
@Transactional
public void approveApplies(Long reqMemberId, List<Long> applyIds) {
    Member reqMember = ...;                                           // 96
    List<Apply> applies = applyRepository.findAllByIdsWithClub(applyIds);
    Club club = applies.get(0).getRecruitment().getClub();
    for (Apply apply : applies)                                        // 99~104 같은 동아리 검사
        if (!apply.getRecruitment().getClub().equals(club)) throw new NotSameClubsAppliesException();
    ClubMember reqClubMember = ...findByClubAndMember(club, reqMember)...;   // 106
    GlobalValidator.isClubManagerOrHigher(reqClubMember);                    // 107 권한 검사
    for (Apply apply : applies) {
        if (REFUSAL) throw new ApplyProcessingException();                   // 110~112
        if (이미 회원) throw new ExistingClubMemberException();               // 114~116
        apply.setApplyStatusType(APPROVE);
        clubMemberRepository.save(ClubMember.createGeneral(apply));          // 121
        memberAlarmManger.sendApplyStateAlarm(...);
    }
}
```

관찰(`DD-07-sonnet-r1.md` §1로 재확인):

1. **전부 아니면 전무, 첫 위반에서 멈춤.** 하나라도 예외면 전체 롤백이다. 오류에는 몇 번째 항목인지가 없고, 첫 위반만 알려 주므로 "1건 빼고 재시도 → 또 다른 1건 실패"가 반복될 수 있다.
2. **알림은 롤백되면 나가지 않는다.** `@TransactionalEventListener`(`domain/member/alarm/MemberAlarmService.java` 37·52행, 단계 미지정이라 기본값인 커밋 뒤). 다만 "커밋됐는데 알림 저장이 실패하면 알림이 사라지는" 경우는 막지 못한다. 즉 DD-02 W-I7 중 **롤백 방향만 충족**하고, 커밋 뒤 보장은 T11(outbox)의 몫이다.
3. **빈 목록은 컨트롤러가 막는다**(`ApplyController.java` 62~64행 `InvalidListParamException`). 진짜 결함은 **보낸 id가 모두 존재하지 않을 때** `applies.get(0)`에서 500이 나는 것, 그리고 일부 id가 없으면 `findAllBy...`가 조용히 빼 버려 호출자가 몇 건이 처리됐는지 모르는 것이다(회원 상태 일괄 변경 `ClubMemberService.modifyStatusTypes`도 같음).
4. **권한 검사 앞의 동아리 검사.** 같은 동아리 검사(99~104행)가 권한 검사(106~107행)보다 먼저 와서, 권한 없는 사람도 응답 차이(`NotSameClubsAppliesException` / 500 / `NotBelongInClubException`)로 id의 존재와 소속을 추측할 수 있다(코드 읽기로 추정, 실행 확인 안 함). 기존 코드를 정답으로 보면 안 되는 사례다.
5. **확인 후 쓰기.** 이미 회원인지 확인(114행) 뒤 저장(121행)이라, 같은 지원자를 두 요청이 동시에 승인하면 중복 회원이 생길 수 있다(ClubMember 유일 제약 여부는 확인 필요). DD-02 W-I5가 선행 조건이다.
6. 프론트는 실패 시 항목 구분 없이 고정 문구만 보여 준다(`ariari-frontend/.../applicationStatus/content/mainSection.tsx` 101~103행, Sonnet 확인).

### B.2 지난 AIP PoC (`기존 코드`)

- `ApproveApplies`(`examples/ariari/app.aip` 604~612행)는 이미 **전체 단위**이고 대상 상한 `max 100`이 있다.
- 항목별 처리 `each … partial`은 구현돼 있다(`crates/aip-runtime/src/exec.rs` 245~261행, 항목마다 `SAVEPOINT`). 결과 형식은 `{index, ok}` / `{index, ok:false, error}`이고 `value`는 없다(253·257행). 실제 쓰임은 이미지 업로드다(`app.aip` 686행 근처). 롤백된 항목의 업로드 스테이징 정리는 확인 필요.

## C. 대안과 트레이드오프

### C.1 대안 (두 축으로 나눔)

성공 단위 축과, 그 단위를 누가 정하는지 축이다. "실행 전 점검 호출이 있나"는 별도 축이라 C.4로 뺐다.

| | 전체 단위 | 항목별 단위 |
|---|---|---|
| 첫 위반에서 멈춤 | U1 (현 아리아리) | 해당 없음 |
| 모든 위반 수집 | **U4** | U2 |

| 누가 정하나 | 내용 |
|---|---|
| 호출자가 요청마다 | U2의 원래 형태(`unit: "item"`). AI·개발자에게 선택지가 하나 는다 |
| 서버가 capability마다 선언 | **U7.** 기본은 하나, 예외 업무만 서버 정의에 "이 bulk는 항목별"이라고 적는다. 호출자는 고르지 않는다 |

### C.2 비교 (이 문제에 맞춘 축. 원문 PART VII §13의 축과 같지 않다)

| 축 | U1 | U4 | U2(항목별) |
|---|---|---|---|
| 사용자 경험 | 1건 때문에 전체 실패, 문제 항목을 하나씩 찾아야 함 | 전체 실패지만 문제 항목을 한 번에 앎. 빼고 한 번 더 | 되는 것은 처리, 실패만 앎 |
| 무결성 | 단순. 불변식은 전체 기준 | 같음. 모든 위반을 모으려면 첫 위반 뒤에도 검사를 계속(쓰기 없이) | 항목마다 저장점. 집합 불변식(예: 관리자 최소 1명에서 3명 일괄 강등)은 **어느 항목이 실패할지가 서버 내부 순서에 달려** 재현이 어렵다 |
| 외부 효과 | 커밋 뒤 한 번에 | 같음 | 성공 항목만 커밋 뒤 |
| 멱등·재시도 | 요청 단위 키 하나 | 같음 | 재전송 시 이미 성공한 항목이 "이미 회원" 실패로 바뀐다. **항목별 결과를 키 저장소에 보존·재생**해야 하므로 T11의 미결 항목이 선행 조건 |
| 한 의도 한 구조 | 하나 | 하나 | U2(호출자 선택)는 선택지 증가, U7(서버 선언)이면 하나 |
| 구현 | 쉬움 | 검사를 끝까지 돌리는 비용(쓰기 없이) | 저장점, 결과 형식, 항목별 불변식 규칙, 결과 재생 |
| 디버깅 | 첫 위반만 | 전체 위반 목록 | 항목별 결과 |
| AI 개발 경험 | 재시도 반복 처리 코드 | 위반 목록을 빼고 재전송하는 표준 처리 하나 | 성공·실패 혼합 결과 처리 |

### C.3 어느 안이든 `[추천]`

1. 존재하지 않는 id, 볼 수 없는 id는 조용히 빼지 않는다. **볼 수 없는 id와 존재하지 않는 id는 같은 코드**로(DD-01 I5, DD-02 W-I9). 볼 수 있는 항목에만 상세 사유 코드를 준다.
2. 위반 응답은 항목 위치(index)와 안정된 오류 코드를 담는다.
3. 권한 판정은 대상 존재·소속 판정보다 먼저 하거나, 둘의 응답을 구분할 수 없게 한다(B.1 관찰 4의 오라클 제거).
4. 같은 id가 두 번 들어오면 요청 오류로 본다(조용히 합치지 않는다).
5. 대상 수 상한(DD-02 W-I4) 초과는 요청 전체 오류. 상한의 근거는 응답 크기가 아니라 **한 트랜잭션의 잠금 시간**이다. 기본값을 두어 AI가 매번 정하지 않게 한다.
6. 대상이 id 목록이 아니라 조건(필터)인 bulk는 실행 시점의 대상 집합을 기준으로 하고, 실제 대상 수를 결과에 담는다. 이때 위반 항목은 요청 안의 위치(index)가 아니라 대상의 식별자로 가리킨다(볼 수 있는 대상만).
7. 외부 효과는 커밋된 쓰기에 대해서만 커밋 뒤 전달(DD-02 W-I7). 커밋 뒤 전달 보장은 T11.

### C.4 이 문서에서 뺀 것: 실행 전 점검

초안 v1은 "실행 전에 안 되는 항목을 먼저 보여 주는 점검 호출"(U3)을 추천했다. Sonnet 비판(§3.2·§4.1)을 받아들여 뺐다.

- 점검과 실행 사이에 상태가 바뀌면 "된다고 했는데 실패"가 남는다. 실패 확률을 줄일 뿐 실패 모드를 없애지 않는다.
- 점검은 잠금 없이 읽으므로 집합 불변식은 근사값이다.
- 점검 응답이 대상의 상태를 알려 주는 새 노출 표면이 된다(반복 호출로 집계 정보 획득 가능).
- 아리아리에 앱별 사전 검사가 있었다는 증거가 없어, "앱마다 쓰던 사전 검사가 사라진다"는 근거가 없었다.

U4가 같은 정보(어느 항목이 왜 안 되는지)를 새 호출 없이 준다. 다만 U4가 "한 번에 모두" 모으는 것은 쓰기 전에 검사할 수 있는 위반이고, 집합 불변식처럼 커밋 시점에만 판정되는 위반은 그때 따로 보고된다. 화면이 실행 전에 "승인 가능한 지원자"만 보여 주고 싶다면, DD-01 읽기 조합에서 행마다 "전이 가능 여부"를 파생 값으로 돌려주는 방법(U5)이 먼저 검토 대상이다. 이 값은 정책 평가 결과를 읽기 값으로 노출하는 것이라 DD-10(소유 관계에서 나오는 값)의 범위 밖이고, 담당 문서가 아직 없다(후속 결정 문서 후보). 그것도 부족하다고 E1에서 확인되면 별도 결정 문서로 연다.

## D. 최초 철학과의 관계

| 원칙 | 관계 |
|---|---|
| 반복 흡수 | 아리아리 일괄 쓰기 4개(`approveApplies`·`refuseApply`·`processApply`·`modifyStatusTypes`)가 같은 "조회 → 첫 위반 throw" 패턴이다. 결과 형식과 위반 수집을 표준으로 흡수 |

## F. 확인된 답과 남은 일

- 확인된 방향: 일괄 작업은 기본적으로 전체 단위의 원자적 성공/실패를 우선 검토한다.
- 기술 검증: 항목별 부분 성공이 필요한 실제 사례, 오류 수집 방식, 사전 점검의 한계와 트랜잭션 비용을 비교한다(E). 업무별 예외를 표준으로 둘지는 근거가 나온 뒤 정한다.
- 기존 F1의 즉시 창시자 선택 및 에이전트의 전체 단위 추천은 승인된 상세 명세가 아니다.

## G. 결정 상태

**검증 필요.** 원자적 기본 방향은 확인됐고, 예외적 부분 성공·오류 수집·사전 점검의 동작과 비용을 검증한다. U4/U7은 검토안이다.

## 이탈 방지 점검 (U4 + U7 기준)

| 질문 | 답 |
|---|---|
| 백엔드 개발이나 이중 유지보수를 줄이는가 | **조건부 예.** 결과 형식과 위반 수집이 표준이 되어 앱마다 쓰지 않는다. 새 호출은 만들지 않는다 |

| JS/Python 생태계와 사람의 사용성 | **판정 보류.** 작성 방식(DD-04) 미정 |
| 복잡성을 옮기기만 했나 | 검사를 끝까지 돌리는 비용이 엔진에 생기고, 앱의 재시도 반복이 줄어든다. 항목별 처리는 필요한 업무에만 |
