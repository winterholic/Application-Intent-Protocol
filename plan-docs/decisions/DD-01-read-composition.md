## A. 지금 결정할 문제

화면이 새로운 모양의 데이터를 원할 때 **호출자가 어떤 읽기 Intent를 표현할 수 있고, 서버는 무엇을 쥐고 있는가**를 정한다.

- 지금까지(Spring 아리아리, AIP PoC 모두): 서버 개발자가 조회를 화면 단위로 하나씩 정의한다. 화면이 바뀌면 서버도 바뀐다.
- 바꾸려는 방향: 호출자는 서버가 공개한 계약 안에서 필요한 데이터를 조합해 표현한다. 서버는 그 요청의 의미를 검증하고, 정책(행·필드·관계·연산별 권한, 테넌트, 무결성)을 끼워 넣고, 실행 방법을 정하고, 비용을 통제한다. 서버가 가시성만 쥐는 것이 아니다.

원문의 A/B/C 세 안은 모두 "읽기 조합"을 포함하고 쓰기에서만 갈린다. 그래서 읽기를 먼저 떼어 결정한다.

## B. 실제 개발 시나리오: 아리아리 모집 목록

### B.1 기존 방식 (`기존 코드`)

`ariari-backend/.../domain/recruitment/recruitment/RecruitmentController.java`에는 GET이 **11개** 있다(10-03 `grep -c` 확인). 상세 1개(32~40행)를 빼면 10개이고, 그중 `RecruitmentListRes`를 돌려주는 목록형이 **8개**, 나머지 둘은 존재 여부 `boolean`(138~143행)과 진행 중 단건(145~150행)이다.

| 목록형 엔드포인트 | 하는 일 |
|---|---|
| `/recruitments` | 활성 + (교외 또는 내 학교), 카테고리·지역·대상 필터, 페이지 |
| `/recruitments/external` | 활성 + 교외 |
| `/recruitments/internal` | 활성 + 내 학교(학교 인증 필요) |
| `/recruitments/search` | 활성 + (교외 또는 내 학교) + 제목 검색 |
| `/recruitments/my-bookmarks` | 내 북마크 |
| `/clubs/{clubId}/recruitments` | 특정 동아리의 모집(학교 일치 검사) |
| `/recruitments/external/ranking` | 활성 + 교외, 조회수 상위 9 |
| `/recruitments/internal/ranking` | 활성 + 내 학교, 조회수 상위 9 |

프론트 `ariari-frontend/app/api/recruitment/api.ts`는 이 대부분을 함수 하나씩으로 감싼다. 같은 URL 래퍼가 두 개인 경우(243~253, 292~302행)와 래퍼를 찾지 못한 경우(존재 여부 GET)가 있어 일대일 대응은 아니다.

관찰 1. **가시성 규칙이 흩어져 있다.** 정확히 같은 합성식 "활성 && (교외 || 내 학교)"는 2개 메서드의 본 조회·count 조회 4곳(`RecruitmentRepositoryImpl.java` 41~43, 59~61, 136~138, 152~154행)에 있다. 변형("활성 && 교외", "활성 && 내 학교")까지 포함하면 6개 목록 메서드에 흩어져 있다(74~75, 91~92, 105~106, 122~123, 165~166, 176~177행). 서비스 계층에도 학교 인증·일치 검사가 따로 있다(`RecruitmentListService.java` 59~65, 82~93, 106~112행). 새 조회를 만들 때 이 중 하나를 빠뜨리면 다른 학교의 교내 모집이 보인다.

관찰 2. **화면이 바뀌면 엔드포인트가 는다.** 교외 랭킹과 교내 랭킹은 조건 하나만 다른데 엔드포인트, 서비스 메서드, 리포지토리 메서드가 각각 있다.

관찰 3. **정책 없는 호출자 조합이 이미 있다.** 프론트가 `pageable.sort`를 보내면(`api.ts` 62~68행) 리포지토리가 그 문자열을 허용 목록 없이 `PathBuilder`로 정렬에 쓴다. 전체·교외·교내·검색 네 곳(50~53, 82~85, 113~116, 143~146행)이다. 확인 필요: 존재하지 않는 속성, 연관 경로, 노출하면 안 되는 속성을 보냈을 때의 실제 동작(정적 코드로는 판정 불가).

### B.2 지난 AIP PoC (`기존 코드`, `.aip`)

`aip/examples/ariari/app.aip` 425~444행 `RecruitmentList`는 하나의 선언 쿼리로 여러 필터·정렬을 받는다. 필터 레코드(`RecruitmentFilter`, 53~58행)와 정렬 enum(`LATEST VIEWS SCRAPS OLDEST DEADLINE`, 31행)을 서버가 선언하고, 결과 모양(`select`, 438~443행: `club.name`, `club.affiliation`만, 로고 없음)도 서버가 고정한다.

남은 점: 화면이 "동아리 로고도 같이"를 원하면 서버 `select`를 고쳐야 한다. 새 정렬 기준이 필요하면 enum을 고쳐야 한다. 기존 엔드포인트 8개가 모두 이 쿼리와 동등하게 대체되는지에 대한 대응표는 아직 없다(E1에서 만든다).

### B.3 새 요구가 들어왔을 때

> 요구: 홈 화면에 "마감이 가까운 모집 5개"를 카드로 보여 준다. 카드에는 동아리 이름과 로고, 북마크 수를 넣는다.

| 방식 | 서버 쪽에서 해야 하는 일 |
|---|---|
| Spring 아리아리 | 응답 DTO에 로고·북마크 수가 없으면 DTO 수정. 정렬은 무정책 임의 정렬 경로로 될 수도 있음(관찰 3). 아니면 새 엔드포인트, 서비스, 리포지토리. 가시성 규칙 복사 |
| AIP PoC | `RecruitmentList`의 `select` 수정 또는 새 query 선언 |
| 수정 대안 2 | **전제:** `periodEnd`의 filter·sort, `club.logo`의 select, 모집별 북마크 총수 집계가 리소스 계약에 이미 열려 있으면 **화면별 서버 작업 없음.** 하나라도 닫혀 있으면 그 capability를 리소스에 한 번 연다(화면이 아니라 리소스 단위) |

수정 대안 2의 모습 (`개념 예시`. 실제 문법이 아니다. 작성 언어(DD-04)와 요청 형식(T06)은 미정이며, 아래 모양은 그 결정을 전제하지 않는다):

```ts
// 서버 쪽: 화면과 무관하게 리소스마다 한 번
resource("Recruitment", {
  rows: "isOpen && (club.school == null || club.school == actor.school)",
  preset: {
    publicList: {                       // 명시적·유한 목록. 새 필드는 자동 포함되지 않는다
      select: ["title", "poster", "periodEnd", "views"],
      filter: ["periodEnd", "field", "region", "target"],
      sort:   ["periodEnd", "createdAt", "views"],
    },
  },
  traverse: { club: { select: ["name", "logo"] } },
  // 공개 집계: 북마크 "행"을 보여 주는 것이 아니라, 모집별 총수라는 비식별 결과를 따로 공개한다
  publicAggregate: { bookmarkCount: "count(bookmarks)" },
})
resource("RecruitmentBookmark", {
  rows: "member == actor",              // 간선 행(누가 북마크했나)은 본인만
})

// 호출자: 화면이 필요한 것을 표현
aip.read("Recruitment", {
  where: { periodEnd: { gte: today() } },
  orderBy: { periodEnd: "asc" },
  take: 5,
  select: { title: true, poster: true, periodEnd: true,
            club: { name: true, logo: true }, bookmarkCount: true },
})
```

이 요청을 받으면 서버는 (1) 요청의 의미를 하나의 canonical 형태로 정리하고, (2) 각 연산이 열린 capability인지 확인하고, (3) 행 정책·테넌트 조건을 모든 스캔과 관계 단계에 끼워 넣고, (4) 자원 상한 안에서 실행 방법을 정해 실행한다. 요청에 가시성 조건이 없어도 다른 학교의 교내 모집은 나오지 않는다.

`bookmarkCount`는 `RecruitmentBookmark`의 간선 정책을 건너뛰는 예외가 아니다. 서버가 "모집별 총수"라는 결과를 별도 capability로 공개한 것이다. 호출자는 이 집계에 임의 필터(예: "특정 회원의 북마크만")를 걸 수 없다. 간선 행은 여전히 본인 것만 보인다.

열리지 않은 필드(예: `club.internalMemo`)를 요청했을 때의 오류는 경로에 따라 다르다. 운영 런타임의 응답은 "없는 필드"와 같은 모양으로 존재를 감춘다. 권한이 반영된 계약을 가진 빌드·개발 도구는 "이 필드는 열려 있지 않다"는 정확한 진단을 준다(AI가 오타와 권한 부족을 추측하지 않도록).

## C. 대안과 트레이드오프

### C.1 대안

| | 대안 1. 서버가 조회를 하나씩 선언 | 수정 대안 2. capability가 분리된 canonical 조합 읽기 | 대안 3. 서버가 조회 틀을 선언, 호출자는 결과 모양만 |
|---|---|---|---|
| 내용 | 조건·정렬·결과 모양을 서버가 정한다. 공통 정책 삽입, 코드 생성, 타입 있는 쿼리 빌더로 개선할 수는 있다 | 서버는 리소스마다 select / filter / sort / traverse / aggregate capability와 행·필드·간선 정책을 선언한다. 호출자는 그 범위 안에서 하나의 canonical 읽기 Intent로 조합한다 | 서버가 `from`·`where`·정렬 후보를 가진 틀을 선언하고, 호출자는 필드·관계만 고른다 |
| 원문 A/B/C | 해당 없음(기각된 D-R5) | A, B, C 모두의 읽기 부분 | 원문에 없는 중간안 |

수정 대안 2의 **실행 하위안**(최종 선택은 DD-03, 비용 비교에는 포함):
- 2-R 런타임: 요청마다 정리·검증·계획·실행
- 2-M manifest 승인: 자사 프론트의 요청을 빌드 때 추출해 같은 규칙으로 plan을 만들고 검토·승인. 운영은 승인된 plan만 실행
- 2-RM 혼합: 같은 의미 모델 위에서 호출자 신뢰 등급마다 2-M 또는 2-R(더 엄격한 한도)
- (DD-03 v3.1 갱신) 2-RM은 DD-03의 대안 S(단일 런타임 의미 파이프라인 + 선택적 명시 등록 + 배포 정책으로 고르는 `registered-only` 입장)로 대체 검토 중. "호출자 신뢰 등급"은 실행 경로 선택 기준으로 쓰지 않는다

**이름이 붙는 읽기 두 종류** `[기존 제안, 승인 아님]`:
- 저장된 조회(saved read): 표준 조합 요청에 이름만 붙인 것. 새 의미가 없다. DD-03의 "등록된 요청"은 빌드가 자동으로 만든 저장된 조회의 일종이다(이름 대신 해시 식별자, 서버 정의에는 나타나지 않음). 둘 다 새 의미를 만들지 않는다.
- 확장 읽기(extension read): 표준 조합으로 표현할 수 없는 조회를 JS/Python으로 서버에 구현한 것. 이름, 타입, 권한, 비용 한도 계약을 가진 별도 capability다. 표준 조합으로 표현할 수 있는 것을 확장 읽기로 다시 만들지 않는다.

| AI 개발 경험 | 화면마다 "서버 조회를 추가할까"를 판단하고 양쪽을 쓴다 | 프론트 한쪽만 쓴다. canonical 정리가 있어야 같은 의도가 한 모양으로 수렴 | "조건이 바뀌었나"를 매번 판단 |
| 없어지는 중복 | (기준) | 화면별 엔드포인트, 서비스·리포지토리 메서드, 응답 DTO, 프론트 래퍼, 가시성 규칙 복사 | 응답 DTO 다수 |
| 새로 생기는 비용 | **새 공통 엔진 비용은 없음. 화면별 한계비용이 계속 든다:** 계층 코드, 규칙 복사, 계약 동기화, 회귀 테스트, 리뷰 | 엔진: 층 1 불변식을 지키는 최소 구현. 앱: 리소스마다 capability·preset 선언. 층 2는 필요해질 때 | 필드 선택 해석기, 틀 선언 |

### C.3 수정 대안 2의 기술 제안 (창시자 질문 아님. 근거와 함께 제안)

**층 1. 의미·안전 불변식.** 관찰 가능한 성질로 쓴다. 이것이 서지 않으면 수정 대안 2를 내놓지 않는다.

| 불변식 | 내용 | 근거 |
|---|---|---|
| I1 공개된 것만 실행 | select, filter, sort, traverse, aggregate는 서로 다른 capability이고 모두 기본 거부. 리소스가 명시적으로 연 것만 실행된다 | 선택할 수 있다고 비교·정렬까지 허용하면 값과 순위가 샌다 |
| I2 모든 경로에 정책 | 행·필드·간선 정책과 테넌트 조건이 호출자가 조합하는 모든 스캔, 관계 단계(역방향 포함), 서브쿼리, 집계에 적용된다. 서버가 명시적으로 공개한 비식별 결과는 I7의 공개 집계로 따로 다룬다 | 관계 경유 우회, 간선(북마크)으로 개인 행동 노출, 테넌트 교차 |
| I3 실행 방법은 서버가 | 호출자 요청에는 raw SQL, 임의 코드, 실행 계획 힌트가 들어갈 수 없다. 의미가 같은 요청은 같은 정책을 받는다 | 원문 "호출자가 서버 내부 구현을 임의로 제어할 수 없어야 한다" |
| I4 자원 상한과 중단 | 요청 복잡도, 결과 크기, 실행 시간, 주체별 동시 실행 수에 상한이 있고 넘으면 거부하거나 중단한다 | `take: 1`이어도 전 테이블 스캔·정렬은 일어난다 |
| I5 존재를 드러내지 않음 | 운영 런타임에서 볼 수 없는 행은 "없음", 열리지 않은 필드·관계는 없는 것과 같은 오류 모양. total count·cursor 같은 목록 메타데이터도 정책을 통과한 결과로만 계산. 개발·빌드 도구는 권한 맥락 안에서 정확한 진단을 준다 | 존재 오라클 방지와 명확한 오류(AI First)를 함께 지킴 |
| I6 확장도 같은 통제 | JS/Python 확장 읽기도 인증, 행·필드·간선 정책, 테넌트, 자원 상한을 우회하지 못한다. 서버가 준 capability 계약과 데이터 접근 수단을 통해 실행한다. 프로세스 경계·연동 방식은 DD-06에서 검증한다 | 원문 "확장도 서버 보안 규칙을 우회해서는 안 된다" |
| I7 민감 집계는 보호 없이 닫힘 | 집계는 기본 거부. 공개 집계는 서버가 정한 결과(예: 모집별 총수)로만 열고 호출자가 임의 필터를 걸 수 없다. 작은 집단이나 개인 행동을 추론할 수 있는 집계를 열려면 그 집계에 맞는 보호(최소 집단 크기, 구간화, 질의 예산 등)가 함께 있어야 한다. 일반 공개 총수에 노이즈를 강제하지는 않는다 | count 차분 공격 |

**층 1의 가장 단순한 구현으로 시작할 수 있다:** plan cache 없음, 보수적인 고정 상한, DB 문장 타임아웃, 단일 DB, 응답 시간 균일화 없음.

**작성량을 줄이는 preset** (`개념 예시`의 `publicList`):
1. 리소스에 명시적으로 넣는다. 새 필드가 생겨도 자동 포함되지 않는다.
2. select·filter·sort의 명시적이고 유한한 목록으로 펼쳐진다. 인덱스 유무는 권한이 아니라 비용 검사(I4)의 입력일 뿐이다.
3. 펼친 결과를 사람이 보고 변경 diff를 검토할 수 있다.
4. 필드별로 빼거나 덮어쓸 수 있고, preset 정의가 바뀌어도 기존 앱의 노출이 조용히 넓어지지 않는다.
5. 이름은 용도와 대상을 드러낸다(`publicList`, `ownerDashboard` 등. 실제 이름은 미정).

**canonical 정리:** 같은 의미의 요청(중첩 where와 관계 필터, 저장된 조회와 원형 등)은 하나의 canonical 형태로 정리돼 같은 정책을 받는다. 같은 의도를 같은 구조로 표현한다는 승인된 AI First 원칙을 구현하는 내부 수단이다.

**표준·확장 경계 판정:** 표준 읽기 연산으로 표현할 수 있으면 조합 요청(필요하면 저장된 조회), 표현할 수 없으면 확장 읽기. 확장 읽기를 등록할 때 같은 결과를 표준 조합으로 낼 수 있는지 검사하는 규칙을 둔다(검사 방법은 후속 기술 문서).

**층 2. 실행 방식에 따른 조건부 수단과 운영 성숙도.** 필요해질 때 가장 단순한 것부터.
- 안정적 해시와 manifest: 2-M을 택할 때
- plan cache: 쓰기로 할 때. 쓴다면 "정책·스키마·권한 맥락이 다른 결정을 재사용하지 않는다"를 지키고, 정책 평가 결과가 아니라 정책이 매개변수로 들어간 plan만 재사용하는 단순안부터 비교
- 정교한 비용 추정(예상 스캔 행, fan-out, 정렬 메모리)
- 조합 결과 캐시 무효화와 실시간 동기화 범위(T13)
- 여러 DB의 capability 차이 진단(DB 범위는 미결정)
- 응답 시간 균일화(현실성 확인 필요)

## D. 최초 철학과의 관계

| 원칙 | 수정 대안 2와의 관계 |
|---|---|
| 존재 목적 | **실현, 조건부.** 화면별 조회 구현은 대부분 사라진다. 새 capability가 필요할 때 리소스 계약 변경은 남는다. 기본 거부라 선언이 늘 수 있고 preset으로 줄인다 |
| 작동 모델(호출자 표현) | **실현.** 자유의 범위는 공개된 capability 계약 안이다. 무제한 연산 허용이 아니다 |
| 요청의 자유와 실행 권한 분리 | **실현.** 요청에는 원하는 것만 담기고, 연산별 권한·정책 삽입·실행 방법·자원 상한은 서버가 매번 정한다(I1~I7) |
| AI First(한 의도 한 구조) | canonical 정리와 표준·확장 경계 판정이 있어야 성립한다. 개발 도구의 정확한 진단(I5)으로 AI가 오류 원인을 추측하지 않게 한다 |
| GraphQL과의 관계 | 영감은 같다(호출자 중심 데이터 선택). 연산별 capability, 정책 삽입, 정규화, 자원 상한 같은 안전 장치는 GraphQL 구현에서도 가능하므로 그것만으로 차별이라 하지 않는다. AIP의 차이는 읽기와 동작(DD-02)을 같은 Intent 체계로 다루고, 서버 계약·오류·확장까지 AI First로 정형화하는 **전체 체계**에서 판정한다 |
| 자연어 설명 | **기준 확인됨.** 선택적 구조화 metadata로 선언에 귀속시키며, 의미 검증을 필수로 하지 않고 실행·보안 판단의 근거로 쓰지 않는다. 메타데이터 스키마와 표시 범위는 DD-05의 기술 설계에 남는다 |
| JS/Python 생태계 | 판정 보류. 작성 방식(DD-04) 미정. 확장 읽기(JS/Python)는 원칙에 맞는다 |

남은 검증: 새 필드 공개 기본값 후보가 보안·작성 부담에 주는 영향을 비교한다. 이는 확인된 최종 통제 원칙과 별개의 구현 세부다.

요약:
- **대안 1**: 서버 조회 11개. 가시성 검사를 조회마다 넣어야 하고, 실제로 2개에서 빠져 있다.
- **수정 대안 2**: 서버에는 Recruitment·RecruitmentBookmark 리소스 계약 하나씩(capability: 분야·지역·대상·기간·동아리·동아리 학교·제목 포함 filter, 생성·조회수·기간 sort, 동아리 traverse, 북마크 count 공개 집계, 간선 정책). 11개 모두 표현 가능하나 **두 가지 새 요구가 드러났다**: (1) 읽기에 붙는 쓰기(조회수 증가) (2) 행위자 기준 파생 값(내 동아리인가 등). 둘 다 DD-01이 아직 다루지 않는다. 행 정책이 리소스에 한 번 있으므로 위 두 누락은 구조적으로 생기지 않는다.
- **대안 3**: 조건이 바뀌는 조회마다 틀이 필요해 틀 7~9개(정확한 수는 틀 설계에 따름, 확인 필요). 대안 1보다 적지만 화면별 서버 작업이 남는다.

새로 생긴 질문(추가 결정 문서 후보):
- 읽기에 딸린 부수 효과(조회수, 열람 기록)를 표준으로 둘 것인가. 지난 PoC에는 `touch r.views`(`examples/ariari/app.aip` 422행 근처)와 `counter via redis dedupe`가 있었다.
- 행위자 기준 파생 값(`exists membership(actor, r.club)` 같은 것)을 읽기 조합에서 어떻게 표현하고 어떤 정책을 적용할 것인가. PoC `RecruitmentDetail`의 `isMyClub`·`isMyApply`가 선례.
- (DD-09 통지) 조회수를 올리는 "열람 지점"을 선언하려면 저장된 조회(새 의미 없음)와 별개로 "효과가 붙은 읽기"가 필요할 수 있다(DD-09 C.4). 이 문서 C.1의 저장된 조회 정의를 바꿀지 재토론 필요.
- (DD-09 통지) 값이 계속 바뀌는 카운터로 정렬할 때 커서 페이지가 흔들리는 문제, 14일 같은 집계 창이 랭킹 의미 요건이라는 점.

## F. 확인된 답과 남은 일

- 확인됨: 호출자는 필요한 데이터를 조합해 표현하고, 서버가 허용 범위와 실행을 최종 통제한다. JS/TS·Python 공식 확장도 제공한다. 기존 F1·F4는 재질문하지 않는다.
- 기술 검증: 새 필드 공개 기본값 후보, select/filter/sort/traverse/aggregate별 capability, 비용 한도와 표준·확장 경계(C.3·E).
- 추가 가치 판단: 초기 요청 작성자 범위(F3)는 비용·운영 모델 비교 뒤 필요할 때만 묻는다.
- 이전 F2의 비공개 기본값과 C.3의 canonical·저장 조회 추천은 확정 결정이 아니라 검증할 설계안이다.

---

## G. 결정 상태

**잠정 합의.** 확인된 호출자 조합·서버 최종 통제 방향 위에서 capability, 공개 기본값, 비용 통제를 설계·검증한다. 기존 대안 2 추천은 새 원문의 승인이 아니다.

|---|---|
