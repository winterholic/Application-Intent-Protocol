# DD-02. 쓰기에서 호출자는 무엇을 표현하고, 서버는 무엇을 쥐는가

> 결정 상태: **잠정 합의** (새 기준: [B §5](../alignment/B-decision-reclassification.md#5-dd-문서의-현재-처리-상태))

## A. 지금 결정할 문제

원문 PART VII §13의 세 안은 읽기에서는 모두 조합을 허용하고 **쓰기에서 갈린다.** 이 문서가 그 갈림길을 다룬다.

쉽게 말하면 두 가지다.

1. 화면에 단순한 생성·수정·삭제·상태 변경 버튼을 새로 달 때, 서버에 무언가를 추가해야 하는가.
2. 여러 데이터가 함께 바뀌는 업무(예: 최고 관리자 위임)에서 호출자가 표현하는 것은 **원하는 업무 결과**인가, **그 결과를 만드는 절차**까지인가.

어느 쪽이든 서버는 허용 범위, 무결성, 실제 실행 방법(순서, 잠금, 트랜잭션, 외부 효과 시점)을 끝까지 쥔다. 그것은 이 문서가 바꾸지 않는다.

## B. 실제 개발 시나리오: 아리아리의 쓰기 네 가지

### B.1 기존 코드 (`기존 코드`)

아리아리 백엔드의 쓰기 매핑 어노테이션(`@Post/Put/Patch/DeleteMapping`) 문자열은 93개다(POST 52, PUT 13, PATCH 6, DELETE 22). 그중 3개는 주석 처리돼 있어(`domain/club/financial/FinancialRecordController.java` 52·62행, `domain/club/clubmember/ClubMemberController.java` 64행) 활성 형태는 90개다. 실제 런타임 엔드포인트 수는 확인 필요.

난이도가 다른 넷을 골랐다. 경로는 `ariari-backend/src/main/java/com/ariari/ariari/` 기준.

| # | 동작 | 위치 | 코드상 규칙 |
|---|---|---|---|
| W1 | 알림 읽음 표시 | `domain/member/alarm/MemberAlarmService.java` 68~77행 | 내 알림만(71~72행), 안 읽은 것만 읽음으로(74~75행) |
| W2 | 닉네임 변경 | `domain/member/member/MemberController.java` 31~37행, `MemberService.java` 31~40행 | 내 것만. 중복 확인 후 변경(35~39행). DB 선언 `unique`(`domain/member/Member.java` 54~56행) |
| W3 | 동아리 회원 권한 변경 | `ClubMemberController.java` 40~53행, `ClubMemberService.java` 60~71행 | 서비스가 `GlobalValidator.isClubAdmin`(67행, `commons/validator/GlobalValidator.java` 69~72행)으로 **ADMIN만** 허용. 컨트롤러 API 설명(40행)은 "스텝 이상"이라 해 서비스 실행 규칙과 다르다(어느 쪽이 의도인지 확인 필요. 실제 역할 enum은 GENERAL·MANAGER·ADMIN뿐: `domain/club/clubmember/enums/ClubMemberRoleType.java` 8~10행). **ADMIN으로 바꾸는 것 금지는 컨트롤러 46~50행에만** 있고 서비스는 받은 역할을 그대로 쓴다(70행) |
| W4 | 최고 관리자 위임 | `ClubMemberController.java` 56~61행, `ClubMemberService.java` 74~85행 | ADMIN만(81행), 같은 동아리(82행). 대상을 ADMIN, 나를 GENERAL로(84~85행). "동아리 ADMIN은 정확히 1명"은 요구사항일 뿐 엔티티(`commons/entity/ClubMember.java`)에 제약이 없다 |

관찰:

1. W1·W2는 "누가, 어떤 필드를, 어떤 값으로"만 정하면 끝나는 쓰기다. 그런데도 각각 컨트롤러, 서비스, DTO, 프론트 래퍼가 있다.
2. W2는 확인 후 쓰기다. 동시에 같은 닉네임을 요청하면 둘 다 확인을 통과하고 DB `unique`가 막는다(JPA 선언이 실제 스키마에 반영됐다는 전제. 실제 응답 모양은 확인 필요).
3. W3의 "ADMIN 금지"는 컨트롤러에 있다. 같은 서비스를 다른 경로에서 부르면 빠진다. 문서와 구현의 허용자도 다르다. **규칙이 경로에 붙어 있고 데이터·동작 계약에 붙어 있지 않다.**
4. W4는 자기 자신에게 위임하면 같은 행을 ADMIN으로 쓴 뒤 GENERAL로 써서, 단독 ADMIN인 동아리에 ADMIN이 0명이 된다(코드로 확인되는 결함. 기존 기술 기록 `aip/docs/design/01-reality-test.md` 70~76행에도 있음. Spring 앱 실행 재현은 하지 않음).

### B.3 새 요구가 들어왔을 때

> 요구 1: 알림 목록 화면에 "모두 읽음" 버튼을 단다.
> 요구 2: 동아리 관리 화면에 "회원 권한 변경"을 단다.

| 방식 | 요구 1 | 요구 2 |
|---|---|---|
| Spring | 새 엔드포인트, 서비스(일괄 UPDATE), 프론트 래퍼 | 이미 있음(W3). 규칙은 컨트롤러에 |
| A. 쓰기는 서버 선언 동작 | 새 동작 선언 | 동작 선언(PoC `ChangeMemberRole`) |
| B+ (아래) | **전제:** 알림의 "읽음" 상태 전이와 그 일괄 적용이 리소스 계약에 열려 있으면 화면별 서버 작업 없음 | **전제:** 회원 역할 전이가 열려 있으면 없음 |

B+의 모습 (`개념 예시`. 실제 문법이 아니다. 작성 언어(DD-04)와 요청 형식(T06)은 미정이며 아래 모양은 그 결정을 전제하지 않는다):

```ts
// 서버 쪽: 리소스마다 한 번
resource("MemberAlarm", {
  rows: "member == actor",
  transition: {
    read: { field: "isChecked", from: false, to: true },   // 일반 update가 아니라 이름 있는 전이
  },
  bulk: { read: { maxRows: 500 } },                         // 일괄 적용은 별도 capability, 대상 수 상한
})
resource("ClubMember", {
  transition: {
    changeRole: {
      field: "role", to: ["GENERAL", "MANAGER"],             // 허용 값 목록. ADMIN은 목록에 없다
      allowWhen: "actorRoleIn(row.club) == ADMIN && row.member != actor",
    },
  },
  invariant: { oneAdminPerClub: "exactly one where role == ADMIN per club" },
  // 최고 관리자 위임(W4)은 아래 C.1의 판정에 따라 표준 동작인지 확장 동작인지 정한다
})

// 호출자
await aip.apply("MemberAlarm", "read", { all: true })        // 서버가 rows 정책을 덧붙여 내 알림만
await aip.apply("ClubMember", "changeRole", { id: target, role: "MANAGER" })
```

W3의 "ADMIN 금지"는 컨트롤러가 아니라 전이 계약의 **허용 값 목록**에 붙는다. 새 역할이 추가돼도 목록에 넣기 전에는 그 값으로 바꿀 수 없다(기본 거부).

## C. 대안과 트레이드오프

### C.1 대안

| | A. 쓰기는 서버 선언 동작 | B+. capability 분리형 표준 쓰기 + 확장 동작 | C'. 제한된 묶음 |
|---|---|---|---|
| 내용 | 쓰기는 모두 서버가 이름 붙여 선언한 동작. 불변식·정책은 공통 적용할 수 있다 | 서버는 리소스마다 create / update / delete / link / transition / bulk를 서로 다른 capability로 기본 거부하고 필요한 것만 연다. 호출자는 열린 capability 안에서 원하는 결과를 canonical Intent로 표현한다. 표준 의미로 완결되지 않으면 타입 있는 확장 동작(JS/Python)을 선언한다 | B+에 더해, 호출자가 공개된 원자 capability 여러 개를 **의존 없는 묶음**으로 보내고 "함께 성공 또는 함께 실패"만 요청한다. 순서·잠금·격리·효과 시점은 서버가 정한다. "의존 없음"은 (1) 단계 사이 값 전달이 없고 (2) 묶음 안의 각 capability가 **단독으로도 공개돼 있고 단독 실행만으로 불변식을 지킨다**는 뜻이다 `[추천]`. 묶음 안에서만 유효한 전이(묶음 전용 capability)는 두지 않는다. 단계별 조건, 외부 효과는 기본 금지 |
| 원문 A/B/C | 원문 A | 원문 B를 구체화 | 원문 C를 "무제한 명령 실행이 아닌" 형태로 구체화한 후보. 창시자가 말한 C인지는 확인 필요 |

**표준 쓰기와 확장 동작의 판정 규칙** `[추천]` (리소스 개수가 아니라 의미로 판정):

1. 요청 의미가 공개된 capability 하나와 그 전이 계약으로 완결되는가?
2. 허용 여부가 행위자, 변경 전·후 상태, 대상 집합에 대해 서버가 선언한 정책으로 결정되는가?
3. 여러 행·리소스에 걸친 불변식의 범위와 잠금 키를 엔진이 표준 방식으로 계산할 수 있는가?
4. 단계 사이 값 전달, 조건 분기, 장기 실행, 외부 효과가 필요한가?
5. 표준 capability로 표현 가능한 것을 확장 동작으로 등록하려 하면 거부하거나 진단할 수 있는가?

1~3이 성립하고 4가 없으면 표준 쓰기, 아니면 타입 있는 확장 동작. 이 규칙의 반례는 E1에서 찾는다. 예: W1·W3은 표준 transition, W2는 본인 범위 update + unique, W4(최고 관리자 위임)는 두 행이 함께 바뀌는 의미 있는 동작이라 표준 "transfer" 형식인지 확장 동작인지 E1에서 판정한다(여기서 확정하지 않는다).

**이름 있는 동작이 곧 철학 위반은 아니다.** 원문이 경계하는 것은 "화면마다 서버가 요청 형태를 반복 정의하는 구조"이지 이름 자체가 아니다. "최고 관리자 위임" 같은 의미 있는 업무 결과에 이름이 붙는 것은 오히려 호출자가 **결과**를 표현하는 방식일 수 있다(F2).

### C.2 비교 (원문 PART VII §13의 8개 축)

| 축 | A | B+ | C' |
|---|---|---|---|
| 철학 정합성 | 단순 쓰기도 화면마다 동작 선언이 쌓이면 원문이 경계한 구조. 의미 있는 업무 동작에는 맞을 수 있다 | 단순 쓰기는 화면별 서버 작업 없음, 업무 동작은 표준 형식이나 확장으로 | 호출자가 묶음까지 표현. 절차 표현을 허용하는 만큼 "서버가 실행 방법을 정한다"와 긴장 |
| 서버 작성량 | 동작마다 선언 | 리소스 capability·전이·불변식 선언 + 확장 동작 | B+와 비슷하거나 적음 |
| 보안 | 동작 단위 검토. 불변식을 공통 적용하면 경로 누락 위험은 줄어든다 | 필드 확대, 전이 우회, 일괄 범위 폭발을 capability 분리와 C.3 불변식으로 막아야 한다 | B+ + 묶음 부분 실패, 묶음 중 거부 사유로 존재 노출 |
| 비즈니스 규칙 처리 | 동작 안 | 전이 계약, 불변식, 확장 동작으로 나뉜다. 판정 규칙(C.1)이 기계적이어야 한다 | 일부가 호출자 묶음 구성으로 새어 나갈 위험 |
| 구현 난이도 | 낮음 | 높음: capability·전이·불변식 엔진, 잠금 키 계산, canonical화, 개발 진단 | B+ + 묶음 의미론 |
| 확장성 | 동작이 쌓인다 | 새 화면은 계약 안에서 흡수 | 가장 넓다 |
| 디버깅 | 이름으로 추적 | 요청 → canonical → 정책·불변식 판정 경로를 보여 주는 도구 필요 | 묶음 단위 추적 필요 |
| AI 개발 경험 | 버튼마다 "동작을 만들까"와 본문 작성 | 판정 규칙이 기계적이면 선택이 사라진다. 아니면 "표준이냐 확장이냐"가 새 선택지 | 같은 결과를 표준 동작과 묶음 두 방식으로 쓸 수 있어 한 의도 한 구조와 충돌 위험 |
| 없어지는 중복 | (기준) | 단순 쓰기의 엔드포인트·서비스·DTO·래퍼, 경로마다 복사되던 규칙 | B+ + 다중 리소스 동작 일부 |
| 새로 생기는 비용 | **새 공통 엔진 비용은 작을 수 있으나 화면별 동작 선언과 계약 동기화·테스트·리뷰 비용이 계속 든다** | 엔진: C.3 층 1을 지키는 최소 구현. 앱: capability·전이·불변식 선언 | B+ + 묶음 전체의 정책 재평가, 같은 결과를 표준 동작과 묶음으로 쓴 경우의 canonical 중복 제거. 묶음 전용 전이를 두지 않으므로 표현 범위는 "단독으로 안전한 동작들의 묶음"으로 좁다. 묶음 전용 전이를 연다면 별도 capability 종류와 분석 복잡도가 크게 늘어난다 |

W4(최고 관리자 위임)에 같은 불변식을 공정하게 적용하면:

| 대안 | 표현 | 자기 위임 결함 |
|---|---|---|
| A | `EntrustAdmin` 동작. 불변식 "ADMIN 정확히 1명"이 공통 적용 | 동작 작성자가 "target ≠ me"를 빠뜨려도 불변식이 커밋 거부 |
| B+ | 타입 있는 확장 동작 `[추천]`. 반복되는 같은 구조가 E1에서 확인될 때만 표준 transfer 형식으로 승격 후보. 같은 불변식 | 같음 |
| C' | **C'로는 표현하지 않는다.** "대상을 ADMIN으로"는 단독 실행하면 ADMIN 2명이 되어 불변식을 깨므로 단독 공개 capability가 될 수 없고, 묶음 전용 전이는 두지 않는다. B+와 같은 확장 동작을 쓴다 | B+와 같음 |

즉 **결함을 막는 것은 대안이 아니라 불변식 선언이다.** 대안의 차이는 서버 작성량, 호출자 표현 범위, 판정 규칙의 기계성에 있다. 또한 W4 같은 "함께 바뀌어야만 불변식이 서는" 업무는 C'에서도 결국 확장 동작이 된다. C'가 줄일 수 있는 것은 "각각 단독으로 안전한 동작들을 한 번에 함께 성공시키는" 경우뿐이며, 그 실제 빈도는 E1로 잰다.

### C.3 기술 제안 (창시자 질문 아님. 근거와 함께 제안)

DD-01 v3의 I1~I7에 대응하는 쓰기 쪽 층 1. 관찰 가능한 성질로 쓴다. 이것이 서지 않으면 B+·C'를 내놓지 않는다.

| 불변식 | 내용 | 막는 것 |
|---|---|---|
| W-I1 공개된 것만 실행 | create / update / delete / link / transition / bulk는 서로 다른 capability이고 모두 기본 거부. 허용 필드와 허용 값은 닫힌 목록. 새 필드·새 값은 자동 포함되지 않는다(쓰기 preset도 DD-01과 같은 규칙) | 필드 확대(`role` 끼우기), 새 역할 값 자동 허용 |
| W-I2 상태는 전이로만 | 상태 필드는 일반 update로 바꿀 수 없고 선언된 전이로만 바뀐다. 전이는 허용 간선, 행위자 조건, 부수 효과를 함께 가진다 | 승인 흐름 건너뛰기, `EntrustAdmin` 우회 |
| W-I3 변경 전·후 모두 정책 | 행·필드·테넌트 정책을 대상 선택 시점과 변경 후 값 모두에 적용 | 내 행이라는 이유로 남의 소유로 바꾸기 |
| W-I4 일괄은 범위가 닫혀야 | bulk는 별도 capability. 허용된 필터만, 빈 조건 금지, 최대 대상 수, 실행 전 실제 대상 수 검사, 성공 단위(전부 또는 항목별)를 요청 전에 명시. 어느 쪽을 지원할지는 T11 `[미정]` | `where ... OR true` 범위 폭발 |
| W-I5 불변식은 모든 경로에서 | 선언된 불변식은 표준 쓰기, 확장 동작, 묶음 어디서 쓰든 커밋 시점에 최종 재평가되고, 동시 요청이 있어도 깨진 채 커밋되지 않는다. 위반은 불변식마다 안정된 오류 코드로 돌려준다. 생성·삭제 같은 수명주기 구간과 복구(repair) 규칙을 함께 선언. (구현 후보: 유일성·"최대 1개"는 DB 제약, "정확히 1개"·"최소 1개" 같은 집계형은 범위 키 잠금이나 직렬화 격리) | 자기 위임 ADMIN 0명, 동시 위임 write skew |
| W-I6 실행 방법은 서버가 | 호출자 요청에 raw SQL, 코드, 실행 순서·잠금·격리 힌트가 없다. 묶음(C')이어도 순서·잠금·효과 시점은 서버가 정한다 | 호출자가 트랜잭션 설계 |
| W-I7 숨은 부분 성공 없음 | 요청이 선언한 성공 단위 밖의 부분 성공이 없다. DB 결과와 외부 효과(메일, 알림, 결제)의 관계가 계약대로 관찰된다(예: 롤백된 쓰기의 알림은 나가지 않는다). 전부 롤백인지 항목별 결과인지는 T11 `[미정]` | 부분 실패 후 알림만 나가는 상태 |
| W-I8 재시도 안전 | "재시도 안전"을 약속한 동작(생성, 외부 효과, 묶음)은 재전송으로 중복 적용되지 않는다. 토글처럼 재시도에 취약한 동작은 목표 상태를 명시하는 형태로 | 재전송 시 중복 생성·토글 원복 |
| W-I9 존재를 드러내지 않음 | 운영 오류는 숨은 행·필드의 존재를 새지 않게(묶음 중 어느 단계에서 거부됐는지도 포함). 권한 맥락을 가진 개발 도구는 정확한 진단 | 거부 사유로 비공개 회원 존재 추측 |
| W-I10 확장도 같은 통제 | JS/Python 확장 동작도 정책, 불변식, 멱등, 감사, 효과 통제를 우회하지 않는다. 보장 방식은 DD-06 F2·F3 답에 따른다(다른 프로세스면 구조로, 임베드면 규약·검사·감사로) | 확장 경유 우회 |
| W-I11 선언한 감사는 빠지지 않음 | 감사 대상(`audited`)으로 선언한 동작은 감사 기록 없이 커밋되지 않는다. 어떤 동작을 감사 대상으로 둘지는 리소스 선언 | 대리 접속 등 고위험 동작의 기록 누락 |

**가장 단순한 구현으로 시작:** 불변식 범위 키 잠금(PoC의 동아리 ADMIN 행 잠금 방식), 고정 상한, 외부 효과는 PoC의 outbox 재사용 후보.

**층 2·T11(필요해질 때, 구현 수단):** outbox 형식, 멱등 키·결과 저장과 재생·키 보존 기간, 일반 감사 연결(주체·canonical 요청·판정·영향 행 수·트랜잭션 식별자, 민감 값 가림), 정교한 잠금 최적화, 항목별 부분 성공 일괄 처리(T11 결정 후), 긴 묶음, 확장 동작의 격리 수준 선택(T03·T09와 함께).

## D. 최초 철학과의 관계

| 원칙 | 관계 |
|---|---|
| PART I §1 호출자가 데이터와 **동작**을 표현 | 동작 표현의 핵심은 "원하는 업무 결과"를 표현하는 것이다. 절차를 호출자가 조립하는 것이 항상 더 충실한 표현은 아니다. B+는 단순 쓰기와 표준 전이를 결과로 표현하게 하고, C'는 단독으로도 안전한 동작들의 제한된 묶음까지 연다. 어느 쪽이 창시자의 뜻인지가 F2 |
| PART I §1 "서버가 모든 요청 형태를 사전에 정의하는 구조를 경계" | A에서 단순 쓰기까지 화면마다 동작을 선언하면 이 경계에 걸린다. 의미 있는 업무 동작에 이름이 있는 것 자체는 해당하지 않는다 |
| PART I §2 실행 권한 분리, 무결성 | W-I1~W-I11. 특히 W-I6(실행 방법은 서버)과 W-I5(불변식은 모든 경로)가 핵심 |
| PART I §4 AI First | capability 분리와 판정 규칙(C.1)이 기계적이어야 "표준이냐 확장이냐"가 선택지로 남지 않는다. C'는 같은 결과를 두 방식으로 쓸 여지를 만든다 |
| PART I §8 확장 | 표준으로 완결되지 않는 쓰기는 타입 있는 확장 동작. 승인 절차 없이 쓰되 같은 통제(W-I10) |
| GraphQL·CQRS 영감 | B+가 필드 단위 CRUD 엔진에 머물면 원문이 경계한 "CRUD 자동 생성"이다. 전이, 관계, 일괄, 불변식, 확장 동작을 하나의 Intent 체계로 다루는 것이 차이 |
| 자연어의 문법화 | 전이 이름·불변식 이름(예: `oneAdminPerClub`)과 목적·전제·기대 결과를 공식 구조로 담을지는 DD-05에서. 이 문서는 그 자리를 막지 않는다 |

## F. 확인된 답과 남은 일

- 확인됨: 가능한 많은 단순 변경을 표준 요청으로 표현하고, 풍부한 표준 동작을 제공한다. 창시자는 결과 표현만으로 제한하지 않았다. 서버는 권한·실행을 최종 통제한다.
- 기술 검증: 원자적 조합·분기·불변식·트랜잭션 경계, 확장 동작 계약, 업무별 성공 단위(E).
- 기존 F2의 결과 하나만 말하기 추천은 새 원문의 승인이 아니다. 두 방식 중 어느 하나를 미리 배제하지 않고 표준 기능 범위를 비교한다.

## G. 결정 상태

**잠정 합의.** 단순 쓰기와 풍부한 표준 동작을 목표로 하며 조합 의미·범위는 기술 설계와 검증이 남아 있다. 기존 B+ 및 C' 추천은 새 원문의 승인으로 보지 않는다.
