# DD-09. 상세를 열면 올라가는 익명 통계(조회수)를 어떻게 다루는가

> 결정 상태: **검증 필요** (새 기준: [B §5](../alignment/B-decision-reclassification.md#5-dd-문서의-현재-처리-상태))
> 기존 에이전트 리뷰·추천은 이전 지침 아래 작성된 검토 이력이다. 제안 본문은 보존하되 새 원문과 B의 확정 기준에 충돌하면 그 기준을 우선한다.
> 출처: DD-01 E1에서 발견한 요구. 아리아리 모집·동아리 상세 조회가 조회수를 올린다.
> 범위: **익명 통계 카운터**(조회수)만. "최근 본 항목", "열람 감사"처럼 **개인별 행동 기록**은 간선 정책(DD-01 I2)이 걸리는 다른 문제라 별도 문서 후보로 뺀다.
> 이전 지침 토론 기록: `../reviews/DD-09-sonnet-r1.md`, `../reviews/DD-09-sonnet-r2.md` (이전 지침 아래 에이전트 검토 이력; 새 기준은 B)
> 관련: `DD-01`(읽기 조합, 저장된 조회), `DD-02`(W-I8 재시도 안전), `DD-03`(등록), `DD-08`(읽기 GET·HTTP 캐시는 후속)

## A. 지금 결정할 문제

화면이 모집 상세를 **읽기만** 했는데 조회수가 1 오른다. 이 익명 통계를

- 서버 정의에 "이 상세를 열면 센다"고 선언해 서버가 알아서 올릴까,
- 읽기는 읽기만 하고 화면이 "열람했다"를 따로 보내게 할까.

어느 쪽이든 이 숫자는 **정확한 값이 아니라 조작에 어느 정도 강한 참고 수치**다. 그 성격을 함께 정한다.

## B. 실제 개발 시나리오

### B.1 아리아리 (`기존 코드`)

`commons/manager/views/ViewsManager.java`, `ViewsScheduler.java`:
1. 상세를 열면 "같은 접속(`x-forwarded-for` 헤더 값)이 하루 안에 본 적 있나"를 Redis에서 확인.
2. 없으면 조회수 +1(DB), 일별 집계 키 +1(Redis 14일 보관), 접속 키 기록(하루).
3. 스케줄러가 15일 전 일별 집계를 DB 조회수에서 빼서 "최근 14일 조회수"를 **의도**한다.

관찰:
- **의도와 실제 동작이 다를 수 있다.** 일별 집계 키를 만드는 `resolveViewsKey`가 콘텐츠 종류 대신 **현재 조회수 값**을 키에 넣는다(87행 `content.getViews().toString() + content.getId() + '_' + date`). 조회수가 바뀌면 키가 달라져 15일 뒤 빼기가 같은 키를 찾지 못할 가능성이 크다(코드 추론, 실행 확인 안 함).
- 확인 후 기록이라 같은 접속이 동시에 두 번 열면 두 번 셀 수 있다.
- 중복 제거 키(`x-forwarded-for`)는 프록시 구성에 따라 호출자가 조작할 수 있고, 학교 공용망은 여러 사람을 한 명으로 센다.
- 같은 코드가 동아리 상세(`ClubService.java` 59~61행)와 모집 상세에 반복된다.
- 랭킹("조회수 상위 9개", DD-01 E1)이 이 값에 의존한다.
- 아리아리 전체에서 **읽기에 딸린 쓰기는 조회수 한 종류, 두 곳뿐**이다. 알림 읽음은 이미 명시적 PATCH다(Sonnet E1).

### B.2 지난 AIP PoC (`기존 코드`)

```text
views: Int counter via redis dedupe by client within 1d window 14d     // app.aip Recruitment
query RecruitmentDetail(r: Recruitment) { ... touch r.views }          // 422행 근처
```

- 중복 제거는 실제로 구현돼 있다(PostgreSQL 테이블 `_aip_counter_seen`, 런타임 `engine.rs` 323~347행 근처, DDL `ddl.rs` 52~55행 근처). 런타임에 Redis 코드는 없다.
- **`window 14d`는 선언만 있고 실행에 쓰이지 않는다.** 중복 제거 기록을 지우는 코드도 없다(`[PoC 부채]`).
- 중복 제거 키는 `x-aip-client` 헤더 값을 그대로 쓴다(`http.rs` 104~111행, 신뢰 프록시 설정 시 `x-forwarded-for`). **호출자가 정하는 값**이다.

즉 "수십 줄이 선언 한 줄로 흡수됐다"는 절반만 맞다. 중복 제거는 흡수됐고, 창 집계와 기록 청소는 아직이다.

## C. 대안과 트레이드오프

### C.1 대안

| | V1 선언한 상세 읽기에서 서버가 자동 집계 | V2 화면이 "열람" 신호를 따로 보냄 |
|---|---|---|
| 무엇을 세나 | 서버 정의가 **선언한 열람 지점**이 호출돼 정책을 통과한 행을 돌려줬을 때만. 요청 모양에서 추측하지 않는다. "열람 지점"을 무엇으로 선언할지는 C.4(미결정) | 화면이 보내는 표준 신호 쓰기(`view` 신호). 전이 같은 무거운 쓰기가 아니라 카운터 전용 신호 |
| 판정이 보이는가 | 서버 정의에 보인다. 임의 조합 읽기는 세지 않는다 | 화면 코드에 보인다 |

### C.4 "열람 지점"을 무엇으로 선언하나 `[미결정]`

DD-01은 저장된 조회를 "이름만 붙인 것, 새 의미 없음"으로 정의한다(DD-01 C.1). 여기에 "센다"를 붙이면 새 의미가 생겨 DD-01과 충돌한다. `detail` 같은 형태도 DD-01에 없는 새 개념이다. 후보:
- (a) 리소스가 "열람 집계"를 따로 선언하고, 어떤 표현으로 읽든 지정된 읽기와 같은 canonical로 정리되면 센다. DD-01을 바꾸지 않지만, canonical이 같은 프리페치·미리보기도 함께 세는 문제가 남는다.
- (b) "효과가 붙은 읽기"라는 새 종류를 DD-01에 추가한다(저장된 조회와 별개로, 이름과 효과를 가진 읽기). 판정은 정확하지만 DD-01 개정이 필요하다.
- 어느 쪽이든 DD-01에 통지가 필요하다(DD-01 E1 결과 "새로 생긴 질문"에 연결). 에이전트는 (b)를 약하게 선호하나 DD-01 재토론 뒤 정한다.

초안 v1은 "id 하나로 읽는 요청 = 열람"으로 추측하는 판정을 썼으나 폐기했다. 프리페치·미리보기 카드, 관리자의 수정 화면, 중첩 선택, 같은 행을 다른 모양으로 읽는 요청(한 의도 여러 표현), 서버 렌더링·봇에서 어긋난다.

### C.2 비교

| 축 | V1 | V2 |
|---|---|---|
| 철학 정합성 | 반복 흡수(조회수 코드·스케줄러가 선언으로). CQRS 관점에서는 **읽기 트랜잭션 경계는 분리하지만 책임 분리는 아니다.** 읽기 이벤트에서 파생되는 통계라는 것이 정당화 근거다(영감은 규격이 아니다, 원문 PART I §1) | CQRS식 책임 분리에 가깝다 |
| 서버 작성량 | 상세 형태 선언에 "센다" 한 줄 | 신호 capability 한 줄 |
| 화면 작성량 | 없음 | 상세 화면마다 신호 한 줄(빠뜨리기 쉬움) |
| 조작 저항 | 중복 제거 키를 서버가 파생(C.3) | 같은 키 규칙을 신호에도 적용해야 함. 읽기 권한 검사도 필요(볼 수 없는 행에 신호를 보내 존재를 확인하는 경로) |
| 구현 | 선언 읽기에 집계 훅, 비동기 기록, 창 집계 | 신호 쓰기 + 같은 집계 |
| AI 개발 경험 | 서버 쪽 선언만. 화면은 몰라도 됨 | 화면마다 기억해야 함 |

실행 방식(읽기 경로에서 바로 올림 / 큐로 / 접근 로그에서 사후 집계)은 V1·V2와 별개의 구현 선택이라 C.3의 성질만 정하고 구현은 DD-06(백그라운드 작업 위치)과 함께 정한다.

### C.3 어느 안이든 지킬 성질 (층 1) `[추천]` (창시자 질문 아님)

| 성질 | 내용 |
|---|---|
| VC-1 읽기 응답과 무관 | 집계가 실패해도 읽기는 성공한다 |
| VC-2 읽기 트랜잭션 안에서 쓰지 않음 | 집계는 별도 경로. 읽기를 읽기 전용 연결로 보낼 수 있다 |
| VC-3 정책을 통과한 행만 | 볼 수 없는 행, 오류, 거부된 읽기는 세지 않는다. 조회수 변화로 존재를 추측할 수 없게 한다 |
| VC-4 중복 제거 키는 서버가 정한다 | 로그인 사용자면 행위자, 아니면 서버가 연결에서 얻은 값. 호출자가 보낸 임의 헤더를 그대로 쓰지 않는다 |
| VC-5 식별 값은 가려서 짧게 | 원본 접속 식별 값(IP 등)은 저장하지 않고 일 단위로 바뀌는 해시를 쓰며, 창이 지나면 삭제한다 |
| VC-6 원자적 중복 제거 | "확인 후 기록" 경쟁 없이 한 번만 센다(재시도 포함) |
| VC-7 최종 일관성 | 랭킹 등 이 값을 쓰는 읽기에는 즉시 반영을 약속하지 않는다. 계약에 "참고 수치"로 표시 |

열린 점(DD-01 후속 목록에도 기록): 14일 같은 창은 랭킹의 의미 요건이라 집계 방식과 함께 정해야 한다. 값이 계속 바뀌는 카운터로 정렬하면 커서 페이지가 흔들릴 수 있다. HTTP 계층 캐시·브라우저 프리페치가 선언 읽기를 대신 응답하면 집계가 빠지거나 부풀 수 있다. 읽기를 GET으로 노출할지(DD-08 W7)와 함께 정한다. 봇·크롤러 제외는 아리아리 프론트의 서버 렌더링 사용 여부와 실제 봇 비율을 확인한 뒤(확인 필요).

## F. 확인된 답과 남은 일

- 확인된 방향: 명시적으로 선언된 읽기 통계는 허용 후보이며, 일반 조회에 숨은 증가를 붙이지 않는다.
- 기술 검증: 선언 지점·중복 제거·보관 기간·캐시 및 prefetch 영향·집계 비용을 비교한다. 개인별 최근 열람 기록은 별도 기능으로 다룬다.
- 기존 F1의 일반적 허용/불허 선택은 재질문하지 않는다. V1은 구체 동작 사양이 아니라 기존 기술 제안이다.
