## A. 지금 결정할 문제

창시자는 "자연어로 표현하던 목적, 의도, 맥락을 AIP의 공식 구조나 문법으로 표현"하길 원한다. 주석을 많이 쓰자는 것이 아니고, 주석 자동 생성이나 JSDoc 확장으로 축소해서도 안 된다(원문 PART I §6).

이전 원문은 실행 의미·메타데이터·검증 연결 등을 열어 뒀으나, 통합 지침은 선택적 구조화 설명과 실행 계약의 분리를 직접 확인했다. 지금 설계할 것은 문법 위치·소속·키·타입·공개 범위·개발 도구 출력이다.

이 문서는 서버 정의를 쓰는 개발자(또는 AI)가 특정 선언에 남기는 설명을 다룬다. 이것은 호출자가 요청에 담는 Intent와 별개다. 자연어 설명은 실행 권한이나 요청 시점의 보안 판단을 정하지 않는다.

## B. 실제 개발 시나리오: 아리아리의 자연어 설명

아리아리 백엔드의 Swagger `@Operation(summary, description)`은 148개다. 개발자가 각 API의 목적과 규칙을 자연어로 적은 것이다. 그중 권한·제약을 말하는 문장(키워드 "만이·만 가능·이상·관리자만·본인·작성자")은 36개다.

### B.1 사례 1: 설명보다 코드가 엄격 (`기존 코드`)

```java
// ClubMemberController.java 40행
@Operation(summary = "동아리 회원 권한 수정",
  description = "... '스텝' 권한 이상의 동아리 회원이 타 동아리 회원의 권한을 수정할 수 있습니다.")
```

코드는 ADMIN만 허용한다(`ClubMemberService.java` 67행). '스텝'이라는 역할은 없다(enum은 GENERAL·MANAGER·ADMIN). 에이전트도 DD-02 초안에서 이 설명을 그대로 믿고 틀렸다가 바로잡았다.

### B.2 사례 2: 설명보다 코드가 느슨 — 보안 결함 (`기존 코드`)

```java
// SystemNoticeController / SystemFaqController
@Operation(summary = "서비스 공지사항 등록", description = "운영 관리자만이 등록할 수 있습니다.")
```

```java
// SystemNoticeService.saveSystemNotice (domain/system/notice/SystemNoticeService.java 43~45행 근처)
// 검증 로직이 필요함
SystemNotice systemNotice = saveReq.toEntity(...);
```

```java
// SystemFaqService.java 32·40행 근처
// 검증 로직 추가 필요
```

서비스 FAQ·공지 8개 API가 "운영 관리자만"이라고 설명하지만 서비스 코드에는 역할 검사가 없다. 코드 읽기로는 로그인한 회원이면 서비스 공지를 등록할 수 있다(실행 확인 안 함. 프론트·게이트웨이 단계의 보호 여부는 확인 필요). **설명이 코드보다 안전한 쪽으로 틀려서, 설명을 믿은 사람과 AI는 "이미 막혀 있다"고 가정한다.**

### B.3 36개 전체 대조 결과 (`DD-05-sonnet-r1.md` §2)

| 분류 | 개수 | 예 |
|---|---|---|
| 불일치 | 13 (그중 서비스 FAQ·공지 8개는 코드 읽기로 역할 검사 부재 확인, 실행 확인 안 함) | 스텝 이상, 회계 수정·삭제(죽은 API), 출석 리스트, 지원 삭제, 서비스 FAQ 4, 서비스 공지 4 |
| 설명에 없는 예외(슈퍼관리자 통과) | 4 | 공지 상세·리스트, 일정 리스트, 지원 형식 조회 |
| 강제 불완전 | 1 | 공지 고정 최대 3개(확인 후 쓰기) |
| 일치하나 설명에 없는 조건·부수 효과 | 6 | 위임(위임자 강등), 공지 등록(전 회원 알림) 등 |
| 단순 일치 | 12 | |

"관리자"라는 한 단어가 최소 네 뜻으로 쓰인다: MANAGER 이상, ADMIN, 운영 관리자, "관리자 권한을 가진 동아리 회원". 설명 칸에 "(해당 API 불필요할 시 비활성화 하겠습니다.)" 같은 개발 메모도 섞여 있다. 사유·상태를 적을 정해진 자리가 없어서로 보인다(추정).

초안 v1의 E1은 "12개 대조, 불일치 2"라고 적었으나 실제 대조 범위와 숫자가 맞지 않았다. 위 표로 대체한다.

## C. 이전 탐색 후보 (새 기본 요구사항 아님)

아래 ①~⑥ 비교는 이전 지침의 탐색 이력이다. 구조적 소속을 제공하는 방향은 확인됐으나 자연어 의미 검사·문장→실행 규칙 생성은 기본 요구사항으로 채택하지 않는다. 설명을 실행 권한/보안 정책의 근거로 삼는 해석은 통합 지침과 충돌한다.

### C.1 후보를 "효과"와 "출처"로 정리

후보들은 서로 다른 질문에 답하므로 하나를 고르는 대안이 아니라 조합할 수 있는 효과다. **원문 §16에 있는 방향**과 **에이전트가 구체화한 후보**를 구분해 표시한다.

| 효과 | 후보 | 출처 | 아리아리 사례에서 잡는 것 | 한계·비용 |
|---|---|---|---|---|
| ① 목적·전제·기대 결과·맥락을 정해진 자리에 적고 AI·사람이 찾기 쉽게 | N-A1 자유 서술 칸 / N-A2 타입 있는 칸(목적 분류, 기대 결과는 효과 선언과 대조 가능, 사유·상태 칸 포함) | 원문 §16 "목적·전제·기대 결과의 구조화", "AI가 탐색 가능한 의미 정보" | 개발 메모가 설명에 섞이는 것(사유·상태 칸), Index → Contract 탐색 | N-A1만으로는 주석과의 차이가 약하다. N-A2는 칸 설계가 필요 |
| ② 실행되는 규칙과 설명을 분리하고, 설명이 규칙과 어긋나면 도구가 경고 | N-B 설명 문장 ↔ 규칙 연결 | 원문 §16 "실행 가능한 계약과 설명적 정보의 분리" + 에이전트 구체화 | 연결된 규칙이 없는 문장(B.2의 8개처럼 규칙 자체가 없는 경우), 규칙이 바뀐 뒤 낡은 문장 | **의미 차이는 못 잡는다.** "스텝 이상"처럼 규칙은 있으나 문장이 다르게 말하면 연결만 보고는 모른다 |
| ③ 기대 결과를 예시로 써서 실행 가능한 검사가 되게 | N-F 예시가 계약("일반 회원이 권한 변경 요청 → 거부, ADMIN → 허용") | 원문 §16 "기대 결과의 구조화"를 예시로 실현(에이전트 구체화) | 의미가 다른 불일치(스텝 이상, 출석 리스트, 지원 삭제)를 예시 실행 순간 잡음 | 예시 작성이 늘어난다 |
| ④ 쓴 문장 자체가 규칙으로 실행 | N-C 자연어에 가까운 규칙 문법 | 에이전트 구체화 | 문장과 규칙이 같은 것이라 어긋날 수 없음 | 원문 "Intent는 자연어 무제한 해석이 아니다"와 경계. 문법 밖 문장을 쓰는 오류 |
| ⑤ 자연어로 요구를 말하면 규칙이 만들어지고 원문이 함께 남음 | N-D 자연어 → 정형 규칙 생성 | 에이전트 구체화 | 요구 원문이 남아 나중에 대조 가능 | 만드는 것은 **규칙**이지 설명이 아니다. 생성 도구의 정확도와 검토 절차 필요 |
| ⑥ 같은 말을 어디서나 같은 용어로 | N-E 도메인 어휘 | 원문 §16 "도메인 의미 표현" | "관리자" 네 가지 뜻, 존재하지 않는 '스텝' | 용어 정의 작성 필요. 자유 문장 속 용어 검증은 문장 일부를 구조화해야 가능 |
| (참고) 규칙에서 설명을 자동으로 만듦 | N-G | 에이전트 | 설명과 규칙이 어긋날 여지가 없음 | **원문 "주석 자동 생성으로 축소하지 마라"에 정면으로 걸린다.** 단독으로는 원문 뜻을 채울 수 없어 보조 수단으로만 |

### C.2 문서화와의 구분 (원문 §6 후속 합의)

문서 작성 자체는 강제하지 않는다. 원문 §6 후속 합의(문서화 표준은 주되 작성 의무는 만들지 않는다)를 따르면, 어느 후보든 칸을 비워 두는 것은 허용되고 채웠다면 그 형식과 연결을 검증하는 모양이 된다.

### C.3 각 효과가 다른 결정과 만나는 지점

| 효과 | 만나는 곳 |
|---|---|
| ① | DD-01 I5 개발 진단에서 거부 사유 설명, 계약 공개 범위(T06), AI 탐색 순서 |
| ② | DD-02 전이·불변식, DD-01 capability |
| ③ | DD-02 E3·DD-01 E3 공격 요청 모음과 같은 형식의 예시 실행 |
| ④ | DD-04 작성 방식(고유 문법 A·E일 때 현실적) |
| ⑤ | DD-04 작성 도구, AI 작성 흐름 |
| ⑥ | 오류 코드 이름(DD-01 I5, DD-02 W-I5), 리소스·전이 이름 |

## D. 최초 철학과의 관계

| 원칙 | 관계 |
|---|---|
| 자연어의 문법화, 주석과 구별 | ②③④⑤는 실행·검증과 연결돼 주석과 구별된다. ①은 정해진 자리와 타입(N-A2)으로 구별되며, 원문 §16의 "AI가 탐색 가능한 의미 정보"에 직접 대응한다. ⑥은 용어의 일관성으로 구별된다 |
| AI First: AI가 구현 내부를 추측하지 않게 | ①은 AI가 찾을 자리를 고정하고, ②③은 설명과 규칙의 어긋남을 드러내고, ④⑤는 어긋날 여지를 없애고, ⑥은 용어 혼동을 줄인다. 어느 쪽이 B.1·B.2를 실제로 막는지는 E2로 확인 |
| Intent는 자연어 무제한 해석이 아니다 | ④는 이 경계를 지켜야 한다. ⑤는 결과가 정형 규칙이라 경계 안 |
| 서버 최종 통제(`docs/PRINCIPLES.md` §2) | 확인된 기준: 자연어 설명은 실행·보안 판단의 근거가 아니다. 실행되는 규칙은 별도 정형 계약으로 검증한다 |
| 문서 작성 강제 금지 | 칸을 비우는 것은 허용, 채운 것만 검증 |

## F. 확인된 답과 남은 일

- 확인됨: 선언에 귀속되는 선택적 구조화 설명을 제공한다. 자연어 의미 검증을 필수로 요구하지 않으며, 설명을 요청 시점의 실행·보안 판단 근거로 쓰지 않는다. 기존 F1~F3의 의미 질문과 Q5 자료 대기는 해제한다.
- 기술 검증: 문법 위치, 키·타입, 보존·공개 범위 및 선택적 개발 도구 연결을 설계한다. 설명과 실행 계약은 분리한다.
- 남은 기술 검증은 E4·E5와 메타데이터의 소속·공개/표시 방식이다. 이전 후보 ①~⑥ 및 E2·E3 계획을 승인된 기본 요구사항으로 재사용하지 않는다.

## G. 결정 상태

**잠정 합의.** 구조화·선택성·실행 판단과의 분리는 확인됐다. 문법·메타데이터 스키마·표시 방식의 상세 설계가 남아 있다.
