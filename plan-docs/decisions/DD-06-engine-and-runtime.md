> 결정 상태: **잠정 합의** (새 기준: [B §5](../alignment/B-decision-reclassification.md#5-dd-문서의-현재-처리-상태))

## A. 지금 결정할 문제

이전 문서는 독립 서버와 Node·Python 임베드 및 자동 기동을 비교했으나, 이 구도는 현재 결정 질문이 아니다. 확인된 구조는 Rust 기반 자체 포트 서버와 별도 프론트엔드 SDK이며 JS/TS·Python 확장을 지원한다. 이 문서는 확장 호출 경계·워커·배포 세부를 검증한다. 서버 자동 기동은 개발 편의 옵션으로 남긴다.

쉽게 말하면 세 가지다.
1. 운영할 때 AIP 엔진이 **별도 서버**로 도나, **기존 Node/Python 앱 안**에서 도나.
2. 메일 발송·예약 작업·잡·실시간 구독 같은 **상시 백그라운드 일**은 어디서 도나.
3. JS/Python으로 쓴 **확장 코드**를 엔진이 어떻게 부르고, 확장이 DB 규칙을 우회하지 못하게 어떻게 막나.

## B. 실제 개발 시나리오

### B.1 지금 아리아리 (`기존 코드`)

프론트 Next.js 14(`ariari-frontend/package.json` 21행)와 백엔드 Spring Boot를 따로 배포한다.

### B.2 지난 AIP PoC (`기존 코드`)

- `crates/aip-runtime`(약 4.5천 줄). 진입점 `run(program, opts)`(`lib.rs` 99행)이 서버를 띄운다.
- 참고: 지금 런타임이 받는 입력은 Core IR 자체가 아니라 그것을 컴파일한 실행 계획(`aip_plan::Program`)과 계약이다. 이 문서의 "검증된 Core IR 산출물"은 그 산출물 묶음을 가리킨다.
- **엔진 본체는 HTTP에 의존하지 않는다**(`engine.rs`에 axum 없음). HTTP는 `http.rs`, 구독(WebSocket)은 `subscribe.rs`·`http.rs` 49행에 있다. 엔진을 라이브러리로 떼어 내는 비용은 크지 않을 것으로 보인다(확인 필요: E1).
- 시작할 때 **상시 루프 4개**를 띄운다: outbox 디스패치, 아웃바운드 웹훅 전달, 스케줄(타이머), 잡 워커(`lib.rs` 116~123행, `opts.workers`가 켜져 있을 때). 구독은 별도 DB 연결로 변경 알림을 듣는다. `workers`를 끄면 API만 도는 프로세스도 띄울 수 있다(`lib.rs` 88행 근처 `Options.workers`).
- 잡은 heartbeat와 재개 모델이라 프로세스가 죽어도 정확성은 유지된다(`jobs.rs` 머리 주석).
- 확장 효과는 `dispatch.rs` 223·230행에 하드코딩. JS/Python을 부르는 경로는 없다. `fn … wasm` 문법은 있으나 실행 경로가 없다(OI-E2).

### B.3 운영 형태 (`개념 예시`)

```text
S  [Next.js] ──HTTP──▶ [aip 서버: API + 백그라운드 루프] ──▶ PostgreSQL
                              │ 확장 호출
                              ▼
                       [확장 프로세스(Node/Python)]

E  [Node 앱 프로세스 안: 호스트 HTTP + aip 엔진(네이티브 모듈) + 백그라운드 루프 + 확장 코드] ──▶ PostgreSQL
   (서버리스 함수에 올리면 백그라운드 루프가 돌 곳이 없다 → 별도 상시 프로세스 필요)
```

## C. 대안과 트레이드오프

### C.1 축이 여럿이다

| 축 | 선택지 |
|---|---|
| 엔진 위치 | 이전 비교 기록: S 별도 서버 / E 호스트 프로세스 임베드 / H SDK가 별도 서버를 자동 기동. 현재 기준은 자체 서버 + 별도 프론트 SDK이며 자동 기동은 편의 옵션 |
| 백그라운드 작업 | 엔진과 같은 프로세스 / D API 프로세스와 워커 프로세스 분리(PoC에서 이미 `workers` 끄기 가능) |
| 확장 호출 | 같은 프로세스 함수 호출 / 로컬 확장 프로세스(IPC) / X 별도 서비스(HTTP, 엔진의 아웃바운드 웹훅 인프라 재사용. 서버리스와 잘 맞지만 지연이 크고 엔진 트랜잭션에 참여할 수 없어, 외부 효과형 확장에 한정해 검토) / W WASM 샌드박스(순수 계산 확장만) |

### C.2 엔진 위치 비교 (원문 PART VII §13의 축을 이 문제에 적용)

| 축 | S | E | H |
|---|---|---|---|
| 철학 정합성 | Rust 엔진. JS/Python은 SDK·확장으로 | "JS/Python 생태계에서 자연스럽게"에 가까움 | 개발 경험은 E, 실행은 S |
| 보안(확장 격리) | 확장이 별도 프로세스. 확장에 DB 자격증명을 주지 않으면 우회를 **구조로** 막을 수 있다(그 약속을 설정에서 지켜야 함) | 같은 프로세스라 확장이 DB URL·메모리에 닿을 수 있다. **구조로는 막을 수 없고 개발 규약·감사로 관리**. Rust 패닉이 호스트를 함께 죽일 수 있다 | S와 같음 |
| 비즈니스 규칙 처리 | 엔진 | 엔진 | 엔진 |
| 확장의 트랜잭션 참여 | 확장 쓰기를 엔진에 되돌리려면 트랜잭션을 연 채 프로세스 경계를 오가야 한다(타임아웃·교착 위험) | 함수 호출이라 쉽다 | S와 같음 |
| 구현 난이도 | 확장 IPC, 확장 프로세스 수명 관리(기동·재시작·상태 확인) | 엔진 분리(작음) + N-API·PyO3 바인딩 + 비동기 런타임과 호스트 이벤트 루프·GIL 연동(확인 필요) | S + 바이너리 배포(플랫폼별 네이티브 바이너리를 패키지에 동봉, 확인 필요) |
| 배포 | 컨테이너에 바이너리 + 확장 프로세스 | 장수 프로세스 호스트면 기존 배포 그대로. **서버리스면 백그라운드 루프용 상시 프로세스가 따로 필요** | S와 같음 |
| 디버깅 | 프로세스 둘의 추적을 이어야 함 | 한 프로세스지만 Rust 오류가 JS 쪽에서 어떻게 보이는지 미평가 | S와 같음 |
| AI 개발 경험 | 서버를 따로 띄우는 절차(H로 완화 가능) | `npm install` 후 몇 줄 | 한 줄 시작 |
| 성능 | 확장 호출마다 IPC | 바인딩 경계 + 요청·응답 직렬화(엔진이 JSON 값을 다룸, 확인 필요) | S와 같음 |

E에서 호스트를 N개로 늘리면 백그라운드 워커도 N개가 된다. PoC의 작업 선점 방식으로 정확성은 유지되지만 DB 부하와 웹훅 중복 전송 가능성은 평가해야 한다.

### C.3 확장 우회 방지의 위협 모델 `[추천]` (창시자 질문 아님)

"확장이 엔진을 거치지 않고 DB를 직접 건드리지 못하게"(DD-01 I6, DD-02 W-I10)를 무엇으로부터 지키는지 먼저 정한다.

| 위협 | S·H·X | E |
|---|---|---|
| 앱 개발자·AI의 실수(엔진을 안 거치고 직접 쿼리) | 확장에 DB 자격증명이 없으니 구조적으로 불가 | 린트·코드 검사와 감사 로그로 관리 |
| 악의적이거나 오염된 서드파티 확장 패키지 | 프로세스·네트워크 격리 + 자격증명 미보유 | 같은 프로세스라 막을 수 없음 |

1차 범위가 "앱 개발자 본인과 AI가 쓴 확장"이면 E도 감수할 수 있고, "서드파티 확장 생태계"까지면 S·H·X가 필요하다.

### C.4 어느 안이든 `[추천]`

1. **엔진 본체는 HTTP와 분리된 라이브러리.** 이미 대부분 분리돼 있다(B.2). S·E·H 어느 포장도 가능하게 한다(코드 변경이므로 승인 뒤).
2. **운영 엔진은 정의 모듈을 실행하지 않는다**(DD-04 C.3).
3. **확장 호출 계약은 형태와 무관하게 하나**: 입력·출력 타입, 효과 종류(읽기만 / 엔진 경유 쓰기 / 외부 효과), 재시도 안전 여부, 시간·메모리 상한, 엔진 트랜잭션 참여 여부, 계약 버전, 오류 코드.
4. **확장의 데이터 접근은 엔진이 준 수단만.** E에서는 확장에 DB 연결 정보를 넘기지 않는 SDK 구조로 실수를 줄인다.
5. **백그라운드 작업은 API와 분리 가능해야 한다**(D). 서버리스 배포를 고르면 워커 프로세스를 따로 둔다.
6. **어느 형태로 실행해도 같은 결과**를 같은 시험 모음으로 확인한다.

## D. 최초 철학과의 관계

| 원칙 | 관계 |
|---|---|
| Rust 핵심 엔진 | 모든 안에서 충족. "Rust가 모든 일을 하는 것이 최적은 아니다"에 따라 HTTP 수신은 호스트에 맡길 수 있다 |
| JS/Python 생태계 | E가 가장 직접. H는 개발 경험만 같고 실행은 별도. W(WASM)는 npm/pip 패키지 사용이 막혀 순수 계산 확장 등급에만 |
| 서버 최종 통제 | S·H·X는 확장 우회를 구조로 막음. E는 관리로 막음(C.3) |
| 이전 감사의 "독립 서버를 승인 없이 택했다" | 새 원문에서 서버와 프론트 라이브러리의 병렬 구조를 확인했다. 이전 감사 문장은 현재 결정의 전제가 아니다 |

## F. 확인된 답과 남은 일

- 확인됨: Rust 핵심 엔진은 자체 포트에서 실행되는 서버 프레임워크이고, 별도의 프론트엔드 라이브러리를 제공한다. JS/TS·Python 확장은 공식 기능이며, 앱 개발자와 AI가 작성할 수 있어야 한다.
- 기존 F2의 독립 서버/임베드 양자택일은 폐기한다. 자동 기동·임베딩은 서버와 SDK를 대체하는 선택이 아니라 개발 편의 옵션으로 검토한다.
- 기술 검증: 서버·워커 배치, 확장 프로세스 연결·취소·트랜잭션 수명·권한 경계, 플랫폼별 배포 제약(E). 서드파티 패키지 범위와 초기 배포 환경은 근거를 준비한 뒤 가치 판단으로 남긴다.

---

## G. 결정 상태

**잠정 합의.** 자체 포트 서버·프론트 SDK·JS/TS 및 Python 확장은 확인됐다. 설치 편의, 배포 환경, worker 및 확장 연동의 세부를 검증한다. 기존 S/H·임베드 비교 추천은 대체 구조 결정이 아니다.

## 이탈 방지 점검

| 질문 | 답 |
|---|---|
| 백엔드 개발이나 이중 유지보수를 줄이는가 | E·H는 개발자가 관리할 배포물이 줄거나 같아 보인다. 백그라운드 워커는 어느 안이든 운영 대상 |
| 호출자 표현에 도움이 되는가 | 직접 관계 없음 |
| 서버가 최종 권한을 통제하는가 | **E에서 중대한 긴장.** 확장 우회를 구조로 막을 수 없다. C.3 위협 모델과 F3 답에 따라 E의 적합성이 갈린다 |
| AI의 불필요한 선택을 줄이는가 | (라)는 "어느 형태로 실행할까"라는 선택을 만든다. 하나를 정하는 편이 낫다 |
| JS/Python 생태계와 사람의 사용성 | E·H가 시작 경험이 좋다 |
| 복잡성을 옮기기만 했나 | E는 엔진 쪽에 바인딩·이벤트 루프 연동을, H는 바이너리 배포를 둔다. 앱 개발자 쪽은 줄어든다 |
