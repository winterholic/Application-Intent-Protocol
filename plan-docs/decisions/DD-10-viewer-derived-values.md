## B. 실제 개발 시나리오

### B.1 아리아리 응답 DTO 전수 조사 (`기존 코드`, Sonnet E1)

보는 사람 기준 값 11개를 찾았다(예: `RecruitmentData.isMyBookmark`, 상세 `isMyClub`·`isMyApply`·`myRecentApplyTempId`, 동아리 `isMyBookmark`, 댓글 `isMine`, 차단 `isBlocked`, 동아리 회원의 내 역할·상태 등). 계산 방식은 리소스마다 4종으로 갈리고 계산 위치는 11곳 안팎이다. "목록 DTO마다 같은 처리"라기보다 **리소스 종류와 계산 방식 사이에 흩어져 있다.**

종류별 분류:

| 종류 | 형태 | 개수 |
|---|---|---|
| K1 내 소유 간선이 있나 | 내 북마크, 내 지원 등 | 5 |
| K2 내 소속 관계가 있나 | 내 동아리인가(현행은 회원 상태를 보지 않음) | 1 |
| K3 내 간선 중 하나를 골라 값으로 | 내 최근 임시 저장 id | 1 |
| K4 내 간선 행 자체 | 내 역할·상태 | 1 |
| K5 행의 필드와 나를 비교 | 댓글 작성자가 나인가 | 1 |
| K6 남이 쥔 간선 | 나를 차단한 사람인가(상대가 소유한 간선) | 1 |
| K7 내 속성을 행에 붙임 | 내 학교 | 1 |

K1~K5(9개, 82%)가 "내가 소유하거나 내가 주체인 관계에서 나오는 값"이라는 한 가족이다. K6은 남이 소유한 간선이라 정책 문제, K7은 세션 정보다.

### B.2 지난 AIP PoC (`기존 코드`, `examples/ariari/app.aip`)

`RecruitmentList`·`RecruitmentDetail`의 `select` 안 식으로 썼다(`exists RecruitmentBookmark b where b.recruitment = r and b.member = actor`, `exists membership(actor, r.club)`, `latest ApplyDraft d … by d.createdAt`). `relation` 선언(88·139~144행 근처)과 `ClubDetail.myMembership`(207행 근처)도 선례다. 차단은 행 정책으로 처리했다(672행 근처).

### B.3 대안별 모습 (`개념 예시`)

```ts
// V1. 서버가 리소스에 보는 사람 기준 값을 이름 붙여 선언(K1~K5 범위)
resource("Recruitment", {
  viewer: {
    isBookmarked: "exists bookmarks b where b.member = actor",                // K1
    isMyClub:     "exists membership(actor, club) where status = ACTIVE",     // K2
    myLatestDraft:"latest applyDrafts d where d.member = actor by created",   // K3
  },
})
aip.read("Recruitment", { select: { title: true, isBookmarked: true } })      // 호출자는 이름만 고름

// V5. 간선에 "소유 컬럼"을 한 번 선언하면 엔진이 mine 관계를 제공
resource("RecruitmentBookmark", { owner: "member" })
aip.read("Recruitment", { select: { title: true, bookmarks: { mine: { exists: true } } } })
```

## C. 대안과 트레이드오프

### C.1 대안

| | V1 서버가 이름 붙인 viewer 값 | V5 소유 컬럼 선언 + `mine` 관계 | V3 화면이 내 간선을 따로 읽어 맞춤 |
|---|---|---|---|
| 서버 작성량 | 소유 컬럼 선언 + 값마다 한 줄(11개 안팎) | 간선마다 소유 컬럼 한 줄 | 없음 |
| 호출자 표면 | 이름 고르기 하나 | 관계 select 하나 | 별도 요청 + 결합 |
| 표현 범위 | 선언한 것만. K1~K5를 문법이 지원해야 함 | 소유 간선 전체를 일반적으로. K2의 "활성 회원만" 같은 의미는 별도 | 내 간선이 보이는 범위 |
| 새 개념 | viewer 값 | `owner`, `mine` | 없음 |
| 캐시 | 응답이 행위자마다 다름 | 같음 | 공용 목록은 공유 캐시 가능, 내 간선만 따로 |

초안 v1에 있던 V2(호출자가 `exists … where member = $actor`를 직접 쓰기)는 **뺐다.** 호출자 표면이 셋(이름 고르기·요청 안 식·클라이언트 결합)으로 늘어 한 의도 한 구조를 깨고, 호출자가 쓴 where가 정말 "본인 간선"인지 의미 검사가 영구 과제로 남는다. 호출자 표현은 이름을 고르고 관계를 select/traverse하는 것으로 충족된다.

### C.2 비교

| 축 | V1 | V5 | V3 |
|---|---|---|---|
| 철학 정합성 | 반복 흡수(계산 방식 4종이 선언 하나로) | 더 일반적. 화면별·값별 선언도 줄어든다 | 서버 작업 없음, 화면이 일함 |
| 보안 | 서버가 식을 정하므로 노출 범위가 명확 | 소유 컬럼이 정책과 별개라 정의를 잘못하면 넓게 열림 | 간선 정책이 본인 것만 보여 주면 안전(북마크에만 확실) |
| AI 개발 경험 | 이름 하나 | 관계 문법 하나 | 결합 코드를 매번 |
| 구현 | viewer 식 평가 | 소유 관계 자동 생성 | 없음 |

어느 쪽이 나은지는 DD-04 표기와 DD-01 F1에 걸려 있어 이 라운드에서 확정하지 않는다. 다만 VV-1a에 따라 둘 다 소유 컬럼 선언을 전제로 하므로, 차이는 "값에 이름을 붙여 고르게 하느냐(V1), 소유 관계를 고르게 하느냐(V5)"라는 표기 차이로 좁혀진다.

**파생 값의 종류는 작성자가 고르지 않는다** `[추천]`. 서버 정의의 파생 식이 행위자를 참조하면 viewer 값(VV 조건 적용), 참조하지 않으면 일반 판정식(DD-01 predicate)이나 공개 집계(DD-01 I7)로 서버가 추론한다. 다른 파생 값이나 관계를 거쳐 행위자를 간접 참조해도 viewer 값으로 본다(참조를 끝까지 따라가 판정). 작성자가 "viewer냐 predicate냐 publicAggregate냐"를 선택하는 일을 없앤다(DD-04와 함께 표기 확정).

### C.3 안전 조건 (층 1, 관찰 가능한 성질) `[추천]` (창시자 질문 아님)

| 조건 | 내용 |
|---|---|
| VV-1 소유 관계만 근거 | viewer 값의 근거는 **소유 관계**뿐이다. 소유 관계 = 리소스(간선 리소스 또는 그 행 자체)에 선언된 소유 컬럼이 행위자인 것. 예: 내 북마크·내 지원·내 회원 자격(간선의 소유 컬럼), 내가 쓴 댓글(행의 작성자 컬럼, K5). 행위자가 대상인 간선(나를 차단한 사람, K6)이나 운영진이 볼 수 있는 남의 간선은 viewer 값이 아니라 행 정책 안에서만 쓴다 |
| VV-1-0 선언 중복 방지 | 간선 리소스에 소유 컬럼을 선언하면 그 간선의 행 정책 기본값은 "소유 컬럼 = 행위자"가 된다. 같은 사실을 행 정책과 소유 선언에 두 번 쓰지 않는다. 행 정책을 따로 쓰면(예: 운영진도 보게) 소유 선언과 별개로 동작한다 |
| VV-1a 소유 선언과 정적 검사 | V1이든 V5든 **소유 컬럼 선언(`owner`)이 전제**다. V1의 viewer 식은 소유 컬럼이 선언된 리소스만 참조할 수 있고, 식 안에 "그 소유 컬럼 = 행위자" 조건이 **최상위 AND 항으로** 반드시 있어야 한다(OR·NOT 안에 들어가면 거부). 이 조건이면 식의 구문으로 검사할 수 있다(의미 검사가 아님). 따라서 V1과 V5는 같은 소유 선언 위에서 표기만 다르다 |
| VV-2 범위 | viewer 값은 행위자와 리소스 사이의 도메인 관계(간선 한 단계까지)에서만 나온다. 화면 이름 같은 값(`canApplyNow` 등 화면 판단)은 viewer 값이 아니다 |
| VV-3 행 정책 먼저 | 행 정책을 통과한 행에만 viewer 값을 계산한다 |
| VV-4 행위자는 서버가 | 행위자는 항상 서버가 인증 정보에서 해석한다. 요청에 행위자를 적을 수 없다 |
| VV-5 캐시 | 행위자는 plan의 매개변수다(DD-03 T-I2). viewer 값이 든 응답은 HTTP·CDN 공유 캐시에 넣지 않는다(`private`). viewer 값 결과 캐시는 T13 설계 전에는 쓰지 않는다(DD-11이 결정되면 DD-11 CI-2가 이 조건을 대체) |
| VV-6 비로그인 | 인증 정보가 **없을 때만** 기본값(false/null)을 준다. 무효·만료된 인증 정보는 인증 오류다(조용히 비로그인으로 바꾸지 않는다). 비로그인에게 값을 생략할지 false로 줄지는 앱 개발자 선언 |
| VV-7 select만 | viewer 값은 기본적으로 select에만 쓴다. "내가 북마크한 것만"을 거르려면 간선 traverse(DD-01)로 표현한다(비용 상한 I4) |

## F. 확인된 답과 남은 일

- 이 항목은 창시자에게 새 질문을 묻지 않는다. 행위자 기준 파생값과 소유 관계 표현은 읽기 요구에 대한 기술 설계 후보이며, DD-01·DD-04 답 대기를 선행조건으로 두지 않는다.
- 기술 검증: 후보 표면의 권한 적용, 테넌트 경계, 결과 캐시, 비로그인 출력 처리를 비교한다.
- "내 동아리" 같은 업무 의미와 비로그인 값의 표현은 각 앱의 계약 사례를 모은 뒤 정한다.
