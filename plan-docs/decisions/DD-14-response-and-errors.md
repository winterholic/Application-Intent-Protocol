## A. 지금 결정할 문제

호출자가 받는 응답 모양을 하나로 정한다. 오류는 AI와 사람이 **추측 없이** 처리할 수 있어야 하고(AI First), 동시에 **볼 수 없는 데이터의 존재와 서버 내부 구현을 드러내지 않아야** 한다(DD-01 I5, 원문 PART I §2). 이 둘이 부딪치는 지점(사유를 얼마나 자세히 알려 줄까)이 핵심이다.

## B. 실제 개발 시나리오

### B.1 아리아리 (`기존 코드`)

`commons/exception/ExceptionControllerAdvice.java`, `dto/ExceptionRes.java`(`{code, message, occurredDateTime}`), 커스텀 예외 62개:
- **안정된 오류 식별자가 없다.** 사람 문장과 숫자뿐이다.
- 커스텀 예외 핸들러는 HTTP 상태를 **400으로 고정**하고 본문 `code`에 예외의 상태를 담는다. 62개 중 17개는 둘이 어긋난다(Sonnet 확인).
- 500·NPE·IllegalState 처리는 `e.getMessage()`를 그대로 돌려준다. DB 오류는 400으로 분류하고 `"DB 접근 중 에러가 발생했습니다." + e.getMessage()`로 **SQL 오류 내용이 클라이언트에 나갈 수 있다**(77~86행).
- 입력 검증 오류는 `Map<String,String>`, 인증 필터 오류는 어드바이스 밖에서 따로 쓴다(`JwtAuthenticationFilter.java` 67~85행). 오류 응답 모양이 여럿이다.

### B.2 지난 AIP PoC (`기존 코드`)

- 오류 코드 레지스트리(`crates/aip-ir/src/codes.rs`, 코드 하나에 의미 하나, D-P17), HTTP 상태와 재시도 가능 여부를 코드마다 정의(53~58행: "같은 멱등 키로 다시 보내도 되나"). `aip explain-code`.
- **PoC도 같은 원칙을 일부 어긴다**(`[PoC 부채]`):
  - DB 제약 오류의 원문 메시지를 응답 `message`에 넣는다(`crates/aip-runtime/src/exec.rs` 92~94·112행 근처 `db.message()`).
  - `TENANT_MISMATCH`는 HTTP 404로 맞췄지만 **본문 코드가 `NOT_FOUND`와 다르다**(`codes.rs` 1039~1046행). 본문 코드로 다른 테넌트 행의 존재를 구분할 수 있다.

### B.3 AIP라면 (`개념 예시`)

```json
// 성공(읽기): 부분 성공 없음
{ "data": [ ... ], "page": { "next": "c_9f" }, "depends": ["Recruitment:*"], "validUntil": "2026-10-03T12:00:00Z" }

// 성공(쓰기)
{ "data": { ... }, "changed": ["ClubNotice:club_1"] }

// 실패: 일괄 위반(DD-07 U4)
{ "error": { "code": "BULK.REJECTED", "category": "violation", "retryable": false,
             "violations": [ { "index": 17, "code": "APPLY.ALREADY_MEMBER", "params": { "member": "m_3" } } ] } }

// 성공: 항목별 처리로 선언된 bulk(DD-07 U7). HTTP 200, 항목마다 결과
{ "data": { "results": [ { "index": 0, "ok": true }, { "index": 17, "ok": false, "code": "APPLY.ALREADY_MEMBER" } ] }, "changed": ["Apply:club_1"] }

// 실패: 필터 bulk 위반(DD-07 C.3-6, 볼 수 있는 대상의 식별자로 지시)
{ "error": { "code": "BULK.REJECTED", "category": "violation", "retryable": false, "violations": [ { "target": "ap_9", "code": "APPLY.ALREADY_REFUSED" } ] } }

// 실패: 볼 수 없거나 없는 대상(구분하지 않음)
{ "error": { "code": "NOT_FOUND", "category": "not_found", "retryable": false } }

// 실패: 서버 오류(내부 내용 없음)
{ "error": { "code": "INTERNAL", "category": "server", "retryable": true, "trace": "t_8c1…" } }
```

사람이 읽는 문장은 서버가 만들지 않는다. 코드와 `params`로 SDK나 앱의 문구 목록이 만든다(C.3 RE-8).

## C. 대안과 트레이드오프

### C.1 형식

| | R1 안정 코드 + 구조화 세부(위 B.3) | R2 HTTP 상태 + 사람 문장(지금 아리아리) | R3 표준 문제 형식(RFC 9457 problem+json) |
|---|---|---|---|
| AI 처리 | 코드로 분기 | 문장 해석 필요 | 코드로 분기(확장 필드) |
| 보안 | C.3 규칙이 서면 안전 | 내부 메시지 노출(B.1) | R1과 같음 |
| 생태계 | AIP 전용 | 흔함 | 표준 도구 호환(범위 확인 필요) |

B.3 모양과 R3는 최상위 구조가 달라 함께 고를 수 없다. **R1을 택하고, R3는 필요해질 때 어댑터로** 제공한다 `[추천]`.

### C.2 개발 진단을 얻는 방법 `[추천]`

운영 서버에 "개발 모드 응답"을 두지 않는다. 정확한 사유("이 필드는 열려 있지 않다", "이 행은 정책 X 때문에 안 보인다")는 다음 중 하나로만 계산한다.
- 개발 환경에서, 진단용 계약(DD-13)을 가진 개발자 인증 맥락의 별도 진단 경로
- 운영 요청의 추적 번호로 서버 로그를 오프라인에서 재현(운영자 권한)

### C.3 지킬 성질 (층 1) `[추천]`

| 성질 | 내용 |
|---|---|
| RE-1 안정 코드 | 코드 하나에 의미 하나, 공개된 코드는 의미를 바꾸지 않는다(D-P17). 레지스트리에 없는 코드를 내는 정의는 빌드 실패 |
| RE-2 존재를 드러내지 않음(세 층) | (a) **볼 수 없는 대상**은 `NOT_FOUND`와 코드·상태·모양이 완전히 같다(다른 테넌트 행 포함, B.2의 `TENANT_MISMATCH`처럼 본문 코드가 달라지면 안 된다). (b) **보이는 대상에 대한 동작 거부**는 사유 코드를 줄 수 있다(예: 전이 불가). 역할 부족을 얼마나 자세히 알릴지는 F1. (c) **DB 제약·참조·유일 위반에서 나오는 코드**는 호출자가 그 충돌 대상 행을 볼 수 있을 때만 구체 코드로 내고, 아니면 일반 코드로 접는다. 한 줄로: 코드는 호출자가 볼 수 있는 행에 대해서만 달라진다. **한계**: 유일 위반을 일반 코드로 접어도 "실패했다"는 사실 자체가 숨은 행의 존재를 알린다(예: 닉네임 중복). 이것은 유일성 제약의 본질이라 오류 모양으로는 막을 수 없고, 민감한 유일 값은 요청 속도 제한(DD-01 I4)으로 추측 비용을 높인다 |
| RE-3 내부 내용은 나가지 않음 | 어떤 경로에서도 외부 오류 메시지(DB, 런타임 예외, 확장 코드 예외)가 응답에 합성되지 않는다. 서버 오류는 추적 번호만. 원문은 서버 로그로 |
| RE-4 HTTP 상태는 코드에서 | 레지스트리가 코드와 상태를 함께 정한다. 4xx는 호출자가 요청을 바꿔 해결할 수 있는 것, 5xx는 서버 책임 |
| RE-5 모양은 하나 | 인증·파싱·크기·속도 제한 같은 처리 이전 단계 오류까지 같은 봉투 |
| RE-6 성공 봉투 | 페이지(`page`), 의존·변경 태그(`depends`·`changed`, DD-11), 유효 기한(`validUntil`)은 정해진 자리에, 없으면 생략. 읽기는 `data`와 `error`를 함께 주지 않는다(부분 성공 없음). DD-13의 "응답 봉투 소멸"은 앱이 봉투 타입을 손으로 쓰지 않는다는 뜻이고, 봉투 자체는 SDK가 다룬다 |
| RE-7 재시도 가능 여부 | 코드마다 "**같은 멱등 키로** 다시 보내도 되나"(PoC 정의 그대로). 멱등 키 전달 방식은 DD-08 후속에 의존 |
| RE-9 분류 값 | `category`는 정해진 집합(`auth`, `forbidden`, `not_found`, `violation`, `input`, `limit`, `conflict`, `server`)이고 DD-13 S12의 오류 분류와 같은 집합이다 |
| RE-8 문구는 코드 + 매개변수로 | 서버는 사람 문장을 만들지 않고 코드·분류(`category`)·매개변수(`params`)만 보낸다. 문장은 SDK·앱의 문구 목록이 만들고, 모르는 코드는 분류별 기본 문구로. 개발 환경에는 `explain-code` 같은 설명 도구 |

## F. 확인된 답과 남은 일

- 확인된 방향: 서버 공개 정책에 맞춰 오류 진단을 제공하고, 볼 수 없는 대상이나 내부 구현 정보는 노출하지 않는다.
- 기술 검증: 오류 코드·카테고리·필요 역할 안내의 공개 경계, 테넌트 간 존재 비노출, HTTP 응답 및 진단 계약을 위협 모델로 검토한다.
- 역할명을 어디까지 알릴지는 기술 결과와 서비스 공개 정책 사례를 바탕으로 제안한다. 기존 (나) 추천은 승인된 오류 정책이 아니다.

## 이탈 방지 점검

| 질문 | 답 |
|---|---|
| 백엔드 개발이나 이중 유지보수를 줄이는가 | 예. 예외 처리기·응답 DTO·프론트 오류 분기가 표준으로 |
| 호출자 표현에 도움이 되는가 | 간접. 실패 이유를 기계적으로 안다 |
| 서버가 최종 권한을 통제하는가 | RE-2·RE-3·C.2로 노출 통제 |
| AI의 불필요한 선택을 줄이는가 | 예. 코드로 분기, 문구는 목록에서 |
| JS/Python 생태계와 사람의 사용성 | R3 어댑터로 표준 도구와 맞출 수 있음(확인 필요) |
| 복잡성을 옮기기만 했나 | 코드 레지스트리와 문구 목록 관리가 생기지만 앱마다 반복되던 예외 처리기가 사라진다 |
