# DD-12. 서버 정의가 바뀔 때, 무엇을 사람이 확인한 뒤에만 반영하는가

> 결정 상태: **검증 필요** (새 기준: [B §5](../alignment/B-decision-reclassification.md#5-dd-문서의-현재-처리-상태))

## A. 지금 결정할 문제

서버 정의가 바뀌어 배포할 때,

1. 어떤 변경은 자동으로 반영하고, 어떤 변경은 **사람이 확인한 뒤에만** 반영할까.
2. 배포 뒤 문제가 생기면 **이전 버전으로 되돌릴 수** 있어야 할까.
3. 이미 배포된 화면(구버전 호출자)을 얼마나 오래 받아 줄까.

AI가 정의를 쓰는 시대에는 "정의에 의도를 적었다"가 곧 "사람이 승인했다"가 아니다. 이 점이 이 문서의 출발점이다.

## B. 실제 개발 시나리오

### B.1 아리아리 (`기존 코드`)

`application.yml` 16행 `ddl-auto: none`, `build.gradle`에 Flyway·Liquibase 없음. 엔티티를 바꾸면 운영 DB는 사람이 따로 손으로 바꾼다(방법은 저장소로 알 수 없음, 확인 필요). DB는 MariaDB(`application.yml` 12~13행)이고, PoC의 스키마 진화는 PostgreSQL 전용이다.

### B.2 지난 AIP PoC (`기존 코드`)

- `crates/aip-pg/src/evolve.rs`(883줄): 배포된 정의와 새 정의를 의미 수준에서 비교해 변경 단계를 만든다. "저장된 데이터를 프로그램이 말하지 않은 채 없애거나 다르게 해석할 수 있는 변경은 거부"(파일 머리 주석). 이름 변경 `was`(`spec/grammar.md` 88·95행 근처), 삭제 `removed field`·`removed entity`(204~205행).
- 단계의 분류는 **데이터 안전 기준**뿐이다. 테이블 크기, 잠금 시간(`lock_timeout`) 같은 운영 기준은 없고 모든 단계가 한 트랜잭션이다(Sonnet 확인).
- expand/contract(확장 → 전환 → 축소 배포)는 자동 구현이 없고 규약과 거부 메시지 안내뿐이다.
- 계약 호환 판정(`crates/aip-contract/src/compat.rs`)은 형태를 깨는 변경을 오류로, `allow`·`requires` 같은 **동작 변경(권한 확대 포함)은 경고로만** 처리한다(8·386~410행 근처). 경고는 배포를 막지 않는다.
- 롤백: 추가만 한 배포 뒤 옛 서버 코드로 되돌리면 기록된 정의와 맞지 않아 기동이 막힐 가능성이 있다(코드 읽기 추정, 실행 확인 안 함).

### B.3 세 가지 변경 (`개념 예시`)

```text
resource Recruitment {
  applyUrl: Url?  was externalUrl                 // ① 이름 변경(데이터 보존)
  removed field earlyClosed                       // ② 데이터 삭제
  preset publicList { select title, period, views, internalNote }   // ③ 노출 확대: 운영진 메모가 공개 목록에 들어감
}
```

AI가 이 세 줄을 썼다면, ②의 `removed`는 PoC에서 "의도 선언"으로 통과하고 ③은 경고만 남긴다. 사람이 보지 않아도 운영에 반영될 수 있다.

## C. 대안과 트레이드오프

### C.1 반영 관문

| | G1 전부 자동 | G2 위험 등급이 높은 변경만 사람 확인 | G3 전부 사람 확인 |
|---|---|---|---|
| 유지보수 | 가장 적다 | 중간 | 많다 |
| 안전 | 거부 규칙과 의도 선언에만 의존. AI가 쓴 의도 선언이 그대로 통과 | 등급 정의가 맞으면 안전과 유지보수를 함께 | 가장 안전, 확인 피로 |
| 필요한 것 | 거부 규칙 | **위험 등급 정의(C.2)** + 확인 절차 | 확인 절차 |

### C.2 위험 등급 (세 축) `[추천]`

| 축 | 낮음 | 높음 |
|---|---|---|
| 데이터 | 추가, 이름 변경(보존), 기본값 있는 새 필드 | 삭제, 의미가 바뀌는 타입 변경, 기존 데이터가 위반할 수 있는 새 제약·불변식 |
| 운영 | 작은 테이블, 짧은 잠금 | 큰 테이블의 잠금(NOT NULL 추가, 인덱스 생성 등). 추정 행 수와 잠금 수준으로 판정 |
| 권한 | 노출·허용 범위 축소 또는 변화 없음 | **노출·허용 범위 확대**(preset·capability·정책·필드 공개 범위가 넓어짐). DD-01 preset 규칙 3·4(펼친 노출 diff 검토)와 연결 |

G2라면 세 축이 **모두 낮을 때만** 자동 반영한다.

### C.3 지킬 성질 `[추천]`

2·3·4·5·6은 어느 안이든 지킨다(층 1). **1은 F1 답에 따른다**: F1이 (가)면 데이터·권한 축 모두, (나)면 데이터 축만, (다)면 적용하지 않는다(대신 거부 규칙과 알림만).

1. **(F1에 따름) 의도 선언은 승인이 아니다.** 정의 소스에 쓴 `removed`·`was`는 "이렇게 하겠다"는 의도이고, 운영에서 위험 등급 높음 변경은 **소스와 별개의 사람 확인**(변경 계획의 요약과 영향 행 수를 보고 승인)을 거친다. AI가 거부 메시지를 보고 의도 선언을 써 넣는 것으로 관문이 풀리지 않게 한다.
2. **같은 정의는 같은 DB**(PoC 불변식): 기존 DB + 변경 단계 = 새로 만든 DB.
3. **새 제약·불변식은 기존 데이터를 먼저 검사**한다. 기존 행이 위반하면 반영하지 않고 위반 목록을 보인다. 검사할 수 없는 종류의 불변식은 반영을 거부하거나 검사 쿼리를 함께 만든다(종류별 표는 E3).
4. **권한 확대도 축소와 똑같이 보인다.** 계약 diff는 축소(호출자를 깨는 변경)와 확대(노출이 늘어나는 변경)를 모두 표시하고, 확대는 권한 축 높음으로 분류한다.
5. **호출자를 깨는 변경은 배포 전에 보인다.** 계약 diff로 깨지는 필드·capability를 보인다. 등록 기능(DD-03 S의 등록·`registered-only`)을 쓰는 경우에만 등록된 요청 중 깨지는 것의 목록을 함께 낸다(`runtime` 입장만 쓰면 낯선 요청은 목록에 없다).
6. **개발 환경은 자동**: 개발 DB에는 관문 없이 반영한다(의도 선언 거부 규칙은 유지).

## D. 최초 철학과의 관계

| 원칙 | 관계 |
|---|---|
| 유지보수 최소화 | 낮은 위험 변경은 자동. 손 DDL이 사라진다 |
| 운영 규칙 6(안전 희생 금지) | 높은 위험 변경은 사람 확인, 새 불변식은 기존 데이터 검사 |
| 서버 최종 통제 | 권한 확대가 조용히 통과하지 않게(C.3-4) |
| AI First | AI가 정의를 쓰는 시대라 "소스의 선언 ≠ 사람의 승인"(C.3-1) |

## F. 확인된 답과 남은 일

- 확인된 방향: 데이터 손실과 권한 확대는 배포 승인·검토 설계에서 다루며, 안전한 롤백 경로를 목표로 한다.
- 기술 검증: 위험 분류, 변경 계획과 사람 확인 경계, 복원 가능성, 호환 정책을 기존 DB·배포 흐름에 대조한다. 새 확장 동작의 추가만으로 별도 승인을 강제하지 않는다.
- 남은 가치 판단: 구버전 호출자 호환 기간(OI-P2/Q21)은 운영 비용과 배포 자료를 준비한 뒤 질문한다. 이를 현재 착수의 선행조건으로 삼지 않는다.
- 기존 G2 권고 및 F1~F3 선택지는 확정 정책이 아니다.

## 이탈 방지 점검 (G2 기준)

| 질문 | 답 |
|---|---|
| 백엔드 개발이나 이중 유지보수를 줄이는가 | 예. 손 DDL이 사라지고 낮은 위험 변경은 자동 |
| 호출자 표현에 도움이 되는가 | 호출자를 깨는 변경을 미리 보여 준다 |
| 서버가 최종 권한을 통제하는가 | **예, C.3-4가 있을 때.** 지금 PoC는 권한 확대를 경고로만 처리해 이 관문이 비어 있다 |
| AI의 불필요한 선택을 줄이는가 | 의도 선언 형식이 하나. 단 AI가 쓴 선언이 관문을 대신하지 못하게 한다 |
| JS/Python 생태계와 사람의 사용성 | 변경 계획 승인 흐름은 기존 도구와 비슷한 경험이 될 수 있다(확인 필요) |
| 복잡성을 옮기기만 했나 | 엔진에 위험 등급 판정과 승인 절차가 생긴다. 운영 축(테이블 크기, 잠금)은 PoC에 없어 새로 만들어야 한다 |
