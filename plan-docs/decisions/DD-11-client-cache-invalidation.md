## A. 지금 결정할 문제

화면에서 공지를 삭제하면, 이미 화면에 떠 있는 "공지 목록"뿐 아니라 "내 동아리 목록의 최근 공지 시각"도 낡는다. 지금은 프론트 개발자가 **어떤 조회가 낡는지 기억해서** 손으로 다시 불러오게 적는다. 서버와 프론트가 같은 지식(이 쓰기가 무엇을 바꾸고, 이 읽기가 무엇에 의존하나)을 따로 유지하는 이중 유지보수다. 엔진은 두 가지를 다 알 수 있다. 이 정보를 화면에 어떻게 전할지 정한다.

## B. 실제 개발 시나리오

### B.1 아리아리 프론트 (`기존 코드`, Sonnet E1)

React Query(`@tanstack/react-query` 5.x)를 쓴다. `invalidateQueries`는 **34곳**(재확인). `useMutation` 31곳 중 26곳이 무효화하고, 나머지 읽기·쓰기 일부는 React Query 밖에서 직접 호출한다. 전역 `staleTime` 60초.

확인한 쓰기 경로 26개 중 **7곳에서 무효화가 빠졌고 1곳은 과잉**이었다. 예:
- 공지 삭제: 공지 목록은 갱신하지만 "내 동아리 목록"의 최근 공지 시각은 갱신하지 않는다(추가에서는 갱신하면서 삭제에서는 안 함). 서버는 그 값을 공지에서 읽는다(`ClubListService.java` 86행).
- 활동 삭제: 컴포넌트에서 직접 호출해 무효화 코드가 아예 없다.
- 모집 마감: 목록에 `"CLOSED"`를 **프론트가 직접 써 넣는다.** 서버의 파생 상태를 클라이언트가 다시 구현한 것이다. 진행 중 모집·상세는 갱신하지 않는다.
- 지원 승인: 동아리 회원이 생기는데 회원 목록은 갱신하지 않는다.
- 초대로 가입: 서버가 내 알림을 지우는데 알림 캐시는 그대로다.

`app/hooks/club/useClubFinanceMutation.tsx`의 "기록 + 잔액" 무효화도 같은 유형이다. 잔액은 컬럼이 아니라 합계 질의다(`FinancialRecordService.java` 42행 `findTotalByClub`).

### B.2 지난 AIP PoC (`기존 코드`)

- 구독(`crates/aip-runtime/src/subscribe.rs`): 테이블 단위 변경 알림 트리거 → 그 테이블을 읽는 구독을 구독자 권한으로 다시 실행해 결과가 바뀌었으면 보낸다. **무효화의 실제 선례는 이것**이다.
- `crates/aip-pg/src/writes.rs`는 변경 집합 수집기가 아니라 "절대값으로 쓰이는 필드 / 증분으로만 바뀌는 필드" 정적 분석이다(1~5행).

### B.3 AIP라면 (`개념 예시`)

```ts
// 읽기 응답: 이 결과가 의존하는 태그를 서버가 계산해 싣는다
const clubs = await aip.read("Club", { select: { name: true, latestNoticeAt: true } })
// clubs.depends = ["Club:mine", "ClubNotice:club_1", "ClubNotice:club_2"]

// 쓰기 응답: 이 쓰기가 바꾼 태그
const r = await aip.apply("ClubNotice", "delete", { target: "n_9" })
// r.changed = ["ClubNotice:club_1"]

// SDK: 캐시된 읽기 중 depends ∩ changed 가 있는 것만 낡음 처리
```

태그는 "리소스 + 파티션"이다(예: 어느 동아리의 공지). 행 id만으로는 **새로 생긴 행**이 어느 캐시에도 없어서 닿지 못하므로, 파티션 단위가 기본이다.

### C.3 지킬 성질 `[추천]` (창시자 질문 아님)

| 성질 | 내용 |
|---|---|
| CI-1 태그는 볼 수 있는 것만 | 읽기 태그는 결과에 나타난 파티션만 드러낸다. 결과가 볼 수 없는 리소스·파티션에 의존하면 그 의존은 **리소스 전체 태그로 접는다**(예: "ClubNotice:*"). 이 때문에 과잉 무효화가 생길 수 있고, 그만큼 "정확"은 "놓치지 않음"의 뜻이다(덜 무효화하지는 않는다). 필드명·개수 노출, 쓰기 뒤 정책으로 못 보게 된 행의 처리는 후속 |
| CI-2 viewer 값은 행위자 파티션 | DD-10의 viewer 값이 든 읽기는 의존 태그에 행위자 파티션을 포함하고 결과 캐시는 그 행위자만. DD-11이 결정되면 이 조건이 DD-10 VV-5를 대체한다 |
| CI-3 캐시 키는 SDK가 | SDK는 호출자 요청의 결정적 직렬화를 캐시 키로 쓴다. 서버의 canonical 정리를 클라이언트가 복제하지 않는다. 의미가 같은 요청이 다른 키로 중복 캐시되는 것은 허용(정확성 문제 아님). 화면 개발자가 문자열 키를 정하지 않는다 |
| CI-4 실패한 쓰기는 변경 없음 | DD-07 U4 위반 응답은 변경 태그가 비어 있다 |
| CI-5 정확도의 한계를 명시 | B가 정확한 것은 **동기 경로**뿐이다. 커밋 뒤 비동기 효과(알림 생성 등, DD-02 W-I7 outbox), 시간이 지나 바뀌는 판정(모집 `open`처럼 `now`가 들어간 값), 응답을 받지 못한 쓰기, 확장 동작이 엔진을 거치지 않고 바꾼 것은 쓰기 응답에 없다. 시간 의존 값은 읽기 응답에 `유효 기한`(응답 필드 `validUntil`, DD-14 RE-6)을 싣고, 나머지는 C(전체 재조회)나 M3로 보완한다 |
| CI-6 서버 파생 상태를 프론트가 다시 만들지 않는다 | 모집 마감처럼 서버가 판정하는 값은 쓰기 응답의 변경 태그로 다시 읽게 하고, 프론트가 직접 값을 써 넣지 않게 SDK가 유도한다 |
| CI-7 재생 응답 | 재시도로 같은 결과를 돌려주는 응답(DD-02 W-I8)에 변경 태그를 담을지는 `[미정]` |

| 원칙 | 관계 |

## F. 확인된 답과 남은 일

- 확인된 방향: 재조회가 기본이며 실시간 동기화는 선택 확장으로 검토한다.
- 기술 검증: 의존 태그·쓰기 변경 집합의 정확도, 폴백 재조회, 시간 의존 값, actor별 캐시 경계를 비교한다.
- 즉시 반영이 필요한 구체 화면이 확인되면 해당 요구의 가치와 운영 비용을 따로 판단한다. 기존 F1의 포괄적 freshness 선택은 선행 질문으로 남기지 않는다.
