# DD-08. 호출자의 요청을 서버에 어떤 형태로 보내는가

> 결정 상태: **검증 필요** (새 기준: [B §5](../alignment/B-decision-reclassification.md#5-dd-문서의-현재-처리-상태))
> 기존 에이전트 리뷰·추천은 이전 지침 아래 작성된 검토 이력이다. 제안 본문은 보존하되 새 원문과 B의 확정 기준에 충돌하면 그 기준을 우선한다.
> 분석 전제: 조합 읽기·표준 쓰기 목적은 창시자 기준이다. DD-01·02의 capability 상세, DD-03의 파이프라인/등록, DD-07의 오류 수집은 검증 중인 기술 후보이며 전체 승인 전제가 아니다.
> 범위: **요청의 전송 형식**(wire format)과 그 층의 안전 규칙. 응답 형식(DD-14), 인증 전달·CSRF, 구독(T13), 요청 취소·멱등 키 전달, 오류 코드 체계는 후속 문서. 프로토콜 의미와 전송을 분리한다는 OI-P1(`docs/DECISIONS.md`)의 한쪽(전송)을 다룬다.
> 기준 원문: 창시자 인계 PART I §2("HTTP를 반드시 버리는 것이 아니다", "Intent는 명확한 문법·계약·타입·정책을 갖춘 구조화된 요청"), 의제 10
> 이전 지침 토론 기록: `../reviews/DD-08-sonnet-r1.md`, `../reviews/DD-08-sonnet-r2.md` (이전 지침 아래 에이전트 검토 이력; 새 기준은 B)

## A. 지금 결정할 문제

호출자가 표현한 요청(읽기 조합, 쓰기, 전이, bulk, 저장된 조회, 확장 호출)이 **네트워크를 타고 서버에 도착하는 모양**을 정한다. 이것은 서버의 정규화, 보안 검사, 등록(DD-03 S), 로그·디버깅, SDK가 요청을 만드는 방식에 영향을 준다.

이 결정은 대부분 기술 판단이다. "REST를 다른 이름으로 바꾸지 않는다"는 원문 요구의 실질은 이 형식이 아니라 DD-01·DD-02(호출자가 조합하고 서버가 판단)에서 충족된다.

## B. 실제 개발 시나리오

### B.1 지금 아리아리 (`기존 코드`)

REST 경로 + 쿼리 파라미터. 정렬은 `sort=createdAt,desc` 같은 문자열이고 서버가 그 필드 이름을 그대로 정렬 경로로 쓴다(`RecruitmentRepositoryImpl.java` 50~53행). 값이 아니라 **필드 이름(식별자)이 주입되는** 경로다.

### B.2 지난 AIP PoC (`기존 코드`)

`POST /aip/{intent}`와 별칭 `/aip/query/{intent}`, `/aip/command/{intent}`(`crates/aip-runtime/src/http.rs` 50~52행)에 JSON 입력. 계약은 `/aip/describe`(45행)와 생성된 TS 타입(`examples/ariari/client/aip.ts`, `aip-protocol/0.1`).

### B.3 같은 요청들을 여러 형식으로 (`개념 예시`)

**읽기**(DD-01 B.3)와 **전이**(DD-02 W3 권한 변경), **bulk**(DD-07 지원자 일괄 승인)를 함께 보인다.

**W1. JSON 트리, 값 섞임**

```json
{ "read": "Recruitment",
  "where": { "periodEnd": { "gte": "2026-10-03" } },
  "orderBy": [{ "periodEnd": "asc" }], "take": 5,
  "select": { "title": true, "club": { "select": { "name": true, "logo": true } }, "bookmarkCount": true } }

{ "apply": "ClubMember.changeRole", "target": "cm_123", "input": { "role": "MANAGER" } }

{ "apply": "Apply.approve", "targets": ["ap_1", "ap_2", "ap_3"] }   // W5에서는 targets도 vars로 분리 가능
```

**W5. JSON 트리 + 값 분리(`vars`)**

```json
{ "read": "Recruitment",
  "where": { "periodEnd": { "gte": { "$var": "from" } } },
  "orderBy": [{ "periodEnd": "asc" }], "take": 5,
  "select": { "title": true },
  "vars": { "from": "2026-10-03" } }
```

구조(무엇을 원하는가)와 값(어떤 값으로)이 갈라진다. 구조만 해시하면 등록·plan cache·로그 마스킹이 쉽다.

**W2. 질의 문자열 + 값 분리**

```text
read Recruitment where periodEnd >= $from order by periodEnd asc take 5
select { title club { name logo } bookmarkCount }
-- vars: { "from": "2026-10-03" }
```

**W4. 등록 식별자만 전송**(DD-03 S의 `registered-only` 경로)

```json
{ "registered": "q_7f3a…", "vars": { "from": "2026-10-03" } }
```

**W7. 읽기를 GET으로**: `GET /aip?q=<인코딩된 트리>` 또는 `GET /aip/r/q_7f3a…?from=…`(등록분)

## C. 대안과 트레이드오프

### C.1 비교 (이 문제에 맞춘 축)

| 축 | W1 JSON(값 섞임) | W5 JSON + vars | W2 문자열 + vars | W4 등록 ID | W7 읽기 GET |
|---|---|---|---|---|---|
| 철학("구조화된 요청") | 충족 | 충족 | 파싱 뒤 충족 | 등록된 구조의 참조 | 형식 아닌 메서드 문제 |
| 보안 | 값 주입은 없음. 필드명은 허용 목록 대조 필요 | W1 + 구조·값 분리로 로그 마스킹 쉬움 | **값을 `vars`로 분리하면 값 주입은 W5와 같다.** 파서가 추가 공격 표면 | 가장 좁다(등록분만). 단 등록은 권한이 아니다(DD-03 T-I2) | URL 길이·로그·캐시에 요청 노출, 민감 값이 URL에 남을 위험 |
| 정규화·등록 | 구문 정규화 쉬움(키 순서·숫자 표기). **의미 정규화는 어느 형식이든 서버가 따로 해야 함**(DD-01 C.3) | 구조 해시가 값과 무관 | 파싱 후 트리 | 이미 등록됨 | W5·W4 위에 얹음 |
| 구현 | 스키마 검증 | 같음 | 문법·파서·위치 보고 | 등록 저장소(DD-03) | HTTP 캐시 정책 |
| 디버깅 | 길고 중첩 | 같음 | 짧고 읽기 쉬움 | ID만 보여 추적 도구 필요 | |
| AI 개발 경험 | 생성·검증 쉬움(확인 필요, E3) | 같음 | 짧지만 문법 오류 가능(확인 필요) | SDK가 처리 | |
| 사람용 표기 | 별도 출력기 필요(W2 모양으로 출력) | 같음 | 그 자체 | | |

"결과 타입을 select에서 추론"은 SDK의 일이고 전송 형식과 무관하다(TS 타입 추론의 깊이 한계와 Python 경로는 확인 필요). 필드 정책(DD-01 I5)으로 일부 필드가 거부될 수 있으므로 추론 타입은 "요청이 통과했을 때"의 모양이다.

바이너리 직렬화(MessagePack 등)는 원문 "HTTP를 버리는 것이 아님"과 PoC 결정(커스텀 바이너리 프로토콜 없음, D-P13)에 따라 기각한다. GraphQL 문법 호환은 DD-01의 연산별 capability·간선 정책과 의미가 달라 그대로 받기 어렵다(확인 필요).

### C.2 와이어 층의 안전 규칙 (층 1, 관찰 가능한 성질) `[추천]`

DD-01 I1~I7은 요청 **의미**의 안전이다. 그 앞, 요청을 **읽는 단계**에서:

| 규칙 | 내용 |
|---|---|
| WI-1 크기 상한 | 본문 크기, 중첩 깊이, 노드 수, 배열 길이를 **파싱하면서** 제한한다(다 읽은 뒤가 아니라) |
| WI-2 모르는 것 거부 | 스키마에 없는 키, 중복 키, 허용되지 않은 content-type은 거부. 조용히 무시하지 않는다 |
| WI-3 식별자는 목록 대조 | 필드명·관계명·연산자는 계약의 허용 목록과 대조한다. 문자열을 경로로 그대로 쓰지 않는다(B.1의 반례). 허용 목록에 없는 식별자의 오류는 DD-01 I5(존재를 드러내지 않음)를 따른다 |
| WI-4 값은 구조와 분리 | 요청 안에서 값을 구조에 문자열로 이어 붙이지 않는다(W5·W2의 `vars`) |
| WI-5 로그는 구조 해시 + 마스킹 | 운영 로그는 구조 해시와 값 마스킹판이 기본, 원문은 개발 모드에서만 |

### C.3 어느 형식이든 `[추천]`

1. **전송은 HTTP.** 커스텀 바이너리 프로토콜은 만들지 않는다.
2. **의도마다 엔드포인트를 늘리지 않는다.** 진입점을 읽기·쓰기 둘로 나눌지(PoC의 `query`·`command` 별칭처럼) 하나로 둘지는 HTTP 의미(GET 안전성, 캐시, CSRF)와 함께 후속 문서에서 정한다. 어느 쪽이든 화면별 엔드포인트는 없다.
3. **서버 안의 정본 표현은 하나.** 어떤 형식으로 들어와도 하나의 canonical 트리로 정리되고 등록·해시·plan cache는 그 위에서만.
4. **프로토콜 버전과 IR 버전 분리**(PoC `aip-protocol/0.1` 방식 유지 후보).

## D. 최초 철학과의 관계

| 원칙 | 관계 |
|---|---|
| 프로토콜: Application Intent Protocol | 의미 단위가 엔드포인트가 아니라 구조화된 요청 |
| REST 이름 바꾸기 금지 | 실질은 DD-01·DD-02. 이 문서는 C.3-2(화면별 엔드포인트 없음)로 뒷받침 |

| 고유 문법(DD-04) | DD-04가 고유 문법을 작성 형식으로 남기면(F1 "예"), 요청에도 같은 계열 문법(W2)을 줄지 다시 검토한다 |

## F. 확인된 답과 남은 일

- 확인됨: AIP는 정형화된 요청 프로토콜을 지향한다. 요청 형식과 응답 계약의 구체 사양은 창시자 선택 질문이 아니라 기술 설계다.
- 기술 검증: JSON 트리·값 분리, 등록 식별자, 사람이 읽는 표기 간 계약 동일성·버전·오류·캐시 호환을 비교한다. DD-04 작성 형식과 DD-03 입장 정책은 각자 별도 의제다.
- 기존 W5(JSON+vars) 추천은 기술 제안이며 확정된 와이어 형식이 아니다.

---

## G. 결정 상태

**검증 필요.** 정형 프로토콜 목적은 확인됐다. JSON+vars와 등록·사람용 표기, 버전·응답 계약은 기술 비교가 남아 있다. 기존 W5는 제안이다.

## 이탈 방지 점검 (W5 기준)

| 질문 | 답 |
|---|---|
| 백엔드 개발이나 이중 유지보수를 줄이는가 | 요청 스키마 하나. 화면별 엔드포인트·DTO 없음(실질은 DD-01·02) |
| 호출자 표현에 도움이 되는가 | DD-01·02가 허용한 범위를 그대로 담는다 |
| 서버가 최종 권한을 통제하는가 | 요청은 원하는 것만 담고 판단은 서버(DD-01 I3). 와이어 층은 WI-1~WI-5 |
| AI의 불필요한 선택을 줄이는가 | 정본 하나. 다만 W4·W7까지 더하면 경로가 늘어나므로 SDK가 숨겨야 한다 |
| JS/Python 생태계와 사람의 사용성 | JSON은 어디서나. 사람 가독성은 출력 표기로 |
| 복잡성을 옮기기만 했나 | 파서 대신 스키마 검증. 출력 표기기는 별도 비용(DD-04 E4와 공유) |
