# DD-13. 프론트 개발자가 쓰는 AIP 클라이언트 SDK는 무엇을 맡는가

> 결정 상태: **잠정 합의** (새 기준: [B §5](../alignment/B-decision-reclassification.md#5-dd-문서의-현재-처리-상태))
> 기존 에이전트 리뷰·추천은 이전 지침 아래 작성된 검토 이력이다. 제안 본문은 보존하되 새 원문과 B의 확정 기준에 충돌하면 그 기준을 우선한다.
> 출처: 교차 정합성 검토(`../reviews/CROSS-sonnet-r1.md` 3-4). DD-03(등록 산출물), DD-06(코드 생성), DD-08(결과 타입), DD-11(캐시·무효화)이 각각 "SDK가 한다"고 넘겼는데 맡은 문서가 없었다.
> 범위: 호출자 쪽 SDK의 구조·책임, 타입을 얻는 방식, 기존 캐시 도구와의 관계. 서버 쪽 정의 작성(DD-04)과 전송 형식(DD-08)은 다루지 않는다.
> 기준 원문: 의제 14("프론트엔드 라이브러리와 통신 규약까지 포함하는 통합 개발 체계"), PART I §1(프론트 API 호출 코드, DTO·타입 정의, 양쪽 계약 유지보수), PART I §3(JS 생태계 우선, 기존 생태계 자연스럽게 활용)
> 이전 지침 토론 기록: `../reviews/DD-13-sonnet-r1.md`, `../reviews/DD-13-sonnet-r2.md`, `../reviews/DD-13-sonnet-r3.md` (이전 지침 아래 에이전트 검토 이력; 새 기준은 B)
> 관련: `DD-01`, `DD-02`, `DD-03`, `DD-07`, `DD-08`(W5), `DD-10`, `DD-11`, `docs/DECISIONS.md` OI-P3(계약 공개 범위)

## A. 지금 결정할 문제

원문이 없애려는 반복 작업에는 백엔드뿐 아니라 프론트의 "API 호출 코드 작성", "DTO 및 타입 정의", "양쪽 계약 변경 및 유지보수"가 있다(PART I §1). 이것을 맡는 것이 SDK다. 정할 것:

1. SDK의 **구조와 책임**(무엇을 하고 무엇을 하지 않나)
2. **타입을 얻는 방식**
3. **기존 캐시 도구와의 관계**와 그 한계
4. (창시자) AIP 프론트 라이브러리의 **소유 범위**와 **첫 출시 지원 프레임워크**

## B. 실제 개발 시나리오

### B.1 아리아리 프론트 (`기존 코드`, 10-03 재측정, 하위 폴더 포함)

| 층 | 위치 | 규모 | 하는 일 |
|---|---|---|---|
| API 래퍼 | `app/api/**` | 2,963줄 | 엔드포인트마다 axios 호출 함수, 인증 토큰 처리(`axiosInstance.ts` 인터셉터) |
| 응답 타입 | `app/types/**` | 1,132줄 | 백엔드 DTO를 손으로 다시 적은 타입 |
| 쿼리 훅 | `app/hooks/**` | 1,885줄(31개 파일) | React Query 훅, 손 무효화 34곳(DD-11) |

`app/types` 선언 119개를 분류하면(Sonnet E1, 수작업 ±5%p) 약 83%가 서버 응답 모양을 옮긴 타입이고 17%가 화면 전용이다. 서버 모양 타입 중 응답 봉투(페이지 정보 등, 약 19%)는 "생성"이 아니라 select 기반 요청으로 **필요 없어지는** 부분이다. 같은 필드가 파일마다 다른 타입으로 선언된 표류도 있다(예: `ApplyQuestionData.id`가 `number`와 `string`으로 공존).

### B.2 지난 AIP PoC (`기존 코드`)

`aip gen-ts`가 계약에서 TS 클라이언트를 생성한다(`examples/ariari/client/aip.ts`, 선언 query/command마다 함수와 입출력 타입, 멱등 키·업로드 처리 포함). 선언 Intent 모델이라 "이름 + 입력" 함수였다.

### B.3 AIP라면 (`개념 예시`)

```ts
// 프레임워크 중립 코어: 다른 결정 문서들이 쓰는 이름 그대로
import { aip } from "./.aip/client"           // 계약에서 생성: 노출된 리소스·필드 타입 + 요청 빌더
const list = await aip.read("Recruitment", { where: {...}, select: { title: true, club: { name: true } } })
const r = await aip.apply("Apply", "approve", { targets: [...] })

// React Query 어댑터(얇은 층): 코어를 감싼 훅
import { useAipRead, useAipApply } from "@aip/react-query"
const { data } = useAipRead("Recruitment", { select: { title: true } })   // data 타입은 select에서 추론
```

프론트 개발자는 API 래퍼, 응답 타입, 캐시 키, 무효화 코드를 쓰지 않는다.

## C. 대안과 트레이드오프

### C.1 구조

**프레임워크 중립 코어 + 얇은 어댑터** `[추천]`. 코어(`aip.read`/`aip.apply`, 전송, 타입, 위반 응답, 변경 태그)는 어떤 화면 프레임워크에도 붙고, React Query 같은 캐시 도구별 어댑터가 그 위에 얹힌다. 다른 결정 문서가 쓰는 이름(`aip.read`, `aip.apply`)은 코어의 이름이다.

### C.2 타입을 얻는 방식

| | T1 계약에서 요청별 함수 생성 | T2 계약에서 리소스 타입 생성 + select에서 결과 타입 추론(추천, 잠정: E2 확인 전) | T3 런타임 검증만 |
|---|---|---|---|
| 조합 읽기와의 궁합 | 나쁨(저장된 조회에만) | 좋음 | 타입 안전 없음 |
| 서버 변경 반영 | 재생성 | 재생성 후 컴파일 오류로 드러남 | 런타임에서야 |
| 복잡도 | 낮음(PoC 자산) | TS 타입 수준 추론(깊은 중첩의 컴파일 성능 한계, 확인 필요) | 낮음 |
| Python 호출자 | 생성 | 추론은 TS만큼 안 됨, 생성 + 런타임 검증(확인 필요) | 같음 |

**생성 입력은 공개 계약뿐이다** `[추천]`. T2가 만드는 타입에는 그 호출자에게 공개된 리소스·필드·capability만 들어간다(닫힌 필드 이름을 프론트 번들에 싣지 않는다). 공개 계약의 범위는 OI-P3(Open)와 DD-01 F3(호출자 신뢰 등급)에 따른다.

**진단용 계약은 별도 산출물** `[추천]`. 개발 도구가 "이 필드는 열려 있지 않다" 같은 정확한 진단(S6)을 하려면 닫힌 필드까지 아는 계약이 필요하다. 이것은 개발 환경에서 인증된 개발자에게만 주는 별도 진단 계약이며, 프론트 번들(공개 계약에서 생성한 타입)에는 들어가지 않는다.

### C.2-1 의존: 응답 형식과 오류 코드

S3(위반 처리), S4(변경 태그), S8(인증), S9(멱등 키), S12(오류 분류)는 응답 형식과 오류 코드 체계에 기댄다. DD-08이 이를 후속 문서로 미뤘고, 그 문서가 DD-14(응답과 오류)다. 이 책임들의 구체 모양은 DD-14를 따른다(멱등 키 전달 방식만 아직 후속).

### C.3 캐시 도구와의 관계

| | C1 AIP 자체 캐시 | C2 기존 도구 어댑터 | C3 캐시 없음 |
|---|---|---|---|
| JS 생태계 | 새 도구 학습 | 이미 쓰는 도구 | |
| DD-11 태그 무효화 | 직접 구현 | 어댑터가 도구의 무효화로 번역 | 해당 없음 |
| 보장 | DD-11 CI-3(캐시 키)·CI-6(서버 파생 상태 재구현 금지)을 구조로 강제 | **구조로는 못 막는다.** 도구의 `setQueryData`·임의 쿼리 키를 앱이 직접 쓸 수 있어 CI-3·CI-6은 린트·문서로 관리 | |

원문 PART I §3("기존 JS 생태계를 자연스럽게 활용")에 비추어 C2를 기본으로 제안한다 `[추천, 잠정: E3 확인 전]`. 대신 C2에서는 CI-3·CI-6이 "구조"가 아니라 "관리"로 지켜진다는 점을 받아들인다.

### C.4 SDK 책임 `[추천]` (창시자 질문 아님)

| # | 책임 | 연결 / 근거 |
|---|---|---|
| S1 | 요청 작성 API와 W5 전송(값 분리) | DD-08 |
| S2 | 결과 타입(T2) | DD-01, DD-10 |
| S3 | 위반 응답 표준 처리(항목별 사유) | DD-07 |
| S4 | 변경 태그로 무효화(어댑터 경유) | DD-11 |
| S5 | 자사 프론트 등록 산출물 생성(빌드 플러그인). **DD-03 F1이 등록을 쓰는 쪽일 때만** | DD-03 |
| S6 | 개발 도구의 정확한 진단 표시(운영 응답은 존재를 감춤) | DD-01 I5 |
| S7 | 서버 파생 상태를 프론트가 직접 써 넣지 않게 유도(C2에서는 린트) | DD-11 CI-6 |
| S8 | 인증 토큰 전달·갱신 | 아리아리 `axiosInstance.ts` 인터셉터 |
| S9 | 멱등 키 생성·재전송 | DD-02 W-I8, PoC gen-ts |
| S10 | 파일 업로드 | PoC gen-ts(multipart), 아리아리 다수 화면 |
| S11 | 페이지 넘김(커서) | DD-01, DD-09(바뀌는 정렬 키) |
| S12 | 오류 분류: DD-14 RE-9의 `category` 집합(auth, forbidden, not_found, violation, input, limit, conflict, server)을 그대로 쓴다 | DD-14 RE-9 |
| S13 | 프로토콜 버전 확인(서버와 클라이언트 버전 맞추기) | DD-08 C.3-4, DD-12 F3 |

SDK는 권한 판단을 하지 않는다. 클라이언트 쪽 검사는 편의일 뿐이고 서버가 매번 다시 판단한다(DD-01 I3).

## D. 최초 철학과의 관계

| 원칙 | 관계 |
|---|---|
| 이중 유지보수 감소 | 아리아리 프론트의 래퍼·응답 타입·무효화(약 6,000줄 중 상당 부분)가 생성·추론으로. 타입 표류(`number`/`string` 공존)가 구조적으로 사라진다 |
| 통합 개발 체계(의제 14) | 엔진·계약·SDK가 같은 정보(타입, 태그, 위반 사유)를 공유 |
| JS 생태계 우선 | 코어 + C2 어댑터 |
| 서버 최종 통제 | SDK는 판단하지 않고, 생성 타입은 공개 계약만 |

## F. 확인된 답과 남은 일

- 확인됨: 공식 프론트엔드 호출 라이브러리는 필수다. 요청 작성·계약·데이터 접근을 프론트에서 돕는다.
- 기술 검증: 프레임워크 중립 코어·어댑터, 타입 생성·추론, 기존 캐시 도구 연결, 진단·등록 산출물 책임을 비교한다.
- 추가 가치 판단: 데이터 계층과 화면 UI의 경계, 첫 출시 프레임워크 범위는 비교 가능한 비용·사용성 자료 뒤에 제안한다. 기존 F1·F2 및 캐시 추천은 승인된 제품 범위가 아니다.

---

## G. 결정 상태

**잠정 합의.** 공식 SDK 필수 여부는 확인됐다. 요청 API·타입·캐시·진단 책임과 프레임워크 지원 범위는 기술 검증 및 가치 비교가 남았다. 기존 코어/어댑터·타입·캐시 추천은 설계 제안이다.

## 이탈 방지 점검

| 질문 | 답 |
|---|---|
| 백엔드 개발이나 이중 유지보수를 줄이는가 | 예. 프론트의 래퍼·타입·무효화가 생성·추론으로 |
| 호출자 표현에 도움이 되는가 | 예. 조합 요청을 타입 안전하게 |
| 서버가 최종 권한을 통제하는가 | 예. SDK는 판단하지 않고 생성 타입은 공개 계약만 |
| AI의 불필요한 선택을 줄이는가 | 예. 래퍼·타입·키를 매번 정하지 않는다. C2에서 도구의 우회 API는 린트로 |
| JS/Python 생태계와 사람의 사용성 | C2로 보존. Python은 TS만큼 추론이 안 된다(확인 필요) |
| 복잡성을 옮기기만 했나 | 생성기·추론·어댑터가 AIP 쪽에 생기고 앱마다 반복되던 프론트 계층이 사라진다 |
