## A. 지금 결정할 문제

호출자가 조합한 읽기 요청을 서버가 **어느 시점에 무엇을 검사하고, 운영에서 어떤 요청을 받아 주는가**를 정한다.

먼저 바뀌지 않는 것: 실제 로그인 사용자, 권한, 테넌트, 현재 정책, 실행 비용 상한은 **운영 서버가 매 요청마다 다시 판단한다.** 빌드 시점에는 실제 사용자도 최신 정책도 없으므로, 빌드에서 할 수 있는 것은 요청의 구조·타입·공개 capability·정적 복잡도 검사와 실행 계획 미리 만들기(prewarm)뿐이다. 이 문서는 그 위에서 "운영 서버가 처음 보는 모양의 요청도 받아 주는가"를 다룬다.

## B. 실제 개발 시나리오

### B.1 자사 프론트: 아리아리 홈 화면 카드 (DD-01 B.3의 요청)

| 단계 | 런타임 입장 | 등록된 것만 입장(registered-only) |
|---|---|---|
| 개발 중 | 로컬 서버가 바로 실행. 개발 도구가 canonical 해시와 "운영에서도 받아 주는가"를 즉시 보여 준다 | 같음 |
| 빌드·배포 | 할 일 없음(원하면 prewarm용 등록) | 빌드가 프론트의 읽기 요청을 canonical 형태로 **명시적으로 등록**한다(작성 API나 코드 생성이 등록 산출물을 내는 방식으로 시작. 소스 코드 정적 분석은 나중 최적화). 자동 계약 검사 통과분만 활성 목록에 들어간다 |
| 운영 | 계약에 맞으면 처음 보는 모양도 실행 | 활성 목록에 있는 모양만 입장. 입장 뒤에는 런타임과 같은 정책 평가·자원 상한 |
| 화면이 바뀔 때 | 프론트만 배포 | 프론트와 함께 새 등록분이 자동 활성화. 사람 검토는 요청 모양마다가 아니라 capability 확대나 예외 한도에만 |

### B.2 지금 아리아리 요청은 정적으로 드러나는가 (`기존 코드`)

부분적으로만 그렇다. 경로 상수는 `ariari-frontend/app/api/apiUrl.ts` 16~23행처럼 정적이고 모집 목록 호출의 필드도 코드에 보인다(`api/recruitment/api.ts` 45~75행). 그러나 정렬 파라미터는 조건부로 붙고(63~68행), 지원 상태 변경은 상태에 따라 본문 모양과 URL이 바뀐다(`api/apply/api.ts` 271~289행). 그래서 "소스를 분석해 요청을 뽑아낸다"를 필수 전제로 두기는 어렵다. 호출자 요청 작성 API(DD-13 S1·S5)가 정해지면 그 API가 등록 산출물을 직접 내게 하는 쪽이 현실적이다(확인 필요).

### B.3 동적 호출자: 사내 AI 에이전트

예: 동아리 운영자가 사내 AI에게 "지난 학기 우리 동아리 모집 중 북마크가 많았던 순서로 보여줘"라고 묻는다. 이 요청 모양은 빌드 때 존재하지 않는다. 런타임 입장이 필요하다. 이때도 의미 체계는 같고, 서버가 그 호출자의 credential에 맞춰 더 낮은 비용·속도·동시성 한도를 건다.

## C. 대안과 트레이드오프

### C.1 대안

| | R. 런타임 단일 경로 | M. 빌드 승인 목록 중심 | S. 단일 파이프라인 + 선택적 등록 |
|---|---|---|---|
| 내용 | 모든 요청을 운영에서 정리·검사·계획·실행 | 자사 프론트 요청을 빌드 때 뽑아 승인 목록과 계획을 만들고 운영은 그것만 실행 | 모든 요청이 같은 canonical 정리 → 타입 검사 → capability 검사 → 정책 삽입 → 비용 상한 파이프라인을 탄다. 자사 프론트는 빌드 때 요청을 명시 등록해 prewarm할 수 있고, 운영 배포 정책으로 `registered-only`(등록분만 입장) 또는 `runtime`(계약 안이면 입장)을 고른다. 두 정책의 **실행 의미는 같다** |
| DD-01 하위안과의 관계 | 2-R | 2-M | 2-R을 기반으로 하고 2-M의 장점을 입장 정책·최적화로 얹은 것(DD-01의 2-RM을 대체) |

S에서 등록·prewarm·registered-only는 **입장 정책과 최적화**일 뿐 실행 권한이나 의미를 대신하지 않는다. 서버는 등록된 요청에도 actor·tenant·현재 정책·자원 상한을 매번 적용한다.

### C.2 비교 (원문 PART VII §13의 8개 축)

| 축 | R | M | S |
|---|---|---|---|
| 철학 정합성 | 호출자 표현이 가장 자유 | 새 화면마다 승인 목록의 재생성·배포가 필수라 운영적으로는 "허용 요청 형태의 사전 열거"에 가까워질 수 있다 | 표현은 R과 같고, 운영 예측성은 배포 정책으로 선택 |
| 보안 | I1~I7을 매 요청 적용. 처음 보는 모양이 운영에서 계획된다 | 낯선 모양을 일찍 차단. 그러나 오래된 목록 재생, 권한 철회 뒤 구 계획, 테넌트 치환은 매 요청 검사가 없으면 오히려 위험. **M이 자동으로 가장 강한 것은 아니다** | R과 같은 매 요청 검사 + `registered-only`를 고르면 낯선 모양 차단 |
| 비즈니스 규칙 처리 | 런타임 정책 | 빌드 검사 + 런타임 정책 | 런타임 정책. 빌드는 구조 검사만 |
| 구현 난이도 | 런타임 계획기(현재 PoC에 없음, 새로 만들어야 함) | 런타임 계획기(개발 모드용) + 추출기 + 목록 형식·신뢰·서명·활성화·폐기·구버전 공존·롤백 | 런타임 계획기 + 명시 등록과 활성 목록(정적 추출기는 필수 아님) |
| 확장성 | 새 호출자도 그대로 | 새 호출자 종류는 별도 경로 | 같은 파이프라인에 credential별 한도만 다르게 |
| 디버깅 | 요청 원문 기록 필요 | 목록 ID로 추적 | canonical 해시로 개발·운영·등록 상태를 같은 식별자로 추적 |
| AI 개발 경험 | 요청을 쓰면 끝 | 추출 가능한 모양으로 써야 하고, 로컬에서 되는데 빌드·운영에서 실패할 수 있다 | 요청을 쓰면 끝. 운영 정책이 `registered-only`여도 개발 도구가 즉시 같은 판정을 보여 준다 |
| 없어지는 중복 / 새 비용 | 화면별 서버 작업 없음 / 런타임 계획기와 실시간 방어 | 서버 코드 변경은 없음. 그러나 화면당 등록·배포가 필수 작업이 될 수 있다(확인 필요) / 위 구현 항목 전부 | 화면별 서버 작업 없음 / 런타임 계획기 + 선택한 경우에만 등록 체계 |

현재 PoC 사실: 컴파일 시점에 SQL과 실행 계획을 고정하는 것은 **선언 Intent 경로**다(`crates/aip-pg/src/lib.rs` 1~3·37~42·67~80행). 런타임은 SQL을 만들지 않는다(`crates/aip-runtime/src/lib.rs` 1~2행). 따라서 R·M·S 모두 조합 읽기용 계획기를 새로 만들어야 하고, 기존 컴파일러의 재사용 범위(SQL 생성기, plan 타입 등)는 확인 필요다.

### C.3 "승인"을 세 가지로 나눈다 `[추천]`

| 종류 | 언제 | 누가 |
|---|---|---|
| 계약 검사(구조·타입·capability·정적 복잡도) | 모든 요청, 개발·빌드·운영 어디서든 | 엔진, 자동, 필수 |
| 등록과 계획 미리 만들기 | 자사 프론트가 원할 때 | 빌드, 자동, 선택 |
| 사람 검토 | 기존 리소스의 capability를 넓히거나 예외 한도를 줄 때만(새 확장 등록은 제외, 원문 "확장은 승인 절차 없이") | 사람. **요청 모양이 바뀔 때마다 요구하지 않는다** |

사람 검토가 화면 변경마다 관문이 되면 서버 작업이 "승인 작업"으로 이름만 바뀌어 되살아난다(원문 PART I §1의 경계).

### C.4 층 1 조건 (DD-01 I1~I7에 더해, 관찰 가능한 성질) `[추천]`

T-I1·T-I5는 언제나 적용된다. T-I2~T-I4는 등록 기능을 켠 경우에만 적용되고, R(런타임 단일 경로)에서는 해당 대상이 없다.

| 조건 | 내용 |
|---|---|
| T-I1 의미 동일 | 같은 canonical 요청, 같은 actor·tenant, 같은 데이터 상태, 같은 capability·정책·스키마 버전, 같은 자원 한도라면 `runtime`과 `registered-only`는 같은 결과·오류를 낸다. 빌드·개발 도구의 **구조 판정**(타입, capability, 정적 복잡도, 등록 적격성)은 운영의 같은 구조 판정과 일치하며, 실행 시점에만 알 수 있는 권한·데이터·비용 판정을 성공으로 가장하지 않는다 |
| T-I2 등록은 권한이 아니다 | 등록 식별자를 안다고 실행 권한이 생기지 않는다. actor·tenant·현재 정책이 달라지면 같은 등록 식별자도 새 판정 결과를 낸다(예: 정책 변경 뒤 거부) |
| T-I3 등록은 신뢰된 주체만 | 등록과 활성화는 신뢰된 빌드·배포 주체만 할 수 있다. 앱·환경·연산 종류·capability·스키마가 다른 곳으로 식별자를 바꿔 쓰면 거부된다. 읽기 등록이 쓰기·확장 경로로 쓰일 수 없다 |
| T-I4 권한 축소는 유예 없이 | 정책·capability가 줄어들어 맞지 않게 된 등록분은 다음 입장부터 유예 없이 거부되고, 안정된 `stale` 오류를 낸다 |
| T-I5 경로는 서버가 정한다 | 호출자가 헤더나 파라미터로 `runtime` 경로를 주장해 `registered-only`를 우회할 수 없다. 입장 경로는 서버가 credential과 배포 정책으로 정한다 |

**배포 전 일치 검사:** 로컬 즉시 실행과 별개로, 배포 전에 CI와 로컬에서 운영과 같은 엔진으로 canonical 구조 판정과 등록 적격성 검사를 돌린다. "로컬에서는 되는데 운영에서 거부"가 정상 개발 흐름이 되지 않게 한다.

**층 2(필요해질 때):** 아직 현재 계약과 호환되는 구 프론트 등록분의 공존 기간(유예), 최대 보존 기간, 롤백 절차(보안상 축소는 T-I4로 즉시 거부), 소스 정적 추출, 서명 형식, plan cache 세부(DD-01 층 2 원칙 상속: 정책이 매개변수로 들어간 plan만 재사용, 판정 결과 공유 금지), 동시 miss 폭주 방지, DB 통계 변화 뒤 비용 재평가.

## D. 최초 철학과의 관계

| 원칙 | 관계 |
|---|---|
| 존재 목적 | R·S는 화면별 서버 작업 없음. M은 서버 코드는 안 바뀌지만 등록·배포가 화면당 필수 작업이 되면 형태만 바뀐 서버 작업이 될 수 있다. 판정 기준은 "새 데이터 요구가 생길 때 프론트 변경 말고 어떤 중앙 산출물·검토·동기 배포가 반드시 필요한가" |
| 작동 모델 | R·S는 동적 호출자 포함 표현 가능. M만으로는 동적 호출자를 막는다 |
| 서버 최종 통제 | 세 안 모두 I1~I7과 해당하는 T-I 조건(C.4)을 매 요청 적용할 때만 성립. 등록은 추가 방어선이지 대체물이 아니다 |
| AI First | 의미 체계가 하나여야(S, T-I1) AI가 "어느 모드용으로 써야 하나"를 고민하지 않는다 |
| PART V 수단과 목적 | M은 추출기·목록 형식·서명·배포·폐기를 초기에 필수화한다. S는 가장 단순한 기반(런타임 파이프라인)에서 시작해 등록을 필요할 때 얹는다 |

| E2 | 호출자 요청 작성 API(DD-13) 후보로 요청 10~20개를 써 보고 등록 산출물 생성 가능성, 동적으로 조립되는 요청 비율을 잰다. DD-04 미정이면 후보 둘을 비교하고 결과는 확인 필요로 둔다 | 명시 등록의 현실성 |
| E3 | 공격 모음: 등록 식별자 위조·치환, 오래된 등록분 재생, 권한 철회 뒤 호출, 테넌트 치환, 버전 엇갈림, `runtime` 경로 주장, plan cache 교차 문맥. R은 I1~I7과 T-I1·T-I5, 등록을 쓰는 S는 I1~I7과 T-I1~T-I5로 판정 | 등록이 권한을 대신하지 않는지 |

## F. 확인된 답과 남은 일

- 확인됨: 허용 정책 안에서 새 읽기 조합을 수용하는 방향이다. 등록 여부를 기본 차단으로 두는지와 구체 admission 규칙은 아직 고정하지 않는다.
- 기술 검증: 단일 의미 파이프라인, 선택 등록·prewarm, 운영 요청별 구조·권한·자원 검사, 등록 경로와 런타임 경로 동등성을 비교한다.
- 자사 프론트 외 호출자 범위는 DD-01의 기술·운영 비교 뒤 필요한 가치 판단이다. 기존 A/B 선택 질문은 완료된 것으로 처리한다.

## G. 결정 상태

**검증 필요.** 동적 읽기 수용 방향은 확인됐다. 런타임 입장 정책과 선택 등록·prewarm의 비용·안전성은 기술 비교가 남았다. 기존 S 추천은 확정 설계가 아니다.

## 이탈 방지 점검 (S 기준)

| 질문 | 답 |
|---|---|
| 백엔드 개발이나 이중 유지보수를 줄이는가 | **예(`runtime`), 확인 필요(`registered-only`).** 후자는 등록·배포가 화면당 필수 작업이 되는지 E1로 잰다 |
| 호출자 표현에 도움이 되는가 | **예.** 동적 호출자도 같은 의미 체계로. `registered-only`를 고르면 자사 프론트의 새 요청은 배포 주기만큼 지연된다 |
| 서버가 최종 권한을 통제하는가 | **I1~I7, T-I1~T-I5를 매 요청 적용할 때만 예.** 등록은 추가 방어선 |
| AI의 불필요한 선택을 줄이는가 | **예에 가깝다.** 의미 체계가 하나라 모드별 작성 방식이 없다(T-I1). 확인은 E2 |
| JS/Python 생태계와 사람의 사용성 | **확인 필요.** 작성 방식 미정. 명시 등록은 번들러 의존을 줄인다 |
| 복잡성을 옮기기만 했나 | `runtime`은 런타임 계획기 하나로 시작. `registered-only`는 등록·폐기·버전 계층이 추가되므로 순효과는 E1로 판단 |
