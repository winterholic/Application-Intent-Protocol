# V9. 캐시 수명과 미확정 쓰기 복구 실험 계획

> 상태: 기술 후보, 창시자 결정 아님. V5/V6/V8의 연결 경계를 검증한다. 본 `crates/`는 변경하지 않는다.

## 설계 관문

1. 원칙 1·2·4·6: 화면별 만료·재시도 코드를 SDK가 흡수하고 서버의 실행 권한을 유지한다. 캐시 수명만으로 즉시 권한 회수를 보장하려는 해석과 긴장한다.
2. 호출자의 select/filter/apply 표현 범위는 그대로 유지한다. 캐시가 서버 검증을 무기한 생략하는 경로를 제한한다.
3. 애플리케이션별 API나 선언을 추가하지 않는다. 서버 응답에 공통 캐시 수명 정보를 연결한다.
4. 서버가 서명을 검증한 세션 수명과 실험용 신선도 상한 중 작은 값을 반환한다. 요청의 actor·클라이언트 시계·TTL을 권한 근거로 신뢰하지 않는다.
5. Rust 서버와 기존 TS SDK를 재사용한다. Python 확장 계약은 영향 없고 Python 클라이언트는 미검증이다.
6. 기존 read/apply API에 경계를 추가한다. 새로운 업무 표현 방식은 만들지 않는다.
7. IR 확장이 아닌 실제 HTTP·캐시·DB 결과를 검증한다.
8. TTL 수치·즉시 동기화·세션 갱신 방식은 확정하지 않는다. 실험용 상한은 제품 기본값이 아니다.

## 가설과 반례

- 서버 응답의 `maxAgeMs`를 클라이언트 단조 시계에서 요청 왕복시간만큼 차감하면, 서버·클라이언트 벽시계 차이에 기대지 않고 캐시 수명을 제한할 수 있다. 정보가 없거나 잘못되면 캐시 저장을 하지 않는다.
- 수명이 끝난 hit와 수명을 넘겨 도착한 응답을 저장하지 않는다. 세션 만료 뒤 재조회는 서버의 `TOKEN_EXPIRED`를 받는다.
- 다른 클라이언트가 데이터를 바꾸거나 권한을 회수하면 상한 안에서는 이전 결과가 남을 수 있다. 만료 뒤 재조회로 변경을 확인한다. 즉시 회수·실시간 구독은 범위 밖이다.
- 고정 `NOW`를 실제 UTC 시각으로 바꾸고 시간에 따라 달라지는 정책을 실제 DB 조회로 검증한다.
- 같은 미확정 키를 반복 요청해도 저장 보류 횟수는 키당 하나다. 다른 본문 재사용은 원래 복구 요청을 덮어쓰지 않는다. 인증·입장 거부는 이전 쓰기의 롤백 증거가 아니므로 pending을 지우지 않는다.
- 재시도는 처음 보낸 요청의 복사본을 사용한다. 호출자가 객체를 변경해도 이전 키의 의미가 바뀌지 않는다.

## 완료 조건

기존 동작을 깨지 않고 반례가 먼저 실패하는 것을 확인한다. 좁은 Node 테스트, 실제 Rust HTTP/PG 테스트, 기존 V5·V6·V8 회귀 검증을 실행한다. Sol high 독립 검토를 코드·재현으로 확인하고 결과 문서·상태에 실제 보장과 남은 범위를 함께 기록한다.
