# V13. 큰 Id의 손실 없는 왕복 비교 계획

> 상태: 독립 후보 구현·실행 검증(2026-10-04). [실행 결과·한계](V13-id-boundary-results.md), [독립 검토](../reviews/codex-v13-sol-review.md). 아래는 실행 전 관문과 비교 기준이다. [V5 R5-05](V5-sdk-results.md)의 손실 반례와 [V12](V12-typed-transport-results.md)의 남은 Id 경계를 이어받는다. 공개 Id 표현을 창시자 대신 확정하지 않는다.

## 현재 증거와 우선순위

V5 생성 `Id<R>`는 number이며 V12에서도 그대로다. V2는 PG `json_build_object`의 JSON 숫자를 읽고 V6가 전달한다. V3 `parse_ids`와 compose Id 값은 18자리 이하 숫자 문자열만 허용한다. V5의 기존 기록에는 `9007199254740993`의 JS 왕복 손실 반례가 있다. 큰 Id를 typed apply에 그대로 연결하면 잘못된 행을 가리키는 경계를 타입만으로 가릴 수 있다.

Sol high의 다음 후보 대조에서 이 실제 손실 경계를 우선으로 선정했다. 시간 의존 조회는 현재 미캐시로 처리하며, 변경 통보·worker 격리는 더 넓은 운영 비교다. typed apply 자체도 남은 과제다.

## 설계 관문

1. 원칙 1·2·3·4·6: 호출자가 읽은 Id로 같은 행을 다시 조회하고 변경할 수 있어야 한다. 편의상 숫자로 제한하는 후보는 DB의 표현 범위와 긴장한다.
2. 숫자 안전범위 제한과 십진 문자열 wire를 비교한다. 전자는 허용 domain을 줄이고 후자는 큰 Id를 유지하되 입력/타입 경계를 바꾼다.
3. 공통 서버/SDK 경계에서 처리해 화면별 변환을 요구하지 않는 후보를 검증한다. 서버 정의나 화면별 mapper를 늘리지 않는다.
4. 서버 타입·범위·권한 검사는 유지한다. 올바른 Id 형식은 권한이 아니다. 읽은 값을 이용한 다른 actor 쓰기도 거부해야 한다.
5. TS/JS의 안전 정수와 문자열, Python의 정수 표현을 구분한다. 이번 slice가 Python SDK를 구현했다고 표시하지 않는다.
6. 같은 API에서 두 공개 표현을 임의로 섞지 않는다. 독립 실험 모드로 동일한 반례를 비교하고 최종 표현은 열린 선택으로 남긴다.
7. 기존 facts·planner·SQL·write·생성 타입의 실제 Id 경계만 변경 후보로 둔다. 새 IR/숫자 타입 체계를 만들지 않는다.
8. 문자열/숫자 공개 표현과 유효 Id domain은 창시자 선택이다. 후보의 정확성·수정 지점만 측정하고 본 `crates/`는 보존한다.

## 최소 비교와 반례

- 실제 PG에서 안전범위 안 Id, 경계 Id, `2^53+1`, 18자리 값, 19자리 i64 상한을 읽기→filter→apply로 왕복한다. 결과의 동일 행과 변경 대상·다른 행 불변을 DB에서 단언한다.
- 숫자 제한 후보는 안전범위 밖을 JSON으로 손실 전송하기 전에 명시 거부하고 안전범위 안의 기존 동작을 유지한다.
- 문자열 후보는 JSON 숫자 파싱 뒤에 변환하지 않는다. 서버가 typed Id를 직렬화할 때 십진 문자열로 내보내고 생성 TS 타입과 요청 값 검사를 연결한다.
- 루트 Id·관계 Id·null 관계를 확인한다. 일반 Int나 문자열 필드를 Id처럼 일괄 변환하지 않는다.
- 현재 18자리 제한과 DB i64 범위 차이를 실패 대조에 포함한다. 음수·앞자리 0·범위 밖·빈 문자열의 처리 기준은 기존 의미와 후보 차이를 명시해 비교한다.
- 정상/음성 tsc·raw 요청 검사·실제 HTTP/PG·선택적 검사 불변·고장 주입으로 확인한다. 변환 위치별 변경 파일과 호출자 추가 변환 필요 여부를 기록한다.

성공은 두 후보가 침묵 반올림을 막는 근거와 개발자 부담 비교다. 숫자 후보의 범위 밖 명시 거부는 손실 없는 전 범위 지원과 구분한다. 일반 Int의 bigint 정밀도, 호환 기간, 전체 프로토콜 규격은 별도 한계다.
