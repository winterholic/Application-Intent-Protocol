# AIP — Founder Intent & Complete Architecture Context Handoff

## 0. 이 문서의 목적과 최우선 지침

이 문서는 AIP(Application Intent Protocol) 프로젝트의 최초 구상, 창시자의 철학, 지금까지 진행한 설계 논의, 기존 구현에서 발견된 문제, 앞으로 해결할 설계 의제를 AI 개발 에이전트에게 전달하기 위한 컨텍스트다.

**이 문서는 구현 명세서가 아니라 설계 맥락과 의도에 관한 인계 문서다.**

가장 중요한 지침은 다음과 같다.

1. 창시자의 최초 목적을 기술적 구현보다 우선한다.
2. 기존 코드가 존재한다는 이유로 현재 아키텍처를 정답으로 간주하지 않는다.
3. 기존 구현을 최대한 활용하되 최초 철학에 맞지 않으면 수정 가능성을 검토한다.
4. 미확정 설계를 임의로 확정하지 않는다.
5. 기술적으로 일반적인 설계라는 이유만으로 도입하지 않는다.
6. 모든 설계는 AIP의 존재 목적에 기여해야 한다.
7. AI가 임의로 해석한 내용을 창시자가 승인한 결정으로 취급하지 않는다.
8. 구현 전에 핵심 설계의 정합성을 충분히 검토한다.
9. 실서비스에서 사용할 수 있는 프레임워크를 목표로 한다.
10. 현재 단계에서는 설계 검토와 제안을 우선하며 승인 없이 코드를 변경하지 않는다.

특히 이 프로젝트에서는 과거 AI 에이전트와의 논의 과정에서 최초 의도가 일부 소실되거나 왜곡된 문제가 발생했다.

따라서 이 문서를 읽은 후에도 기존 설계 문서를 무조건 신뢰하지 말고, 아래에 명시한 최초 요구사항을 기준으로 검증해야 한다.

# PART I. AIP가 탄생한 이유

## 1. 기존 프론트엔드와 백엔드의 경계를 재정의한다

이것이 AIP의 가장 근본적인 존재 이유다.

기존 웹 애플리케이션은 프론트엔드와 백엔드가 분리되어 있다.

새로운 기능을 구현하려면 일반적으로 다음 작업이 반복된다.

- 프론트엔드에서 필요한 데이터와 동작 정의
- 백엔드 API 설계
- Controller 구현
- Service 구현
- Repository 또는 데이터 접근 로직 구현
- DTO 및 타입 정의
- 직렬화와 검증
- 프론트엔드 API 호출 코드 작성
- 양쪽 계약 변경 및 유지보수

프론트엔드에서 필요한 데이터가 달라지면 백엔드 API도 수정해야 하는 경우가 많다.

창시자는 이러한 개발 구조 자체를 근본적으로 개선하고 싶어 했다.

**AIP의 목표는 서버를 없애는 것이 아니라, 애플리케이션별로 작성하고 유지보수해야 하는 백엔드 코드를 극단적으로 줄이는 것이다.**

이상적인 개발 경험은 다음과 같다.

1. AIP 서버와 필요한 정책·데이터 정의를 준비한다.
2. 프론트엔드에서 필요한 데이터와 동작을 표현한다.
3. AIP가 요청의 의미와 권한을 검증한다.
4. AIP가 적절한 실행 방법을 결정한다.
5. 서버가 실제 작업을 수행한다.
6. 프론트엔드는 필요한 형태의 결과를 받는다.

새로운 화면이나 데이터 요구사항이 생길 때마다 서버에 별도 API를 추가하는 상황을 최소화해야 한다.

궁극적인 지향점은 **애플리케이션별 백엔드 유지보수 부담을 0에 가깝게 만드는 것**이다.

단, 이는 모든 비즈니스 규칙이나 서버 설정이 완전히 사라진다는 보장이 아니다.

그러한 이상을 향해 프레임워크가 얼마나 많은 책임을 흡수할 수 있는지 탐구하는 것이 핵심이다.

### 최초 영감: GraphQL과 CQRS

창시자는 GraphQL의 호출자 중심 데이터 선택과 CQRS의 읽기·쓰기 책임 분리에서 영감을 받았다.

하지만 AIP는 GraphQL을 복제하거나 CQRS를 단순 구현하는 프로젝트가 아니다.

GraphQL과 CQRS는 설계에 영감을 준 기술일 뿐, AIP의 최종 형태를 제한하는 규격이 아니다.

특히 다음과 같은 구조는 경계해야 한다.

- 서버가 모든 요청 형태를 사전에 정의해야 하는 구조
- 기존 REST API를 단순히 다른 문법으로 감싼 구조
- 클라이언트가 이름 붙은 서버 함수를 호출하는 데 그치는 구조
- 단순한 GraphQL 래퍼
- CRUD 자동 생성에 머무르는 구조

AIP는 호출자가 필요한 데이터와 동작을 표현할 수 있는 범위를 기존 방식보다 넓히는 것을 목표로 한다.

그 범위와 제약은 안전성을 고려해 별도로 설계해야 한다.

## 2. 새로운 통신 규약: Application Intent Protocol

AIP는 기존 RESTful API 중심의 통신 모델을 대체하거나 보완할 새로운 애플리케이션 통신 체계를 지향한다.

여기서 핵심은 HTTP를 반드시 버리는 것이 아니다.

**요청과 응답을 어떤 의미 단위로 정의하고, 서버가 이를 어떻게 검증하고 실행할 것인가**가 중요하다.

Application Intent Protocol이라는 이름에는 호출자가 원하는 목적이나 동작을 표현한다는 철학이 담겨 있다.

기존 방식에서는 개발자가 특정 엔드포인트를 호출한다.

AIP에서는 호출자가 필요한 결과와 동작을 표준화된 방식으로 표현하고, 서버가 이를 안전하게 실행하도록 하는 모델을 추구한다.

다만 Intent라는 표현이 자연어 명령을 무제한으로 해석한다는 의미는 아니다.

Intent는 명확한 문법, 계약, 타입, 정책을 갖춘 구조화된 요청이어야 한다.

### 보안 철학

창시자는 프론트엔드와 서버 실행 영역의 경계가 잘못 설계되면 심각한 보안 문제가 발생할 수 있다는 점에서 문제의식을 얻었다.

React 서버 측 취약점과 같은 사례도 이러한 고민의 계기가 되었다.

다만 특정 취약점의 정확한 원인과 AIP의 설계 철학은 구분해야 한다.

AIP에서 반드시 지켜야 할 원칙은 다음과 같다.

- 프론트엔드의 표현 자유와 서버의 실행 권한은 별개다.
- 클라이언트가 요청한다고 모든 작업을 허용해서는 안 된다.
- 인증과 인가는 서버가 최종 결정한다.
- 데이터 접근 범위와 실행 가능한 동작은 서버 정책을 따른다.
- 테넌트 격리와 데이터 무결성을 보장해야 한다.
- 호출자가 서버 내부 구현을 임의로 제어할 수 없어야 한다.
- 조합 가능한 요청이 권한 우회로 이어지지 않아야 한다.
- 실행 비용, 깊이, 복잡도 및 자원 사용량을 통제할 수 있어야 한다.

**백엔드 개발을 최소화하는 것과 백엔드의 보안 책임을 제거하는 것은 완전히 다르다.**

이 차이를 AIP의 핵심 설계 원칙으로 유지해야 한다.

## 3. Rust 핵심 엔진과 JavaScript/Python 생태계

창시자는 AIP의 핵심 내부 구현에 Rust를 활용하는 방향을 선택해 개발을 시작했다.

Rust는 내부 엔진의 성능, 안정성, 메모리 안전성, 독립적인 실행 구성 요소 구현 등을 고려한 기술적 선택이다.

그러나 Rust 자체가 AIP의 목적은 아니다.

AIP의 주요 사용자 생태계는 다음과 같다.

1. JavaScript / TypeScript
2. Python

특히 JavaScript 생태계를 우선적으로 고려한다.

창시자는 개발자와 AI가 기존 JS/Python 생태계를 자연스럽게 활용하면서 AIP의 기능을 사용할 수 있기를 원한다.

예를 들어 AIP가 어떤 기능을 제공한다면, 개발자는 JS/Python 환경에서 AIP의 표준 인터페이스를 통해 그 기능을 사용할 수 있어야 한다.

내부 구현이 Rust라는 사실 때문에 개발자가 Rust를 직접 작성해야 하는 구조는 지양한다.

### 주의: 확정하지 않은 사항

다음 사항은 아직 상세 설계가 확정되지 않았다.

- Rust 독립 서버가 유일한 실행 형태인지
- Node.js/Python 프로세스에 임베드할 것인지
- 독립 서버와 임베딩을 모두 지원할 것인지
- Rust와 JS/Python 사이의 호출 경계
- 바인딩 및 FFI 구조
- AIP 전용 문법과 JS/Python 인터페이스의 관계
- 코드 생성 방식의 필요성과 범위

Rust로 구현한다는 사실만으로 컴파일러 구조를 확정해서는 안 된다.

반대로 JS/Python 생태계를 활용한다는 이유만으로 Rust 엔진이나 AIP 고유 문법을 제거해서도 안 된다.

## 4. AI First: AI가 개발하는 시대를 위한 프레임워크

AIP는 AI가 주된 코드 작성자가 되는 시대를 전제로 설계한다.

기존 프레임워크에서는 같은 요구사항을 구현하는 방법이 매우 다양하다.

예를 들어 같은 데이터 조회 기능을 구현하더라도 다음 선택지가 존재한다.

- ORM 사용
- SQL 직접 작성
- Repository 패턴
- Service 패턴
- Query Builder
- 별도 API 구성
- 다양한 캐싱 및 상태 관리 방법

각 방법에는 장단점이 있지만, AI는 매번 선택하고 판단해야 한다.

창시자는 이러한 불필요한 선택 자체를 줄이고 싶어 한다.

### 핵심 철학

**AI가 구현 방법을 고민하는 시간을 줄이고, 요구사항의 의미와 비즈니스 목적에 집중하도록 만든다.**

이를 위해 AIP는 다음을 추구한다.

1. 가능한 한 많은 일반적 개발 패턴을 표준 기능으로 제공한다.
2. 동일한 의도는 가능한 한 동일한 구조로 표현한다.
3. 기본값을 풍부하게 제공한다.
4. 불필요한 설정과 선택지를 제거한다.
5. 문법과 계약을 명확히 한다.
6. 모호한 관습보다 기계적으로 검증 가능한 규칙을 우선한다.
7. 프로젝트 구조와 기능의 위치를 예측 가능하게 만든다.
8. 오류를 명확하고 구조화된 형태로 제공한다.
9. AI가 외부 문서나 구현 내부를 추측해야 하는 상황을 줄인다.
10. 인간도 이해하고 유지보수할 수 있어야 한다.

중요한 것은 자유를 무조건 제거하는 게 아니라 **불필요한 자유와 구현 다양성을 줄이는 것**이다.

## 5. 풍부한 표준 문법과 기본 기능

창시자는 AI가 자주 작성하는 코드를 가능한 한 프레임워크 차원의 기능과 문법으로 흡수하고 싶어 한다.

이것은 단순히 짧은 코드를 작성하려는 목적이 아니다.

일반적인 개발 패턴을 표준화하여 AI가 구현 방법을 임의로 선택하지 않도록 하기 위한 것이다.

예를 들어 다음과 같은 영역을 표준화 대상으로 검토할 수 있다.

- 데이터 조회와 변경
- 검증
- 권한 검사
- 트랜잭션
- 반복 및 조건 처리
- 비동기 작업
- 스케줄링
- 이벤트
- 승인 흐름
- 검색
- 외부 서비스 연동

이 목록은 기능 구현을 확정한 명세가 아니라 설계 대상의 예시다.

### AIP 고유 문법

AIP가 독립적인 표현 체계를 가져야 한다는 방향을 논의했다.

최근에는 선언 블록 중심의 AIP DSL을 선호하는 방향으로 합의했다.

예를 들어 resource, query, command 등의 구성 요소를 검토했다.

또한 단순 선언뿐 아니라 조건문, 반복문, 함수, 표현식 등의 제어 흐름도 지원하는 방향을 논의했다.

다만 **AIP 고유 문법이 반드시 독립적인 소스 파일 언어여야 하는지, JS/Python 내부에서 사용하는 API 형태여야 하는지, 또는 두 방식을 함께 제공해야 하는지는 재검토가 필요하다.**

과거 대화에서는 독립 DSL을 선호했지만, 이후 구현 감사에서 이것이 최초의 JS/Python 통합 의도와 충돌할 가능성이 발견되었다.

따라서 기존 `.aip` 문법을 무조건 폐기하거나 유지한다고 단정하지 않는다.

창시자의 실제 개발 경험 목표를 기준으로 결정해야 한다.

## 6. 자연어의 문법화

이 원칙은 이전 구현에서 누락된 중요한 창시자 의도다.

창시자는 단순히 코드에 자연어 주석을 많이 작성하려는 것이 아니다.

**자연어로 표현하던 목적, 의도, 맥락 등을 AIP의 공식적인 구조나 문법으로 표현할 수 있기를 원한다.**

일반적인 주석은 실행 엔진이나 검증기가 이해하지 않는 경우가 많다.

창시자는 이러한 자연어적 정보를 정형화하여 AI가 더 일관되게 이해할 수 있는 개발 체계를 구상했다.

다만 다음 사항은 아직 결정되지 않았다.

- 목적과 의도를 어떤 문법으로 표현할 것인지
- 자연어적 정보가 실행 의미에 영향을 주는지
- 문서 및 메타데이터로만 사용되는지
- 타입이나 계약 검증에 활용할 수 있는지
- AI가 탐색하는 구조와 어떻게 연결할 것인지

이 항목을 단순한 주석 자동 생성이나 JSDoc 확장으로 축소하지 마라.

### 문서화에 관한 후속 합의

이전 논의에서는 문서의 목적별 형식과 위치를 정형화하는 방향에 동의했다.

하지만 문서 작성 자체를 모든 상황에서 강제하지는 않기로 했다.

즉, 문서화의 표준은 제공하되 불필요한 문서 작성 의무를 만들지 않는다.

또한 AI가 필요한 정보를 탐색할 때 Index → Contract → Implementation 순서로 점진적으로 살펴보는 방식을 검토했다.

이는 확정된 파일 포맷이 아니라 AI 탐색 효율을 높이기 위한 설계 방향이다.

---

## 7. SPR 패턴

AIP에서는 SPR이라는 아키텍처 모델을 논의했다.

- S: Specification
- P: Presentation
- R: Runtime

개념적으로 다음 역할을 가진다.

### Specification

애플리케이션의 리소스, 계약, 정책, 동작, 제약 및 의도를 표현하는 영역이다.

### Presentation

프론트엔드 또는 다른 호출자가 필요한 데이터와 동작을 표현하고 결과를 사용하는 영역이다.

### Runtime

요청을 검증하고 정책을 적용하며 실제 동작을 실행하는 영역이다.

개념적인 흐름은 다음과 같다.

Presentation
→ Application Intent Protocol
→ Specification 기반 검증
→ Runtime 실행
→ 결과 반환

단, SPR의 정확한 경계와 세부 책임은 아직 충분히 확정되지 않았다.

특히 Specification이 서버에만 존재해야 하는지, 클라이언트와 어떤 정보를 공유해야 하는지, 계약의 배포 및 버전 관리를 어떻게 처리할지는 추가 논의가 필요하다.

중요한 것은 SPR을 단순한 MVC의 이름 변경으로 만들지 않는 것이다.

SPR은 AIP의 호출자 중심 개발 경험과 서버 권한 통제를 구현하는 데 실질적인 역할을 해야 한다.

## 8. 예외 처리와 기존 JS/Python 활용

AIP가 아무리 풍부한 표준 기능을 제공하더라도 모든 비즈니스 요구사항을 미리 예측할 수는 없다.

따라서 표준 기능으로 처리할 수 없는 요구사항은 기존 JS/Python 코드로 자연스럽게 확장할 수 있어야 한다.

창시자는 예외적인 코드를 작성하기 위해 별도의 승인을 받거나 복잡한 절차를 거치는 구조를 원하지 않는다.

기본적으로는 AIP의 표준 방식을 사용하되, 필요한 경우 명시적으로 확장한다.

중요한 원칙은 다음과 같다.

- 표준 기능을 우선한다.
- 확장은 자연스럽게 사용할 수 있어야 한다.
- 불필요한 승인 절차를 만들지 않는다.
- 확장 경계는 명확해야 한다.
- 서버 권한과 보안 규칙을 우회해서는 안 된다.
- 확장 기능도 가능한 한 타입과 계약을 유지한다.

이것은 일반적인 프로그래밍 자유를 모두 제한하려는 철학과 다르다.

**AIP는 표준 경로를 강하게 제시하지만, 현실적인 확장 가능성은 유지한다.**

# PART II. 지금까지의 주요 설계 합의

## 9. 이미 논의한 방향

다음 사항들은 이전 대화에서 긍정적으로 검토하거나 방향에 동의한 내용이다.

단, 상세 기술 명세까지 확정되었다는 의미는 아니다.

### 9.1 선언 중심의 AIP 표현 체계

AIP는 개발자가 구현 방법보다 목적을 표현할 수 있도록 설계한다.

선언 블록 중심의 문법을 선호했다.

이전 논의에서 A형 문법을 B형보다 선호했으며, B형은 Java와 비슷한 느낌이라는 이유로 선호하지 않았다.

다만 정확한 A형 문법의 세부 규칙은 원본 설계 기록을 확인해야 한다.

### 9.2 풍부한 기본 제공 기능

AIP가 반복적인 개발 패턴을 최대한 흡수한다.

개발자가 매번 구현해야 하는 기능을 표준 구성 요소로 제공한다.

단순 CRUD 프레임워크에 머물러서는 안 된다.

### 9.3 기본값과 명시적 재정의

AIP는 기본적으로 표준 방식을 사용한다.

하지만 모든 상황을 강제하지는 않는다.

필요한 경우 사용자가 명시적으로 동작을 재정의할 수 있어야 한다.

### 9.4 공통 의미 모델

서로 다른 작성 방식이 동일한 의미를 갖는다면 공통 내부 표현으로 정규화하는 방향을 논의했다.

이를 Canonical Typed IR이라고 불렀다.

하지만 IR의 구체적인 구조와 역할은 아직 확정하지 않았다.

특히 IR을 사용한다는 이유만으로 AIP를 별도의 범용 프로그래밍 언어 또는 컴파일러 프로젝트로 만들어서는 안 된다.

### 9.5 AI 친화적인 구조

AIP가 제공하는 표준 기능과 문법은 AI가 쉽게 탐색하고 이해할 수 있어야 한다.

동일한 요구사항에 대해 불필요하게 많은 표현이 생기는 것은 지양한다.

### 9.6 문서와 메타데이터

문서의 목적과 형식을 표준화할 수 있다.

그러나 모든 문서의 작성을 의무화하지 않는다.

자연어의 문법화와 일반적인 문서화는 구분해야 한다.

# PART III. 기존 1~14번 설계 의제

이 14개는 과거 논의에서 정리한 주요 설계 의제다.

**현재 1번은 상위 방향만 논의했고, 2번부터 본격적인 상세 토의가 필요한 상태다.**

다만 최근 창시자 의도 감사 결과가 나왔으므로, 기존 1번의 합의도 최초 목적과의 정합성을 재검증해야 한다.

## 1. AIP 독립 DSL

논의한 내용:

- 독립적인 AIP 표현 체계
- 선언 블록 중심 문법
- resource/query/command 등의 표준 구성 요소
- 조건문, 반복문, 함수, 표현식 지원 방향
- AI가 동일한 의도를 일관되게 작성할 수 있는 구조
- 기본값 우선
- 명시적 재정의
- JS/Python과의 확장 경계
- 목적별 문서화 구조

상태: 상위 방향 논의 완료, 세부 문법 미확정, 최초 의도와 재검증 필요.

중요한 질문:

AIP의 고유 문법을 JS/Python 사용 경험과 어떻게 결합할 것인가?

## 2. Canonical Typed IR

논의 대상:

- 공통 의미 표현의 필요성
- IR의 역할과 경계
- 타입 정보
- 실행 의미
- 정책과 부작용
- 기본값의 정규화
- JS/Python과의 연결
- Runtime이 사용하는 정보
- 통신 계약과의 관계
- AI가 탐색할 메타데이터
- 버전 관리

이전에 단일 Canonical IR과 목적별 파생 모델을 제안했지만 확정하지 않았다.

상태: 미확정.

중요한 질문:

IR이 AIP의 호출자 중심 실행과 안전한 통신을 어떻게 실질적으로 지원할 것인가?

## 3. 사용자 정의 비즈니스 로직

논의 대상:

- 일반적인 CRUD를 넘어서는 비즈니스 로직
- 복잡한 조건과 제어 흐름
- 사용자 정의 함수
- 비동기 처리
- 외부 서비스 호출
- 재사용 가능한 로직
- 표준 기능과 자유 코드의 경계

방향:

복잡한 비즈니스 로직도 AIP의 중요한 지원 대상이다.

상태: 목표는 합의, 상세 실행 모델 미확정.

## 4. Escape Hatch

논의 대상:

- 표준 기능 밖의 JS/Python 코드 사용
- 명시적인 확장 경계
- 승인 없는 자유로운 확장
- 타입과 계약 유지
- 예외 처리
- 보안과 실행 격리
- 디버깅

방향:

표준 방식을 우선하되 자유로운 확장 경로를 제공한다.

상태: 철학 합의, 기술 설계 미확정.

## 5. 인증 및 인가

논의 대상:

- 인증 체계
- 권한 정책
- 리소스별 접근 제한
- 필드별 접근 제한
- 행 단위 접근 제어
- 테넌트 격리
- 대리 접근
- 권한 검증 시점
- 조합 요청의 보안
- 민감 데이터 노출 방지

기존 Rust 구현에서 상당 부분 구현 및 테스트되었다는 감사 보고가 있다.

하지만 새로운 호출자 중심 요청 모델에서도 안전하게 동작하는지 별도 검증이 필요하다.

상태: 기존 구현 존재, 새로운 실행 모델에 대한 정합성 검증 필요.

## 6. DB 추상화

논의 대상:

- DB별 기능 차이
- 공통 데이터 모델
- 지원 가능한 연산
- 관계 표현
- 데이터베이스별 capability
- 지원되지 않는 기능에 대한 명시적 오류
- 성능 차이
- 특정 DB 종속성

기존 구현은 PostgreSQL 중심이라는 감사 보고가 있다.

상태: 확장 범위 미확정.

## 7. Query Planner

논의 대상:

- 호출자가 표현한 데이터 요구사항 해석
- 관계 탐색
- 필터
- 정렬
- 페이지네이션
- 집계
- 실행 계획
- 비용 제한
- N+1 문제
- 권한 적용
- DB별 최적화

중요한 원칙:

호출자의 표현 자유를 제공하면서 서버가 안전하고 효율적인 실행을 보장해야 한다.

상태: 상세 설계 미확정.

## 8. 자동 CRUD 지원 범위

논의 대상:

- 기본 조회
- 생성
- 수정
- 삭제
- 관계 변경
- 일괄 처리
- 자동 생성 범위
- 비즈니스 규칙이 필요한 변경
- 단순 쓰기 조합의 허용 여부

중요한 미결정 사항:

읽기만 조합 가능하게 할지, 안전한 범위의 쓰기까지 조합 가능하게 할지 결정해야 한다.

기존 에이전트는 읽기 조합과 사전 선언된 Command만 허용하는 방식을 추천했다.

그러나 이는 확정된 창시자 결정이 아니다.

상태: 미확정.

## 9. Runtime 언어 및 구조

논의 대상:

- Rust Core
- 독립 서버
- JS/Python 임베딩
- 언어 바인딩
- 실행 프로세스 구조
- 비동기 실행
- 메모리와 자원 관리
- 배포 모델
- 런타임 장애 격리

Rust 기반 개발은 이미 진행되었다.

하지만 독립 서버가 유일한 실행 모델이어야 한다는 결정은 승인되지 않았다.

상태: Rust 구현 존재, 실행 아키텍처 재검토 필요.

## 10. Transport / Application Intent Protocol

논의 대상:

- 요청 및 응답 구조
- Intent 표현
- 타입 계약
- 직렬화
- 버전 관리
- 오류 모델
- 스트리밍
- 실시간 통신
- 요청 취소
- 재시도
- 멱등성
- 서버와 클라이언트의 호환성

중요한 원칙:

기존 REST API를 단순히 다른 이름으로 바꾸는 데 그쳐서는 안 된다.

상태: 상세 프로토콜 미확정.

## 11. Migration

논의 대상:

- 데이터 스키마 변경
- 선언 변경

- 위험한 변경 탐지

상태: 최종 정책 미확정.

## 12. Extension ABI

논의 대상:

- Rust와 JS/Python 연결
- 사용자 정의 기능 등록
- 확장 모듈 호출
- 타입 변환
- 오류 전파
- 비동기 함수
- 실행 격리
- 버전 호환성
- 성능과 경계 비용

기존 감사에서는 실제 Extension ABI가 구현되지 않았다고 보고되었다.

상태: 미구현 또는 설계 미완료. 실제 코드 재검증 필요.

## 13. Transaction 및 Side Effect

논의 대상:

- 이벤트 발행
- 재시도
- 중복 실행 방지
- 보상 트랜잭션
- 장기 실행 작업
- 부작용 선언 및 검증

상태: 세부 의미와 실행 정책 미확정.

## 14. Frontend Cache 및 동기화

논의 대상:

- 프론트엔드 데이터 캐시
- 변경 후 무효화
- 재조회
- 낙관적 업데이트
- 실시간 동기화
- 일관성 수준
- 구독 모델
- 여러 호출자 간 상태 반영
- 서버와 클라이언트 계약

중요한 원칙:

AIP는 단순한 백엔드 프레임워크가 아니라 프론트엔드 라이브러리와 통신 규약까지 포함하는 통합 개발 체계를 지향한다.

상태: 미확정.

또한 기존 Java 약 2만 줄 규모의 기능이 약 1천 줄의 `.aip` 선언으로 축약되었다는 보고가 있다.

이 수치는 특정 비교 사례이며 일반적인 코드 감소율을 증명하는 것은 아니다.

### 보고된 핵심 문제

#### A. 호출자 중심 요청 조합이 구현되지 않음

현재 클라이언트는 서버에 미리 정의된 이름의 Intent만 호출할 수 있다고 보고되었다.

특히 D-P8이라는 결정에서 클라이언트의 임의 쿼리를 금지했다고 한다.

무제한 쿼리를 금지하는 것 자체는 보안상 타당할 수 있다.

그러나 현재 구조가 호출자의 안전한 요청 조합까지 막는다면 AIP의 최초 목적과 충돌한다.

가장 중요한 검토 대상이다.

#### B. 독립 DSL 및 컴파일러 중심으로 설계가 이동함

AIP를 별도의 `.aip` 언어로 정의하는 구조가 만들어졌다.

이 자체가 잘못되었다고 단정할 수는 없다.

하지만 기존 JS/Python 생태계에서 자연스럽게 사용하는 프레임워크라는 원래 목표가 충분히 구현되지 않았다고 보고되었다.

#### C. JS/Python 확장 경로 부족

실제 Extension ABI가 없고 일부 확장이 런타임 내부에 하드코딩되어 있다고 보고되었다.

#### D. 자연어의 문법화 누락

창시자가 강조했던 자연어적 의도와 맥락의 공식적인 구조화가 설계에 반영되지 않았다고 보고되었다.

#### E. 실행 구조의 승인 없는 확정

독립 서버 중심 아키텍처가 창시자의 명시적 승인 없이 선택되었다고 보고되었다.

### 기존 문서의 문제

다음 문서에는 최초 의도와 충돌할 가능성이 있는 해석이 포함되어 있다고 보고되었다.

- design_draft.md
- full_context_handoff.md

특히 다음과 같은 표현을 검토해야 한다.

- 특정 비즈니스 동작은 반드시 서버에서 사전 정의되어야 한다는 해석
- AIP를 GraphQL과 유사한 쿼리 언어로 이해해서는 안 된다는 해석

이러한 문장은 일부 상황에서는 타당할 수 있지만, 최초의 호출자 중심 개발 목표 자체를 배제하는 근거가 되어서는 안 된다.

GraphQL을 그대로 복제하지 않는 것과 GraphQL에서 영감을 받은 호출자 중심 데이터 선택을 금지하는 것은 다른 문제다.

# PART V. 왜 설계가 어긋났는가

## 11. 목적과 수단의 역전

과거 설계 논의에서는 다음 기술들이 등장했다.

- DSL
- Parser
- AST
- Typed IR
- Semantic Analyzer
- Execution Planner
- Runtime
- Code Generation
- Extension ABI

이 기술들은 필요에 따라 사용할 수 있는 구현 수단이다.

그러나 논의가 진행되면서 이러한 구성 요소를 만드는 일이 AIP 자체의 목표처럼 취급되었다.

그 결과 원래 목적이었던 다음 질문이 후순위로 밀렸다.

**프론트엔드에서 필요한 데이터와 동작을 표현하면 서버에 매번 API를 추가하지 않아도 되는가?**

앞으로 모든 기술적 결정을 이 질문과 연결해 검토해야 한다.

예를 들어 IR을 설계한다면 다음을 설명해야 한다.

- 왜 필요한가?
- 호출자 중심 실행에 어떤 도움이 되는가?
- 서버의 보안 통제에 어떤 도움이 되는가?
- JS/Python 생태계와 어떻게 연결되는가?
- IR이 없을 때의 실제 문제가 무엇인가?
- 더 단순한 대안은 없는가?

기술적 정교함 자체를 성공 기준으로 삼지 마라.

# PART VII. 반드시 다시 검토할 핵심 질문

## 13. 호출자 중심 모델

다음 세 가지를 비교하라.

A. 읽기는 조합 가능하고 쓰기는 사전 선언된 Command만 허용

B. 읽기와 단순 쓰기를 모두 정책 안에서 조합 가능하게 허용

C. 더 일반적인 Intent 기반 실행 모델을 제공하되 안전한 의미 체계와 실행 제한을 도입

어느 것도 자동으로 정답으로 취급하지 마라.

특히 C는 단순한 자연어 추론 엔진이나 무제한 명령 실행 모델이어서는 안 된다.

각 방식에 대해 다음을 분석하라.

- 최초 철학과의 정합성
- 필요한 백엔드 개발량
- 보안 위험
- 비즈니스 규칙 처리
- 구현 난이도
- 확장성
- 디버깅
- AI 개발 편의성

## 14. 문법과 생태계의 관계

다음 모델을 비교하라.

A. 독립 `.aip` DSL 중심

B. TypeScript/Python API 중심

C. 독립 AIP 의미 모델과 여러 공식 작성 방식

이전 논의에서는 C에 가까운 방향을 긍정적으로 검토했다.

하지만 C를 구현하는 과정에서 문법과 표현 방법이 지나치게 다양해지면 AI First 철학과 충돌할 수 있다.

따라서 여러 작성 방식을 지원하더라도 canonical한 표준 표현과 명확한 우선순위를 정의할 필요가 있는지 검토하라.

## 15. Rust 엔진의 역할

다음 사항을 구분하라.

- Rust가 실행해야 하는 작업
- JS/Python이 실행해야 하는 작업
- 서버 측에서만 수행해야 하는 작업
- 클라이언트가 표현할 수 있는 작업
- 프로토콜로 전달할 정보
- 공통 IR이 담당할 정보

Rust가 모든 일을 수행하는 것이 반드시 최적은 아니다.

그러나 Rust를 선택한 이유와 이미 구현한 자산도 존중해야 한다.

## 16. 자연어의 문법화

# 최종 강조

AIP는 단순한 AI 친화적 백엔드 프레임워크가 아니다.

AIP는 단순한 Rust 기반 DSL 컴파일러도 아니다.

AIP는 단순한 GraphQL 변형도 아니다.

AIP는 단순한 CRUD 자동화 도구도 아니다.

**AIP는 기존 프론트엔드와 백엔드의 개발 경계를 재정의하고, 호출자가 필요한 데이터와 동작을 안전하게 표현할 수 있도록 하며, 반복적인 서버 구현을 공통 엔진으로 흡수하여 애플리케이션별 백엔드 유지보수를 극단적으로 줄이려는 AI 중심 통합 프레임워크다.**

이를 위해 Application Intent Protocol, SPR, Rust Core, JS/Python 생태계, AI 친화적인 문법과 표준 기능을 함께 설계한다.

하지만 그 어떤 기술적 선택도 최초 목적보다 중요하지 않다.

**창시자의 의도를 기술적 관습으로 대체하지 마라.**

기존 구현을 무조건 폐기하지도, 기존 구현에 맞춰 최초 철학을 왜곡하지도 마라.

먼저 충분히 이해하고 분석한 뒤, 근거를 제시하고 설계 승인을 요청하라.
