# AIP — 창시자 의도 복구 및 설계 고도화 통합 지침

**기준일:** 2026-10-03  
**대상:** Claude Code, Codex  
**목적:** 창시자의 최초 철학을 정확하게 복구하고, 기존 설계를 재검토하여 AIP를 고도화한다.

---

# 0. 가장 중요한 지시

이 문서는 AIP 창시자가 여러 차례 설명한 최초 목적과 추가 결정을 통합한 것이다.

기존 코드, 기존 설계 문서, 에이전트 간 합의보다 **창시자가 직접 밝힌 목적과 원칙을 우선한다.**

단, 이 문서에도 세 가지 수준의 정보가 존재한다.

- **[FOUNDER]** 창시자가 직접 설명하거나 명시적으로 결정한 내용
- **[DIRECTION]** 창시자의 철학에 부합하는 설계 방향이지만 세부 사항은 검증이 필요한 내용
- **[OPEN]** 아직 확정되지 않았거나 에이전트의 기술적 검증이 필요한 내용

이 세 가지를 절대로 혼동하지 마라.

특히 에이전트가 기술적으로 합의했다는 이유만으로 미결정 사항을 창시자의 승인 사항으로 변경하지 마라.

기존 구현이 현재 요구사항과 충돌한다면 기존 구현을 정답으로 가정하지 말고, 충돌을 보고하고 수정 방향을 제안하라.

이번 작업의 목적은 단순히 현재 코드를 완성하는 것이 아니다.

**AIP가 원래 해결하려던 문제를 실제로 해결하는 프레임워크가 되도록 설계를 고도화하는 것**이다.

# 1. AIP가 존재하는 이유

## 1.1 AI First의 정확한 의미 [FOUNDER]

AIP는 AI가 소프트웨어를 작성하고 유지보수하는 시대에 맞춰 설계하는 프레임워크다.

그러나 AI First는 다음을 의미하지 않는다.

- 인간 개발자가 사용하기 어려운 프레임워크
- 인간의 가독성을 포기한 문법
- AI만 사용할 수 있는 프로그래밍 언어
- 기존 프레임워크에 AI 코드 생성 기능을 추가한 제품
- AI가 기존의 복잡한 구조를 더 빠르게 작성하도록 돕는 것만을 목표로 하는 제품

창시자의 문제의식은 더 근본적이다.

기존 프레임워크는 인간 개발자가 코드를 작성하고 이해하고 유지보수하는 것을 주요 전제로 발전했다.

AI가 구현과 수정의 상당 부분을 담당하는 시대에는 이 전제 자체를 재검토할 필요가 있다.

AIP는 다음을 추구한다.

**AI가 기존 구조의 코드를 더 잘 작성하게 만드는 것에 그치지 않고, 애초에 작성하고 유지보수해야 하는 코드 자체를 구조적으로 줄인다.**

특히 프론트엔드와 백엔드 사이의 이중 구현과 이중 유지보수를 최소화한다.

이는 인간 개발자의 사용성을 포기한다는 의미가 아니다.

인간과 AI 모두가 이해하고 검증할 수 있으면서도 불필요한 구현 작업을 줄이는 것이 목표다.

## 1.2 핵심 문제: 프론트엔드와 백엔드의 중복 구현 [FOUNDER]

일반적인 웹 애플리케이션에서는 새로운 기능을 개발할 때 다음 작업이 반복된다.

1. 프론트엔드가 필요한 데이터를 정의한다.
2. 백엔드가 해당 데이터를 제공할 API를 구현한다.
3. 양쪽에서 요청과 응답의 계약을 관리한다.
4. 기능 변경 시 프론트엔드와 백엔드를 함께 수정한다.
5. 유사한 기능에도 새로운 API와 구현이 추가된다.

AI가 코드를 작성한다고 해서 이러한 구조적 중복이 자동으로 사라지는 것은 아니다.

AIP는 이 구조를 재검토한다.

프론트엔드가 필요한 데이터와 동작을 정형화된 표현으로 요청하고, 서버는 공통 실행 엔진과 정책을 통해 이를 처리하도록 한다.

가능한 많은 표준 기능을 프레임워크에 내장하여 애플리케이션별 백엔드 구현을 최소화한다.

단, **백엔드 자체를 없애려는 것은 아니다.**

서버는 계속해서 다음 책임을 가진다.

- 인증과 인가
- 데이터 접근 통제
- 비즈니스 불변조건
- 데이터 무결성
- 트랜잭션
- 실행 비용과 자원 제한
- 외부 시스템 연동에 대한 통제
- 실행과 운영의 안정성

핵심은 책임을 제거하는 것이 아니라 반복 구현을 공통화하는 것이다.

## 1.3 설계 평가의 최우선 질문 [FOUNDER]

새로운 설계 요소를 제안할 때마다 다음을 검토하라.

1. 이 기능이 기존의 어떤 반복 구현을 없애는가?
2. 새 화면이나 기능을 추가할 때 서버 코드를 얼마나 덜 수정하게 되는가?
3. 프론트엔드와 백엔드의 계약 중복이 줄어드는가?
4. AI가 임의로 결정해야 하는 구현 방식이 줄어드는가?
5. 인간 개발자도 이해하고 검증할 수 있는가?
6. 보안과 데이터 무결성이 유지되는가?
7. 단순히 복잡성을 다른 계층으로 옮긴 것은 아닌가?

이 질문에 답하지 못하는 추상화는 도입 필요성을 재검토해야 한다.

# 2. 창시자의 최초 7가지 원칙

다음 원칙은 창시자가 직접 설명한 최초 의도를 기준으로 재구성한 것이다. 기존 설계 문서의 기술적 해석보다 우선한다.

## 원칙 1. 애플리케이션별 백엔드 개발 최소화 [FOUNDER]

AIP 서버를 설치하고 설정하면 공통 기능을 수행할 준비가 된 서버가 실행되어야 한다.

프론트엔드가 필요한 데이터와 동작을 표현함으로써 많은 기능을 별도의 서버 API 구현 없이 사용할 수 있어야 한다.

GraphQL의 데이터 선택 및 조합 개념, CQRS의 관심사 구분 등에서 영감을 받았지만, 이를 그대로 복제하려는 것은 아니다.

목표는 백엔드의 존재를 없애는 것이 아니라 애플리케이션별 반복 구현과 유지보수를 최소화하는 것이다.

## 원칙 2. 새로운 Application Intent Protocol [FOUNDER]

AIP는 단순히 REST 엔드포인트를 자동 생성하는 프레임워크가 아니다.

프론트엔드가 필요한 데이터와 동작을 표현할 수 있는 별도의 통신 모델을 지향한다.

다만 클라이언트가 표현할 수 있다는 사실과 클라이언트에게 실행 권한이 있다는 사실은 다르다.

서버가 최종적으로 허용 범위와 실행 방식을 결정한다.

## 원칙 3. Rust 엔진과 JS/TS·Python 생태계 [FOUNDER]

핵심 실행 엔진은 Rust를 활용하는 방향으로 구상했다.

개발자는 JS/TS 및 Python 생태계를 자연스럽게 활용할 수 있어야 한다.

특히 JS/TS 개발 경험을 중요하게 고려한다.

Rust 엔진을 사용한다는 사실이 개발자에게 불필요한 복잡성을 강요해서는 안 된다.

## 원칙 4. AI를 위한 정형화와 선택 최소화 [FOUNDER]

AI가 같은 기능을 구현할 때 수많은 패턴 중 하나를 임의로 선택해야 하는 상황을 줄인다.

표준 기능과 정형화된 문법을 최대한 제공한다.

핵심은 모든 자유를 제거하는 것이 아니라 **근거 없이 발생하는 구현 다양성을 최소화하는 것**이다.

가능한 경우 하나의 명확한 표준 표현을 제공한다.

표준으로 해결할 수 없는 문제에는 기존 언어의 확장성을 활용한다.

## 원칙 5. 자연어 메타데이터의 구조화 [FOUNDER]

일반적인 주석은 어느 선언이나 코드에 속하는 설명인지 모호해질 수 있다.

AIP는 설명을 특정 선언에 구조적으로 귀속시킬 수 있는 공식적인 문법적 위치를 제공한다.

그러나 다음을 명확히 한다.

- 자연어 메타데이터 작성은 선택 사항이다.
- 설명 작성을 강제하지 않는다.
- 자연어의 의미를 자동 검증하는 기능을 필수로 요구하지 않는다.
- 자연어 설명을 실행 권한이나 보안 정책의 근거로 사용하지 않는다.

목표는 설명의 소속과 목적을 명확하게 하는 것이다.

## 원칙 6. SPR: Specification–Presentation–Runtime [FOUNDER]

AIP의 개념적 구성은 다음과 같다.

**Specification**

서버 측 데이터 모델, 허용 범위, 권한, 정책, 업무 규칙, 확장 계약 등을 정의한다.

**Presentation**

프론트엔드가 필요한 데이터와 동작을 AIP 문법으로 표현한다.

**Runtime**

요청을 검증하고 정책에 따라 안전하게 실행한다.

SPR은 책임을 이해하기 위한 기본 모델이다.

구체적인 패키지 구성이나 내부 구현을 SPR이라는 이름만으로 성급하게 고정하지 마라.

## 원칙 7. JS/TS·Python 확장성 [FOUNDER]

표준 기능으로 처리할 수 없는 복잡하거나 특수한 로직은 JS/TS 또는 Python으로 작성할 수 있어야 한다.

이것은 임시 우회 수단이 아니다.

AIP가 공식적으로 제공해야 할 확장 구조다.

확장 기능 역시 서버의 보안 정책과 계약을 준수해야 한다.

# 3. AIP의 기본 실행 구조

## 3.1 Spring Boot와 비교한 개발 경험 [FOUNDER]

창시자가 명시적으로 설명한 구조다.

Spring Boot 프로젝트를 설치하고 설정하면 애플리케이션 서버가 특정 포트에서 실행된다.

아직 기능을 구현하지 않았다면 해당 애플리케이션은 제공할 기능이 거의 없다.

AIP도 프레임워크를 설치하고 필요한 설정을 마치면 독립적인 포트에서 서버가 실행되는 경험을 지향한다.

차이점은 AIP 서버가 처음부터 풍부한 표준 기능을 내장한다는 것이다.

데이터베이스 연결, 데이터 모델, 권한 정책 등 필요한 설정은 당연히 존재한다.

하지만 개발자가 화면마다 컨트롤러와 서비스 및 API를 반복적으로 구현하지 않도록 설계한다.

이것이 창시자가 원하는 백엔드 프레임워크 경험이다.

## 3.2 프론트엔드 전용 라이브러리 [FOUNDER]

AIP에는 프론트엔드 전용 호출 라이브러리가 필요하다.

프론트엔드는 기존 REST API 호출 코드를 반복적으로 작성하는 대신 AIP의 정형화된 문법으로 필요한 데이터와 동작을 표현한다.

이 라이브러리는 AIP 프로토콜을 사용하는 공식적인 개발 인터페이스다.

따라서 AIP는 적어도 개념적으로 다음 요소를 가진다.

1. AIP 백엔드 서버 프레임워크
2. AIP 프론트엔드 라이브러리
3. Application Intent Protocol
4. 공통 실행 엔진과 계약·정책 체계

이 구조를 독립 서버와 임베디드 라이브러리 중 무엇을 선택할지의 단순한 양자택일 문제로 다시 취급하지 마라.

독립 실행 서버와 프론트엔드 라이브러리는 서로 대체하는 요소가 아니다.

Node/Python 패키지 내부에서 서버를 자동 기동하는 방식 등은 개발 편의 기능으로 별도 검토할 수 있다.

## 3.3 프론트엔드 표현의 역할 [FOUNDER]

프론트엔드의 AIP 표현은 단순한 API 이름과 파라미터 전달에 머물러서는 안 된다.

창시자는 프론트엔드에서 작성하는 간결한 표현이 기존에 백엔드에서 반복적으로 작성하던 상당 부분을 대체하기를 원한다.

예를 들어 다음 요구사항을 검토해야 한다.

- 특정 필드 선택
- 관계 데이터 조회
- 조건부 필터링
- 정렬과 페이지네이션
- 서버가 허용한 단순 데이터 변경
- 표준 동작의 호출과 조합
- 복잡한 업무 로직에 대한 확장 호출

단, 프론트엔드에 무제한 실행 권한을 부여하는 것이 아니다.

서버는 요청을 정책과 계약에 따라 검증하고 실행한다.

# 4. 표준 기능의 철학

## 4.1 가능한 많은 기능을 미리 제공한다 [FOUNDER]

창시자는 AIP에 최대한 풍부한 표준 기능을 제공하기를 원한다.

기존에 개발자가 반복적으로 작성하던 로직을 가능한 한 프레임워크의 공통 기능으로 흡수한다.

검토할 범위에는 다음이 포함된다.

- 조회와 데이터 조합
- 생성·수정·삭제
- 조건과 분기
- 반복과 컬렉션 처리
- 검증과 변환
- 관계 데이터 처리
- 업무 동작
- 트랜잭션
- 일반적인 비동기 작업과 외부 연동

이 목록은 모든 기능의 구체적인 구현이 승인되었다는 뜻이 아니다.

표준화할 가치가 있는 기능을 폭넓게 탐색하라는 요구다.

## 4.2 Rust 엔진과 간결한 작성 문법 [FOUNDER]

개발자가 반복 동작의 내부 구현을 매번 작성하는 대신, AIP가 제공하는 정형화된 표현으로 기능을 사용하도록 한다.

공통 기능의 구현은 가능한 한 엔진과 프레임워크가 담당한다.

그러나 모든 제어 흐름을 Rust로 직접 실행해야 한다는 기술적 결론까지 내린 것은 아니다.

Rust와 JS/TS·Python 사이의 실행 경계는 실제 비용과 확장성을 검증하여 설계한다.

## 4.3 기존 언어의 확장성을 보존한다 [FOUNDER]

AIP의 표준 기능만으로 모든 요구사항을 해결하려고 억지로 제한하지 마라.

표준 기능이 적합하지 않거나 부족한 경우 JS/TS 또는 Python으로 자연스럽게 확장할 수 있어야 한다.

확장 코드를 작성한다는 이유만으로 매번 특별한 예외 승인이나 복잡한 절차를 요구하는 구조는 지양한다.

다만 타입, 권한, 실행 비용, 트랜잭션, 데이터 접근 계약 등 필요한 기술적 제약은 유지한다.

# 5. AIP 문법 설계

## 5.1 문법의 최우선 목적 [FOUNDER]

AIP 문법은 AI가 코드와 정형화된 메타데이터만으로 최대한 많은 의도와 계약을 명확하게 파악할 수 있도록 설계한다.

AI가 추측해야 하는 부분을 줄여야 한다.

백엔드의 반복 구현이 줄어드는 만큼, 프론트엔드 표현과 서버 계약이 명확해야 한다.

다음 요소를 중요하게 평가한다.

- 선언의 소속이 명확한가?
- 같은 개념이 일관된 방식으로 표현되는가?
- 타입과 제약을 쉽게 파악할 수 있는가?
- 암묵적인 동작이 과도하지 않은가?
- AI가 사용 가능한 표준 기능을 탐색하기 쉬운가?
- 잘못된 표현을 정적으로 탐지하기 쉬운가?
- 인간 개발자도 이해할 수 있는가?
- 불필요하게 장황하지 않은가?

## 5.2 선언형 A형 문법 선호 [FOUNDER]

이전 토론에서 창시자는 절차형 함수와 Java를 연상시키는 B형보다 선언형 A형을 선호한다고 밝혔다.

따라서 선언형이고 구조가 명확한 문법을 우선 검토한다.

단, 과거 예시를 현재 문법의 확정 사양으로 취급하지 마라.

정확한 문법과 표현 방식은 에이전트 간 상호 검토를 통해 고도화한다.

## 5.3 독립 `.aip` 파일과 JS/Python의 관계 [OPEN]

AIP 고유의 정형화된 표현 체계를 유지한다는 방향은 분명하다.

하지만 그 표현을 반드시 독립 `.aip` 파일로만 작성해야 한다고 최종 확정하지는 않았다.

다음 대안을 검증하라.

- 독립 선언형 AIP 문법
- JS/TS·Python 내부의 정형화된 선언 방식
- 공통 의미 모델을 공유하는 여러 작성 방식

여러 방식을 지원할 경우 같은 의미를 여러 형태로 작성하면서 AI의 선택 부담이 증가할 수 있다.

따라서 표현 다양성을 무조건 장점으로 보지 마라.

공통 의미 모델이나 Typed IR이 필요하다면 그 이유와 비용을 검증하라.

## 5.4 문법 설계의 자율 고도화 [FOUNDER]

창시자는 문법의 세부 사항을 직접 일일이 결정하기보다 Claude Code와 Codex가 서로 독립적으로 검토하고 비평하기를 원한다.

두 에이전트는 다음을 수행하라.

1. 독립적인 설계안 제시
2. 상대 설계의 모호성과 반례 탐색
3. 실제 애플리케이션 사례로 검증
4. 중복 구현 감소 효과 비교
5. 보안과 실행 가능성 검증
6. 개선안 도출
7. 합의점과 남은 이견 기록

창시자는 핵심 철학과 제품 경험에 영향을 미치는 결정에 집중한다.

에이전트 간 합의는 창시자 승인과 동일하지 않다.

# 6. 자연어 메타데이터

## 6.1 기본 목적 [FOUNDER]

일반 주석은 설명이 정확히 어느 선언이나 표현에 연결되는지 모호할 수 있다.

AIP는 설명을 작성할 수 있는 정형화된 위치를 제공한다.

예를 들어 다음과 같은 구조를 검토할 수 있다.

```text
resource User {
  command delete {
    docs {
      summary: "사용자를 삭제한다"
      rationale: "권한 없는 삭제를 방지한다"
    }
  }
}
```

이 예시는 개념 설명을 위한 가상 문법이며 최종 사양이 아니다.

중요한 것은 `docs`라는 키워드 자체가 아니라 메타데이터가 해당 선언에 명확하게 귀속된다는 사실이다.

## 6.2 강제하지 않는다 [FOUNDER]

메타데이터는 선택적으로 작성한다.

설명을 작성하지 않았다는 이유만으로 문법 오류를 발생시키지 않는다.

특정 길이의 설명이나 장황한 문서를 강제하지 않는다.

## 6.3 자연어 의미 검증은 기본 요구사항이 아니다 [FOUNDER]

자연어 설명의 참·거짓이나 의미적 정합성을 자동 판정하는 기능을 기본적으로 요구하지 않는다.

자연어를 요청마다 LLM이 해석하여 보안상 실행 여부를 결정하는 모델도 기본 실행 구조로 삼지 않는다.

실행 계약과 설명용 메타데이터를 구분한다.

# 7. AI를 위한 선택적 검증 계층

## 7.1 별도의 검증 기능을 제공한다 [FOUNDER]

AIP는 AI가 작성한 코드와 선언에 이상한 부분이 없는지 개발자가 편리하게 점검할 수 있는 구조를 지향한다.

이는 자연어 메타데이터의 의미 검증과 별개다.

검증 계층은 필요할 때 선택적으로 사용할 수 있어야 한다.

검토할 검사 항목의 예시는 다음과 같다.

- 존재하지 않는 선언이나 필드 참조
- 잘못된 타입 사용
- 계약 간 불일치
- 중복 정의
- 사용되지 않는 선언
- 불필요하게 복잡한 표현
- 권장 표준 기능을 우회한 반복 구현
- 잘못된 설정이나 지원하지 않는 기능 사용

구체적인 검사 범위와 자동 수정 가능 여부는 에이전트가 설계하고 검증한다.

## 7.2 필수 검증과 선택적 검증의 구분 [FOUNDER]

다음 두 계층을 혼동하지 마라.

**필수 실행 안전성 검증**

- 인증과 인가
- 타입 및 입력 제약
- 데이터 무결성
- 권한 범위
- 트랜잭션 안전성
- 실행 비용 및 자원 제한

필수적인 검증은 서버에서 시행한다.

**선택적 개발 지원 검증**

- 정적 분석
- 구조적 일관성 검사
- 중복 구현 탐지
- AI 작성 코드 점검
- 개발 경험 개선을 위한 권고

선택적 검증을 사용하지 않았다는 이유로 필수 보안 검증이 생략되어서는 안 된다.

# 8. 오픈소스 운영 철학

## 8.1 자유로운 오픈소스 [FOUNDER]

AIP는 오픈소스 프로젝트로 개발한다.

창시자는 외부 개발자의 기여를 환영한다.

현재 별도의 수익 모델이나 상업화를 주요 목표로 삼고 있지 않다.

프로젝트의 기술적 완성도와 자유로운 활용, 생태계 발전을 중요하게 생각한다.

## 8.2 라이선스 [OPEN]

구체적인 오픈소스 라이선스는 아직 선택하지 않았다.

MIT와 Apache-2.0 등 적합한 라이선스의 조건을 비교할 수 있다.

다만 창시자가 자유로운 이용을 원한다는 사실만으로 특정 라이선스를 자동 선택하지 마라.

## 8.3 공개 범위와 보안의 구분 [DIRECTION]

프레임워크의 소스코드가 공개되어 있다는 사실과 운영 중인 AIP 서버에 누구나 접근할 수 있다는 사실은 다르다.

실제 서버는 인증, 권한, 리소스 정책에 따라 접근을 제한해야 한다.

# 9. 기존 결정 질문에 대한 통합 답변

이 절은 기존 `90-founder-questions.md`의 번호 1~25를 기준으로 한다.

아래에서 '방향'은 최종 세부 설계가 아니라 창시자의 의도에 부합하는 방향 또는 이전에 제시된 잠정 권고를 뜻한다.

## DD-01: 읽기 조합

[FOUNDER] 채택 방향.

**2. 신규 필드 기본 비공개**

[DIRECTION] 안전한 기본값으로 제안한다.

새로운 필드가 의도치 않게 외부로 노출되지 않도록 설계한다.

구체적인 공개 정책은 기술적으로 검증한다.

**3. 첫 출시의 직접 요청 작성 주체**

[OPEN] 오픈소스로 공개한다는 사실은 확정되었지만, 첫 출시부터 불특정 서드파티 클라이언트의 동적 요청까지 모두 지원할지는 별개다.

초기 지원 범위와 장기 확장성을 구분해 제안하라.

**4. JS/Python 확장 읽기**

[FOUNDER] 표준 기능으로 표현하기 어려운 조회에 대한 공식 확장 구조를 제공한다.

권한과 실행 비용 제한은 유지한다.

## DD-02: 쓰기 모델

**5. 단순 변경의 표준 표현**

[FOUNDER] 가능한 한 지원한다.

단순 변경마다 별도의 서버 Command를 반복 구현하는 구조를 피한다.

**6. 복잡한 변경과 동작 조합**

[FOUNDER] 가능한 많은 표준 동작을 제공하고 프론트엔드가 이를 간결하게 표현할 수 있도록 한다.

[OPEN] 여러 변경의 원자적 조합 범위, 비즈니스 불변조건, 트랜잭션 경계는 구체적인 기술 설계가 필요하다.

복잡한 업무 로직을 공식 JS/TS·Python 확장으로 처리할 수 있어야 한다.

## DD-03: 운영 읽기

**7. 미등록 읽기 요청 허용**

[DIRECTION] 서버 정책상 허용된 범위에서 새로운 조회 조합을 처리하는 모델을 지향한다.

다만 운영 환경의 보안·성능·비용 문제를 검증한다.

배포 시 등록만 허용하는 구조가 화면별 백엔드 작업을 다시 증가시키는지도 평가한다.

## DD-04: 작성 방식

**8. AIP 고유 문법 유지**

[FOUNDER] 정형화된 AIP 고유 표현 체계를 지향한다.

[OPEN] 독립 `.aip` 파일이 반드시 필요한지는 확정하지 않는다.

**9. 서버 규칙 작성 방식**

[FOUNDER] 명확하고 일관된 선언형 문법, JS/TS·Python 생태계와의 자연스러운 연결을 원한다.

[OPEN] 최종 문법은 Claude와 Codex의 반복 검토 및 실제 예제로 고도화한다.

**10. TS/Python 초기 지원 범위**

[FOUNDER] 두 생태계를 지원하는 것이 목표이며 특히 JS/TS가 중요하다.

[OPEN] 첫 출시부터 완전한 기능 동등성을 제공할지는 기술 검증과 개발 비용을 기준으로 결정한다.

## DD-05: 자연어 메타데이터

**11. 설명 문장의 표현**

[FOUNDER] 특정 선언에 구조적으로 귀속되는 선택적 메타데이터를 제공한다.

**12. 자연어 메타데이터의 역할**

[FOUNDER] 정해진 문법적 위치를 제공한다.

자연어 의미 검증은 기본 요구사항이 아니다.

[OPEN] 구체적인 메타데이터 키와 타입은 문법 설계 과정에서 결정한다.

**13. 자연어를 실행 규칙으로 사용하는가**

[FOUNDER] 자연어를 매 요청마다 해석하여 실행 규칙이나 보안 판단으로 사용하는 구조를 기본 모델로 삼지 않는다.

자연어 설명과 실행 가능한 계약은 구분한다.

## DD-07: 일괄 처리

**14. 부분 실패 처리**

[DIRECTION] 하나의 원자적 작업이라면 전체 성공 또는 전체 실패를 기본으로 검토한다.

[OPEN] 부분 성공이 필요한 배치 작업을 별도 모드로 제공할지 검증한다.

## DD-06: 실행 환경

**15. 초기 배포 환경**

[DIRECTION] 일반 서버와 컨테이너 환경을 우선 검토한다.

서버리스 지원은 기술적 제약과 수요를 분석한다.

**16. 서버 실행 방식**

[FOUNDER] AIP는 Spring Boot처럼 설정 후 자체 포트에서 실행되는 서버 프레임워크와 별도의 프론트엔드 라이브러리를 제공한다.

[OPEN] 설치 편의성, 자동 기동, 추가 임베딩 지원 등의 구체적인 배포 방식은 기술적으로 검증한다.

**17. 확장 작성 주체**

[FOUNDER] 앱 개발자와 AI가 JS/TS·Python으로 확장 기능을 작성할 수 있어야 한다.

[OPEN] 서드파티 확장 패키지 생태계의 초기 지원 범위는 미정이다.

## DD-12: 배포와 호환성

**19. 데이터 손실·권한 확대 승인**

[DIRECTION] 명시적 승인과 변경 영향 확인을 기본 정책으로 검토한다.

**20. 롤백**

[DIRECTION] 안전한 롤백 경로를 제공하는 것을 목표로 한다.

삭제된 데이터까지 자동 복구할 수 있다고 가정하지 않는다.

**21. 구버전 필드 호환성**

[OPEN] 명시적인 호환성과 폐기 정책이 필요하다.

정확한 지원 기간은 아직 정하지 않았다.

## DD-11: 데이터 동기화

**22. 화면 동기화 수준**

[DIRECTION] 재조회 기반 동기화를 기본으로 검토한다.

실시간 동기화는 선택 기능으로 확장할 수 있는지 분석한다.

## DD-13: 프론트엔드

**23. 프론트 라이브러리의 책임**

[DIRECTION] AIP 데이터 접근, 요청 작성, 계약 처리, 상태 동기화 등을 우선 검토한다.

일반적인 UI 컴포넌트 라이브러리까지 직접 제공할지는 별도 검토한다.

**24. 프론트 환경**

[FOUNDER] AIP는 프론트엔드 전용 호출 라이브러리를 제공해야 한다.

[OPEN] React를 첫 공식 통합으로 선택할지, 프레임워크 독립 코어를 먼저 개발할지, 다른 환경을 언제 지원할지는 미정이다.

## DD-14: 권한 오류

**25. 필요한 역할 안내**

[DIRECTION] 개발자에게 유용한 오류 정보를 제공하되 비공개 리소스나 권한 구조가 노출되지 않도록 제한한다.

오류 메시지의 상세도는 서버 정책과 정보 공개 범위에 따라 결정한다.

# 10. 기존 Q0~Q9에 대한 정리

기존 질문 번호와 새로운 25개 질문 번호를 혼동하지 마라.

- **Q0 최초 7가지 원칙:** 이 문서의 1~2절을 창시자 의도 복구의 기준으로 사용한다.
- **Q1 호출자 표현 범위:** 읽기·표준 쓰기 조합을 최대화하되 서버 정책과 안전성을 유지한다.
- **Q2 정의 작성 방식:** 선언형·정형화 방향은 확인되었으며 독립 파일 여부는 미정이다.
- **Q3 A/B 문법:** 창시자는 선언형 A형을 선호한다. 과거 예시는 확정 문법으로 간주하지 않는다.
- **Q4 Rust와 JS/Python:** Rust 기반 엔진, JS/TS·Python 확장, 독립 실행 AIP 서버 및 프론트 라이브러리 구조를 기본으로 한다.
- **Q5 자연어 문법화:** 선택적 구조화 메타데이터를 제공하며 자연어 의미 검증을 강제하지 않는다.
- **Q6 SPR 계약 공유:** 공개 가능한 계약과 서버 내부 정책을 구분해야 한다. 구체적인 공개 범위는 미정이다.
- **Q7 확장 격리:** 확장은 서버 정책을 우회해서는 안 된다. 격리 기술과 실행 방식은 검증 대상이다.
- **Q8 성공 지표:** 중복 구현, 변경 비용, AI의 불필요한 설계 판단 감소를 핵심 측정 대상으로 삼는다. 수치 목표는 아직 정하지 않았다.
- **Q9 데이터베이스:** 초기 지원 DB 및 capability 모델은 기술적 검증 대상이다.

# 12. 기존 구현에서 발견된 문제

이전 Claude Code 감사 보고서에서는 다음 문제가 제기되었다.

이는 감사 보고서의 주장으로서 기록하며, 필요한 경우 실제 코드로 재검증하라.

## 12.1 서버 사전 정의 Intent에 대한 과도한 의존

클라이언트가 서버에 미리 정의된 Intent 이름과 입력만 전달하는 구조는 새로운 화면마다 서버 정의를 추가하게 만들 수 있다.

이는 프론트엔드 중심 표현과 이중 유지보수 감소라는 목표에 충분히 부합하지 않는다.

정책을 벗어나는 임의 쿼리를 금지하는 것과 정책 안에서 안전하게 조합 가능한 쿼리까지 금지하는 것을 혼동하지 마라.

## 12.2 JS/Python 생태계와의 연결 부족

독립 `.aip` 문법만으로 구성된 구현이 JS/TS·Python 개발자에게 충분히 자연스러운 경험을 제공하는지 검증해야 한다.

단, 이 문제를 해결한다는 이유만으로 AIP 고유의 정형화된 표현 체계를 폐기해서는 안 된다.

## 12.3 확장 구조 부족

표준 기능으로 표현하기 어려운 로직을 JS/TS·Python으로 구현할 수 있는 공식적인 확장 계약이 필요하다.

## 12.4 기존 구현의 성과도 보존

기존에 구현한 서버 정책, 권한 검증, Rust 실행 엔진, 표준 기능, 테스트 자산 등은 검증 후 재사용 가능성을 평가한다.

기존 설계에 문제가 있다고 해서 전체 구현을 폐기하는 결론으로 바로 이동하지 마라.

# 14. Claude Code와 Codex의 협업 방식

## 14.1 독립적인 검토

두 에이전트는 동일한 창시자 원칙을 기준으로 설계한다.

서로의 의견을 단순히 수용하는 대신 다음을 검토한다.

- 숨겨진 가정
- 최초 철학과의 충돌
- 보안 문제
- 과도한 추상화
- AI의 선택 부담 증가
- 인간 개발자의 사용성 저하
- 운영 복잡성
- 실제 구현 가능성

## 14.2 반복적인 상호 피드백

권장 과정은 다음과 같다.

1. Claude Code의 제안
2. Codex의 독립 비평
3. Claude Code의 수정 또는 반론
4. Codex의 재검토
5. 남은 이견과 검증 계획 정리

필요하면 반복하되, 단순히 라운드 수를 채우기 위해 토론하지 마라.

양쪽이 동의하더라도 검증되지 않은 가정은 그대로 기록한다.

## 14.3 창시자에게 질문하는 기준

창시자는 기술적 세부 구현을 모두 결정하는 역할이 아니다.

창시자에게 질문해야 하는 경우는 다음과 같다.

- 제품 철학을 변경해야 할 때
- 사용자 개발 경험에 중대한 차이가 발생할 때
- 두 방향이 모두 합리적이지만 가치 판단이 필요할 때
- 기존 명시적 원칙과 충돌하는 설계가 불가피해 보일 때

기술적 실험으로 해결할 수 있는 문제는 우선 실험하라.

이미 창시자가 답한 질문을 반복하지 마라.

# 17. 최종 지시

AIP는 단순한 REST 대체 문법이나 API 자동 생성기가 아니다.

AI가 소프트웨어 개발의 중요한 작성 주체가 되는 시대에 맞춰, 애플리케이션의 구현과 유지보수 구조를 다시 설계하려는 프로젝트다.

프론트엔드와 백엔드의 책임은 유지하되 반복 구현을 최소화한다.

프론트엔드는 AIP 전용 라이브러리로 필요한 데이터와 동작을 표현한다.

백엔드는 독립 실행 가능한 AIP 서버 프레임워크로서 풍부한 표준 기능을 제공하고, Rust 기반 엔진과 정책에 따라 안전하게 실행한다.

표준 기능이 부족한 부분은 JS/TS·Python으로 확장한다.

문법은 명확하고 정형화되어야 하며, AI가 불필요한 추론과 선택을 하지 않도록 설계한다.

자연어 메타데이터는 구조적으로 작성할 수 있게 하되 강제하지 않는다.

별도의 선택적 개발 검증 계층을 제공하되 필수 실행 안전성 검증과 구분한다.

AIP는 자유로운 오픈소스 프로젝트로 발전시키며 외부 기여를 환영한다.

**창시자의 철학을 기술적 구현의 편의에 맞춰 변경하지 마라. 기술적 구현을 창시자의 철학을 실현하는 방향으로 고도화하라.**

이 문서를 기준으로 먼저 기존 설계의 정합성을 재검토하고, 두 에이전트가 독립적인 비평과 검증을 거쳐 개선안을 제시하라.

승인되지 않은 대규모 코드 변경은 진행하지 마라.
