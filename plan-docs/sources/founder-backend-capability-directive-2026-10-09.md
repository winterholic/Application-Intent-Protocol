# AIP 백엔드 기능 포괄성 감사 및 선언형 실행 모델 고도화

## 0. 작업 목적

현재 AIP의 설계와 구현이 SQL, CRUD, 데이터 조회 및 Query Planner 중심으로 편향되고 있지 않은지 전면 점검하라.

AIP는 단순한 데이터 접근 프레임워크가 아니다.

AIP의 궁극적인 목표는 **기존 백엔드 애플리케이션에서 반복적으로 작성하던 로직 전반을 표준화된 선언과 공통 Runtime으로 최대한 흡수하는 것**이다.

프론트엔드 개발자 또는 AI 에이전트가 AIP의 정형화된 문법으로 필요한 데이터와 동작을 표현하면, 서버는 정책과 실행 계약을 검증한 뒤 해당 작업을 수행해야 한다.

단, 이것이 프론트엔드에 임의의 서버 코드 실행 권한을 부여한다는 의미는 아니다.

AIP 서버는 보안, 권한, 트랜잭션, 비즈니스 불변조건, 실행 비용을 최종 통제한다.

이번 작업은 AIP가 실제 백엔드 개발의 얼마나 넓은 영역을 대체하거나 단순화할 수 있는지 검증하고, 부족한 부분을 체계적으로 보완하는 것이 목적이다.

## 1. 가장 중요한 설계 원칙

### 1.1 SQL 중심 사고에서 벗어나라

AIP를 다음과 같은 제품으로 축소하지 마라.

- GraphQL과 유사한 데이터 조회 도구
- SQL Query Builder
- CRUD 자동 생성기
- ORM의 대체재
- REST API 자동 생성기
- 데이터베이스 프록시

이 기능들은 AIP의 일부가 될 수 있지만 전체가 아니다.

AIP가 해결하려는 문제는 **애플리케이션 백엔드 로직의 반복적인 작성과 유지보수**다.

SQL이 필요하지 않은 백엔드 기능도 AIP의 중요한 설계 대상이다.

### 1.2 선언형 표현과 실행 엔진의 책임 분리

가능한 한 많은 공통 동작을 AIP의 표준 기능으로 제공하라.

개발자와 AI는 구현 절차를 반복적으로 작성하기보다 의도와 실행 조건을 간결하게 표현하도록 한다.

Runtime은 해당 선언을 실행 가능한 동작으로 해석한다.

다만 모든 로직을 억지로 선언형 문법에 집어넣지는 마라.

표준화할 수 없는 복잡한 로직은 JS/TS 또는 Python으로 자연스럽게 확장할 수 있어야 한다.

### 1.3 프론트엔드와 서버 선언의 역할을 구분하라

AIP는 프론트엔드 전용 라이브러리와 독립 실행 가능한 백엔드 서버 프레임워크를 제공한다.

프론트엔드는 필요한 데이터와 동작을 표현한다.

서버는 허용 가능한 기능과 실행 정책을 정의하고 검증한다.

다음 세 가지를 구분하여 설계하라.

1. 프론트엔드에서 자유롭게 조합할 수 있는 표준 동작
2. 서버에 한 번 선언해 두고 여러 화면에서 재사용하는 업무 동작
3. JS/TS·Python으로 구현해야 하는 특수 로직

세 번째 유형이 지나치게 많다면 표준 기능의 포괄성이 부족한 것인지 검토하라.

반대로 보안이나 업무 불변조건 때문에 서버에서만 정의해야 하는 동작을 억지로 프론트엔드에 옮기지 마라.

## 3. 각 기능을 AIP 관점에서 재설계하라

단순히 기능 목록을 수집하지 마라.

각 기능에 대해 다음을 평가하라.

### 3.1 현재 일반적인 구현 방식

기존 프레임워크에서 개발자가 어떤 코드를 작성해야 하는가?

Controller, Service, Repository, Middleware, Worker, Event Handler 등 어떤 구현이 필요한가?

### 3.2 AIP에서의 이상적인 개발 경험

AIP에서는 같은 기능을 어떻게 더 간결하게 표현할 수 있는가?

- 프론트엔드 선언만으로 충분한가?
- 서버에 재사용 가능한 정책이나 계약을 선언해야 하는가?
- 공통 Runtime 기능으로 처리할 수 있는가?
- JS/TS·Python 확장이 필요한가?

### 3.3 표준화 가능성

해당 기능이 여러 프로젝트에서 반복되는가?

표준화할 때 공통으로 유지할 수 있는 의미와 동작이 무엇인가?

표준화가 오히려 지나치게 복잡한 문법을 만드는가?

### 3.4 실행 안전성

해당 기능을 호출자가 표현해도 안전한가?

서버가 검증해야 하는 권한과 제약은 무엇인가?

트랜잭션, 부작용, 재시도, 멱등성, 실행 비용을 어떻게 처리해야 하는가?

### 3.5 실제 유지보수 감소

AIP를 사용하면 어떤 코드와 계약이 사라지는가?

서버에 새로운 선언을 작성해야 한다면 기존 방식보다 어떤 점에서 유지보수가 줄어드는가?

복잡성이 Runtime이나 Specification으로 이동하기만 하는 것은 아닌가?

## 4. 기능별 표준화 등급을 분류하라

모든 기능을 하나의 문법으로 강제로 처리하지 마라.

다음 네 가지로 분류하라.

**Level 1 — Built-in Primitive**

AIP Runtime에 내장되어 별도 애플리케이션 코드 없이 사용할 수 있는 기본 기능.

**Level 2 — Declarative Composition**

여러 표준 기능을 정형화된 문법으로 조합하여 표현할 수 있는 기능.

**Level 3 — Reusable Server Specification**

보안이나 업무 규칙상 서버에서 선언해야 하지만, 일단 정의하면 여러 클라이언트가 재사용할 수 있는 기능.

**Level 4 — JS/TS·Python Extension**

표준 문법으로 표현하기 어렵거나 프로젝트 고유의 복잡성이 있는 기능.

각 기능에 대해 어느 등급이 적절한지 판단하고 근거를 기록하라.

중요한 것은 모든 기능을 Level 1로 만드는 것이 아니다.

**Level 4에 불필요하게 반복 구현이 쌓이지 않도록 Level 1~3의 표현력을 충분히 확보하는 것**이다.

## 5. 실제 백엔드 애플리케이션으로 검증하라

단순 CRUD 예제만 사용하지 마라.

최소한 다음 시나리오를 검증하라.

### 시나리오 A — 전자상거래

주문 생성 → 재고 확인 → 재고 차감 → 결제 요청 → 결제 결과 처리 → 주문 상태 변경 → 알림 발송.

결제 실패, 중복 요청, 부분 실패, 재시도, 보상 작업도 검증한다.

### 시나리오 B — 업무 승인 시스템

신청 → 조건 검증 → 승인자 결정 → 다단계 승인 → 반려 → 알림 → 감사 기록.

조건부 분기, 상태 전이, 권한, 예약 실행을 검증한다.

### 시나리오 C — SaaS 멀티테넌트

조직 생성 → 사용자 초대 → 역할 부여 → 조직별 데이터 격리 → 사용량 집계 → 요금제별 제한.

권한과 테넌트 격리가 모든 실행 경로에 적용되는지 검증한다.

### 시나리오 D — 외부 서비스 연동

외부 API 호출 → 응답 검증 → 데이터 변환 → 저장 → 이벤트 발행 → 실패 시 재시도.

Timeout, Rate Limit, Secret, Retry, Idempotency를 검증한다.

### 시나리오 E — 실시간 협업

데이터 변경 → 권한 확인 → 이벤트 발행 → 구독자 전달 → 클라이언트 상태 동기화.

연결 종료, 재연결, 이벤트 유실을 검증한다.

### 시나리오 F — 데이터와 무관한 백엔드 작업

사용자 요청 → 파일 처리 또는 외부 계산 → 장기 실행 Job → 진행 상태 조회 → 결과 반환.

SQL을 전혀 사용하지 않거나 최소한만 사용하는 시나리오에서도 AIP가 유용한지 확인한다.

각 시나리오에 대해 다음을 제시하라.

1. 기존 백엔드 구현의 구성 요소
2. AIP 프론트엔드 작성 예시
3. 필요한 AIP 서버 Specification
4. Runtime이 담당하는 표준 기능
5. JS/TS·Python 확장이 필요한 부분
6. 남아 있는 애플리케이션별 백엔드 코드
7. 보안 및 트랜잭션 경계
8. AIP가 실제로 제거한 중복 구현

코드 예시는 가상 문법인지 실제 구현된 문법인지 반드시 표시하라.

## 6. 오픈소스 조사 방식

단순히 유명한 오픈소스의 기능을 모방하지 마라.

기존 프레임워크와 라이브러리가 해결한 문제, 반복되는 추상화, 알려진 한계와 트레이드오프를 조사하라.

예를 들어 다음 영역의 프로젝트를 참고할 수 있다.

- Spring Boot / Spring Framework
- NestJS
- Django / Django REST Framework
- FastAPI
- Laravel
- Temporal
- BullMQ
- Celery
- Apache Camel
- Dapr
- Hasura
- PostGraphile
- Prisma
- Supabase
- OpenFGA
- Casbin

이 목록은 조사 후보이지 필수 의존성이나 채택 기술 목록이 아니다.

각 프로젝트의 최신 공식 문서, 실제 소스코드, 설계 문서, 테스트 및 이슈를 가능한 범위에서 확인하라.

조사 결과는 다음을 구분한다.

- 실제 소스나 공식 문서로 확인한 사실
- AIP에 적용할 수 있는 설계 아이디어
- 적용하면 안 되는 이유 또는 트레이드오프
- 추가 검증이 필요한 가설

오픈소스 코드의 라이선스와 특허 조건을 확인하라.

다른 프로젝트의 코드를 무분별하게 복사하지 마라.

**AIP의 철학에 맞는 공통 실행 모델을 만드는 것이 목표이지, 여러 프레임워크의 기능을 무작정 합치는 것이 목표가 아니다.**

## 7. 아키텍처의 포괄성 검증

현재 AIP Runtime과 Protocol이 SQL 외의 동작을 자연스럽게 표현할 수 있는지 검토하라.

특히 다음을 확인한다.

- Intent가 반드시 DB 쿼리와 연결되어야 하는 구조인가?
- SQL이 없는 작업도 동일한 실행 모델로 처리할 수 있는가?
- 비동기 작업, 이벤트, 파일, 외부 API, 상태 머신 등을 공통 실행 계약으로 표현할 수 있는가?
- 실행 결과가 즉시 반환되지 않는 작업을 처리할 수 있는가?
- 실패, 취소, 재시도, 보상 작업을 표현할 수 있는가?
- 여러 동작을 조합할 때 서버가 안전성을 검증할 수 있는가?
- Rust Runtime이 JS/TS·Python 확장 기능과 자연스럽게 연결되는가?
- 기능을 추가할 때마다 새로운 하드코딩된 Intent Handler를 만들어야 하는가?
- AIP 프론트엔드 라이브러리의 표현력이 실제로 백엔드 반복 구현을 줄이는가?

SQL 중심으로 설계된 구조가 다른 실행 영역의 확장을 방해한다면 그 구조적 원인을 분석하라.

단, 모든 동작을 하나의 범용 실행 엔진에 억지로 통합하지 마라.

공통 의미 체계가 유효한 범위와 전문 실행기가 필요한 범위를 구분하라.

## 8. AI First 관점의 추가 점검

기능을 많이 제공하는 것만으로 AI First가 실현되는 것은 아니다.

다음도 함께 검증하라.

### 8.1 발견 가능성

AI가 어떤 표준 기능을 사용할 수 있는지 쉽게 찾을 수 있는가?

### 8.2 결정의 명확성

동일한 목적을 달성하는 표준 방식이 지나치게 많지 않은가?

### 8.3 문법의 예측 가능성

유사한 기능이 일관된 문법 구조를 사용하는가?

### 8.4 검증 가능성

AI가 작성한 선언을 타입 검사, 계약 검사, 정적 분석, 테스트로 검증할 수 있는가?

### 8.5 변경 비용

기능 변경 시 AI가 여러 계층의 코드를 함께 수정해야 하는가?

### 8.6 메타데이터

자연어 설명을 필요한 위치에 선택적으로 작성할 수 있는가?

메타데이터를 작성하지 않아도 정상적으로 동작하는가?

### 8.7 확장성

표준 기능으로 해결할 수 없는 요구사항을 JS/TS·Python으로 구현할 수 있는가?

확장 과정에서 기존 AIP의 안전성과 일관성이 유지되는가?

## 9. Claude Code와 Codex의 상호 검증

두 에이전트는 독립적으로 분석한 뒤 상호 비평하라.

특히 다음 관점에서 서로의 설계를 검토한다.

- SQL 중심 편향
- CRUD 중심 편향
- 실제 백엔드 기능 누락
- 지나치게 제한적인 프론트 표현력
- 과도한 범용화
- 불필요한 DSL 복잡성
- JS/TS·Python 확장성 부족
- 보안·트랜잭션 경계의 모호성
- AI가 선택해야 하는 구현 방식의 증가
- 기존 구현을 정당화하려는 편향

합의에 도달하는 것 자체를 목표로 삼지 마라.

반례와 실제 구현 실험을 통해 검증하라.

기술적으로 판단 가능한 사항은 창시자에게 무분별하게 넘기지 말고, 근거를 갖춘 제안을 작성하라.

창시자가 이미 밝힌 철학을 다시 질문하지 마라.

## 10. 요구 결과물

### A. Backend Capability Matrix

기존 백엔드 기능 영역을 전수 조사하고 AIP의 현재 지원 수준을 정리한다.

각 항목에 다음을 포함한다.

- 기능
- 일반적인 구현 방식
- AIP의 현재 지원 상태
- 목표 표준화 Level
- 프론트 표현 가능 여부
- 서버 Specification 필요 여부
- JS/TS·Python 확장 필요 여부
- 보안 및 실행 제약
- 참고한 오픈소스
- 우선순위

### B. SQL 편향 감사 보고서

현재 AIP의 설계와 코드가 데이터베이스 중심으로 제한되는 부분을 식별한다.

SQL 외 기능을 표현하기 어려운 원인을 구체적으로 분석하라.

### C. 선언형 실행 모델 고도화 제안

조회, 변경, 비즈니스 로직, 외부 연동, 이벤트, 비동기 작업을 어떻게 표현할지 제안한다.

기존 아키텍처를 최대한 활용하되 필요한 구조 변경은 숨기지 않는다.

### D. 실제 애플리케이션 검증

앞서 제시한 6개 시나리오를 기반으로 AIP의 표현력과 한계를 평가한다.

### E. 우선순위별 구현 로드맵

기능 수를 늘리는 것보다 **백엔드 반복 구현을 가장 많이 제거하는 기능**을 우선한다.

다음 기준으로 우선순위를 평가한다.

- 실제 프로젝트에서의 반복 빈도
- 제거 가능한 코드와 계약
- AI의 구현 선택 감소 효과
- 다른 기능에서의 재사용성
- 보안 및 실행 위험
- 구현·유지보수 비용

### F. 설계상 위험과 미해결 문제

에이전트 간 이견, 구현 가능성, 성능 위험, 보안 문제, 철학과의 충돌을 정리한다.

## 11. 작업 제한

이번 단계에서는 기존 설계와 구현을 분석하고 고도화 제안을 작성한다.

창시자의 명시적 승인 없이 대규모 구조 변경을 진행하지 마라.

기존에 잘 작동하는 기능을 단순히 새로운 아키텍처가 더 아름답다는 이유로 교체하지 마라.

기능 포괄성을 확보한다는 명목으로 불필요하게 거대한 DSL이나 만능 Runtime을 설계하지 마라.

오픈소스에서 확인한 사실과 에이전트의 추론을 구분하라.

검증하지 않은 생산성 향상이나 성능 개선을 확정적으로 주장하지 마라.

## 12. 최종 평가 기준

이번 작업이 끝났을 때 다음 질문에 명확하게 답할 수 있어야 한다.

**"AIP는 SQL과 CRUD를 간단하게 만드는 프레임워크인가, 아니면 기존 백엔드 애플리케이션에서 반복적으로 작성하던 기능 전반을 선언형으로 표현하고 공통 엔진으로 실행할 수 있는 프레임워크인가?"**

후자를 목표로 설계하라.

단, 모든 업무 로직을 무조건 선언형으로 표현해야 한다는 의미는 아니다.

**표준 기능을 최대한 제공하고, 표준 기능을 조합할 수 있게 하며, 부족한 부분은 JS/TS·Python으로 자연스럽게 확장하는 구조**가 AIP의 핵심이다.

그리고 이 모든 설계는 AI 시대에 불필요한 코드 작성, 구현 선택, 프론트엔드와 백엔드의 이중 유지보수를 구조적으로 줄인다는 최초 목적에 부합해야 한다.
