## Q1. 호출자가 무엇을 얼마나 표현하나 (가장 중요)

- 배경: 지금 PoC는 호출자가 이름과 입력만 보낸다. 새 화면마다 서버 정의가 늘어난다.
- 선택지: A 읽기 조합 + 선언 Command / B 읽기·단순 쓰기 조합 + 복잡한 쓰기만 Command / C 일반 Intent 실행 모델 + 안전 의미 체계·실행 제한.
- 장단점 요약: A는 안전하고 구현이 가장 쉽지만 쓰기마다 Command가 쌓인다. B는 서버 추가량이 가장 적은 축에 들지만 쓰기 정책 표현력이 성패를 가른다. C는 표현이 가장 넓지만 트랜잭션 경계를 호출자가 사실상 설계하게 되고, 같은 의도를 여러 모양으로 쓸 위험이 크다.
- 원칙: 작동 모델과 보안이 정면으로 당기는 지점.
- 하위 질문 Q1-b: C안이 생각하시는 그림이 `topics/T01-caller-model.md` §4의 C1(읽기 조합 + 여러 쓰기 동작 묶음 + 서버가 묶음 전체 검증)과 같은가?
- 하위 질문 Q1-c: 아리아리 호출 115곳 분류 실험(T01 §7)을 결정 전에 진행할까? 코드 변경은 없다.
- 상세: `topics/T01-caller-model.md`. **2026-10-03 갱신:** 이 질문은 결정 문서의 질문으로 쪼개졌다. 읽기는 `decisions/DD-01-read-composition.md` F1~F4, 쓰기는 `decisions/DD-02-write-scope.md` F1·F2. 두 문서 모두 Codex와 3라운드 토론 후 에이전트 합의 상태다

## Q2. 정의를 무엇으로 쓰나

- 배경: 10-02에는 `.aip`를 정본 언어로 삼지 않기로 기록했다(D-R6). 10-03 원문은 "`.aip`를 무조건 폐기하거나 유지한다고 단정하지 말라", "AIP 고유 문법을 제거해서도 안 된다", "선언 블록 DSL 선호에 합의"라고 한다. 두 기록이 어긋난다.
- 선택지: A 독립 `.aip` 중심 / B TS·Python API 중심 / C 의미 모델 하나 + 여러 공식 작성 방식(canonical 표현과 우선순위 필요).
- 장단점 요약: A는 한 의도 한 표현을 문법으로 강제하기 쉽지만 JS/Python 생태계 밖이다. B는 생태계 안이지만 표현 다양성을 린트로 좁혀야 한다. C는 둘의 장점을 노리지만 비용이 가장 크고 선택지가 늘어난다.
- 원칙: 구현(JS/Python 생태계)과 AI 철학(정형 문법)이 당기는 지점.
- 하위 질문: "독립적인 표현 체계"가 독립 소스 파일을 뜻하나, JS/Python 안의 정형 형식도 포함하나?
- 상세: `topics/T02-authoring-model.md`
