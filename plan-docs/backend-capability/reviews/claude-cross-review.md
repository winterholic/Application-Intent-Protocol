# Codex 분석 비평과 본인 분석 정정 (READ ONLY, 코드 읽기만, 실행 없음)

Codex 분석의 대부분은 코드와 일치합니다. 다만 세 군데는 반례가 있습니다. 그리고 제 이전 분석에서 사실 오류 1건과 과장 3건을 확인했습니다.

## 1. 본인 분석 정정

**① 사실 오류: "요청 상한 5초 때문에 장기 실행이 불가능하다"**
- `REQUEST_TIMEOUT`(`server.rs:15`, `:156`)이 쓰이는 곳은 헤더 읽기, 본문 읽기, 인증, fence 조회뿐입니다(`lib.rs:219`, `:375`, `:387`, `:476`).
- 확장 실행 시간은 선언한 `deadlineMs`로만 제한됩니다(`lib.rs:532-536`, `v4 write.rs:33`).
- `dur()`에는 상한 검사가 없고(`parser.rs:137-145`), sema도 deadline이 있는지만 확인합니다(`sema.rs:1513`).
- 따라서 정정합니다. 긴 **동기** 실행은 가능합니다. 대신 실행하는 동안 HTTP 연결, DB 연결(`lib.rs:471`), 확장 슬롯 4개 중 하나(`server.rs:247`)를 계속 붙잡습니다. write 확장이면 트랜잭션과 advisory lock까지 잡습니다(`write_extension.rs:38-52`, `:77`). 진행률 보고, 재개, 별도 취소 경로는 없습니다.
- 클라이언트가 연결을 끊었을 때 worker가 중단되는지는 확인하지 못했습니다.

**② 과장: "F 시나리오는 전 단계가 불가능하다"**
- read 확장 하나로 짧은 순수 계산을 수행하고 결과를 반환할 수 있습니다(`worker.mjs:43`, `lib.rs:541`). Codex의 지적이 맞습니다.
- 다만 다음 전제가 붙습니다. resource 아래에 선언해야 하고(`parser.rs:541`), 서명된 세션이 필요하며(`lib.rs:434`), 계약 지문이 맞아야 하고(`:437`), macOS에서만 돕니다(`server.rs:320`).
- F에서 실제로 빠진 것은 durable 실행, 진행 상태 조회, 대용량 입력입니다. 요청 본문은 1MiB로 제한됩니다(`lib.rs:213`).

**③ 오류: "/status를 run id 기준으로 바꾸자"는 제안**
- 현재 `/status`는 `aip_idem` 재생 조회입니다. 같은 키에 다른 요청이 오면 `IDEMPOTENCY_MISMATCH`를 반환하고, 결과가 없으면 "아직 확정되지 않음"을 뜻합니다(`lib.rs:185-207`). write 확장도 이 경로를 씁니다(`lib.rs:548`).
- 이 의미를 교체하면 기존 SDK의 복구 계약이 깨집니다. run 상태 조회는 **별도로 추가**해야 합니다. Codex가 맞습니다.

**④ 과장: "C 시나리오에 사용량 집계가 없다"**
- aggregate가 `count`, `sum`, `min`, `max`와 `where`, `groupKey`를 지원합니다(`parser.rs:705-724`).
- 쓰기 시점의 제한도 `limit … atMost … where`(`parser.rs:210-219`)와 advisory lock(`v3 lib.rs:566`)으로 강제됩니다.
- 정확히 빠진 것은 결제 주기 단위 계량입니다. 또 `atMost`가 정수 리터럴이라서(`parser.rs:216`) 요금제 행 값에 따라 한도가 달라지는 정책은 표현할 수 없습니다. 이 부분은 반례로 남습니다.

**⑤ 과장: "Intent가 테이블에 종속된다"**
- 접근 대상이 없는 read 확장은 테이블을 읽지 않습니다. 이 경우 resource는 실질적으로 이름공간 역할만 합니다(`sema.rs:1522`).
- 실제 비용은 두 가지입니다. 이름을 붙이려면 resource가 있어야 하고, 요청마다 DB를 거칩니다. 확장을 붙이려고 만든 가짜 resource가 DDL을 만드는지는 확인 필요입니다.

## 2. Codex 분석에 대한 동의와 이견

**동의하는 부분**
- **제품과 PoC의 구분**: 의존 관계로 확인됩니다(`aip-service/Cargo.toml:15-19`).
- **"DB 없는 서비스는 불가능"**: 모든 경로가 DB 연결과 fence를 거칩니다(`lib.rs:471-506`).
- **"notify의 기록과 전달은 다르다"**: 맞습니다. 더 나아가 기록 자체도 빈약합니다. outbox 행에는 `topic`, `recipient_id`, `source`, `source_id`만 있고 payload나 템플릿이 없습니다(`sqlgen.rs:598`, `v3 lib.rs:461`). 그래서 전달기가 원본을 다시 조회해야 하며, 그 사이 원본이 바뀌면 스냅샷 의미가 깨집니다.

**이견 1: "DB 없는 서비스 불가능"을 핵심 결함으로 다루는 것**
- durable 실행에는 어차피 상태 저장소가 필요하고, 그 저장소로는 PG가 가장 자연스럽습니다. 그래서 문제의 핵심은 "DB가 있다"는 사실이 아닙니다.
- 제가 보는 핵심은 두 가지입니다.
  - fence는 DB 스키마와 실행 정의가 일치하는지 지키는 장치입니다(`lib.rs:485-497`). 그런데 테이블을 건드리지 않는 순수 확장에도 적용됩니다. 순수 확장의 계약 불일치는 이미 계약 지문 검사(`lib.rs:437`)가 막고 있습니다.
  - 순수 계산이 실행되는 동안 연결 상한 64개(`server.rs:14`) 중 하나와 DB 연결을 계속 소비합니다.
- Codex가 말한 "job 상태 저장소와 비즈니스 SQL의 분리"에 동의합니다. 다만 분리 대상은 저장소 자체가 아니라 **fence와 연결 수명**입니다.

**이견 2: "화면마다 endpoint와 DTO를 만드는 모델로 돌아갈 위험"**
- 우려 자체는 타당합니다. 그런데 제품에는 이미 범용 envelope `{extension, input}`이 있습니다(`lib.rs:440-441`, `:420-422`).
- 따라서 실행 단위를 resource에서 분리해도 새 endpoint가 필요하지 않습니다. 이름공간과 효과 선언만 바꾸면 됩니다. 이 위험은 구조적으로 피할 수 있으므로 반대 근거로 쓰기에는 약합니다.

**이견 3: "PoC의 파일, 구독, 서명 구현을 폐기할 이유는 없다"**
- 결합도가 모듈마다 다릅니다.
  - 서명, 재시도, 공개 주소 검사는 IR에 독립적인 순수 함수입니다(`outbound.rs:71-103`, `:150-167`). 그대로 재사용하기 쉽습니다.
  - 구독은 PoC IR의 쿼리를 LISTEN/NOTIFY 트리거로 다시 실행하는 구조입니다(`subscribe.rs:7-11`). 제품의 read plan(`v2 plan_read_with_wire`)에 맞춰 다시 연결해야 하므로, 이식이라기보다 재구현에 가깝습니다.
  - 파일은 dev 백엔드가 로컬 디렉터리에 씁니다(`objects.rs:1-3`). 운영 저장소 경로는 확인하지 못했습니다.
- 그래서 "폐기 금지"보다는 "모듈별로 재사용 여부를 나눠 판단"하는 편이 정확합니다.

**Codex가 언급하지 않은 위험**
- **non-macOS에서 확장 비활성**: macOS가 아니면 확장 설정 자체가 거부됩니다(`server.rs:320-325`). 운영 환경이 Linux라면 L4 확장이 통째로 없는 셈입니다(코드 판독 기준, 실행 확인은 안 함).
- **샌드박스 범위**: `(allow default)(deny network*)`(`v4 lib.rs:104`)라서 서버 파일시스템은 그대로 열려 있습니다. "확장에서 파일을 처리할 수 있다"는 말은 통제되지 않는 접근이라는 뜻이기도 합니다. 기능이 아니라 보안 위험으로 분류해야 합니다.

## 3. 효과 축과 실행 축

현재 제품은 `kind`와 `effect`가 사실상 같은 축입니다. read는 none, write는 db로 고정됩니다(`sema.rs:1484`, `:1510`). 실행 축은 아예 없고 전부 동기 실행입니다. 두 축으로 나눠 보면 다음과 같습니다.

| 효과 \ 실행 | sync | durable |
|---|---|---|
| **pure** | 지원 (전제는 1-② 참고) | 미지원. 예: 문서 변환 |
| **db** | 지원 (전이 호출, tx와 lock 보유) | 미지원. 예: 대량 import |
| **external** | 미지원 (네트워크 차단) | 미지원. 예: 결제, 메일 |

- **조합 제약 (제안)**: db와 external이 함께 있는 sync 실행은 금지하는 것이 맞다고 봅니다. write 확장은 트랜잭션과 advisory lock을 잡은 채 worker를 실행하므로(`write_extension.rs:38-80`), 그 안에서 외부 호출을 허용하면 잠금 보유 시간이 외부 지연에 묶입니다. 외부 효과는 커밋 이후 outbox로 보내거나 트랜잭션 전에 실행해야 합니다.
- 이 제약을 정적으로 검사하려면 효과를 선언 단계에서 분리해야 합니다.
- durable 실행은 효과와 무관하게 공통 run 기록이 필요합니다. 기존 `aip_idem`의 같은 트랜잭션 기록 패턴(`write_extension.rs:52-66`)이 출발점이 될 수 있습니다.

## 4. 이전 제안의 수정 (제안만)

1. **실행 단위를 resource에서 분리합니다.** 기존 `/extension`과 `/apply`의 envelope는 그대로 두고, 이름공간과 effect 선언만 확장합니다. fence와 DB 연결은 effect가 db일 때만 잡습니다.
2. **durable 실행은 새 경로로 추가합니다.** run id, 진행률, 취소 요청 표시는 새 경로에 두고 기존 `/status` 의미는 유지합니다.
   - 실현 방식은 확인 필요입니다. Temporal 문서를 비교 기준으로 보면, 취소는 heartbeat로 전달되므로 worker ABI에 progress 또는 heartbeat 채널이 있어야 합니다.
3. **external 효과는 커밋 이후 outbox로 보냅니다.** outbox 행에 payload 스냅샷과 멱등 키를 포함하고, PoC의 순수 서명·재시도 함수를 재사용합니다.
4. **요금제 연동 한도를 표현할 수 있게 합니다.** `limit atMost`가 리터럴뿐 아니라 참조 값을 받을 수 있는지 별도로 검토합니다(새 문법은 제안 단계이며 예시는 생략합니다).
5. **플랫폼 중립 격리를 확보합니다.** Linux 운영 경로를 마련하는 것이 L4 전체의 전제 조건입니다.

## 확인 못한 사항

- 가짜 resource가 DDL을 만드는지
- 클라이언트 연결이 끊겼을 때 worker가 중단되는지
- Python worker의 ABI가 Node와 같은지(`worker.py`는 읽지 않음)
- PoC 운영 객체 저장소
- 위 판정은 모두 코드 판독이며 새 코드나 테스트는 실행하지 않았습니다.
