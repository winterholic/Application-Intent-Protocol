# H04 데이터 변경 구독: PoC 모델의 제품 경로 이식 (2026-10-13)

> 범위: [기능 갭 표](capability-gap-2026-10-13.md) 우선순위 7(H04). PoC `subscribe`(D-P24, [DECISIONS](../../docs/DECISIONS.md))의 재조회·가시성 재평가 모델을 제품 경로의 SSE와 WebSocket에 옮겼다. 호출자가 읽기 결과를 열어 두고 그 결과가 바뀔 때 다시 받는다. 구현한 범위와 하지 않은 범위, 창시자 확인이 필요한 점을 나눠 적는다.

## 1. 설계 관문 ([PRINCIPLES §4](../../docs/PRINCIPLES.md))

| # | 질문 | 답 |
|---|---|---|
| 1 | 어느 원칙을 실현하고 어느 원칙과 긴장하는가 | 실현: 2번(호출자가 필요한 데이터를 표현하고 서버가 권한·실행을 최종 결정), 1번(화면마다 새로고침 API나 websocket 서버를 앱이 따로 만들지 않음). 긴장: "호출자의 표현은 무제한 요청이 아니다"(§3)와 상시 연결·재조회 비용. 그래서 구독이 읽는 범위는 `expose read`의 budget 안으로, 연결 수와 수명은 기존 realtime 상한으로 묶는다. |
| 2 | 호출자가 표현할 수 있는 범위가 넓어지는가 | 시간 축으로만 넓어진다. 구독할 수 있는 것은 이미 `expose read`로 열린 읽기뿐이고, 새 필드·필터·정렬 이름이 생기지 않는다. 계약에 없는 요청은 읽기와 같은 코드(`SORT_NOT_ALLOWED` 등)로 거부한다. |
| 3 | 앱 개발자가 서버 쪽에 써야 할 것이 늘어나는가 | 줄어든다. 새 선언이 없다. 이미 쓴 `expose read`의 budget이 구독의 결과 크기와 재조회 비용 상한이다. |
| 4 | 서버의 최종 권한이 유지되는가 | 유지된다. 구독은 서버가 호출자의 세션으로 읽기를 다시 실행한 결과만 보내고, 호출자는 "무엇이 바뀌었다"를 선언하지 못한다. 매 재조회는 주체 재검증(폐기·`min_iat`)과 배포 fence를 먼저 통과해야 하며, 행·필드 정책은 읽기 계획이 그대로 적용한다. 접근을 잃은 구독자는 오류 이벤트를 받고 끝난다. |
| 5 | JS/TS·Python 개발 경험을 활용하는가 | 서버 쪽 확장 경로는 그대로이고 새로 요구하는 것이 없다. 호출 SDK 지원은 아래 "하지 않은 것"이다. |
| 6 | 같은 의도를 여러 방식으로 쓸 여지를 만들지 않는가 | 만든다는 점을 인정한다. 읽기와 구독은 같은 요청 본문을 쓰므로 표현은 하나이고 전달 방식(한 번 / 계속)만 다르다. 이벤트 stream 구독(`stream`)과 읽기 구독(`query`)은 한 구독에 동시에 쓸 수 없다. |
| 7 | 수단을 목적처럼 다루지 않는가 | 변경 신호는 "다시 읽어라"일 뿐 데이터를 싣지 않는다. diff·CDC·행 단위 ACL 같은 장치를 만들지 않았다. |
| 8 | 창시자 결정이 필요한 사항을 임의로 정하는가 | 아래 "확인이 필요한 결정". 모델 자체(전체 재전송, 같으면 보내지 않음, 구독자로 다시 조회)는 D-P24가 이미 정했다. |

## 2. 구현한 것

- 요청: `POST /events/subscribe`(SSE)와 `GET /events/socket`(WebSocket)에 `{query:<읽기 요청>, contractFingerprint}`를 보낸다. `stream`/`after`와 함께 쓰면 `BAD_REQUEST`다. `query`는 재개할 cursor가 없으므로 `after`를 받지 않고, 재연결하면 새 snapshot으로 시작한다.
- 응답: 이벤트의 payload가 `{"type":"snapshot","rows":[...]}`(처음 한 번) 또는 `{"type":"changed","rows":[...]}`다. 항상 읽기 결과 전체이며 직전에 보낸 것과 같으면 보내지 않는다(결과의 digest를 비교). SSE의 `id`와 WebSocket의 `cursor`는 그 digest이며 재개용이 아니다.
- 재조회 시점: 이 프로세스의 커밋(`/apply`, 쓰기 확장, durable job의 `ctx.data.apply`)이 `DataChanges`로 신호하면 100ms 안의 신호를 모아 한 번 다시 읽는다. 이 프로세스가 보지 못한 쓰기(다른 인스턴스, 스크립트)는 안전망 poll(`query_poll_interval`, 기본 5초, 최대 1시간)이 찾는다.
- 재조회의 검사(`durable::read_as_subscriber`): 세션 남은 시간, 주체 재검증과 배포 fence(`guard`), 읽기 계획(계약·정책·예산), 실행 기한, Id wire 변환. 일반 읽기와 같은 계획 함수를 쓴다.
- 한계: 연결 수는 기존 realtime 상한(`max_connections`, 기본 32, `realtime_capacity`)을 같이 쓴다. 구독 하나가 한 연결이다. 결과 크기는 읽기의 budget(`rows`)이 정한다. 최대 수명(기본 15분)과 heartbeat도 같다.
- 시험: `spikes/spike-v6-transport/tests/data_subscription.rs` 4개. 가시성(다른 구성원의 행은 snapshot에 없음), 커밋이 30초 poll보다 먼저 깨움, 보이지 않는 변경은 보내지 않음, 외부 쓰기를 안전망 poll이 찾음, 주체 폐기 뒤 오류와 종료, 잘못된 구독의 거부, WebSocket 같은 흐름, durable job의 쓰기가 깨움. 커밋 신호를 끄면 첫 변경 단계가 실패하는 것을 확인했다.

## 3. 하지 않은 것

| 항목 | 이유와 다음 일 |
|---|---|
| 호출 SDK(TypeScript `connectEventWebSocket`·`readSse`, Python) | 현재 helper는 stream cursor(`stream`, `after`, 숫자 cursor) 전제다. 읽기 구독용 `subscribeRead(query)`가 필요하며 의존성 없이 만들 수 있다. 지금은 SSE/WebSocket을 직접 쓴다. |
| 여러 인스턴스 사이의 즉시 신호 | 다른 인스턴스의 커밋은 안전망 poll로만 알려진다. 즉시 알리려면 커밋 뒤 `pg_notify`를 보내고 인스턴스마다 한 연결로 `LISTEN`하는 방식(PoC와 같은 신호 경로)이 필요하다. 트리거는 배포 schema 변경이라 쓰지 않았고, 서버가 커밋 뒤 보내는 방식으로 해결할 수 있다. |
| fan-out 최적화 | 구독마다 읽기를 한 번씩 다시 실행한다. 같은 읽기·같은 주체를 묶는 공유 재조회는 OI-10과 같은 후속이다. 지금 비용은 `구독 수 × 신호 수`이고 100ms 합치기와 읽기 예산으로 막는다. |
| 변경 범위 필터 | 신호가 어느 resource가 바뀌었는지 싣지 않아 구독이 읽는 resource와 무관한 커밋에도 재조회한다. 결과가 같으면 보내지 않으므로 정확성은 같고 비용만 든다. `write_tags`(바뀐 resource)와 읽기 계획의 `deps`를 맞추면 줄일 수 있다. |
| 조직 전체 broadcast, 행 단위 구독 ACL | 별도 기능이다. 구독의 가시성은 읽기 정책 그대로다. |

## 4. 확인이 필요한 결정

공개 wire를 늘리는 일이라 창시자 확인이 필요한 항목이다. 지금 구현은 아래 기본값으로 동작하며 바꾸기 쉽다.

1. 읽기 구독을 기존 `/events/*` 입구에 `query` 변형으로 넣었다. 대안: 별도 경로(예: `/read/subscribe`). 같은 인증·수명·상한·heartbeat 구현을 재사용하려고 전자를 골랐다.
2. payload의 `type` 이름(`snapshot`, `changed`)은 PoC의 `aip-subscribe/1` 메시지 이름을 따랐다.
3. 안전망 poll의 기본 5초와 최대 1시간.
