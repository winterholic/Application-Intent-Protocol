# 00. 문서 작성 규칙

> 상태: 통합 지침 반영 (2026-10-03). 최상위 기준은 [새 원문](sources/founder-integrated-directive-2026-10-03.md).
> [FOUNDER]는 직접 밝힌 목적/원칙, [DIRECTION]은 확인된 방향의 검증 대상, [OPEN]은 미정 사항이다. 에이전트 합의와 실행 결과는 별도 축이다.

## 1. 이 문서 세트의 목적

AIP 설계를 구현 전에 완성하는 것이 목적이다. 지난 설계가 흐려진 원인은 수단(언어, 파서, IR, 컴파일러)을 만들면서 존재 목적으로 돌아가 확인하지 않은 데 있다(원문 PART V). 그래서 이 문서 세트는 모든 기술 결정을 하나의 질문에 묶는다.

> 프론트엔드에서 필요한 데이터와 동작을 표현하면 서버에 매번 API를 추가하지 않아도 되는가?

## 2. 문서 상태

| 상태 | 뜻 |
|---|---|
| 초안 | 에이전트가 쓴 첫 정리. 사실 확인과 창시자 검토 전 |
| 검토 중 | 창시자가 읽고 의견을 낸 상태 |
| 승인 | 창시자가 명시적으로 승인. 이때만 구현 근거가 된다 |
| 보류 | 다른 결정이 나야 진행할 수 있음 |
| 폐기 | 검토 후 채택하지 않음. 이유를 남기고 지우지 않는다 |

각 문서 안의 개별 항목은 `[확정]`, `[추천]`, `[선택지]`, `[미정]`, `[확인 필요]` 표식으로 구분한다. `[확정]`은 창시자가 결정한 것만 붙인다. 에이전트가 정한 것은 아무리 그럴듯해도 `[추천]`이다.

## 3. 쓰는 규칙

1. **관문 먼저.** topics 문서는 첫 절에 `../docs/PRINCIPLES.md` §4 관문 8문항의 답을 쓴다.
2. **실제 파일만 근거로.** 코드 사실은 파일 경로를 붙인다. 감사 보고서의 수치도 다시 재기 전에는 "감사 시점 값"으로 적는다.
3. **추상 예제보다 실제 서비스.** 판단 자료는 아리아리(`../../ariari`) 실제 프론트·백엔드 코드다.
4. **선택지는 최소 2개.** 각 선택지에 원칙 정합성, 서버 쪽 작성량, 보안 위험, 비즈니스 규칙 처리, 구현 난이도, 확장성, 디버깅, AI 작성 편의를 적는다(원문 PART VII §13의 8개 축).
5. **한 결정은 한 곳에.** 같은 결정을 두 문서에 쓰지 않는다. 다른 문서는 링크만 건다.
6. **수단은 목적으로 정당화한다.** IR, 파서, 플래너 같은 수단을 다룰 때는 원문 PART V의 여섯 질문(왜 필요한가, 호출자 중심 실행에 어떤 도움, 보안 통제에 어떤 도움, JS/Python과 어떻게 연결, 없으면 무엇이 실제로 문제인가, 더 단순한 대안은)에 답한다.
7. **변경 이력.** 문서 끝에 날짜와 변경 요지를 한 줄씩 남긴다.

## 4. 기존 결정 기록과 10-03 원문의 차이

10-03 원문은 10-02 정리보다 몇 군데에서 더 열어 두었다. 원문이 우선하므로 아래 항목은 plan-docs 안에서 **다시 미정으로** 다룬다. `../docs/DECISIONS.md` 자체는 창시자 확인 뒤에 고친다.

| 항목 | 10-02 기록 | 10-03 원문 | plan-docs에서의 취급 |
|---|---|---|---|
| `.aip` 독자 언어 | D-R6 Rejected("정본 작성 언어로 삼지 않는다") | "기존 `.aip` 문법을 무조건 폐기하거나 유지한다고 단정하지 않는다", "Rust 엔진이나 AIP 고유 문법을 제거해서도 안 된다" | `[미정]`. T02에서 A/B/C 비교. 질문 Q2 |
| 선언 블록 DSL | 언급 없음 | "선언 블록 중심의 AIP DSL을 선호하는 방향으로 합의", A형 선호 | 방향은 기록하되 형식(독립 파일 언어인지 JS/Python 내부 API인지)은 `[미정]` |
| 호출자 모델 | 감사 G-1이 "읽기 조합 + 선언 command"를 추천 | "기존 에이전트 추천이지 창시자 결정이 아니다", A/B/C 세 안 비교 요구 | `[미정]`. T01. 질문 Q1 |
| 원칙 개수 | 원칙표 9행 | "최초 7가지 원칙" | 통합 지침 §1·2로 기준 확인. Q0 원문 대기 해제 |
| 제어 흐름 | 옛 전략은 "범용 언어 기능(루프·재귀·예외·가변 변수) 하지 않음" | "조건문, 반복문, 함수, 표현식 등의 제어 흐름도 지원하는 방향을 논의" | 옛 전략 문장은 근거로 쓰지 않는다. T02, T09에서 다룸 |

## 5. 창시자 승인 없이 확정하지 않는 결정 (원문 Step 5)

- AIP의 정체성을 바꾸는 결정
- 호출자의 표현 자유를 제한하는 결정
- 보안 책임을 바꾸는 결정
- 독립 DSL의 역할 변경
- Rust 엔진의 역할 변경
- JS/Python 통합 방식 변경
- SPR의 책임 변경
- 새 프로토콜의 의미 변경

이 목록은 제품 철학을 실제로 바꾸는 경우에 적용한다. 통합 지침으로 이미 확인된 읽기·표준 쓰기·독립 서버+SDK·metadata 역할을 다시 미정으로 돌리지 않는다. 기술적 세부는 우선 실험하고, 가치 판단이 남는 경우에만 `90-open-questions.md`에 올린다.

## 6. 에이전트가 승인 없이 할 수 있는 것

- 문서 초안 작성, 사실 확인, 선택지 비교, 추천
- 아리아리 실제 코드를 이용한 분류 실험(코드 변경 없음)
- `../spikes/` 안의 작은 실험(본 구현과 섞지 않음). 통합 지침은 기술적으로 해결 가능한 문제를 먼저 검증하도록 했다. 대규모 구현의 자동 승인으로 해석하지 않는다.

## 7. 설계 토론 운영 규칙 (2026-10-03 창시자 지시)

원문: `sources/design-operating-rules-2026-10-03.md`. 이 절은 그 규칙을 plan-docs에 적용하는 방법이다.

### 7.1 결정 문서
- 주요 의사결정은 `decisions/DD-NN-<주제>.md` 한 파일에 하나씩 쓴다(규칙 3). topics 문서는 의제 전체를 조망하고, 결정 하나하나는 decisions 문서가 맡는다.
- 결정 문서는 A~G 형식을 따른다: A 지금 결정할 문제 / B 실제 개발 시나리오 / C 대안과 트레이드오프 / D 최초 철학과의 관계 / E 검증 방법 / F 창시자에게 필요한 결정 / G 결정 상태. 끝에 이탈 방지 점검표를 붙인다.
- B의 코드는 머리에 `개념 예시`, `실제 구현 문법`, `기존 코드(파일 경로)` 중 하나를 표시한다. 정의 문법이 미정(T02)이므로 당분간 AIP 쪽 코드는 모두 `개념 예시`다.
- C에서 새 추상화를 넣는 대안은 "없어지는 중복 작업"과 "새로 생기는 비용"을 함께 적는다(규칙 5).

### 7.2 결정 상태 어휘
G에는 다음 넷 중 하나만 쓴다. 창시자 명시 승인 전에는 `확정`을 쓰지 않는다.

이번 지침은 특정 목적과 경계를 직접 확인했다. DD 전체 상태와 그 안의 확정 목적은 분리한다. [B §5](alignment/B-decision-reclassification.md)의 ‘잠정 합의’는 창시자 목적이 확인됐으나 세부 설계가 남은 상태이고, 이전 에이전트끼리의 합의를 창시자 승인으로 승격한 것이 아니다.

| 상태 | 뜻 |
|---|---|
| 확정 | 창시자가 명시적으로 승인 |
| 잠정 합의 | 창시자가 방향에 동의했으나 세부나 검증이 남음 |
| 검증 필요 | 대안은 정리됐고 실험 결과가 있어야 판단할 수 있음 |
| 미결정 | 아직 창시자 판단을 받지 않았거나 대안 정리가 덜 됨 |

§2의 항목 표식(`[확정]`, `[추천]` 등)은 topics 문서의 개별 문장에 계속 쓴다. 결정 문서의 G와 topics의 `[확정]`은 같은 뜻이다.

### 7.3 이탈 방지 점검 (모든 결정 문서 끝)
1. 애플리케이션별 백엔드 개발이나 이중 유지보수를 줄이는가?
2. 호출자가 필요한 데이터와 동작을 표현하는 데 도움이 되는가?
3. 서버가 최종 실행 권한과 보안을 통제하는가?
4. AI의 불필요한 구현 선택을 줄이는가?
5. JS/Python 생태계와 인간 개발자의 사용성을 보존하는가?
6. 복잡성을 다른 계층으로 옮기기만 한 것은 아닌가?

중대한 충돌은 숨기지 않고 점검표에 적는다. §5의 설계 관문 8문항과 겹치는 부분이 있지만, 관문은 "제안 전", 점검은 "결정 후"에 쓴다.
