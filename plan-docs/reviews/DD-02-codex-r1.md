**판정: 맞음.** `$ARIARI/domain/member/alarm/MemberAlarmService.java:68-77`에서 `readAlarm`은 `alarmId`와 요청자 `memberId`를 함께 사용해 행을 찾고(`:71-72`), 현재 `isChecked == false`일 때만 읽음으로 바꾼다(`:74-75`). “내 알림만”, “안 읽은 것만 읽음으로”라는 요약은 코드와 일치한다.

### 1.3 W2, 닉네임 변경과 DB unique

**판정: 부분.** `$ARIARI/domain/member/member/MemberController.java:31-37`은 인증 주체의 ID만 서비스에 넘긴다. `$ARIARI/domain/member/member/MemberService.java:31-40`은 그 회원을 찾고(`:33`), `existsByNickName`으로 먼저 확인한 뒤(`:35-37`) 엔티티를 변경한다(`:39`). `$ARIARI/domain/member/Member.java:54-56`에는 닉네임 열의 `unique = true` 선언도 있다. 따라서 자기 것만 변경하고 “확인 후 쓰기”를 하는 코드 사실은 맞다.

다만 저장소의 실제 운영 DB 스키마와 예외 변환 경로는 이번 검토 범위에서 실행 확인하지 않았다. “동시 요청은 DB unique가 막는다”는 JPA 선언이 스키마에 반영됐다는 전제에서 타당하고, 실제 응답이 일반 DB 오류라는 문장은 DD-02가 이미 적었듯 **확인 필요**다.

### 1.4 W3, 동아리 회원 권한 변경

**판정: 부분이며 중요한 오류가 있음.** ADMIN 값 금지가 컨트롤러에만 있다는 주장은 맞다. `$ARIARI/domain/club/clubmember/ClubMemberController.java:46-50`이 요청 역할을 읽고 ADMIN이면 거부하며, 서비스는 전달받은 역할을 그대로 설정한다(`$ARIARI/domain/club/clubmember/ClubMemberService.java:60-71`, 특히 `:70`). 따라서 다른 호출 경로가 서비스를 직접 사용하면 이 금지가 빠질 수 있다는 관찰도 맞다.

### 1.5 W4, 최고 관리자 위임과 자기 위임

**판정: 부분.** ADMIN만 위임할 수 있다는 것은 `$ARIARI/domain/club/clubmember/ClubMemberService.java:74-85`의 ADMIN 검사(`:81`)와 동일 동아리 검사(`:82`)로 확인된다. 대상에게 ADMIN을 주고 요청자를 GENERAL로 내리는 것도 `:84-85`와 일치한다.

## 2. 철학 정합성 비판

### 2.1 “동작 표현”을 저수준 필드 쓰기와 동일시했다

원문은 호출자가 필요한 “데이터와 동작”을 표현하고 AIP가 의미와 권한을 검증한 뒤 실행 방법을 정한다고 한다(`founder-intent-handoff-2026-10-03.md:60-67`). DD-02 D는 A를 “이름 고르기뿐”, B를 “단일 리소스 동작 표현”, C를 “가장 충실”이라고 서열화한다(`DD-02:128-134`). 그러나 `role = ADMIN`, `me.role = GENERAL`이라는 두 필드 변경은 “최고 관리자 위임”이라는 의미 있는 동작의 한 구현 절차일 뿐이다. 호출자가 절차를 지정하는 것이 항상 동작을 더 잘 표현하는 것은 아니다.

핵심은 호출자가 **원하는 결과나 의미 있는 동작**을 표현하되 서버가 실행 계획을 정하는 것이다(`founder-intent-handoff-2026-10-03.md:103-115`). 따라서 이름 붙은 동작 자체를 무조건 철학 위반으로 보고 저수준 패치를 더 충실하다고 보는 DD-02의 평가는 축소 해석이다. 화면마다 별도 이름을 강요하는 것은 경계해야 하지만(`:85-93`), 표준화된 `transition`, `relate`, `transfer` 같은 의미 capability까지 “Command 이름 고르기”로 낮춰서는 안 된다.

### 2.2 요청의 자유와 실행 권한 분리가 C에서 충분히 구체화되지 않았다

원문은 인증·인가, 동작 범위, 무결성, 내부 구현, 조합 우회, 자원 사용 모두를 서버가 통제하라고 한다(`founder-intent-handoff-2026-10-03.md:125-136`). DD-02는 C에서 호출자가 쓰기 순서와 사실상의 트랜잭션 경계를 정한다고 서술한다(`DD-02:85,96,132`). 이는 단순한 “철학적 긴장”을 넘어, 현재 설명만으로는 서버가 실행 방법을 결정한다는 원문 `:64-66`과 충돌한다.

C를 남기려면 호출자는 허용된 원자 동작과 원하는 원자성만 요청하고, 서버가 의존 관계, 잠금 순서, 격리, 효과 시점, 최종 실행 계획을 결정해야 한다. 원시 SQL·임의 코드뿐 아니라 임의 순서, 중간 결과의 무제한 전달, 정책 재평가 시점도 호출자가 통제하지 못해야 한다. 이 닫힌 의미 체계가 없으면 원문 PART VII §13의 “C는 무제한 명령 실행 모델이 아니다”(`:881-893`)를 충족하지 못한다.

### 2.3 AI First의 “한 의도 한 구조”가 쓰기에는 없다

AI First는 동일 의도를 동일 구조로 표현하고 불필요한 선택을 없애라고 한다(`founder-intent-handoff-2026-10-03.md:197-218`). 현 문서에서는 같은 위임을 Command, 두 개의 일반 update 묶음, 상태 전이, 일괄 update 등으로 만들 여지가 있다. C.3도 “한 리소스냐 여러 리소스냐”만으로는 이 중복을 제거하지 못한다(`DD-02:113-122`).

DD-01 v3가 연산별 capability 기본 거부, canonical 정리, 표준·확장 경계, 개발 진단을 둔 것처럼(`DD-01:134-159`), 쓰기도 `create/update/delete/link/transition/bulk`의 겹치지 않는 canonical 분류가 필요하다. 같은 의미를 표준 transition과 Command로 동시에 공개하지 않는 검사가 있어야 한다.

### 2.4 GraphQL/CQRS 영감을 벗어나는 이유를 써야 한다

원문은 GraphQL과 CQRS가 영감이지 규격이 아니며 CRUD 자동 생성에 머물지 말라고 한다(`founder-intent-handoff-2026-10-03.md:77-95`). DD-02의 B는 지금 상태로는 필드 단위 CRUD 정책 엔진에 가깝다. 이것만으로 AIP 고유의 의미 있는 동작 표현을 실현했다고 할 수 없다. 반대로 Command가 있다는 이유만으로 A가 “정면 위반”이라고 단정한 것도 과하다. 비교 기준은 이름의 유무가 아니라 화면별 요청 형태를 반복 정의하는지, 호출자가 서버 계약 안에서 의미를 얼마나 표현하는지, 실행 권한이 서버에 남는지여야 한다.

### 2.5 확장 원칙이 사실상 빠졌다

표준 범위 밖 요구는 JS/Python으로 자연스럽게 확장하되 동일한 권한과 계약을 지켜야 한다(`founder-intent-handoff-2026-10-03.md:342-363`). DD-02는 외부 효과가 있으면 Command라고만 하고(`DD-02:121`), 표준 write capability 밖 동작을 JS/Python 확장으로 구현할 때 정책, 불변식, 멱등, 감사, 트랜잭션 경계를 어떻게 상속하는지 다루지 않는다. 작성 언어를 확정할 필요는 없지만, **표준 쓰기와 확장 쓰기의 의미 경계 및 동일 통제**는 지금 결정에 들어가야 한다.

## 3. 대안 비판

### 3.1 A/B/C 비교는 공정하지 않다

1. **A의 비용을 “없음”으로 쓴 것은 틀렸다.** 공통 엔진의 새 비용이 적을 수는 있어도 화면별 Command, 계약 동기화, 테스트, 리뷰, 규칙 복사라는 지속 비용이 있다(`DD-02:93-102`). DD-01 v3가 대안 1의 “새 공통 엔진 비용 없음”과 “화면별 한계비용”을 구분한 방식(`DD-01:121-132`)을 그대로 써야 한다.
2. **A를 경로 규칙과 동일시했다.** Command도 리소스 정책과 불변식을 공통 적용할 수 있다. C.2가 “대안과 별개”라면 W4 표에서도 A의 자기 위임은 불변식이 막아야 한다. 현재 `DD-02:83`은 A만 불변식 없이 비교하고 B/C에는 불변식을 줘 불공정하다.
3. **B의 새 비용을 과소평가했다.** 필드 목록과 전이 검사 외에도 old/new 값 정책, 행 집합 선택, 행별 권한, aggregate 불변식의 잠금, 격리 수준, 오류 비노출, canonical화, idempotency, 감사, 효과 순서, 개발 진단이 필요하다. 이는 단순 “쓰기 정책 언어 + 불변식”보다 큰 의미 엔진이다.
4. **C를 가장 표현력 높은 안으로 선취했다.** 호출자가 절차를 조립할 자유는 넓지만, 의미 있는 동작을 표현하는 품질이나 AI 선택 최소화는 오히려 나빠질 수 있다. “표현력”과 “구현 절차 통제”를 분리해 평가해야 한다.

### 3.2 빠진 실질 대안: capability 분리형 B+

현 A/B 사이에 다음 안이 필요하다.

> **B+ 추천 후보:** 서버는 리소스마다 `create`, 일반 `update`, `delete`, 관계 `link/unlink`, 상태 `transition`, 집합 `bulk`를 서로 다른 capability로 기본 거부한다. 호출자는 열린 capability 안에서 원하는 결과를 canonical Intent로 표현한다. 여러 행이어도 표준 전이·관계·집합 동작으로 의미가 완결되면 Command를 만들지 않는다. 표준 의미로 표현할 수 없거나 외부 효과·복잡한 값 의존성이 있으면 타입 있는 확장 동작을 선언하고, 같은 정책·불변식·감사·멱등 체계를 적용한다.

이 안은 `update` 하나에 모든 단순 쓰기를 밀어 넣지 않으면서 화면별 Command도 줄인다. 예를 들어 W1은 `false → true` transition, W2는 self-scoped unique update, W3은 역할 transition, W4는 서버가 정의한 `transfer-admin` 표준/확장 동작이 될 수 있다. `transfer-admin`이 표준 transition인지 확장 동작인지는 분류 실험 뒤 정할 기술 의제이며 여기서 확정하지 않는다.

또한 C를 검토하려면 **제한된 C**를 별도 후보로 둬야 한다. 호출자가 임의 순서를 보내는 대신, 공개된 원자 capability들의 의존 없는 묶음과 원하는 원자성만 요청하고 서버가 순서·잠금·격리·효과를 결정하는 안이다. 중간 값 전달, 단계별 조건, 외부 효과는 기본 금지하고 근거가 생길 때 넓힌다. 이것이 “안전한 의미 체계와 실행 제한”을 실제 대안으로 만든다.

### 3.3 C.2 불변식 선언의 구멍

- “커밋 직전 검사”만으로 동시성은 해결되지 않는다. 두 트랜잭션이 같은 클럽을 각자 유효한 스냅샷으로 검사한 뒤 함께 커밋하는 write skew를 막으려면 클럽 같은 불변식 범위 키를 잠그거나, 직렬화 가능한 격리, 지연 DB 제약/트리거 등 실제 강제 수단이 필요하다.
- `exactly one ADMIN`은 클럽 생성 중, 마지막 회원 탈퇴, 클럽 삭제 중에도 무조건 참인지 수명주기 범위가 필요하다. PoC는 ADMIN 삭제 시 승계하거나 클럽을 삭제한다(`examples/ariari/app.aip:130-136`). 단순 count 식만 복사하면 정상 생성·삭제가 막힐 수 있다.
- “at most one”과 “at least one”은 강제 방식이 다르다. 전자는 부분 unique로 가능하지만 후자는 일반 unique로 보장되지 않는다. 오류 코드와 복구/repair의 원자성도 계약이어야 한다.
- W3의 ADMIN 금지는 불변식이라기보다 특정 capability의 전이 정책이다. DD-02 `:108`은 W3과 W4를 모두 불변식 문제로 묶어 정책과 불변식을 혼동한다.
- 확장 쓰기와 직접 DB 작업, migration이 같은 불변식을 우회하지 않는 범위를 밝혀야 한다. 모두 막는다는 확정이 아니라, 최소한 보장 범위를 결정 의제로 드러내야 한다.

### 3.4 C.3 정책 쓰기와 Command 경계는 기계적이지 않다

리소스 수는 의미 복잡도의 대용물이 아니다. 한 리소스라도 잔액 차감, 좌석 수량, 순위 재배치처럼 집합 불변식이나 동시성 제어가 필요할 수 있다. 반대로 두 리소스라도 표준 관계 생성이나 부모-자식 cascade면 canonical capability로 처리할 수 있다.

경계는 다음 질문으로 바꿔야 한다.

1. 요청 의미가 하나의 공개된 canonical capability와 그 전이 계약으로 완결되는가?
2. 허용 여부가 actor, before/after 상태, 대상 집합에 대해 서버가 선언한 정책으로 결정되는가?
3. 여러 행·리소스의 불변식 범위와 잠금 키를 엔진이 표준 방식으로 계산할 수 있는가?
4. 단계 사이 값 전달, 조건 분기, 장기 실행, 외부 효과가 필요한가?
5. 표준 capability로 표현 가능하면 확장 Command 등록을 거부하거나 진단할 수 있는가?

1~3이 성립하고 4가 없으면 표준 쓰기, 아니면 타입 있는 확장 동작으로 분류하는 것이 더 기계적이다. 이 규칙 자체도 E1 분류 실험으로 반례를 찾아야 한다.

### 3.5 DD-01 v3와 대응되는 쓰기 구조가 필요하다

DD-01의 층 1 I1~I7에 대응해 쓰기에는 최소 다음이 필요하다. 이는 최종 문법이 아니라 관찰 가능한 안전 조건의 제안이다.

- create/update/delete/link/transition/bulk를 별도 capability로 두고 모두 기본 거부한다.
- 모든 선택 대상에 행·필드·테넌트 정책을 적용하고, 권한은 before/after 값 모두로 다시 평가한다.
- 호출자는 raw SQL, 코드, plan·lock·isolation 힌트를 보내지 않는다.
- 단건 수, 일괄 대상 수, 실행 시간, 효과 수, 주체별 동시 실행 수를 제한한다.
- 운영 오류는 숨은 행·필드의 존재를 새지 않게 하고, 권한 맥락을 가진 개발 도구는 정확한 진단을 준다.
- 확장 쓰기도 같은 정책, 불변식, 멱등, 감사, 효과 통제를 우회하지 않는다.
- 같은 의미의 쓰기를 canonical화하고 표준 capability로 가능한 확장 동작의 중복 등록을 진단한다.

또한 쓰기 preset을 둔다면 DD-01과 동일하게 명시적이고 유한하게 펼쳐져야 하며, 새 필드나 새 전이가 추가될 때 기존 앱의 권한이 자동 확대돼서는 안 된다.

## 4. 보안·무결성 비판

아래 요청은 실제 문법이 아니라 위협을 보이는 **개념 공격 요청**이다.

### 4.1 필드 확대

```text
update Member where id = actor.id set { nickname: "ok", role: "SUPER_ADMIN" }
```

단순히 행이 자기 것이라는 정책만 붙이면 권한 필드가 끼어든다. 허용 필드의 닫힌 목록, before/after 값 조건, 새 필드 기본 비공개가 필요하다. preset도 새 필드를 자동 포함하면 안 된다.

### 4.2 상태 전이 우회

```text
update ClubMember where id = target set { role: "ADMIN" }
```

일반 update가 `EntrustAdmin`을 우회하면 기존 ADMIN 강등, 대상 활성 여부, 자기 위임 금지, 알림을 건너뛴다. 상태 필드는 일반 update와 분리된 transition capability로만 바꾸고 허용 간선, actor 조건, 부수 효과를 함께 계약해야 한다. “ADMIN 제외” 한 줄로는 새 역할 추가 시 안전하지 않다.

### 4.3 where 기반 일괄 쓰기의 범위 폭발

```text
update ClubMember where club = requestedClub OR true set { status: "ENDED" }
```

DD-02의 “모두 읽음”은 일괄 쓰기를 평범한 update로 열어 둔다. 서버 actor 조건 강제만으로는 빈 where, 넓은 OR, 다른 테넌트 관계 경유, 예상보다 많은 행, 정책이 다른 행의 혼합을 해결하지 못한다. bulk는 별도 capability여야 하며 허용 filter, tenant/row 정책, 최대 대상 수, 안정된 대상 스냅샷, 실행 전 실제 대상 수 검사, 전체 원자성 또는 항목별 결과 계약이 필요하다.

### 4.4 묶음의 부분 실패와 존재 오라클

```text
atomic? [내 역할을 GENERAL로, 비공개 회원 X를 ADMIN으로, 알림 발송]
```

두 번째 단계가 거부됐을 때 첫 단계가 남는지, 외부 알림이 나갔는지, 어느 단계 오류가 반환되는지 정하지 않았다. 단계별 오류가 “X는 존재하지만 권한 없음”을 알려줄 수도 있다. DB 쓰기는 원자적으로 롤백하고 외부 효과는 커밋 후 outbox 등으로 분리한다는 기본 의미가 필요하다. 항목별 부분 성공을 지원한다면 별도 명시 capability로 한정해야 한다. T11은 이 부분을 아직 열린 질문으로 둔다(`T11-transaction-effects.md:19-33`).

### 4.5 불변식 검사와 동시성

```text
T1: A가 B에게 위임
T2: 거의 동시에 A가 C에게 위임
```

각 트랜잭션이 자기 스냅샷에서 ADMIN 한 명을 보고 통과할 수 있다. 부분 unique가 최종 ADMIN 두 명은 막더라도 “최소 한 명”, 수명주기 repair, 다른 집계 불변식까지 해결하지 않는다. 불변식별 범위 키, 잠금 순서, 재평가 시점, 격리 요구, 충돌 오류를 정해야 한다. PoC의 기술 기록은 같은 클럽 ADMIN 행 잠금과 직렬화를 명시한다(`docs/design/01-reality-test.md:98-101`); DD-02는 이를 “동시성 처리 비용” 한 문장으로 축소했다.

### 4.6 멱등성과 재시도

```text
retry 같은 요청: toggle bookmark / create payment / append event / send mail
```

네트워크 재시도에서 같은 묶음이 두 번 실행되면 toggle은 원상복귀하고, create와 효과는 중복될 수 있다. 생성·효과·묶음에 안정적인 idempotency key, 동일 요청 판정, 결과 재생, 키 범위와 보존 기간이 필요하다. PoC의 멱등 자산이 있다고 해서 조합 쓰기에 자동 승계되는 것은 아니다(`T07-security.md:45-47`).

### 4.7 감사와 사후 설명

권한이 큰 transition, bulk, 확장 쓰기는 적어도 실제 주체, 대리 주체, canonical 요청, 정책·불변식 판정, 영향 행 수, 트랜잭션·outbox ID, 성공/거부 사유를 연계할 수 있어야 한다. 민감한 before/after 값을 그대로 로그에 남기지 않는 필드 정책도 필요하다. C는 단계별 감사 조각이 하나의 의도로 묶여야 한다. DD-02에는 이 비용과 보장이 빠져 있다.

## 5. F 질문 비판

### 5.1 F1

**창시자 결정 사항은 맞지만 현재 문장은 부적합하다.** 호출자 표현 범위와 보안 책임을 정하므로 창시자가 답해야 한다. 다만 A/B/C는 기술 패키지이고 현 비교가 불공정해 그대로 고르게 해서는 안 된다. 다음처럼 결과 중심으로 물어야 한다.

> **제안 F1:** “새 화면의 단순한 생성·수정·삭제·상태 전이가 서버가 미리 연 안전한 범위 안에 있다면, 화면마다 새 서버 동작을 추가하지 않고 프론트가 표준 Intent로 요청하는 것을 쓰기의 기본으로 삼을까요? 서버는 허용 필드·상태 전이·대상 범위·무결성과 실제 실행 방법을 계속 최종 결정합니다.”

이는 B/B+ 방향을 묻되, 기술 수단을 창시자에게 떠넘기지 않는다. 동의하지 않을 때 A의 실제 사용자 비용도 설명해야 한다.

### 5.2 F2

**철학 질문은 맞지만 F1과 중복되고 예시가 답을 유도한다.** “프론트가 두 쓰기를 조립”은 비전문가가 서버 실행 권한까지 넘기는 것으로 받아들이기 쉽다. 핵심은 호출자가 **결과**를 표현할지 **절차와 원자성**까지 표현할지다.

> **제안 F2:** “여러 데이터가 함께 바뀌는 동작에서 프론트는 ‘최고 관리자 위임’처럼 원하는 결과만 요청하고 서버가 순서와 트랜잭션을 정해야 할까요? 아니면 서버가 허용한 원자 동작에 한해 프론트가 함께 실행할 묶음까지 표현할 수 있어야 할까요?”

두 번째를 택해도 raw SQL, 임의 코드, 잠금·격리·실행 순서 통제는 주지 않는다고 덧붙여야 한다.

### 5.3 빠진 창시자 질문과 에이전트가 정할 질문

빠진 핵심은 “호출자가 표현하는 동작”의 의미다.

> **제안 F3:** “AIP에서 호출자가 표현하는 ‘동작’은 원하는 업무 결과인가요, 아니면 그 결과를 만드는 여러 단계의 절차까지 포함하나요?”

이 답이 B+와 제한된 C의 경계를 정한다. 다만 F2를 위 문장으로 충분히 고치면 F3는 별도 질문으로 늘리지 않고 설명 문장으로 합쳐도 된다.

반대로 capability 종류, 잠금 방식, 격리 수준, idempotency key 형식, 오류 코드, 감사 필드, Command 판정 알고리즘은 창시자에게 물을 사항이 아니다. 에이전트가 근거와 반례를 제시하고 기술 제안으로 내야 한다. 작성 언어와 엔진 형태도 별도 미결정 의제이므로 DD-02에서 답을 선취하면 안 된다.

## 7. 구체적 수정 제안 목록

### P0

1. **B.1**: “쓰기 엔드포인트 93개”를 “쓰기 매핑 문자열 93개, 주석 3개를 제외하면 활성 형태 90개, 실제 런타임 수는 확인 필요”로 고친다. 세 주석 파일·행을 붙인다.
2. **B.1 W3**: “스텝 이상”을 코드상 ADMIN만으로 바로잡고, 컨트롤러 설명과 서비스 구현 중 어느 쪽이 요구사항인지는 확인 필요로 분리한다.
3. **B.2**: “W1~W4 모두 command”를 삭제한다. W1 없음, W2 unique 선언만 있음, W3/W4 command 있음으로 표를 만든다. ADMIN 2명 거부와 승계는 `ariari_e2e.rs:157-176`을 직접 인용한다.
4. **C.1 표와 W4 비교표**: A에도 C.2 불변식을 동일하게 적용해 비교한다. A의 새 비용을 “새 공통 엔진 비용은 작을 수 있으나 화면별 Command 한계비용 지속”으로 고친다.
5. **C.2**: 불변식을 DB 제약 가능/집계형으로 나누고, 범위 키·잠금 순서·격리·커밋 재검사·수명주기·오류 의미를 최소 계약으로 추가한다. W3 전이 정책과 W4 불변식을 구분한다.
6. **C.3**: 리소스 개수 기준을 폐기하고 `create/update/delete/link/transition/bulk` capability, before/after 정책, 표준 의미 완결성, 값 의존·외부 효과 기준으로 교체한다.
7. **C.3 또는 새 C.4**: 필드 확대, transition 우회, bulk 범위 폭발, 부분 실패, 동시성, 멱등, 감사에 대한 층 1 안전 불변식을 DD-01 v3와 대응되는 형식으로 추가한다.

### P1

## 8. 결론

추천은 **capability 분리형 B+ + 데이터 불변식 + 타입 있는 확장 동작**이다. 단순 쓰기는 화면마다 Command를 추가하지 않되 create/update/delete/link/transition/bulk를 별도 capability로 기본 거부하고, 호출자는 열린 계약 안에서 원하는 결과를 canonical Intent로 표현해야 한다. 서버는 before/after 정책, 불변식, 대상 범위, 잠금·격리, 멱등, 감사, 외부 효과와 실행 계획을 최종 통제해야 한다.

C의 조합 모델은 폐기할 필요는 없지만, 임의 순서와 절차를 프론트에 넘기는 현재 모습으로 채택해서는 안 된다. 공개된 원자 capability의 제한된 묶음이 아리아리의 실제 Command를 유의미하게 줄이고도 “한 의도 한 구조”를 유지한다는 증거가 나온 뒤 다시 판단하는 것이 맞다.

Claude의 “B + 불변식 선언”이라는 큰 방향에는 동의한다. 차이는 현재 B를 그대로 충분하다고 보지 않는다는 점이다. 일반 field update와 “한 리소스/여러 리소스” 경계만으로는 상태 전이, bulk, 동시성, 멱등, 감사, 확장을 안전하고 기계적으로 나눌 수 없다. 또한 불변식은 모든 대안에 공정하게 적용해야 하며, Command가 있다는 사실 자체를 창시자 철학의 실패로 보아서는 안 된다.
