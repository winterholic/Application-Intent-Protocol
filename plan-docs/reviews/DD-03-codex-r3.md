> 이 문서는 v3의 반영 여부와 에이전트 간 잔여 이견만 확인한다.

## 1. 2라운드 제안 6개와 미합의 2개 반영 확인

| 구분 | 항목 | 판정 | v3 행 근거 |
|---|---|---|---|
| 제안 1 (P0) | T-I1을 동일 맥락의 실행 결과와 빌드 구조 판정으로 분리 | **반영** | canonical 요청, actor·tenant, 데이터 상태, capability·정책·스키마 버전, 자원 한도를 고정한 뒤 두 입장 방식의 결과·오류를 비교한다. 빌드·개발 도구는 구조 판정만 운영과 같게 하고 실행 시점 판정을 성공으로 가장하지 않는다(`DD-03 v3:82`). |

| 제안 3 (P1) | CI·로컬 production-parity 검사 명시 | **반영** | 배포 전 CI와 로컬에서 운영과 같은 엔진으로 canonical 구조와 등록 적격성을 검사한다고 명시했다(`:88`). |
| 제안 4 (P2) | T-I2를 관찰 가능한 결과로 변경 | **반영** | actor·tenant·현재 정책이 달라지면 같은 등록 식별자도 새 판정 결과를 내고 정책 변경 뒤 거부될 수 있다고 썼다(`:83`). |

| 제안 6 (P2) | F1 B의 “서버 계약”을 일상어로 변경 | **반영** | “서버가 허용한 데이터·조건·정렬 범위”로 풀어 썼다(`:119-124`, 특히 `:121`). |

| 미합의 2 | T-I4의 즉시 폐기와 rollout 유예 혼합 | **해소** | 보안 축소의 즉시 거부는 층 1(`:85`), 아직 호환되는 등록분의 운영 유예는 층 2(`:90`)로 분리됐다. |

6개 제안은 모두 반영됐고, 2개 이견은 모두 해소됐다.

## 2. 새 모순·임의 확정 여부

새로운 실질 모순이나 창시자 미결정 사항의 임의 확정은 없다.

- T-I1~T-I5는 이제 외부에서 시험 가능한 성질로 읽힌다. 동일 맥락 결과·구조 판정(`:82`), 현재 권한 재평가(`:83`), 등록 식별자 치환 거부(`:84`), 권한 축소의 다음 입장 거부(`:85`), 호출자 경로 우회 거부(`:86`)가 각각 관찰 가능하다.
- 등록 기능을 쓰지 않는 R과 등록 관련 조건의 범위가 분리됐고(`:78`), 서명 형식·cache·호환 rollout 같은 구현·운영 수단은 층 2로 남았다(`:90`). PART V의 수단-목적 역전 문제를 새로 만들지 않는다.
- 결정 상태는 계속 미결정이며(`:3`, `:128-130`), S는 에이전트 추천이고 기본 입장 정책은 E1·E3 뒤 F1로 결정한다(`:119-130`). 작성 방식도 확인 필요로 남아 있다(`:30-32`).

다만 C.4의 적용 범위를 바꾼 뒤 두 후속 문장이 예전 범위를 그대로 쓴 사소한 불일치가 있다. D의 “세 안 모두 I1~I7과 T-I1~T-I5를 매 요청 적용”(`:100`)은 “I1~I7과 **해당하는** T-I 조건”으로, E3의 “R과 S 모두에서 ... T-I1~T-I5 판정”(`:112`)은 “R은 T-I1·T-I5, 등록을 쓰는 S는 T-I1~T-I5”로 다듬으면 정확하다. 이는 설계 이견이 아니라 범위 표현의 후속 정리다.

## 3. 결론

**에이전트 간 합의 도달.** v3는 단일 canonical 런타임 파이프라인, 선택적 등록/prewarm, `registered-only`를 입장 정책으로만 취급, 등록과 권한의 분리라는 합의안을 유지하면서 2라운드의 두 모순을 제거했다. 남은 창시자 결정은 F1의 기본 입장 정책이며, 문서가 이를 선취하지 않는다.

### 선택적 다듬기

- D `:100`의 T-I 적용 범위를 C.4 `:78`과 맞춘다.
- E3 `:112`에서 R과 등록 기능을 쓰는 S의 T-I 검사 범위를 구분한다.
- DD-01 `:114`의 “DD-03 v2 갱신” 표기를 현재 v3에 맞춘다. 내용상의 변경은 없다.
