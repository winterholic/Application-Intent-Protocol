## 2. 반론 판정

### 2.1 R1 — 두 층 구분에는 동의, 현재 소속과 “층 1이면 모두 구현”에는 반대

**판정: 부분 동의.** 모든 운영 기능을 대안 2의 선행조건으로 만들면 원문이 경고한 목적·수단 역전이 생긴다는 Claude의 문제의식은 맞다. 원문은 기술적 정교함 자체를 성공 기준으로 삼지 말라고 한다(`founder-intent-handoff-2026-10-03.md:792-825`). 최소 안전 계약과 점진적 운영 성숙도를 나누는 것은 필요한 절제다.

다만 v2의 층 1은 **불변식, 구현 수단, 조건부 최적화**를 한데 묶었다.

- `canonical 의미 검증`은 같은 요청 의미에 같은 정책을 적용하기 위해 필요하다. 그러나 `안정적 해시`는 2-M manifest나 cache를 실제로 쓸 때만 필요하다(`DD-01:133`). 2-R만 택하면 선행조건이 아니다.
- `plan cache`는 보안 불변식이 아니다. cache를 쓰지 않는 것이 가장 단순한 안전 구현일 수 있다. 올바른 불변식은 “cache를 쓰면 정책·스키마·권한 맥락이 다른 결정을 재사용하지 않는다”다. v2의 구체 key 목록(`DD-01:134`)은 DD-03과 정책 모델 전에 고정하기 이르며, 행위자 ID·시간·멤버십 같은 정책 입력이 빠질 수 있다.
- `자원 사용량을 제한하고 중단할 수 있음`은 층 1이다. 반면 예상 스캔 행, fan-out, 정렬 메모리를 정확히 추정하는 고급 cost estimator는 층 2여도 된다. v2는 같은 항목에서 둘을 층 1로 넣고(`DD-01:131`), 다시 “정교한 비용 추정”을 층 2로 둬(`:137`) 경계가 겹친다. 층 1은 보수적 hard cap, DB timeout, 결과 바이트, 주체별 rate/concurrency, 취소로 시작할 수 있다.
- 오류를 통한 권한·존재 노출 방지는 층 1이지만, 모든 환경에서 “금지 필드와 오타 필드가 같은 오류”일 필요는 없다. 신뢰되지 않은 런타임 응답은 동일 shape로 감추고, 권한이 반영된 빌드 계약/개발 도구는 정확한 진단을 제공해야 AI First의 명확한 오류 원칙(`founder-intent-handoff-2026-10-03.md:207-216`)도 지킨다.

반대로 층 1에 빠진 것은 다음이다.

1. 호출자 요청에 raw SQL, 임의 코드, plan hint가 들어가지 않고 서버가 실행 방법을 정한다. 이는 원문의 “호출자가 서버 내부 구현을 임의로 제어할 수 없어야 한다”는 원칙이다(`founder-intent-handoff-2026-10-03.md:125-134`).
2. 표준 경로뿐 아니라 JS/Python 확장 읽기도 인증·행/필드/간선·테넌트·비용 정책을 우회하지 못한다. 원문은 확장도 서버 보안 규칙을 우회하면 안 된다고 한다(`founder-intent-handoff-2026-10-03.md:342-359`).
3. 민감한 집계를 열었다면 그 집계의 disclosure control은 선택적 성숙도가 아니라 해당 capability의 선행조건이다. 모든 count에 noise를 넣을 필요는 없지만, 작은 집단·개인 행동을 추론할 수 있는 count를 단순 명시 허용만으로 내놓아서는 안 된다.

따라서 층 구분은 “구성 요소 목록”보다 다음처럼 쓰는 편이 낫다.

- **층 1 의미·안전 불변식:** 공개 capability만 실행, 모든 경로에 정책·테넌트 적용, 서버가 plan 결정, 자원 상한과 중단, 권한·존재 오라클 통제, 확장도 동일 통제, 민감 집계는 적절한 disclosure guard 없이는 닫힘.
- **층 1의 가장 단순한 구현:** cache 없음, 보수적 hard cap, 단일 DB capability, 상세 timing 균일화 없음도 허용.
- **층 2 최적화·운영:** stable hash/manifest, plan cache, 정교한 estimator, cache 무효화·실시간 동기화, 여러 DB의 정교한 진단, 필요 데이터에 한정한 차분 질의 예산·버킷·noise.

### 2.2 R2 — preset 자체에는 동의, 현재 `listable` 예에는 반대

**판정: 조건부 동의.** preset이 명시적이고 유한한 capability 묶음을 펼치는 문법 설탕이라면 기본 공개로의 우회가 아니다. 오히려 반복 선언을 표준 기능으로 흡수하므로 AI First와 백엔드 작성량 최소화에 맞는다.

그러나 v2의 “지정 필드 중 인덱스 있는 필드의 filter·sort를 연다”(`DD-01:127`)는 잘못된 결합이다.

- 인덱스 추가·삭제라는 DB 운영 변경이 외부 요청 권한을 바꾸게 된다.
- 인덱스가 있어도 `email`, `lastActiveAt`, 순번 같은 필드는 필터·정렬 노출이 민감할 수 있다.
- 인덱스가 없어도 작은 공개 enum은 안전하고 저렴할 수 있다.

안전한 preset의 조건은 다음과 같다.

1. 리소스에 명시적으로 opt-in하며 새 필드가 생겨도 자동 포함하지 않는다.
2. preset은 `select`, `filter`, `sort`의 **명시적 유한 목록**으로 확장된다. 성능 eligibility는 별도 비용 검사다.
3. expansion 결과를 사람이 보고 diff·검토할 수 있다.
4. 필드별 deny/override가 가능하고, preset 버전 변경이 기존 앱의 노출을 조용히 넓히지 않는다.
5. preset 이름은 제품 의미를 드러낸다. 막연한 `listable`보다 `publicCatalogFields`, `ownerDashboardFields`처럼 적용 주체와 용도가 분명한 후보를 검토할 수 있다. 실제 이름은 확인 필요다.

예시는 다음 수준이면 충분하다. 실제 문법은 미정이다.

```text
preset publicList {
  select: [title, poster, periodEnd]
  filter: [periodEnd, field, region, target]
  sort: [periodEnd, createdAt]
}
```

이 preset은 선언량을 줄이지만 새 필드·새 연산을 자동 공개하지 않는다. 인덱스는 filter/sort 권한이 아니라 비용 검증과 구조화 오류의 입력으로만 쓴다.

## 3. 새로 생긴 문제

### 3.1 공개 `bookmarkCount`와 비공개 bookmark 간선 정책이 서로 충돌한다

B.3은 `Recruitment.bookmarks`의 count를 공개 집계로 열고(`DD-01:72`), 바로 아래에서는 `RecruitmentBookmark` 행을 `member == actor`로 제한한다(`:74-76`). 이어 모든 관계 단계에 행·간선 정책을 적용한다고 한다(`:88`, `:128`).

두 규칙을 그대로 합치면 공개 `bookmarkCount`는 전체 북마크 수가 아니라 현재 사용자의 북마크 0/1만 세게 된다. 반대로 전체 수를 세려고 간선 정책을 건너뛰면 “모든 집계에 간선 정책 적용” 불변식을 깬다.

해결책은 **간선 행 열람과 승인된 비식별 집계를 분리**하는 것이다. 예를 들어 “bookmark 행/identity는 본인만, recruitment별 total count는 별도 declassified aggregate capability로 공개”처럼 계약해야 한다. 이 aggregate가 작은 집단 차분이나 필터를 허용하지 않게 필터 범위도 함께 제한해야 한다. 실제 문법은 미정이다.

### 3.2 이름 붙은 조회를 모두 별칭으로 제한하면 확장 읽기를 호출할 길이 불명확하다

C.1은 이름 붙은 조회를 canonical Intent의 별칭으로만 규정한다(`DD-01:106`). C.3과 F5는 표준 조합으로 안 되는 조회를 JS/Python 확장으로 보낸다(`:135`, `:188-189`). 그러나 복잡한 검색·통계 같은 typed server extension read를 호출자가 어떤 identity로 부르는지는 없다.

표준 조합의 저장 별칭과 새 의미를 가진 서버 확장 읽기를 구분해야 한다.

- `saved read` 또는 manifest ID: canonical Intent의 별칭, 새 의미 없음.
- `extension read`: 표준 대수로 표현 불가능한 서버 구현. 이름·타입·권한·비용 계약을 가진 별도 capability이며, 표준 조합과 중복 금지.

이 구분이 없으면 원문의 “이름 붙은 서버 함수 호출에 그치는 구조를 경계”한다는 문장(`founder-intent-handoff-2026-10-03.md:85-93`)을 “이름 있는 확장은 모두 금지”로 과잉 해석하게 된다.

### 3.3 층 1이 다시 구현 체크리스트가 됐다

v2는 stable hash, plan cache key, 예상 스캔·fan-out 추정까지 “없으면 내놓지 않는” 층 1에 넣었다(`DD-01:122-135`). 이 중 일부는 2-M이나 cache를 선택했을 때만 필요한 수단이다. 아직 DD-03이 실행 시점을 결정하지 않았는데 DD-01이 manifest/cache 친화적 엔진 형태를 선행조건으로 만든 셈이다.

이는 PART V의 목적·수단 역전 위험이 실제로 남았다는 뜻이다. DD-01은 **관찰 가능한 불변식**을 정하고, hash/cache/estimator는 DD-03이나 후속 기술 문서가 가장 단순한 구현부터 선택하게 해야 한다.

### 3.4 오류 은닉과 명확한 개발 오류가 구분되지 않았다

v2는 금지 필드와 존재하지 않는 필드에 같은 오류 모양을 준다(`DD-01:88`, `:132`). 신뢰되지 않은 런타임에서 schema oracle을 막는 데는 맞지만, 권한이 반영된 계약을 가진 자사 프론트의 빌드 검증에서도 같은 메시지만 주면 오타와 권한 부족을 구분하지 못한다. 이는 명확하고 구조화된 오류와 AI의 추측 감소 원칙(`founder-intent-handoff-2026-10-03.md:207-216`)과 긴장한다.

런타임 공개 오류와 개발 도구 진단을 분리해야 한다. 2-M은 승인된 capability schema를 기준으로 정확한 compile/build 오류를 내고, 2-R의 외부 응답은 존재를 드러내지 않는 통합 오류를 낼 수 있다. 이 구분은 실행 하위안을 새로 확정하는 것이 아니라 두 안의 평가 기준이다.

### 3.5 E2와 G가 “줄 수”를 성공 기준으로 과대평가한다

E2는 capability 선언 줄 수를 세고(`DD-01:164`), G는 그 수가 화면별 조회 작성량보다 적을 때만 추천을 유지한다(`:197`). 그러나 한 줄 preset이 넓은 권한을 열 수도 있고, 명시적인 열 줄이 훨씬 안전하고 유지보수하기 쉬울 수도 있다. 원문의 목표는 짧은 코드가 아니라 반복 구현과 앱별 유지보수 부담의 감소다(`founder-intent-handoff-2026-10-03.md:54-75`, `:222-244`).

E2는 최소한 다음을 같은 단위로 비교해야 한다: 새 화면 요구 N개당 서버 수정 횟수, 수정되는 정의 종류, 중복 정책 수, 프론트·서버 계약 동시 변경 수, 검토해야 할 권한 확대 수. 선언 줄 수는 보조 지표로만 둔다. 운영 비용은 문서 분류 실험으로 실측할 수 없으므로 별도 `확인 필요`로 남겨야 한다.

### 3.6 미결정 사항을 몰래 확정했는가

- **작성 언어:** 확정하지 않았다. TS 예시가 실제 문법이 아니며 DD-04가 미정임을 밝혔다(`DD-01:62`). 적절하다.
- **자연어 문법화 의미:** 확정하지 않았다. 실행·메타데이터 연결을 DD-05로 남겼다(`DD-01:150`). 적절하다.
- **실행 시점:** 2-R/2-M/2-RM을 하위안으로 두고 DD-03에 남겼다(`DD-01:101-104`). 다만 stable hash·plan cache를 무조건 층 1로 둔 것은 구현 형태의 선결정에 가깝다.
- **DB 범위:** 미결정으로 표시했다(`DD-01:137`). 적절하다.
- **서버 확장 호출 형태:** 이름 붙은 조회를 별칭으로만 단정한 문장(`DD-01:106`)이 F5 결정 전에 범위를 제한한다. 추천 표식을 붙이거나 saved read와 extension read를 분리해야 한다.

## 4. 창시자 철학 최종 점검

### PART I §1 — 개발 경계 재정의

**대체로 정합.** 호출자가 읽기 모양을 조합하고 서버가 의미·권한·실행·비용을 쥐는 구조가 선명해졌다(`DD-01:12-17`, `:96-104`). 화면별 API 사전 정의를 경계하는 원문(`founder-intent-handoff-2026-10-03.md:36-95`)과 맞는다.

남은 과장은 “화면별 서버 작업은 사라진다”는 문장이다(`DD-01:145`). v2 자신의 B.3은 닫힌 capability라면 서버에서 한 번 열어야 한다고 한다(`:60`). “대부분의 화면별 조회 구현은 사라지고, 새 capability가 필요할 때 리소스 계약 변경은 남는다”가 정확하다.

### PART I §2 — 요청 자유와 서버 실행 권한

**핵심 충돌은 해소됐지만 두 구멍이 남았다.** 연산별 기본 거부, 간선·테넌트 정책, 비용 통제는 원문의 서버 최종 통제와 맞는다(`DD-01:126-134`; 원문 `:125-138`). 그러나 raw SQL·plan hint·호출자 코드 금지와 확장 읽기의 동일 정책 적용이 층 1에 명시되지 않았다. 공개 aggregate의 간선 정책 예외도 정식 capability로 표현해야 한다.

### PART I §4 — AI First

**방향은 정합, preset과 오류가 잔여 충돌이다.** canonical 의미와 preset은 불필요한 선택·반복을 줄인다(`DD-01:127`, `:133`, `:148`). 그러나 인덱스에서 권한을 파생하면 외부 DB 상태를 추측해야 하고, 개발 도구까지 통합 오류만 주면 오타를 추측해야 한다. 둘 다 AI가 구현 내부를 추측하는 상황을 줄이라는 원칙과 어긋난다(`founder-intent-handoff-2026-10-03.md:201-218`).

### PART I §6 — 자연어의 문법화

**정합.** 목적·기대 결과·전제·도메인 의미와의 연결 후보를 적되 실행 영향은 DD-05로 남겼다(`DD-01:150`). 원문이 미결정으로 둔 범위를 넘지 않았다(`founder-intent-handoff-2026-10-03.md:266-286`, `:937-952`).

### PART V — 수단과 목적

**아직 부분 충돌.** 층 1/2 분리는 개선이지만 stable hash, cache key, 고급 cost estimate를 모두 출시 전 필수로 만들면 다시 기술 체크리스트가 성공 기준이 된다(`DD-01:122-137`). 불변식과 조건부 구현 수단을 분리해야 한다.

### PART VII §13 — 호출자 중심 모델 비교

**읽기 하위 결정으로는 충분히 정합.** 원문의 A/B/C 모두 읽기 조합을 공유하므로 이를 먼저 결정한다는 범위 설정은 타당하다(`DD-01:17`; 원문 `:881-905`). 대안 1·2·3의 보안, 복잡도, AI 경험, 유지보수 비교도 v1보다 공정하다(`DD-01:108-118`). 다만 비즈니스 규칙 처리와 디버깅이 표에서 별도 축으로 보이지 않는다. 읽기에서도 declassified aggregate, extension read, plan 설명이 그 두 축에 해당하므로 C.2에 추가하면 원문의 8개 비교 축을 완전히 충족한다.

## 5. F 질문 최종 검토

### F1 — 창시자 결정이 맞음, 문장은 더 쉽게

읽기 기본 모델은 AIP 정체성과 호출자 표현 범위를 정하므로 창시자만 결정할 수 있다. 다만 현재 문장은 `Intent`, 연산별 권한, 비용 통제를 한 호흡에 넣어 비전문가가 무엇에 동의하는지 분리하기 어렵다(`DD-01:173-175`).

권장 문장:

> **F1. 새 화면이 필요한 데이터를 서버 API 추가 없이 조합해 요청하고, 서버가 허용 범위와 실행 방법을 최종 판단하는 방식을 AIP 읽기의 기본으로 삼을까요?**
> 동의하지 않는다면 서버가 조건·정렬 틀을 미리 정하는 대안 3과 화면별 조회를 만드는 대안 1 중 어느 쪽을 선호하는지 비교한다.

### F2 — 창시자 승인 대상이지만 안전하지 않은 안을 동등하게 제시하지 말 것

새 필드 자동 노출 여부는 보안 기본값과 서버 작성량의 제품 균형이라 창시자 승인 대상이다. 그러나 현재 (b)는 누락 한 번이 정보 노출이 되는 안이고, 운영 규칙은 안전성을 희생해 코드를 줄이지 말라고 한다(`design-operating-rules-2026-10-03.md:21-26`). 기술 권고가 (a)라면 (a)를 기본안으로 제시하고, 자동 공개는 동등한 후보가 아니라 명시적으로 위험을 수용하는 예외로 보여야 한다.

권장 문장:

> **F2. 새 필드는 명시적으로 열기 전까지 호출자에게 보이지 않는 안전 기본값을 AIP 원칙으로 받아들일까요?**
> 선언량은 E2로 측정하고 안전한 preset으로 줄인다. 자동 공개를 원한다면 새 필드가 검토 없이 노출될 수 있다는 보안 책임 변경을 별도로 승인해야 한다.

### F3 — 창시자 결정이 맞고 대체로 이해 가능

첫 제품이 누구를 지원할지는 제품 범위라 창시자 결정이다. `2-M`, `2-R` 용어만 본문을 다시 찾아야 이해되므로 질문 안에서는 빼는 편이 낫다(`DD-01:181-183`). 단계적으로 여러 개를 선택할 수 있음을 보여야 한다.

권장 문장:

> **F3. 첫 출시에서 누가 AIP 읽기 요청을 직접 만들 수 있어야 할까요?**
> 자사 프론트만 / 자사 AI 에이전트까지 / 신뢰된 파트너까지 / 불특정 서드파티까지 중 1차 범위를 정한다. 뒤의 대상은 단계적으로 추가할 수 있고, 대상마다 사전 승인과 실행 한도를 다르게 적용한다.

### F4 — 창시자 질문이 아니라 기술 제안으로 이동

“서버가 받는 canonical 구조 하나”는 같은 의도를 같은 구조로 정규화한다는 승인된 AI First 원칙을 구현하는 내부 수단이다(`DD-01:185-186`; 원문 `:205-218`). 창시자가 답해야 할 사용자 경험의 갈림길이 제시되지 않는다. F에서 삭제하고 C.3 기술 제안으로 남겨야 한다. 여러 작성 방식 허용 여부는 DD-04에서 묻는다.

### F5 — 창시자 결정은 맞지만 saved read와 extension read를 구분해 다시 질문

표준 범위 밖 JS/Python 확장은 승인된 철학이다(`docs/PRINCIPLES.md:24-26`). 여기서 실제 창시자 결정은 특수 조회를 공식 server extension read로 노출할지, 그리고 표준 조합과의 중복을 금지할지다. 현재 문장은 “이름 붙은 조회는 별칭만”과 충돌해 비전문가가 확장 호출의 형태를 알 수 없다(`DD-01:106`, `:188-189`).

권장 문장:

> **F4. 표준 조합으로 표현할 수 없는 특수 조회를 위해, 타입·권한·비용 한도를 가진 서버 확장 읽기를 공식 기능으로 둘까요?**
> 표준 조합으로 표현 가능한 조회는 이 확장 경로로 중복 정의하지 않고, 저장된 일반 조회 이름은 같은 조합 요청의 별칭으로만 쓴다는 규칙을 함께 권한다.

기존 F4를 삭제하면 이 질문이 새 F4가 되고 F5는 없어진다.

## 6. 잔여 수정 제안

### P0 — 창시자에게 보내기 전에 수정

1. **B.3·C.3:** 공개 `bookmarkCount`를 간선 행 열람과 분리된 declassified aggregate capability로 다시 설명한다. 집계가 간선 정책을 건너뛰는 예외가 아니라 서버가 명시적으로 공개한 별도 결과임을 적는다(`DD-01:72-76`, `:128-130`).
2. **C.3:** 층 1을 관찰 가능한 안전 불변식으로 다시 쓰고, stable hash와 plan cache는 2-M/cache 채택 시의 조건부 수단으로 내린다. 보수적 hard cap과 정교한 cost estimator도 층 1/2로 분리한다(`DD-01:122-137`).
3. **C.3:** raw SQL·임의 코드·plan hint 금지와 JS/Python extension read의 동일 정책·테넌트·비용 통제를 층 1에 추가한다.
4. **C.3 R2:** `listable`에서 인덱스 기반 권한 파생을 제거하고, 명시적 유한 필드 목록을 펼치는 opt-in preset으로 바꾼다(`DD-01:127`).
5. **C.1·C.3·F:** saved read 별칭과 typed extension read를 분리하고, 이름 붙은 조회는 모두 별칭이라는 단정을 창시자 결정 전 추천으로 낮춘다(`DD-01:106`, `:135`, `:188-189`).
6. **F:** 기존 F4를 기술 제안으로 이동하고, F5를 §5의 쉬운 확장 읽기 질문으로 다시 쓴다. F1~F3도 용어를 줄여 §5의 문장으로 교체한다.

### P1 — 추천 근거를 정확하게 만들기

7. **E2·G:** capability 선언 줄 수를 보조 지표로 낮춘다. 화면 요구당 서버 수정 횟수, 중복 정책 수, 양쪽 계약 동시 변경, 권한 확대 검토 수를 함께 비교하고 G의 유지 조건을 이 결과와 E3로 바꾼다(`DD-01:164`, `:197`).
8. **C.3·E3:** 민감 aggregate를 허용하는 경우에만 최소 집단 크기·버킷·질의 예산 등 적합한 disclosure guard를 층 1 조건으로 올린다. 일반 공개 count에 무조건 noise를 강제하지 않는다(`DD-01:129`, `:137`, `:165`).
9. **C.2:** 원문 PART VII §13의 8축을 맞추기 위해 비즈니스 규칙 처리와 디버깅 행을 추가한다. declassified aggregate, extension read, canonical plan 설명 가능성을 비교한다.
10. **B.3·C.3:** 공개 런타임 오류와 권한이 반영된 빌드/개발 진단을 분리해 존재 오라클과 명확한 오류를 함께 지킨다(`DD-01:88`, `:132`).

### P2 — 과장과 표현 정리

11. **D:** “화면별 서버 작업은 사라진다”를 “대부분의 화면별 조회 구현은 사라지고 새 capability가 필요할 때 리소스 계약 변경은 남는다”로 고친다(`DD-01:145`).
12. **D:** GraphQL 차별 후보 (1)~(4)는 GraphQL 구현에서도 가능한 안전 장치임을 인정하고, AIP의 최종 차이는 읽기·동작 Intent와 AI First 전체 체계에서 판정한다고 덧붙인다(`DD-01:149`).
13. **C.3:** plan cache를 유지한다면 행위자 속성의 예시 목록이 완전한 key라는 인상을 없애고, 정책 평가 결과가 아니라 정책이 매개변수화된 plan만 재사용하는 단순안도 비교한다(`DD-01:134`).

## 7. 합의 상태 판단

**에이전트 간 합의에 거의 도달했지만 아직 도달하지는 않았다. 남은 이견은 5개다.** 사실 검증, 수정 대안 2의 상위 방향, 연산별 기본 거부, canonical 의미, 관계·테넌트 정책, E1~E4 수행, 자연어 문법화의 미결정 유지에는 합의했다. 남은 이견은 다음과 같다.

1. **R1 층 경계:** Claude는 stable hash·plan cache·상세 비용 추정까지 층 1에 두었고, 나는 이들을 선택된 실행 방식에 따른 조건부 수단 또는 층 2로 내려야 한다고 본다. 대신 raw SQL/plan hint 금지와 확장 경로의 동일 보안 통제를 층 1에 올려야 한다.
2. **R2 preset 기준:** preset 자체에는 합의하지만 Claude 예시는 인덱스에서 filter·sort 권한을 파생한다. 나는 명시적 유한 목록만 펼치고 인덱스는 비용 판단에만 써야 한다고 본다.
3. **공개 집계와 간선 정책:** v2는 공개 전체 bookmark count와 본인만 볼 수 있는 bookmark 간선을 동시에 선언했지만 합성 의미가 모순된다. declassified aggregate를 별도 capability로 분리해야 한다.
4. **이름 붙은 조회와 확장:** Claude는 이름 붙은 조회를 canonical 별칭으로 제한했지만 동시에 JS/Python 확장을 둔다. 나는 saved read와 typed extension read를 구분해야 한다고 본다.
5. **추천 증거:** Claude는 E2의 capability 선언 줄 수와 E3 통과를 추천 유지 조건으로 두었다. 나는 줄 수가 아니라 화면 요구당 서버 변경·중복 정책·계약 동시 변경·권한 확대 검토를 함께 재야 한다고 본다.

이 다섯 가지는 수정 대안 2의 상위 철학을 뒤집는 이견이 아니다. P0 여섯 항목을 고치면 창시자에게 제시할 설계 질문의 뼈대에 대해 **에이전트 간 합의 도달**로 판정할 수 있다.
