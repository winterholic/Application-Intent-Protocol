## 1. 사실 검증

### 1.1 10-02와 10-03 기록 인용

**인용 자체는 맞지만, 한 대목은 잘못 해석했다.** 10-02 정본은 “새로운 프로그래밍 언어가 아니다”와 JS/Python 생태계 유지를 함께 적는다(`docs/PRINCIPLES.md:28-33`). 10-03 원문도 JS/Python 표준 인터페이스를 원하고(`founder-intent-handoff:150-161`), 고유 문법을 제거하지 말라고 하면서 그 문법이 독립 파일·JS/Python API·둘 다 중 무엇인지는 다시 검토하라고 한다(`:163-177`, `:246-262`). 선언 블록과 A형 선호 기록도 실제로 있다(`:375-383`). DD-04 A의 인용 요약(`DD-04:14-19`)은 여기까지는 맞다.

반면 D와 F는 독립 `.aip`를 “루프·가변 변수 없는 선언 언어”라고 전제한다(`DD-04:155`, `:181-182`). 10-03 원문은 조건문·반복문·함수·표현식 지원을 논의했다고 명시한다(`founder-intent-handoff:246-256`). `00-rules.md`도 “제어 흐름을 하지 않는다”는 옛 전략을 근거로 쓰지 말라고 한다(`plan-docs/00-rules.md:37-43`). 현재 문법에도 함수, `if` 표현식, `for`가 있다(`spec/grammar.md:43-47`, `:253-258`, `:393-400`, `:424-432`). 따라서 이 전제로 A와 “새 언어 아님”의 긴장을 약화한 것은 **틀림**이다.

### 1.2 Recruitment PoC 인용

**맞음.** `app.aip`의 `Recruitment`는 필드, 기간 중복 제약, lifecycle, `open` predicate, 가시성을 한 블록에 둔다(`examples/ariari/app.aip:331-355`). DD-04 B.1은 일부 필드를 생략했다고 밝혔으므로(`DD-04:25-45`) 인용 왜곡은 아니다.

다만 “DD-01·DD-02 이전 모델이라 연산별 capability 선언이 없다”는 설명도 맞다(`DD-04:45`). 현재 `RecruitmentList`는 이름 붙은 query 안에서 필터·정렬한다(`examples/ariari/app.aip:425-439`). 이것은 DD-01의 리소스별 select/filter/sort/traverse/aggregate 공개 계약과 다르다. 따라서 C.2의 “문법·예제 4개 그대로”라는 기존 자산 평가는 과장이다(`DD-04:134`). 예제 파일은 실제로 네 개지만(`examples/ariari/app.aip`, `examples/cms/app.aip`, `examples/saas/app.aip`, `examples/shop/app.aip`), DD-01·DD-02 모델을 담으려면 문법·AST·예제를 바꿔야 한다.

### 1.3 파서·문법·도구 자산

**파서와 문법은 맞음, 포매터·언어 서버는 확인되지 않음.** `aip-syntax`는 lexer·AST·재귀 하강 파서이며 문법의 실행 형태라고 명시한다(`crates/aip-syntax/src/lib.rs:1-12`; `crates/aip-syntax/src/parser.rs:1-22`). `spec/grammar.md`도 자신과 파서의 대응을 적는다(`spec/grammar.md:1-11`). 반면 명세는 `aip fmt`를 정본으로 언급하지만(`spec/grammar.md:10-12`), CLI의 전체 subcommand 목록에는 `Fmt`가 없다(`crates/aip-cli/src/main.rs:16-109`). 지정된 코드 범위에서 LSP 구현도 확인하지 못했다. 따라서 DD-04의 “포매터·언어 서버를 새로 만들어야 한다”는 비용 지적은 대체로 맞고, 현재 구현 위치가 따로 있는지는 **확인 필요**다.

### 1.4 파서 이후 자산의 TS/Python 재사용

**부분 확인을 넘어, Core IR 이후는 코드상 재사용을 의도했다.** `.aip` 경로는 parse → AST 확장 → 이름·타입 분석 → Core IR → IR 검증·분석 순이다(`crates/aip-sema/src/pipeline.rs:1-12`, `:42-62`). 앞단 이름·타입 분석은 `aip_syntax::ast::File`을 입력으로 하므로(`crates/aip-sema/src/pipeline.rs:14-17`, `:49-56`) TS/Python 프런트엔드가 그대로 재사용한다고 단정할 수 없다.

그러나 Core IR은 작성 언어와 backend에서 독립이고 TS/Python producer가 같은 규칙을 받도록 설계됐다고 명시한다(`crates/aip-ir/src/lib.rs:1-22`). 구조 검증도 TS/Python이나 도구가 만든 IR에 같은 검사를 적용한다고 적는다(`crates/aip-ir/src/validate.rs:1-4`, `:54-57`). 즉 E3의 “의미 검증 이하 재사용 가능성”(`DD-04:167`)은 전부 미지수가 아니다. **IR 검증·분석과 이후 backend는 재사용 경계가 코드에 있으며, 새 프런트엔드는 이름·타입 해석과 정확한 SourceMap 생성을 해결해야 한다.** 실제 TS/Python lowering 구현량은 확인 필요다.

### 1.5 C1의 `.aip` 정규 출력기

**확인 필요이며, “쉬움”은 근거가 없다.** 현재 확인되는 canonical 출력은 Core IR의 결정적 JSON과 digest다(`crates/aip-ir/src/lib.rs:1289-1306`). CLI에는 `.aip` 포매터나 IR→`.aip` printer 명령이 없다(`crates/aip-cli/src/main.rs:16-109`). 파서는 `.aip`→AST의 단방향 구현이다(`crates/aip-syntax/src/parser.rs:15-22`). 정규화 과정에서 sugar와 source 위치가 사라진다는 Core IR 계약(`crates/aip-ir/src/lib.rs:5-17`)까지 고려하면, 의미 보존 출력 표기를 새로 설계할 수는 있어도 DD-04 C.2의 “정규 출력기(쉬움, 지난 PoC 자산 일부)”(`DD-04:133-134`)는 아직 검증되지 않았다.

### 1.6 DD-01·DD-02 전제의 상태

**“거의 정해졌다”는 표현은 상태를 과장한다.** DD-01과 DD-02는 에이전트 간 추천에는 합의했지만 둘 다 창시자 판단 전 **미결정**이다(`DD-01:3-5`, `:223-225`; `DD-02:3-5`, `:206-208`). DD-04 A의 정의 목록(`DD-04:12`)은 “DD-01·DD-02의 에이전트 합의안이 승인된다고 가정하면 필요한 정의”라고 써야 한다. 작성 방식이 그 미결정안을 몰래 확정하는 근거가 되어서는 안 된다.

## 2. 철학 정합성 비판

### 2.1 긴장을 발견했지만 공정하게 구조화하지는 못했다

DD-04는 10-02와 10-03 사이의 실제 긴장과 `00-rules.md`의 재개방 지침(`plan-docs/00-rules.md:33-43`)을 숨기지 않았다. 그러나 C.1 표는 A를 10-03 편, B를 10-02 편으로 나눠 두 원칙 중 하나를 희생하는 선택처럼 만든다(`DD-04:115-118`). 실제 원문은 10-03 안에서도 JS/Python 자연 사용을 요구하고(`founder-intent-handoff:150-161`), 동시에 고유 문법의 구체적 배치를 열어 둔다(`:246-262`). 10-02도 “풍부하고 정형화된 문법” 자체를 버리라고 하지 않는다(`docs/PRINCIPLES.md:28-33`).

따라서 올바른 질문은 “둘 중 어느 기록이 더 중요한가”가 아니라 다음 두 사용자 경험을 어떤 구조로 함께 만족시키는가다.

1. 개발자는 JS/Python 프로젝트·패키지·확장 생태계 안에서 자연스럽게 작업한다.
2. 서버 정의는 AIP 고유의 선언적이고 기계 검증 가능한 한 구조로 쓴다.

독립 `.aip`, 순수 TS/Python API, 내장 선언 블록은 이 두 조건을 만족하는 정도로 비교해야 한다.

### 2.2 C1은 원문 C가 아니라 B + 파생 출력이다

원문 C는 “독립 AIP 의미 모델과 **여러 공식 작성 방식**”이다(`founder-intent-handoff:906-920`). DD-04 C1은 TS만 쓰고 `.aip`는 읽기·diff·문서 출력으로만 둔다(`DD-04:120-122`). 이는 공식 작성 방식이 하나인 B에 파생 pretty-printer를 더한 것이지 C가 아니다. 정규 리뷰 표기는 A·B·B.4·C2 어디에도 붙일 수 있는 공통 도구이므로 authoring 대안과 같은 축에 놓아서는 안 된다.

이 오분류가 C1을 “두 원칙의 장점”처럼 보이게 하고(`DD-04:128-135`), 에이전트 추천까지 기울인다(`:192`). 특히 Python을 공식 authoring으로 지원하면 “쓰는 방법 하나”가 아니고, 지원하지 않으면 Python 생태계를 어떻게 유지하는지가 빠진다. C1은 이 분기를 설명하지 않는다.

### 2.3 “고유 문법 제거 금지”를 읽는 표기로 축소했다

정규 출력에 AIP다운 표기가 남아 있으면 문자 그대로 문법 파일은 남는다. 그러나 개발자와 AI가 그 문법으로 정의를 **쓸 수 없다면**, authoring 모델에서 고유 문법의 역할은 제거된 것이다. 10-03 원문이 “독립 파일인지 JS/Python 내부 API인지 둘 다인지”를 묻는 맥락(`founder-intent-handoff:246-262`)은 쓰는 형식을 논의한다. C1이 그 요구를 충족한다고 단정할 수 없고 DD-04도 창시자 판단이라고 인정한다(`DD-04:156`). 그럼에도 이를 기본 추천한 것은 미결정 사항을 형식적으로만 열어 둔 채 실질적으로 B 쪽으로 기울인 것이다.

### 2.4 수단-목적과 DD-01~03 일관성

작성 방식은 capability·정책·전이·불변식을 정확히 쓰고 검토하는 수단이다. DD-04는 “개발 경험과 AI 작성 정확도”로 연결했지만(`DD-04:157`), B 예시는 DD-01·DD-02의 핵심인 연산별 capability와 확장 동작 참조를 충분히 보여 주지 않는다. DD-01·DD-02가 요구하는 기본 거부와 정책 diff를 어느 surface가 가장 명확히 드러내는지 먼저 비교해야 한다. 파서나 printer 재사용량이 추천을 이끌어서는 안 된다(`founder-intent-handoff:401-409`; `docs/PRINCIPLES.md:35-46`).

## 3. 대안 비판

### 3.1 A/B/C1/C2/B.4 비교의 불공정

1. **A의 기존 자산을 “그대로” 쓸 수 없다.** DD-04 스스로 PoC에 DD-01·DD-02 capability가 없다고 했다(`DD-04:45`). 그런데 비교표는 parser·문법·예제 4개를 그대로 쓴다고 한다(`:134`). 문법·AST·sema·예제 확장과 LSP/formatter 비용을 A에 넣어야 한다.
2. **B가 TS와 Python 두 프런트엔드를 한 칸에 묶는다.** TS 우선과 Python 동시 지원은 구현비가 다르다. F3에서 시점을 따로 묻는 것(`:184`)과도 맞지 않는다. B-TS 우선과 B-TS/Python 동시를 비용에서 구분해야 한다.
3. **“AI는 TS/Python을 이미 잘 쓴다”는 확인되지 않은 주장이다.** 새 `@aip/define` API와 정책·불변식 의미는 일반 TS 숙련과 다르다. 반대로 낯선 `.aip`가 반드시 더 부정확하다는 근거도 없다(`:130`). E2 결과 전에는 모두 **확인 필요**다.
4. **C1은 authoring 대안이 아니다.** B authoring에 정규 출력 view를 붙인 조합이며, output view는 모든 대안에 독립적으로 비교해야 한다.
5. **C1의 printer 비용을 축소했다.** 의미 보존 printer·source mapping·diff 안정성·왕복 가능 여부가 미검증인데 “쉬움”으로 적었다(`:133-134`).
6. **B.4를 실제 대안 표에서 뺐다.** TS 안의 선언 블록은 두 원문의 긴장을 직접 다루는 실질 대안인데 시나리오에만 있고 A/B/C1/C2 비교에는 없다(`:87-103`, `:124-135`). 문자열 타입 검사와 custom tooling 비용이 있지만, 하나의 쓰기 문법·npm 배포·정적 추출 가능성을 함께 비교할 가치가 있다.
7. **예시가 같은 의미를 담지 않는다.** B.2에는 제약·predicate·행 정책·preset이 있지만(`:49-65`), B.3에는 preset과 `open` predicate가 없고(`:70-84`), B.4에는 기간 중복 제약·predicate·preset은 물론 여러 필드까지 빠졌다(`:87-101`). B.2~B.4는 모두 `track created`를 생략하고, 어떤 예시도 DD-01·DD-02의 연산별 capability와 타입 있는 확장 동작 연결을 공정하게 보여 주지 않는다. F1의 시각 비교가 성립하지 않는다.

### 3.2 빠진 실질 대안

**대안 D: 실행하지 않는 data-only host API.** TS/Python에서는 serializable literal과 AIP가 제공한 순수 constructor만 허용하고, build plugin이 정적으로 추출해 Core IR로 내린다. 정책식 callback, 임의 import, 현재 시각·환경 변수·파일 접근을 금지하고 확장 동작은 함수 객체가 아니라 타입 있는 symbolic reference로 연결한다. 호스트 생태계의 패키지·편집기를 쓰면서 definition module 실행을 피할 수 있지만, 표현력이 낮고 TS/Python 정적 추출기를 각각 만들어야 한다.

**대안 E: 쓰기 가능한 AIP 선언 블록을 TS/Python 프로젝트 안에 둔다(B.4를 승격).** 실제 정의 surface는 하나의 AIP 문법이고 host package는 배포·extension·tooling 경계를 제공한다. 빌드 도구는 tagged template 또는 전용 블록을 **모듈 실행 없이** 추출해 기존 parser로 처리한다. 고유 문법을 authoring으로 남기고 한 의도 한 구조를 강제하기 쉽지만, TS 타입 검사만으로는 블록 내부를 보지 못해 AIP 진단·editor 지원이 필요하다. 이것이 독립 새 언어인지 “JS/Python 안의 정형 AIP 인터페이스”인지는 창시자 확인이 필요하다.

두 대안은 같은 것이 아니다. D는 host 문법의 제한된 data DSL이고, E는 AIP 문법을 host 프로젝트에 내장한다. DD-04는 이 둘과 독립 `.aip`를 같은 의미 사례로 비교해야 한다.

### 3.3 정의 평가 시점의 보안 구멍

C.3의 “임의 코드가 실행되지 않거나, 실행되더라도 결과는 선언 데이터뿐”이라는 조건(`DD-04:139-143`)은 안전 조건이 아니다. TS/Python 모듈은 import/evaluation 순간 파일·환경 변수·네트워크 접근, 프로세스 실행, 전역 상태 변경을 한 뒤 선언 객체를 반환할 수 있다. **출력이 data-only인 것과 평가 중 부작용이 없는 것은 별개다.**

기술 문서는 다음 신뢰 모델 중 하나를 제안해야 한다.

- 정적 추출: 허용 AST만 읽고 모듈은 실행하지 않는다. 가장 단순한 안전 경계지만 callback·동적 조립·직접 함수 참조를 제한한다.
- 격리 평가: 별도 프로세스에서 네트워크·파일·환경·자식 프로세스를 막고 시간·메모리·출력 크기를 제한한다. JS/Python sandbox의 현실성과 escape 위험은 확인 필요다.
- 신뢰된 build code: 애플리케이션 정의를 일반 build script와 같은 신뢰 코드로 명시하고, 운영 서버는 그 코드를 절대 import하지 않으며 검증된·버전 고정된 Core IR artifact만 받는다. 이 경우 CI 권한과 공급망 위험을 비용으로 기록한다.

어느 모델이든 같은 입력이 시간·환경·랜덤에 따라 다른 IR을 만들지 않는 결정성, Core IR 검증, capability·정책 확장의 semantic diff, source 위치가 있는 오류가 필요하다. B.2의 callback과 B.5의 직접 함수 참조(`DD-04:62-65`, `:105-107`)는 이 경계를 정하기 전에는 장점으로 단정할 수 없다.

### 3.4 AI 작성 정확도 검증이 부족하다

E2는 여러 AI 세션의 정규화 결과가 같은지만 본다(`DD-04:165-169`). 여러 답이 같은 필드를 빠뜨리거나 같은 과다 권한을 열어도 “수렴”으로 통과한다. 다음 지표가 필요하다.

- 동일한 완전 요구사항과 같은 참고자료를 주고 첫 시도 compile/validate 성공률
- gold semantic checklist 대비 필드·정책·capability·전이·불변식·확장 참조의 누락/과잉
- DD-01 I1~I7·DD-02 W-I1~W-I11 위반 수와 과다 공개 capability 수
- 구조화된 진단을 받은 뒤 올바르게 고치는 데 필요한 반복 횟수
- 결과 IR 동일성뿐 아니라 의미 테스트/공격 요청의 동일 판정
- 작성 토큰·시간, 사람이 검토해 오류를 찾는 시간

모델·버전·prompt·제공 문서·샘플 수를 고정하지 않은 “AI가 이미 잘 쓴다” 평가는 확인할 수 없다. E2는 이 조건을 기록해야 한다.

## 4. F1~F4와 비전문가 선택 가능성

### F1

**현재는 공정하게 고르기 어렵다.** 질문 자체는 쉬우나 비교하는 B.1~B.4가 같은 정의를 담지 않고, (다) C1은 쓰는 화면과 리뷰 화면을 섞는다(`DD-04:175-179`). 먼저 완전히 같은 semantic checklist의 예시를 보여 주고, 각 선택지가 “평소 쓰는 화면 / 리뷰 때 보는 화면 / 확장 코드를 연결하는 방식”을 각각 어떻게 만드는지 나눠야 한다.

### F2

**답하기 어려운 거짓 양자택일이다.** 두 창시자 기록 중 무엇을 버릴지 묻기보다 둘을 동시에 만족하는 후보를 비교해야 한다. 또한 “루프나 변수 없는 선언 문법” 전제가 원문과 현재 문법에 맞지 않는다(§1.1). 다음처럼 고치는 편이 낫다.

> **AIP 고유 선언 문법은 개발자와 AI가 직접 쓰는 공식 형식이어야 하나요, 아니면 실행 의미를 사람이 읽는 정규 표기로만 남아도 되나요?**  
> 직접 쓰는다면 독립 `.aip` 파일과 TS/Python 프로젝트 안 선언 블록 중 어떤 개발 경험을 원하나요?

이 질문은 “새 언어”의 정의를 추상적으로 묻지 않고 실제 개발 경험을 고르게 한다.

### F3

**창시자가 답할 수 있는 제품 범위 질문이다.** 원문이 JavaScript 우선을 명시하면서 Python도 주요 생태계로 둔다(`founder-intent-handoff:150-159`). 다만 “같은 수준”의 뜻을 parser/진단/editor/extension/type generation 항목으로 풀고, TS 우선일 때 Python authoring을 언제까지 보장하는지 알려 줘야 선택 비용이 보인다.

### F4

**창시자 결정 사항이 아니라 원본 자료 요청이다.** 정확한 A형·B형 예시는 원문도 원본 기록 확인이 필요하다고 한다(`founder-intent-handoff:375-383`). F에서 빼고 E의 선행 자료 또는 “검증 못함: 원본 예시 부재”로 기록해야 한다. 자료가 없으면 현재의 새 예시를 같은 의미로 맞춘 뒤 판단을 계속할 수 있다.

### 권하는 질문 구조

1. **F1:** 평소 직접 쓰는 형식은 독립 `.aip`, TS/Python의 제한된 data API, host 안 AIP 선언 블록 중 무엇이 원하는 경험인가.
2. **F2:** 고유 AIP 문법은 writeable 공식 surface여야 하는가, derived review 표기로 충분한가.
3. **F3:** Python authoring parity를 첫 출시부터 제공할지, TS 우선 뒤 어느 범위까지 호환을 보장할지.

정의 평가의 sandbox, static extraction, Core IR printer는 기술팀이 근거와 함께 제안할 사항이지 창시자 질문이 아니다.

## 7. 결론과 추천

현재 C1 추천에는 동의하지 않는다. C1은 C가 아니라 **TS API(B) + 읽기 전용 printer**이고, writeable AIP 고유 문법을 제거하는 결정을 “표기는 남았다”로 축소한다. 또한 printer 비용과 Python의 역할이 미정이며, TS module 평가의 신뢰 경계도 서지 않았다.

나의 잠정 추천은 **B.4를 보안 조건과 함께 승격한 ‘host 프로젝트 안의 writeable AIP 선언 블록’**을 1순위 검증 후보로 두는 것이다. 실제 정의 문법은 하나이고 JS/Python package는 배포·extension·tooling 경계를 제공하며, build 도구가 module을 실행하지 않고 블록을 정적으로 추출해 공통 Core IR로 내린다. 이 후보는 JS/Python 생태계, 선언 블록 선호, 한 의도 한 구조, 고유 문법 유지의 네 요구를 가장 직접적으로 함께 시험한다.

다만 이것을 확정 추천으로 승격하려면 세 조건이 필요하다. 첫째, 동등한 B.1~B.4 예시에서 작성·리뷰 부담이 실제로 낮아야 한다. 둘째, source 위치가 있는 진단과 editor 경험이 허용 가능해야 한다. 셋째, E2에서 strict data-only TS API보다 AI 의미 정확도와 사람 검토 시간이 낫거나 최소한 열등하지 않아야 한다. 실패하면 **실행하지 않는 data-only TS API**가 다음 후보이고, `.aip`는 단순 읽기 출력으로 축소하지 말고 writeable 공식 surface가 필요한지 F2에서 다시 결정해야 한다.
