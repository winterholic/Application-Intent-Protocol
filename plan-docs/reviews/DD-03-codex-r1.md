## 1. 사실 검증

### 1.1 아리아리 프론트의 요청 모양은 정적으로 드러나는가

**부분.** REST 경로 상수는 `apiUrl.ts`에 다수 정적으로 선언돼 있다. 예를 들어 모집 경로는 `/recruitments`부터 랭킹까지 상수다(`/Users/winterholic/development/projects/ariari/ariari/ariari-frontend/app/api/apiUrl.ts:16-23`). 모집 목록 호출도 필드 이름과 엔드포인트가 코드에 보인다(`.../app/api/recruitment/api.ts:45-75`, `:164-183`). 그러나 요청은 완전한 고정 리터럴이 아니다. 정렬 파라미터가 조건부 spread로 붙고(`recruitment/api.ts:63-68`, `:170-175`), 상태에 따라 본문 형태와 URL이 바뀌는 호출도 있다(`.../app/api/apply/api.ts:271-289`).

따라서 DD-03 E1의 “요청 모양이 코드에 정적으로 드러나는 비율” 측정 제안(`DD-03:92`)은 타당하지만, 현재 REST 래퍼를 세는 것만으로 아직 정해지지 않은 JS/Python AIP 작성 방식에서 canonical 읽기 요청을 정적으로 추출할 수 있다고 입증할 수는 없다. “약 115곳”도 문서에는 집계 기준과 결과가 없어 **확인 필요**다. 단순 텍스트 검색은 주석과 공통 래퍼를 포함하므로 호출 수의 근거가 될 수 없다.

### 1.2 PoC는 컴파일 시점에 SQL과 실행 계획을 고정하는가

**맞음. 단, 선언된 Intent 경로에 한정된다.** `aip-pg`는 Core IR 전체를 DDL과 실행 계획으로 컴파일한다고 명시하고(`crates/aip-pg/src/lib.rs:1-3`), `compile`이 선언된 command/query 각각을 plan으로 만든다(`crates/aip-pg/src/lib.rs:37-42`, `:67-80`). CLI도 소스를 Core IR로 내린 뒤 `aip_pg::compile`을 호출한다(`crates/aip-cli/src/main.rs:404-420`). 런타임은 컴파일된 `aip_plan::Program`을 실행하며 자체 SQL을 만들지 않는다(`crates/aip-runtime/src/lib.rs:1-2`; `crates/aip-runtime/src/exec.rs:1-2`).

### 1.3 PoC 계획기를 manifest 생성에 재사용할 수 있는가

**확인 필요.** DD-03도 가능성으로만 표시했다(`DD-03:54`, `:94`). 현재 컴파일러 입력은 완성된 `aip_ir::Program`이고(`crates/aip-pg/src/lib.rs:37-41`), 계획 대상은 그 안에 선언된 Intent다(`:67-80`). 호출자가 보낸 canonical 읽기 한 건, manifest 서명·버전, 런타임 정책 평가를 처리하는 인터페이스는 이 근거에서 확인되지 않는다. SQL 생성기나 plan 타입 일부를 재사용할 가능성과 “같은 계획기를 그대로 쓴다”는 주장은 구분해야 한다.

### 1.4 “런타임 계획기는 개발 모드에 이미 필요하다”는가

**미래 설계 요구로는 맞지만, 현재 자산에 이미 있다는 뜻이면 틀림.** DD-03은 2-M에서도 개발 모드 즉시 실행을 위해 런타임 계획기가 필요하다고 한다(`DD-03:70-72`). 그러나 현재 런타임은 SQL을 만들지 않는다고 명시한다(`crates/aip-runtime/src/lib.rs:1-2`; `crates/aip-runtime/src/exec.rs:1-2`). 조합 읽기용 계획기를 새로 만들거나 기존 컴파일러를 변형하는 비용은 별도로 잡아야 한다.

### 1.5 OI-C2를 열린 문제로 다루는가

**맞음.** 정본 결정 목록은 선언 경로의 컴파일 시점 SQL 고정은 유효하지만 호출자 조합 요청에는 런타임 계획 또는 빌드 시점 승인 목록이 필요하다고 OI-C2를 Open으로 둔다(`docs/DECISIONS.md:63-71`). DD-03의 문제 설정(`DD-03:12-18`)은 이 상태와 맞는다.

## 2. 철학 정합성

### 2.1 가장 큰 충돌: “빌드 때 정책 적용”은 실행 권한 분리를 약화한다

DD-03은 2-M에서 “같은 정책이 빌드 때 적용”된다고 쓴다(`DD-03:55`). 그러나 빌드 시점에는 실제 행위자, 테넌트, 최신 권한·정책·데이터 상태가 없을 수 있다. 창시자 원문은 인증·인가와 데이터 범위를 서버가 최종 결정하라고 한다(`founder-intent-handoff:125-138`). DD-01도 행·필드·간선·테넌트 정책을 모든 경로에 적용하고(`DD-01:140-146`), 서버가 매번 실행 권한을 정한다고 정리했다(`DD-01:175-178`).

빌드에서는 요청의 **구조, 타입, 공개 capability, 정적 복잡도 상한, plan 생성 가능성**만 검사할 수 있다. 실제 actor·tenant·현재 정책과 실행 시점 비용/중단은 운영 서버가 매 요청 다시 판단해야 한다. Manifest는 실행 권한 증명서가 아니라 등록된 요청 모양 또는 사전 계산된 plan의 식별자여야 한다.

### 2.2 2-M은 서버 사전 정의를 문자 그대로만 피하고 운영적으로 되살릴 수 있다

원문은 새 화면마다 서버 API를 추가하는 일을 최소화하고(`founder-intent-handoff:54-71`), 서버가 모든 요청 형태를 사전에 정의하는 구조를 경계한다(`:85-95`). DD-03은 “호출자가 정의했으므로 서버 사전 정의가 아니다”라고 본다(`DD-03:84`). 작성 주체만 보면 맞지만, 새 화면마다 승인 목록 재생성·검토·배포가 필수이고 서버가 그 목록 밖 요청을 전부 거부한다면 운영 효과는 “허용 요청 형태의 사전 열거”다.

판정 기준은 서버 코드 파일이 바뀌는지가 아니라 **새 데이터 요구가 생길 때 프론트 변경 외에 어떤 중앙 산출물·검토·동기 배포가 반드시 필요한가**여야 한다. 자동 등록과 독립 배포가 실제 한계비용을 충분히 낮추는지는 E1에서 측정하기 전까지 확인 필요다.

### 2.3 AI First와 한 의도 한 구조가 아직 보장되지 않는다

AI First는 동일한 의도를 같은 구조로 표현하고 불필요한 선택을 줄이라는 원칙이다(`founder-intent-handoff:181-218`). 현재 2-R/2-M/2-RM은 호출자 “신뢰 등급”에 따라 작성 제약, 배포 경로, 오류 시점이 달라진다(`DD-03:50-60`). 특히 개발에서는 즉시 실행되지만 운영에서는 정적 추출 여부가 추가 조건이라(`:28-30`, `:65`) 같은 소스가 로컬 성공 후 빌드 또는 운영에서 실패할 수 있다. 하나의 canonical 의미·검증 파이프라인 위에 선택적인 등록/사전 계획을 얹지 않으면 AI가 “어느 모드용으로 어떻게 써야 하는가”를 새로 판단해야 한다.

### 2.4 DD-01·DD-02와의 불일치

- DD-01 층 1은 plan cache와 manifest를 조건부 층 2 수단으로 둔다(`DD-01:161-167`). DD-03은 자사 프론트라는 이유만으로 2-M을 기본 추천한다(`DD-03:68-72`, `:110`). E1~E3 결과 전에는 층 2 수단을 기본 아키텍처로 승격한 셈이다.
- DD-01은 정책 평가 결과가 아니라 정책이 매개변수로 들어간 plan만 재사용하라고 한다(`DD-01:162-164`). DD-03의 “승인된 계획만 실행”과 “정책이 빌드 때 적용”(`DD-03:30`, `:55`)은 그 구분을 흐린다.
- DD-02는 읽기·쓰기 capability를 분리하고 모두 기본 거부한다(`DD-02:102-115`, `:148-160`). Manifest에는 최소한 operation kind와 정확한 capability 계약이 결박돼야 하며, 읽기 manifest ID가 확장 읽기나 쓰기 경로로 치환될 수 없어야 한다. DD-03에는 이 경계가 없다.

### 2.5 PART V의 수단-목적 역전 위험

원문은 planner, code generation 같은 수단이 목표가 되어서는 안 되며 더 단순한 대안을 물으라고 한다(`founder-intent-handoff:792-827`). 2-M은 정적 추출기, canonicalizer, manifest 형식, 서명·등록소, 버전·배포·폐기, 브라우저 롤아웃 호환을 새로 만든다. DD-03은 이 구성요소를 열거하지만(`DD-03:56`, `:60`) 실제로 제거되는 화면당 작업과 순비용을 아직 재지 않았다. 따라서 2-M 기본 추천은 증거보다 앞선다.

## 3. 대안 비판

### 3.1 2-R/2-M/2-RM 비교는 완전히 공정하지 않다

1. **보안 우위 과장:** DD-03은 2-M의 서버 통제를 가장 강하다고 쓴다(`DD-03:82`, `:120`). 2-M은 낯선 구조를 일찍 차단하지만, 오래된 manifest·과도한 입력·현재 권한 변경·테넌트 치환은 매 요청 검사가 없으면 오히려 안전하지 않다. I1~I7은 세 안 모두 같은 층 1 조건이고, manifest는 추가 방어선일 뿐이다.
2. **2-R 비용 과장 가능성:** 2-R은 “요청마다 계획 비용”으로, 2-M은 운영 비용 최소로 적었다(`DD-03:54`). 같은 canonical shape의 안전한 plan cache/prewarm을 쓰면 2-R도 반복 계획을 줄일 수 있다. 반대로 2-M도 actor 정책, 입력, 자원 상한, 실행 시간 중단을 매번 수행해야 한다.
3. **2-M 구현 비용 축소:** “추가 비용은 정적 추출기와 manifest 배포”라고 했지만(`DD-03:72`), 신뢰 루트, 서명, 활성화·폐기, 브라우저 구버전 공존, 캐시 무효화, 정책·스키마 호환, 롤백도 필요하다.
4. **2-RM의 분류 축이 약함:** “호출자 신뢰 등급”(`DD-03:52`, `:57`)은 인증·인가의 보안 경계와 실행 방식 선택을 섞는다. 높은 신뢰의 클라이언트도 변조될 수 있고, 낮은 등급도 유효한 등록 plan을 쓸 수 있다. 서버가 credential과 배포 정책으로 경로를 선택해야지 클라이언트가 모드를 주장해서는 안 된다.

### 3.2 빠진 실질 대안: 단일 런타임 의미 파이프라인 + 선택적 등록/사전 계획

다음 대안을 독립 비교해야 한다.

1. 모든 읽기는 같은 canonical 요청, 타입 검사, capability 검사, 정책 삽입, 비용 상한 파이프라인을 거친다.
2. 자사 프론트는 빌드 시 canonical 요청을 **명시적으로 등록**하고 안정적 해시를 받을 수 있다. 정적 소스 분석은 필수가 아니라 작성 API/codegen이 산출하는 등록 artifact로 시작한다.
3. 등록 시 구조 검사와 plan prewarm을 하지만, 운영에서는 actor·tenant·최신 정책·실행 상한을 다시 평가한다.
4. 운영 배포 정책은 등록된 요청만 받는 `registered-only` 또는 계약상 유효한 새 요청도 받는 `runtime`을 선택할 수 있다. 두 정책의 실행 의미는 동일하다.
5. 동적 호출자는 별도 의미 체계가 아니라 같은 파이프라인의 runtime admission을 쓰며 더 낮은 비용·속도·동시성 한도를 적용할 수 있다.

이는 2-RM과 닮았지만 핵심 차이가 있다. 호출자 등급별 두 실행 체계를 만들지 않고, 등록은 **입장 정책과 prewarm**일 뿐 실행 권한이나 의미의 대체물이 아니다. 정적 추출기 없이도 작은 시작이 가능하다.

### 3.3 “승인”은 세 가지를 분리해야 한다

현재 문서는 자동 검사, plan 생성, 사람/CI diff 검토를 모두 승인이라 부른다(`DD-03:29`, `:64-66`, `:84`). 다음처럼 분리해야 한다.

- 계약 검사: 모든 요청에 자동·필수
- 등록 및 plan prewarm: 선택적 운영 최적화 또는 admission 정책
- 사람 검토: capability 확대나 예외 예산 승인에 한정하고, 새 화면의 요청 모양마다 요구하지 않음

사람 검토가 매 요청 변경의 기본 관문이면 서버 작업이 승인 작업으로 이름만 바뀐다. “자동 검사가 기본”만으로는 어떤 변경이 사람 검토를 요구하는지 불명확하다.

### 3.4 개발 모드와 운영의 의미 일치가 필요하다

개발 모드의 즉시 실행은 UX상 유리하지만(`DD-03:65`), 운영이 registered-only라면 개발 도구도 같은 canonical hash, 정적 계약, 운영 eligibility를 즉시 보여 줘야 한다. 로컬에서는 실행되는데 빌드 추출이 실패하거나 운영 manifest에 없어서 실패하는 경로를 정상 개발 흐름으로 두면 안 된다. 빠른 실행 모드와 별도로 CI 및 로컬 production-parity 검사를 같은 엔진으로 제공해야 한다.

## 4. 보안·운영 비판

### 4.1 Manifest 위조·치환

공격 예: 일반 사용자가 `{"manifestId":"prod:admin-report","params":{"tenantId":"victim"}}`를 보내고 서버가 ID 존재와 입력 타입만 검사한다. ID가 공개 JS에 있다는 사실은 권한이 아니다. Manifest/plan은 신뢰된 빌드·배포 주체가 등록하고, canonical digest·앱·환경·operation kind·capability 집합·schema/compiler protocol version에 결박해야 한다. 서버는 actor·tenant 정책과 입력 허용 범위를 매번 검사해야 한다. 클라이언트가 plan 본문, 서명 주체, 실행 모드를 선택하게 해서는 안 된다.

### 4.2 오래된 Manifest 재생과 폐기

공격 예: `email` 필드 공개를 철회했는데 공격자가 브라우저 캐시의 구 manifest ID를 계속 호출한다. 서명이 유효해도 현재 정책에는 무효다. 서버 측 활성 manifest 집합, 폐기/만료, 정책·스키마 호환 판정, 감사 가능한 activation이 필요하다. 정책 평가를 plan에 굳혀 재생하면 DD-01 I2를 위반한다(`DD-01:141-145`).

### 4.3 프론트·서버 버전 불일치와 롤백

공격이 아니어도 CDN·열린 탭·점진 배포 때문에 구 프론트와 신 서버가 공존한다. 신 manifest 하나만 원자 교체하면 정상 요청이 대량 거부되고, 호환을 위해 모든 과거 manifest를 무기한 허용하면 폐기가 실패한다. 활성 버전의 유예 집합, 최대 보존 기간, rollback, `unknown/stale` 오류의 안정된 계약, 배포 실패 시 fail-closed가 필요하다. 이 비용은 현재 `C.1`의 한 문장(`DD-03:60`)보다 크다.

### 4.4 동적 호출자 경로의 혼동

공격 예: 등록 전용 프론트가 `mode=runtime` 또는 동적 호출자 헤더를 붙여 manifest 거부를 우회한다. 호출자가 경로를 정하지 않고 서버가 검증된 credential/capability와 배포 정책으로 admission을 정해야 한다. 2-R 경로도 I1~I7을 그대로 적용하고 별도 rate·복잡도·동시성 한도와 감사 기록을 가져야 한다. 단, “낮은 신뢰이면 무조건 2-R” 같은 대응은 오히려 공격 표면을 넓히므로 경로와 신뢰 등급을 동일시하면 안 된다.

### 4.5 Plan cache의 권한·테넌트 오염

공격 예: 관리자/테넌트 A 요청으로 만든 plan 또는 정책 판정 결과를 같은 canonical hash의 일반 사용자/테넌트 B가 재사용한다. 캐시 키에는 schema·policy/capability semantic version과 plan 의미가 반영돼야 하고, actor·tenant의 **판정 결과**를 공유 캐시하면 안 된다. 정책은 실행 시 매개변수와 현재 맥락으로 평가해야 한다. 크기 제한·퇴거, 동시 miss 폭주, 무효화, DB 통계 변화 뒤 비용 상한도 필요하다. DD-01은 이미 이 최소 원칙을 둔다(`DD-01:161-164`); DD-03은 이를 상속한다고 명시해야 한다.

## 5. F 질문 비판

DD-03 F1은 제품 경험과 운영 보안의 균형을 바꾸므로 창시자가 결정할 부분은 있다. 하지만 현재 문장은 “모드를 제공할 것인가”만 물어 선택 비용이 희미하고(`DD-03:102-104`), F3의 답에서 “대부분 따라 나온다”는 설명도 지나치다(`:100`). 자사 프론트만이어도 runtime을 기본으로 할 수 있고, 동적 호출자가 있어도 자사 프론트에는 registered-only를 선택할 수 있다. DD-01 F3은 **누가 요청을 만드는가**를 묻고(`DD-01:211-213`), DD-03은 **운영 admission의 기본값**을 묻는 별도 질문이다.

다음처럼 고치는 편이 비전문가에게 더 직접적이다.

> **F1. 자사 프론트의 운영 요청은 어떤 기본으로 할까요?**  
> A. 배포 때 등록한 요청만 허용: 예상 가능한 요청만 실행하지만, 화면의 요청이 바뀔 때 등록 목록도 함께 배포해야 합니다.  
> B. 서버 계약에 맞는 요청이면 처음 보는 모양도 운영 중 허용: 별도 등록 배포는 없지만, 서버가 매 요청 구조와 비용을 안전하게 검사해야 합니다.  
> 어느 쪽이든 로그인 사용자·권한·테넌트·실행 비용은 운영 서버가 매번 다시 검사합니다. DD-01 F3에서 AI/파트너 호출자를 포함하면 그 호출자는 B 경로가 필요할 수 있습니다.

단, 기술팀은 F1 전에 “등록은 실행 의미를 바꾸지 않는 입장 정책/최적화”라는 단일 파이프라인을 우선 제안하고 E1 비용을 제시해야 한다. Manifest 서명, 캐시 키, 추출 방식은 창시자 질문이 아니라 기술 제안이다.

## 7. 구체적 수정 제안

### P0

1. **C.1·C.2:** “같은 정책이 빌드 때 적용”을 “빌드에서는 구조·타입·capability·정적 비용을 검사하고, actor·tenant·현재 정책·실행 상한은 서버가 매 요청 평가”로 바꾼다.
2. **B.1·C.3:** Manifest를 실행 권한 증명서가 아닌 등록된 canonical shape/사전 계획 식별자로 정의한다. ID는 앱·환경·operation kind·capability·schema/compiler protocol version에 결박하고 서버 활성 목록과 폐기 규칙을 둔다.
3. **C.1:** “단일 런타임 의미 파이프라인 + 선택적 명시 등록/plan prewarm + registered-only admission” 대안을 추가해 2-R/2-M/2-RM과 공정 비교한다. 정적 추출기는 필수 전제가 아닌 후속 최적화로 내린다.
4. **C.2·D:** 자동 계약 검사, plan prewarm, 사람 승인을 분리한다. 사람 검토는 capability 확대나 예외 승인에만 두고 요청 모양마다 요구하지 않는다고 명시한다.
5. **C.2:** 개발 즉시 실행에 canonical hash와 운영 등록 적격성 진단을 붙이고, CI/로컬 production-parity 검사를 정의한다. 개발과 운영의 의미·오류 코드가 같다는 관찰 가능 조건을 쓴다.
6. **C.3·G:** E1~E3 전에 “자사 프론트면 2-M 기본”이라고 추천하지 않는다. 우선 단일 2-R 의미 파이프라인을 최소 기반으로 제안하고, registered-only의 기본 여부는 실험과 F1 뒤로 보낸다.

### P1

7. **C.1·신규 보안/운영 절:** 위조·치환·재생, 활성화·폐기, 구/신 프론트 공존, 롤백, 동적 경로 혼동, 캐시 오염과 무효화를 위협 모델 및 수용 조건으로 추가한다.
8. **C.1:** 2-R도 canonical plan cache/prewarm을 쓸 수 있고 2-M도 매 요청 정책·입력·자원 검사가 필요하다는 비용을 반영해 성능·보안 행을 다시 쓴다.
9. **E.1:** REST 호출의 정적 모양 비율 대신 실제 후보 JS/Python 작성 API로 10~20개 요청을 작성해 추출 성공률, false negative, 동적 조립, source map 진단을 잰다. DD-04 미정이면 두 후보를 비교하고 결과를 `확인 필요`로 유지한다.
10. **E.2:** 공격 차단 여부뿐 아니라 오래된 서명 manifest, 권한 철회, 테넌트 치환, 버전 엇갈림, cache cross-context를 포함한다. I1~I7은 2-R과 2-M 모두 동일하게 통과해야 한다.
11. **E·D:** 화면 변경당 프론트 수정 외 작업 수, 중앙 검토 횟수, 등록/배포 시간, 롤백 복구 시간, 구버전 동시 지원량을 측정한다. 운영 표면 감소와 총 개발·운영 비용을 함께 비교한다.

### P2

12. **A·C.1:** “호출자 신뢰 등급”을 실행 모드 선택 기준으로 쓰지 말고, 요청 provenance/등록 상태와 서버가 부여한 credential·capability·rate budget을 분리해 표현한다.
13. **F:** 현재 F1을 위의 “자사 프론트 운영 admission 기본값” 질문으로 바꾸고 DD-01 F3과의 선후·독립성을 설명한다.
14. **사실 근거/E.3:** “기존 계획기 재사용”을 compiler/parser/IR/SQL emitter/plan type/runtime guard별로 나눠 검증한다. 재사용률과 필요한 변형을 확인하기 전에는 2-M 추가 비용에서 빼지 않는다.

## 8. 결론과 추천

추천은 **2-R을 별도 제품 모드가 아니라 단일 canonical 의미·검증·실행 파이프라인의 기반으로 삼고, 그 위에 명시 등록과 plan prewarm, 선택적 `registered-only` admission을 얹는 대안**이다. 이것은 창시자 승인 전 기술 추천이며, 실제 기본 운영 정책은 E1~E3와 고친 F1 답 뒤에 정해야 한다.

이유는 세 가지다. 첫째, 호출자 표현과 서버의 매 요청 권한 판단을 동시에 보존한다. 둘째, manifest가 정책을 대신하지 않아 DD-01 I1~I7 및 DD-02 capability 기본 거부와 일관된다. 셋째, 범용 정적 추출기와 이중 의미 체계를 초기에 필수화하지 않아 PART V의 수단-목적 역전 위험이 작다.

DD-03의 현재 추천은 자사 프론트만이면 2-M, 동적 호출자가 있으면 2-RM이다(`DD-03:110`). 나는 이 조건 분기를 기본 아키텍처로 삼는 데 반대한다. 호출자 범위는 admission과 한도에는 영향을 주지만, 요청 의미와 런타임 정책 평가 체계까지 둘로 갈라야 한다는 근거는 아니다. 등록 전용 운영이 실제로 순이익이라는 증거가 나오면 자사 프론트의 배포 정책으로 선택할 수 있지만, 그때도 서버는 actor·tenant·현재 정책·자원 상한을 매 요청 판단해야 한다.
