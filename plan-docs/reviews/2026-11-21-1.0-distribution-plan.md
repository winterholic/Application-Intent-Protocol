# 1.0 배포 채널 조사와 릴리스 자동화 계획 (2026-11-21)

범위: AIP 1.0의 GitHub Release, npm, PyPI, Docker 채널 현황, 이름 소유권, 버전 정책, 릴리스 자동화 설계. 기준 커밋은 `origin/main` `723fb474`다.

이 문서는 계획이며 승인이 아니다. 이번 조사에서는 어떤 registry에도 publish하지 않았고, 태그·릴리스·이름 선점 등록도 하지 않았다. 버전 문자열도 바꾸지 않았다(Core·TS SDK·Python SDK는 여전히 0.1.0). 토큰과 비밀값은 읽거나 출력하지 않았다. 실제 배포 성공과 "산출물이 로컬에서 만들어짐"은 다른 일이며, 아래 §4는 앞의 것만 다룬다.

표기: `확인 필요`는 이번 조사에서 확인하지 못한 값이다. `추정`은 관찰에서 이끌어 낸 판단이다.

## 1. PyPI `aip-sdk` 소유권과 대체 이름

조회 시각: 2026-11-21 00:19 KST. 방법: `https://pypi.org/pypi/<name>/json`.

```
$ curl -s https://pypi.org/pypi/aip-sdk/json | jq '.info | {name,author,author_email,home_page,project_urls,version}'
{ "name": "aip-sdk", "author": null, "author_email": "Patrik Kjaerran <patrikkja@gmail.com>",
  "home_page": null, "project_urls": {"homepage": "https://github.com/patrikkj/aip", "repository": "https://github.com/patrikkj/aip"},
  "version": "0.0.1" }
```

- 소유자는 winterholic이 아니다. 릴리스는 0.0.1 하나이고 업로드는 2025-01-27이다. 요약은 "AI Pipelines (AIP) SDK Python Package"로, 이 프로젝트(Application Intent Protocol)와 무관하다.
- wheel(1034 bytes)에는 `dist-info`만 있고 Python 모듈이 없다. 의존성은 aiohttp, nest-asyncio, polars, pydantic이다. 즉 자리만 잡아 둔 이름이다.
- 영향: 현재 `product/python/pyproject.toml`의 `name = "aip-sdk"`로는 publish할 수 없다(같은 이름은 소유자만 올릴 수 있다). `SDK.md`는 `pip install ./product/python`만 안내하므로 문서가 이미 틀린 `pip install aip-sdk`를 약속하지는 않는다. 다만 사용자가 추측으로 `pip install aip-sdk`를 치면 남의 껍데기가 설치된다.
- 이름 회수(PEP 541)는 가능성은 있으나 승인 기간과 결과가 불확실하다. 이 계획의 경로로 삼지 않는다.
- 비슷한 이름의 다른 프로젝트: `aip-protocol`(kyalabs, "Agent Intent Protocol", 0.4.0, 2026-03-30), `aip-py`(0.0.4). 약어 AIP가 겹치는 프로젝트가 이미 있으므로 이름에서 "Application Intent"를 풀어 쓰는 편이 혼동이 적다(추정).

대체 이름 후보(전부 조회 시점 HTTP 404, 즉 PyPI 미등록). 선호 순서:

| 순위 | 이름 | PyPI JSON | 이유 |
| --- | --- | --- | --- |
| 1 | `application-intent-protocol-sdk` | 404 | 저장소명과 일치하고 약어 충돌이 없다 |
| 2 | `aip-app-sdk` | 404 | 짧다. 약어는 남는다 |
| 3 | `winterholic-aip-sdk` | 404 | 네임스페이스가 소유자로 고정돼 충돌 위험이 가장 낮다. 이름이 길고 개인 이름이 노출된다 |

그 외 404였던 이름: `application-intent-protocol`, `aip-intent-sdk`, `aip-service-sdk`.

- 미등록은 "지금 비어 있다"는 뜻이다. 소유자가 이름을 정하면 §7.3의 PyPI pending publisher가 첫 publish 때 이름을 확보한다. 그 전에는 선점 등록을 하지 않는다.
- import 이름 `aip_sdk`는 배포 이름과 독립이다. 제3자 wheel에 모듈이 없어 지금은 충돌하지 않는다. 1.0에서는 import 이름을 유지(`import aip_sdk`)하고 배포 이름만 바꾸는 안을 권한다. 결정은 소유자 몫이다.
- PyPI 이름은 `-`, `_`, `.`를 같게 정규화한다. 위 조회는 정규화된 이름 기준이다.

## 2. npm `@aip` scope와 후보

조회: `npm view <pkg> name`(npm 11.19.1), registry 검색 API. 조회 시각은 §1과 같다.

| 이름 | 결과 |
| --- | --- |
| `@aip/sdk`, `@aip/cli`, `@aip/core` | 모두 E404 |
| `aip-sdk`(비 scope) | E404 |
| `@aip-protocol/sdk`, `@aip-app/sdk`, `@application-intent-protocol/sdk`, `@winterholic/aip-sdk` | 모두 E404 |
| `npm whoami` | `ENEEDAUTH`. 이 환경은 npm에 로그인돼 있지 않다 |

- `E404`는 "그 이름의 패키지가 공개되어 있지 않다"만 뜻한다. scope(사용자 또는 org 이름)의 소유 여부는 구분하지 못한다. 비인증 API로 scope 소유자를 확인하는 방법을 찾지 못했다. registry 검색의 `scope:` 한정자는 대조 질의(`scope:types`가 1건)에서 결과가 맞지 않아 쓸 수 없다. `www.npmjs.com/org/aip`은 403(Cloudflare)이다. 따라서 `@aip`의 소유자는 `확인 필요`다.
- 공개 패키지가 하나도 안 보이는 scope도 org로 등록돼 있을 수 있다. `aip`는 3글자 이름이라 이미 등록됐을 가능성을 무시할 수 없다(추정). 확인법은 소유자가 npm에 로그인해 `@aip` org 생성을 시도하는 것이다(이미 있으면 거부된다). 생성은 이름 확보이므로 이 조사에서는 하지 않았다.
- 소유자 쪽 사전 확인 항목: npm 사용자명이 `winterholic`이면 `@winterholic` scope는 별도 생성 없이 쓸 수 있다(`확인 필요`, npm 계정 정보를 읽지 않았다).
- 대체 scope 후보(모두 `@<scope>/sdk` 404, scope 소유는 위와 같이 미확인): 1) `@application-intent-protocol`, 2) `@aip-app`, 3) `@winterholic`. PyPI와 같은 철학으로 풀네임 scope를 1순위로 권한다. npm 패키지명 자체는 scope가 정해지면 `@<scope>/sdk`다.
- npm에는 유사 이름 차단 규칙이 있다. 이름이 404여도 publish 때 거부될 수 있다(`확인 필요`).
- crates.io 참고: `aip-cli`(0.11.0), `aip`(0.3.0), `aip-sdk`(1.8.1)는 제3자 crate가 이미 있다. 이 저장소의 Cargo workspace를 crates.io에 올릴 계획은 없지만, 문서에 `cargo install aip-cli`를 안내하면 남의 crate가 설치된다. `aip-contract`, `aip-syntax`는 404다. CLI는 GitHub Release 아카이브로만 배포하고 README에 이 사실을 적는다.

## 3. GitHub Releases, tags, 권한, 현재 설정

모두 읽기 확인이다.

```
$ gh release list -R winterholic/Application-Intent-Protocol          (출력 없음)
$ gh api repos/winterholic/Application-Intent-Protocol/releases --jq length   → 0
$ gh api repos/winterholic/Application-Intent-Protocol/git/matching-refs/tags --jq length   → 0
$ gh api repos/winterholic/Application-Intent-Protocol --jq '{private,permissions}'
{"permissions":{"admin":true,"maintain":true,"pull":true,"push":true,"triage":true},"private":false}
```

- Release 0개, 태그 0개. 저장소는 공개이고 라이선스는 MIT다(LICENSE 저작권 표기는 "Kim Daeseon").
- 활성 계정 `winterholic`은 admin·push 권한이 있어 release와 태그를 만들 수 있다. 토큰 scope는 `gist, read:org, repo, workflow`다. 실제 생성은 하지 않았으므로 "생성 성공"은 검증하지 않았다. 다른 로그인 계정 `daeseon-dev`는 이 저장소 권한을 조사하지 않았다.
- 현재 저장소 설정: rulesets 없음(빈 응답), environments 없음, Actions 정책 `allowed_actions: all`, `sha_pinning_required: false`, immutable releases `{"enabled":false}`, secret scanning과 push protection은 enabled다. 기존 workflow는 대부분 액션을 SHA로 고정하고 `permissions: contents: read`를 쓴다. 새 workflow도 같은 규칙을 따른다.
- 기존 CI는 Release를 만들지 않는다. 산출물 업로드는 `aip-release-gate.yml`의 `upload-artifact`(retention 7일)뿐이다.

관찰된 문제(배포 계획에 반영):

1. **PG* 환경 변수가 빌드를 막는다.** `crates/aip-test-support/build.rs`는 `PG*`로 시작하는 환경 변수가 하나라도 있으면 빌드 자체를 panic시킨다. 릴리스 workflow는 깨끗한 runner에서 돌므로 문제없지만, 소유자 로컬 릴리스 빌드나 DB 환경이 있는 셸에서는 재현된다. 릴리스 문서에 `env -u PGHOST ...`를 적거나 build.rs가 release 빌드에서 이 검사를 건너뛰게 하는 방안을 검토한다(코드 변경은 이번 범위 밖).
2. **TS 패키지 `private: true`.** `build-sdk.mjs`가 쓰는 `package.json`에 `"private": true`가 있어 `npm publish`가 거부된다(npm 동작 기준, publish는 시도하지 않았다). 또 `repository`, `description`, `README`, `LICENSE`, `publishConfig`가 없다. npm provenance는 `repository.url`이 실제 저장소와 맞아야 한다. 의도된 로컬 전용 설정이므로 1.0에서 빌더 옵션(예: `--publishable`)으로 분리하는 편이 안전하다.
3. **tarball 내부 경로.** 파일이 `package/product/sdk/...`, `package/spikes/spike-v5-sdk/sdk/...`, `package/spikes/spike-v6-transport/client/...`로 들어간다. 동작은 하지만 공개 패키지에 내부 spike 이름이 노출된다. 1.0에서 평탄화(`dist/` 단일 트리)를 검토하되, 이는 SDK.md의 "기존 구현 재사용" 관문과 충돌하지 않게 빌드 단계에서 경로만 재배치하는 방식이어야 한다. 이번 조사에서 평탄화를 시도하지 않았다.
4. **Python 메타데이터가 최소다.** wheel에는 LICENSE, README, authors, URLs, classifiers가 없다(METADATA 6줄). `twine check`는 `PASSED with warnings`(long_description 없음)였다. `License-Expression: MIT`는 있으나 라이선스 파일이 패키지에 없다. 버전이 `pyproject.toml`과 `aip_sdk/__init__.py`의 `__version__` 두 곳에 있다.
5. **`python -m build`는 소스 트리를 더럽힌다.** `product/python/aip_sdk.egg-info`가 남았고, 그 상태에서 `python_sdk_test`의 `test_clean_venv_package_install_and_import_smoke`가 `AssertionError: Lists differ`로 실패했다. 잔여물을 지우자 30개 모두 통과했다(RED→GREEN은 이 한 쌍으로 확인). 릴리스 workflow는 새 checkout에서만 빌드하고 `--outdir`을 소스 밖에 둔다.
6. **버전 0.1.0이 코드 곳곳에 하드코딩돼 있다.** 아래 §5.2의 표 참고. 한 곳만 바꾸면 `PACKAGE_IDENTITY` 검사가 실패한다.
7. **Linux 바이너리 glibc 하한.** trixie(glibc 2.41)에서 빌드한 aarch64 바이너리는 `GLIBC_2.39`를 요구한다(`objdump -T`). ubuntu-24.04 runner(glibc 2.39)에서 빌드해도 비슷한 하한이 생길 것으로 추정한다(미실행). Debian 12(2.36)나 Ubuntu 22.04(2.35)에서는 실행되지 않는다. 지원 하한 OS를 정하고, 필요하면 오래된 glibc 컨테이너에서 빌드한다. 현재 Docker 이미지는 trixie 기반이라 무관하다.
8. **macOS 바이너리 하한.** `minos 11.0`, 링크 대상은 시스템 프레임워크와 libSystem뿐이다(`otool`). 외부 동적 라이브러리 의존은 없다.
9. **Docker 이미지는 앱 단위다.** `deploy/Dockerfile`은 앱 패키지를 `COPY`하는 구조라 일반 공개 이미지가 없다. 레지스트리에 올리지 않았으므로 이미지 digest는 로컬 값뿐이다. Docker Hub `winterholic` 네임스페이스는 존재하며 저장소는 0개다. ghcr 패키지는 토큰 scope(`read:packages` 없음) 때문에 조회하지 못했다(`확인 필요`).
10. 크로스 컴파일은 지원하지 않는다(`app-package.mjs`의 `TARGET_MISMATCH`). 호스트에서 `check`를 돌리면 Linux 패키지는 `TARGET_MISMATCH`를 낸다. 정상 동작이다. 따라서 플랫폼별 아카이브는 플랫폼별 runner에서 빌드해야 한다.

미실행: macOS x64와 Linux x86_64 빌드(이 호스트로는 실행 불가), 전체 `scripts/release-gate.sh`(전용 PostgreSQL 필요), `app-deploy-live.test.mjs`(Docker로 DB 컨테이너를 띄우는 시험이라 이번 범위 밖), `npm publish --dry-run`(publish 계열 명령이라 피함).

| Linux GNU x86_64 | `APP-DEPLOY.md:3`, `DOCKER.md:7`, `APP-MANIFEST.md`의 targets 예시 | **있음.** 전 workflow가 `ubuntu-24.04` 또는 `ubuntu-latest`(x86_64) | release gate, app-packages, Docker live 시험이 여기서 돈다 |
| Linux GNU arm64 | 같음 | **없음.** `ubuntu-24.04-arm` 사용처 없음 | 이번 조사에서 aarch64 컨테이너로 패키지·이미지·`check`만 확인(CI 아님, DB·worker 시험 안 함) |
| macOS arm64 | 같음 | **없음.** macOS runner 사용처 없음 | `RELEASE-GATE.md`와 `VERIFICATION.md`가 소유자 Mac의 수동 실행 기록으로 남음 |
| macOS x64 | 같음 | **없음** | 증거를 찾지 못했다. `VERIFICATION.md`는 "다른 OS 미실행"이라고 쓴다 |
| Windows | 문서에 지원 선언 없음, `RELEASE-GATE.md`가 미검증으로 명시 | 없음 | 해당 없음 |

- 플랫폼 build matrix는 존재하지 않는다. workflow의 `strategy.matrix`는 `cgroup.yml`의 `condition`/`sample`(실험 반복)뿐이다.
- 결론: 문서의 네 target 중 CI가 증명하는 것은 하나뿐이다. 1.0 릴리스 노트가 네 플랫폼 지원을 주장하려면 CI 증거를 만들거나, 문서를 "공식 검증: Linux x64, 수동 검증: macOS arm64, 미검증: 나머지"로 낮춰야 한다. 이 계획의 §7은 전자를 택한다. 단 3개 플랫폼 모두에서 전체 gate(PostgreSQL, bubblewrap worker)를 돌릴 필요는 없다. 최소 요건은 "빌드, `aip --version`, `service check`, SDK smoke(`smoke.mjs`), `shasum` 검증"이다. worker 격리는 Linux 전용 기능이라 macOS는 sandbox-exec 경로를 별도 확인한다.

## 6. 버전 정책 제안

### 6.1 패키지 버전

- **1.0.0 lockstep.** Core(Cargo workspace), `@<scope>/sdk`, PyPI SDK가 같은 SemVer 숫자를 가진다. 근거: 두 SDK는 같은 wire 계약에 묶인 얇은 호출자이고, 호환 표를 하나로 유지하면 소유자가 혼자 운영하기 쉽다. 이후 1.x에서 SDK만 고칠 때도 같은 버전을 올리는 비용이 크면 그때 patch 단독 릴리스를 도입한다(2.0 전에 재검토).
- SemVer를 따른다. patch는 호환 버그 수정, minor는 호환 추가, major는 wire 계약이나 생성 binding 호환이 깨질 때다.
- 사전 릴리스는 `1.0.0-rc.N`으로 태그한다. 표기 변환: Cargo와 npm은 `1.0.0-rc.1`, PyPI는 PEP 440의 `1.0.0rc1`이다. npm은 `--tag next`로 올려 `latest`를 오염시키지 않는다. 변환은 스크립트 한 곳에서 한다.
- publish는 되돌릴 수 없다. npm은 같은 버전 재사용을 막고, PyPI는 파일 이름 재사용을 막는다. 따라서 rc를 반드시 한 번 거친다.
- 버전 원천은 `Cargo.toml`의 workspace 버전 하나로 한다. `product/tools/version.mjs`(신규)가 이를 읽어 build-sdk, package, app-package, smoke가 쓰고, Python은 빌드 전에 `pyproject.toml`과 `__version__`을 같은 값으로 쓰는 스크립트(`scripts/sync-version.mjs`)와, 불일치를 막는 `scripts/check-versions.mjs --tag vX.Y.Z`를 둔다. 후자는 PR CI에서도 돈다.

### 6.2 프로토콜, 계약, 호환 표기

현재 코드에 있는 버전 표지(확인):

| 표지 | 값 | 위치 | 성격 |
| --- | --- | --- | --- |
| wire/계약 문서 버전 | `aip-protocol/0.1` | `crates/aip-contract/src/lib.rs:20` | 계약 문서(`/aip/describe`)의 `protocol` 필드. 생성 TS 헤더 주석에도 기록 |
| Core IR 버전 | `aip-core/0.11` | `crates/aip-ir/src/lib.rs:40` | 의미 체계 버전. 계약의 `core_ir` 필드 |
| 계약 지문 | sha256 | `x-aip-contract` 헤더와 `/capabilities`의 `contractFingerprint` | 앱 계약 정체성. 정확히 일치해야 하며 순서가 없다 |
| 앱 매니페스트 | `app-manifest-v1.json` | `aip.app.json`의 `$schema` | 매니페스트 형식 |
| 패키지 형식 | `BUILD.json`의 `format: 1` | `app-package.mjs:178` | 앱 패키지 형식 |

제안:

1. 1.0에서 `PROTOCOL_VERSION`을 `aip-protocol/1.0`으로, Core IR을 `aip-core/1.0`으로 올린다. 숫자 0.x는 "깨질 수 있음"으로 읽히므로 1.0 선언과 맞지 않는다. 이 변경은 계약 JSON·생성 TS 골든(`crates/aip-cli/tests/golden/*`)이 바뀌므로 별도 PR로 하고 골든 변경이 의도한 줄만인지 확인한다. 이번 단계에서는 하지 않았다.
2. 의미 규칙: protocol의 major가 호환 경계다. 1.x 안에서는 계약 문서에 선택 필드를 더하는 변경만 허용하고(과거 기록도 같은 규칙, `docs/design/agent-logs/.../agent-forms6-log.md`), 필드 제거·의미 변경·오류 코드 삭제는 major다. 오류 코드 레지스트리(`spec/wire-errors.md`)의 추가는 minor, 삭제는 major다.
3. 엔진 버전과 protocol 버전은 별개다. 엔진 `1.4.2`가 `aip-protocol/1.0`을 말한다. 호환 표기는 문서와 메타데이터 양쪽에 둔다.
   - `COMPATIBILITY.md`(신규): 엔진·SDK 버전, 지원 protocol, Core IR, 앱 매니페스트 형식, 패키지 형식의 표. 릴리스마다 한 줄 추가한다.
   - npm `package.json`에 `"aip": { "protocol": "aip-protocol/1.0" }`, Python에 `aip_sdk.PROTOCOL = "aip-protocol/1.0"` 상수와 METADATA의 `Project-URL`로 호환 표 링크를 둔다.
   - `/capabilities`가 서버 protocol을 반환하고 SDK가 지원 major와 비교해 불일치하면 `CLIENT.PROTOCOL_ERROR`를 내는 검사를 추가한다. 현재 SDK는 지문 불일치만 검사한다(`product/python/aip_sdk/__init__.py:274-317`). `/capabilities` 응답에 `protocol`이 실리는지는 계약 문서(`describe`)에서만 확인했고 `/capabilities` 필드는 확인하지 못했다(`확인 필요`).
4. 계약 지문(`contractFingerprint`)은 그대로 앱 단위 정체성으로 둔다. 배포가 바뀌면 binding을 다시 생성해야 한다는 현재 규칙(`SDK.md`)은 SemVer와 독립이다.
5. 형식 번호(`BUILD.json`의 format, 매니페스트 `$schema`)는 정수로 독립 증가시키고 `COMPATIBILITY.md`에서만 대응한다. DB schema fence와 migration 호환은 `upgrade-drill`로 증명한다. 릴리스 gate의 baseline을 "직전 릴리스 태그"로 바꾸고, 롤백 두 경로가 그 태그에서 통과할 때만 minor를 낸다.

### 6.3 1.0 전환 절차(구현 순서)

1. 버전 원천 통일과 `check-versions` 추가(동작 변경 없음, 0.1.0 유지).
2. 패키지 메타데이터 수정(§3의 npm·Python 항목, LICENSE, README 포함).
3. protocol·Core IR을 1.0으로 올리는 PR(골든 갱신).
4. 모든 버전을 `1.0.0-rc.1`로 올리는 커밋과 rc 태그.
5. rc 검증 후 `1.0.0`.

## 7. 릴리스 자동화 설계

모든 것은 설계이며 workflow 파일은 만들지 않았다(이 단계는 계획 문서만 커밋한다). 파일 후보는 `.github/workflows/release.yml`이다.

### 7.1 트리거와 보호

- `on.push.tags`: `v[0-9]+.[0-9]+.[0-9]+` 와 `v[0-9]+.[0-9]+.[0-9]+-rc.[0-9]+`.
- `workflow_dispatch`(입력 `dry_run`, 기본 true): 태그 없이 전체 빌드와 검증, 산출물 업로드까지만 하고 attestation·release·publish는 건너뛴다. 최초 시험은 이 경로다.
- 최상위 `permissions: {}`로 시작하고 job마다 필요한 권한만 부여한다. 액션은 기존 규칙대로 커밋 SHA로 고정한다.
- 태그 ruleset: `v*` 태그는 소유자만 생성하고, 수정·삭제를 금지한다(§7.3).
- `verify` job: `git merge-base --is-ancestor $GITHUB_SHA origin/main`으로 태그가 main 위에 있는지 확인하고, `scripts/check-versions.mjs --tag $GITHUB_REF_NAME`로 태그와 Cargo, npm, Python 버전이 일치하는지 확인한다. 같은 SHA의 `AIP 1.0 release gate` 성공 여부는 `gh run list --commit`으로 확인한다(없으면 실패, 재실행은 소유자가 한다).

### 7.2 job 구성

```
verify ─┬─ build-cli (matrix) ─┐
        ├─ build-sdk-ts ───────┼─ assemble ─ attest ─ draft-release ─┬─ publish-npm   (env: npm-publish)
        └─ build-sdk-py ───────┘                                    ├─ publish-pypi  (env: pypi)
                                                                     └─ finalize-release (두 publish 성공 후 draft 해제)
```

1. **build-cli**: 플랫폼 runner에서 `cargo build --release --locked -p aip-cli`.

   | target | runner | 비고 |
   | --- | --- | --- |
   | `x86_64-unknown-linux-gnu` | `ubuntu-24.04` | glibc 하한 확인(§4-7) |
   | `aarch64-unknown-linux-gnu` | `ubuntu-24.04-arm` | 공개 저장소 무료 여부 `확인 필요` |
   | `aarch64-apple-darwin` | `macos-14` | |
   | `x86_64-apple-darwin` | Intel macOS runner(`macos-15-intel` 등) | runner 종료 시점과 제공 여부 `확인 필요`. 쓸 수 없으면 이 target은 1.0에서 제외하고 문서를 고친다 |

   크로스 컴파일을 지원하지 않으므로 target마다 자기 runner에서 빌드한다. 각 job은 아카이브 `aip-<version>-<target>.tar.gz`(`bin/aip`, `LICENSE`, `README.md`, `config.example.json`, `example.aip`)를 만들고, 풀어서 `aip --version`이 태그 버전과 같은지, `service check example.aip`가 통과하는지 확인한 뒤 업로드한다. 가능하면 `package.mjs --profile release`로 만든 기존 묶음(`SHA256SUMS`, SDK tarball 포함)을 그대로 쓴다. 이미 있고 검증된 경로이기 때문이다. runner에는 `PG*` 환경 변수를 두지 않는다(§4-1).
2. **build-sdk-ts**: 새 checkout에서 `npm ci --prefix spikes/spike-0-ts --ignore-scripts`, 게시용 옵션으로 `build-sdk.mjs`, `npm pack`. `sdk-package.test.mjs`를 먼저 돌린다.
3. **build-sdk-py**: `python -m build --outdir "$RUNNER_TEMP/py"`(소스 밖), `twine check --strict`, 클린 venv에 wheel 설치 후 `import aip_sdk`와 `aip_sdk.__version__ == 태그 버전` 확인.
4. **assemble**: 모든 산출물을 `dist/`에 모으고 아래 둘을 만든다.
   - `SHA256SUMS`: `shasum -a 256 -c`로 검증 가능한 단일 파일. 아카이브 4개, TS tarball, wheel, sdist를 포함한다.
   - `aip-<version>-manifest.json`: `{ version, git_sha, tag, protocol, core_ir, files: [{name, sha256, size, target}] }`. Release 본문과 `COMPATIBILITY.md` 갱신 근거로 쓴다.
5. **attest**(`id-token: write`, `attestations: write`): `actions/attest-build-provenance`를 `subject-path: dist/*`로 실행한다. 저장소가 공개라 Sigstore 공개 인스턴스에 기록된다(비공개였다면 다른 조건 `확인 필요`). 사용자 검증은 `gh attestation verify <file> --repo winterholic/Application-Intent-Protocol`이다. SBOM(`actions/attest-sbom`, CycloneDX)은 선택 사항으로 1.0.1 이후에 검토한다.
6. **draft-release**(`contents: write`): `gh release create "$TAG" --draft --verify-tag --title ... --notes-file ... dist/*`. 초안으로만 만든다. rc는 `--prerelease`를 붙인다.
7. **publish-npm**(environment `npm-publish`, 소유자 승인 대기): `actions/setup-node`에 `registry-url`, `npm publish <tgz> --provenance --access public`(rc는 `--tag next`). `id-token: write`가 필요하다. 인증은 npm Trusted Publishing(OIDC)을 우선하고, 이를 쓰려면 npm CLI 11.5.1 이상이어야 한다. runner의 npm 버전은 `확인 필요`다. 이미 같은 버전이 있으면(`npm view name@version`) 건너뛴다.
8. **publish-pypi**(environment `pypi`): `pypa/gh-action-pypi-publish`에 `id-token: write`만 부여하고 장기 토큰은 쓰지 않는다. PEP 740 attestation을 켠다(`attestations: true`). 리허설은 별도 environment `testpypi`와 `repository-url: https://test.pypi.org/legacy/`로 한다.
9. **finalize-release**: 두 publish가 모두 성공했을 때만 draft를 해제한다. 하나라도 실패하면 draft로 남기고 소유자가 판단한다.

### 7.3 소유자가 해야 하는 설정(내가 할 수 없는 것)

내가 대신하면 이름 선점이나 계정 변경이 되므로 하지 않았다.

1. **이름 결정**: PyPI 배포 이름(§1), npm scope(§2). import 이름을 유지할지.
2. **npm**: 계정 로그인과 2FA 활성화. scope 확보(`@aip`가 가능한지 org 생성으로 확인하고, 불가하면 후보 scope). 첫 publish 이후 패키지 설정에서 Trusted Publisher를 등록한다(GitHub Actions, owner `winterholic`, repo `Application-Intent-Protocol`, workflow `release.yml`, environment `npm-publish`). 패키지가 없는 상태에서 Trusted Publisher를 먼저 등록할 수 있는지는 `확인 필요`다. 불가하면 첫 rc만 단기 granular token으로 올리고(environment secret, publish 직후 폐기), 이후는 OIDC로 전환한다.
3. **PyPI**: 계정과 2FA. Account → Publishing에서 **pending publisher**를 등록한다(프로젝트 이름, owner, repo, workflow `release.yml`, environment `pypi`). 이 등록이 첫 publish 때 프로젝트를 만든다. TestPyPI도 같은 방식으로 한 번 더 등록한다.
4. **GitHub Settings**:
   - Environments 생성: `npm-publish`, `pypi`, `testpypi`, `release`. Required reviewers에 소유자를 지정하고 deployment 대상을 `v*` 태그로 제한한다.
   - Rulesets: `v*` 태그의 생성은 소유자만, 수정·삭제 금지. main 보호가 이미 있는지는 이번에 확인하지 않았다(`확인 필요`).
   - Actions 기본 workflow 권한을 read-only로, `sha_pinning_required`를 켠다(현재 false).
   - Immutable releases: 첫 릴리스가 문제없이 만들어지는 것을 본 뒤 켠다(현재 `enabled: false`). 켜면 게시된 release의 자산과 태그를 바꿀 수 없다.
   - `CODEOWNERS`로 `.github/workflows/`를 소유자 리뷰 필수로 만든다.
5. **Docker**: 1.0에는 공개 이미지를 내지 않는 안을 권한다. 이미지는 앱 단위이고 DOCKER.md의 지원 범위도 "앱 패키지 → 사용자가 직접 `docker build`"다. 공개 엔진 이미지를 원하면 새 Dockerfile과 `ghcr.io/winterholic/...` multi-arch 빌드, `provenance`/`sbom` 옵션, 이미지 digest의 attestation(`push-to-registry`)이 필요하다. 이는 1.0 이후 작업으로 둔다. 그때는 ghcr 패키지 공개 설정과 `packages: write`가 필요하다.
6. **runner 가용성 확인**: `ubuntu-24.04-arm`과 Intel macOS runner가 이 저장소에서 쓸 수 있는지(§7.2).
7. **서명 키는 만들지 않는다.** attestation은 OIDC 기반이라 별도 키가 없다. 이후 GPG 서명이 필요하면 별도 결정이다.

### 7.4 시험 순서

1. `workflow_dispatch` dry-run(publish 없음)을 branch에서 돌려 아카이브와 `SHA256SUMS`를 내려받아 검증한다.
2. TestPyPI에서 wheel publish 리허설, npm은 `npm publish --dry-run`(소유자 승인 후).
3. `v1.0.0-rc.1` 태그: draft release, `gh attestation verify`, 각 플랫폼 설치 확인.
4. rc 문제 없으면 `v1.0.0`. draft를 소유자가 최종 해제한다.
5. 실패 처리: publish가 부분 성공하면 같은 버전을 다시 올릴 수 없다. patch를 올려 새 태그로 간다.

## 8. 결정이 필요한 항목(소유자)

1. PyPI 배포 이름(§1 후보 중 선택)과 import 이름 유지 여부.
2. npm scope(§2). `@aip` 확보를 시도해 볼지, 풀네임 scope로 갈지.
3. lockstep 버전 정책(§6.1)과 protocol 1.0 승격(§6.2)의 승인.
4. 1.0 지원 플랫폼 범위: 네 target 모두 CI로 증명할지, 문서를 낮출지.
5. Linux 지원 glibc 하한.
6. 공개 Docker 이미지의 시기(1.0 포함 여부).
7. TS tarball의 내부 경로 평탄화 시점(1.0 전 또는 이후).
