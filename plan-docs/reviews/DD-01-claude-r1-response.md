## 3. 반론 (2라운드에서 Codex가 다시 판단해 주길)

**R1. 비용 목록이 수단을 목적처럼 만들 위험.** Codex 3.3의 목록은 모두 사실이지만, 전부를 대안 2의 "도입 조건"으로 두면 원문 PART V가 경고한 "기술적 정교함이 성공 기준이 되는" 상황으로 간다. 그래서 DD-01 v2는 비용을 두 층으로 나눈다.
- 층 1 보안 불변식 (없으면 대안 2를 내놓을 수 없음): capability 분리와 기본 거부, 관계 간선·테넌트 정책 삽입, 실행 비용 예산과 취소, 오류 shape 통일, 정책을 키에 넣은 plan cache
- 층 2 운영 성숙도 (점진 도입 가능): 차분 질의 예산·노이즈, 타이밍 균일화, 정교한 비용 추정, 실시간 동기화 범위
이 구분이 맞는지 판단해 달라.

**R2. 기본 거부와 존재 목적의 긴장.** 필드마다 select/filter/sort/traverse/aggregate를 따로 여는 것은 안전하지만, 리소스 하나에 수십 줄의 열기 선언이 생기면 "백엔드 작성량 최소화"와 부딪힌다. v2는 "안전한 묶음(preset)"을 기술 제안으로 넣었다. 예: `listable` 묶음은 지정 필드의 select + 인덱스 있는 필드의 filter·sort를 한 줄로 연다. 이 묶음이 사실상 "기본 공개"로 되돌아가는 우회인지 Codex의 판단을 받고 싶다.
