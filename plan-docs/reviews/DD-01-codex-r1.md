### 1.1 “모집 목록을 돌려주는 GET 10개” — **틀림**

- 그러나 표의 10개가 모두 “모집 목록”은 아니다. `RecruitmentListRes`를 반환하는 목록형 GET은 8개다: `RecruitmentController.java:72-79`, `81-88`, `90-97`, `99-106`, `108-114`, `116-122`, `124-129`, `131-136`. 나머지 둘은 존재 여부 `boolean`인 `RecruitmentController.java:138-143`과 단건 `RecruitmentRes`인 `RecruitmentController.java:145-150`이다.

### 1.2 “같은 가시성 규칙이 5곳에 복사” — **부분적으로 맞지만 수치와 규칙 정의가 부정확**

- DD-01이 인용한 정확한 합성식, 즉 `활성 && (교외 || 요청자 학교)`는 `searchRecruitmentPage`의 본 조회 `RecruitmentRepositoryImpl.java:41-43`과 count 조회 `:59-61`, 검색 조회의 본 조회 `:136-138`과 count 조회 `:152-154`에 있다. 메서드 기준으로는 2곳, 쿼리 절 기준으로는 4곳이다.
- 교내 목록은 `활성 && 요청자 학교`를 본 조회와 count 조회에 반복한다(`RecruitmentRepositoryImpl.java:105-106`, `:122-123`). 교외 목록도 `활성 && 학교 없음`을 반복한다(`:74-75`, `:91-92`). DD-01은 이 교외 목록을 “5곳” 계산에서 빠뜨렸다.
- 랭킹 둘은 각각 `활성 && 학교 없음`과 `활성 && 요청자 학교`다(`RecruitmentRepositoryImpl.java:165-166`, `:176-177`). 그러므로 넓게 “활성·학교 범위 가시성의 변형이 여러 조회에 흩어졌다”고 말하는 것은 맞지만, 동일한 한 규칙이 정확히 5곳에 복사됐다고 할 수는 없다. 목록 메서드 기준으로는 관련 조각이 6곳이고, 그 안의 본 조회/count 중복까지 세면 더 많다.
- 가시성의 일부는 서비스 계층에도 있다. 교내 목록은 학교 인증 후 학교를 넘긴다(`RecruitmentListService.java:59-65`), 교내 랭킹도 같은 검사를 한다(`:106-112`), 동아리 목록은 별도 학교 일치 검사를 한다(`:82-93`). 따라서 “리포지토리의 다섯 줄만 중앙 정책으로 옮기면 가시성 중복이 모두 사라진다”는 결론도 성급하다.

### 1.3 `50~53행` 임의 정렬 — **코드 구조는 맞고 실제 허용 범위는 확인 필요**

## 2. 철학 정합성 비판

### 2.1 호출자 중심 표현은 잘 잡았지만 “서버는 정책만”으로 너무 빨리 축소했다

DD-01의 큰 방향은 원문과 맞는다. 창시자 원문은 프론트가 필요한 데이터와 동작을 표현하고 엔진이 의미·권한을 검증해 실행 방법을 정하는 흐름을 제시한다(`founder-intent-handoff-2026-10-03.md:60-67`). 서버가 모든 요청 형태를 미리 정의하는 구조도 명시적으로 경계한다(`:85-93`). 지난 PoC의 이름 붙은 Intent만 호출하는 구조가 안전한 요청 조합까지 막는다면 최초 목적과 충돌한다는 진단도 있다(`:742-752`). 이 점에서 대안 2를 중심에 놓은 것은 정합적이다.

하지만 DD-01 A절은 바꾸려는 방향을 “서버는 누가 무엇을 볼 수 있나만 정한다”고 쓴다(`DD-01:14`). 원문에서 서버가 맡는 것은 가시성만이 아니다. 요청의 의미와 권한 검증, 실행 방법 결정, 실제 수행까지 포함한다(`founder-intent-handoff-2026-10-03.md:62-67`). 정책도 데이터 접근 범위뿐 아니라 실행 가능한 동작, 테넌트 격리, 무결성, 비용·깊이·복잡도까지 포함한다(`:125-136`). 읽기 범위로 좁혀도 필드 선택, 필터, 정렬, 관계, 집계가 서로 다른 capability와 정책을 필요로 한다. “리소스 정책만”이라는 말은 가능하지만 “가시성만”은 창시자 철학을 축소한다.

또 B.3의 “서버 쪽에서 해야 하는 일 없음”은 조건부 가정을 결과처럼 보이게 한다. 로고 관계, 북마크 집계, 마감일 필터·정렬 capability가 이미 계약에 열렸을 때만 서버 변경이 없다. 원문 역시 첫 단계로 “필요한 정책·데이터 정의를 준비”한다고 했다(`founder-intent-handoff-2026-10-03.md:62`). DD-01은 이 전제 비용을 표와 예시에서 더 선명하게 분리해야 한다.

### 2.2 “요청의 자유와 실행 권한 분리”를 넓은 기본 허용과 혼동했다

원문은 표현 자유와 실행 권한이 별개이며, 요청한다고 모든 작업을 허용하지 않고, 데이터 접근 범위와 실행 가능한 동작은 서버 정책을 따라야 한다고 한다(`founder-intent-handoff-2026-10-03.md:125-134`; `docs/PRINCIPLES.md:8-12`). DD-01 D절은 이 문장을 인용했지만 C.3에서는 “읽을 수 있는 스칼라 필드는 필터·정렬 가능”, `count` 기본 허용을 제안한다(`DD-01:117-120`). 이는 **선택 권한을 필터·정렬·집계 권한으로 자동 승격**한다.

요청의 자유는 “모든 연산을 기본 허용”한다는 뜻이 아니다. 호출자는 서버가 공개한 capability 계약 안에서 자유롭게 조합하고, 서버는 `select`, `filter`, `sort`, `traverse`, `aggregate`를 서로 다른 권한으로 판단할 수 있다. 오히려 이 구분이 있어야 요청을 넓게 받으면서 실행 권한을 끝까지 서버에 남긴다. T01의 추천 불변식도 노출 기본 거부와 숨은 필드의 필터·정렬·집계 금지를 명시한다(`plan-docs/topics/T01-caller-model.md:24-32`). T01이 창시자 확정은 아니지만, DD-01이 같은 문서군 안에서 반대 기본값을 제안한다면 충돌을 명시해야 했다.

### 2.3 AI First를 “서버 조회 추가 여부 제거” 하나로 축소했다

원문에서 AI First는 같은 의도를 같은 구조로 표현하고, 불필요한 설정·선택지를 없애며, 문법·계약과 오류를 명확히 하는 원칙의 묶음이다(`founder-intent-handoff-2026-10-03.md:181-218`). DD-01은 “서버 조회를 추가할지 말지”라는 선택을 없앤 점만 강하게 평가하고, 요청 자체의 동치 표현 문제는 T06으로 넘겼다(`DD-01:108`, `:133`, `:187`).

그러나 읽기 조합 모델을 고르는 순간 이미 한 의도 한 구조의 경계가 생긴다. 예를 들어 관계 필터와 중첩 `where`, `count` 필드와 집계 절, 이름 붙은 서버 조회와 조합 조회, offset과 cursor, `take`와 page가 같은 의도를 중복 표현할 수 있다. DD-01 C.3의 “대안 2로 되는 것은 이름 붙은 조회로 만들지 않는다”는 방향은 좋지만(`DD-01:122`), 무엇이 “된다”를 기계적으로 판정하고 동치 요청을 canonical form으로 정규화하는 규칙이 없다. 이것은 나중 문법의 표면 문제만이 아니라 대안 2의 의미 모델 성립 조건이다.

### 2.4 GraphQL의 영감을 허용하되 복제가 아닌 이유를 설명하지 않았다

원문은 GraphQL의 호출자 중심 데이터 선택에서 영감을 받았지만 복제는 아니라고 분명히 한다(`founder-intent-handoff-2026-10-03.md:77-95`). 또한 “GraphQL 복제 금지”를 호출자 선택 금지의 근거로 쓰지 말라고 경고한다(`:781-788`). DD-01의 `select` 예시와 대안 3 자체는 이 철학에 어긋나지 않는다.

문제는 DD-01이 대안 2를 GraphQL과 구별하는 적극적 설명을 하지 않는다는 점이다. AIP 읽기 모델의 차별점 후보는 capability별 서버 계약, 정책이 삽입된 canonical plan, 동일 의도의 정규화, 명시적 비용·자원 계약, 읽기와 동작을 함께 다루는 Intent/SPR 전체 체계다. 어느 것이 필수이고 어느 것이 미결정인지 적어야 “GraphQL 비슷한 객체 쿼리”가 목적을 대신하지 않는다. 반대로 대안 3의 “필터 추측 공격이 없다”는 서술(`DD-01:106`)은 과장이다. 서버가 정한 조회 틀도 입력 파라미터와 결과 유무·개수 차이를 통해 추측 공격이 가능하다. 표면을 줄일 뿐 공격 종류가 0이 되지는 않는다.

### 2.5 자연어의 문법화는 생략할 수 없지만 실행 의미로 확정해서도 안 된다

자연어로 표현하던 목적·의도·맥락을 공식 구조나 문법으로 표현하는 것은 누락됐던 창시자 의도다(`founder-intent-handoff-2026-10-03.md:266-286`). 동시에 그것이 실행 의미, 메타데이터, 타입·계약 검증, AI 탐색 중 어디에 연결되는지는 미결정이다(`:278-285`, `:937-952`).

DD-01은 읽기 요청을 `where/orderBy/select`의 데이터 연산으로만 설명하고 이 원칙과의 관계를 전혀 다루지 않는다. 당장 자연어 목적을 요청에 넣으라는 뜻은 아니다. 다만 읽기 Intent가 다음 중 무엇을 공식적으로 담을 수 있는지는 열린 의제로 표시해야 한다: 목적, 기대 결과, 전제조건, 도메인 의미, 감사·탐색용 설명. 이 정보가 실행 권한이나 비용 판단에 영향을 주는지 여부도 창시자 결정 전에는 확정하면 안 된다. “T04와 별도”라고만 분리하면 읽기 의미 모델을 먼저 굳힌 뒤 자연어 문법화를 장식처럼 붙일 위험이 있다.

## 3. 대안 비판

### 3.1 대안 1·2·3 비교는 공정하지 않다

1. **대안 1의 새 비용을 0으로 쓴 것은 틀렸다.** “새 엔진 구성 요소가 없다”는 뜻이라면 그렇게 써야 한다. 실제로는 화면마다 Controller/Service/Repository/DTO/프론트 래퍼, 가시성 규칙 복사, 계약 동기화, 회귀 테스트와 리뷰 비용이 계속 발생한다. DD-01 자체가 B절에서 그 비용을 증명해 놓고 C.2의 “새로 생기는 비용” 행에서는 `없음`으로 지웠다(`DD-01:41-44`, `:110-111`).
2. **대안 2의 효익은 최선 조건으로, 비용은 최소 조건으로 계산했다.** “리소스·정책 범위 안이면 서버 변경 없음”은 맞지만, 새로운 관계·집계·연산 capability가 필요할 때의 서버 계약 변경과 정책 검증은 제외했다. B.3의 북마크 수가 단순 필드가 아니라 집계라는 사실부터 C.3의 별도 허용 정책이 필요하다.
3. **대안 3의 보안 우위를 절대화했다.** 서버가 조건 틀을 정하면 표면은 줄지만 파라미터 추측, 존재 오라클, 비용 공격, 관계 정책 누락은 남는다. “필터 추측 공격이 없다”가 아니라 “호출자가 새 필터 필드를 선택하는 공격 표면이 줄어든다”가 정확하다.
4. **대안 1과 3을 불필요하게 약하게 정의했다.** 대안 1은 지난 PoC의 고정 결과뿐 아니라 코드 생성, 공통 정책 삽입, typed query builder를 쓸 수 있다. 채택할 이유는 약해도 가장 약한 구현만 대표로 세우면 비교가 공정하지 않다.
5. **구성 주체와 실행 승인 시점을 완전히 분리하지 못했다.** 문서 머리는 DD-03으로 실행 시점을 분리한다고 하지만, B.3과 C.3은 사실상 런타임 동적 요청을 전제로 보안·비용을 논한다. 호출자가 요청을 구성하는 것과 운영 서버가 새 모양을 즉시 받아들이는 것은 별개 축이다.

### 3.2 빠진 실질적 대안: “호출자 구성 + canonical manifest/plan 승인”

다음 안은 대안 2와 3의 단순 절충이 아니라, **정의 주체와 승인 주체를 분리**한다.

1. 서버는 리소스마다 `select/filter/sort/traverse/aggregate` capability와 행·필드·관계 정책을 선언한다.
2. 호출자는 하나의 canonical read Intent로 필요한 결과를 조합한다. 서버 개발자가 화면별 조회를 작성하지 않는다.
3. 빌드 도구 또는 런타임은 같은 정규화기를 사용해 Intent를 canonical plan으로 만든다.
4. 자사 프론트는 배포 전에 manifest/plan을 추출·검증·승인할 수 있고, 동적 호출자는 같은 Intent를 런타임에서 더 엄격한 예산으로 검증할 수 있다. 어느 경로를 1차로 삼을지는 DD-03과 호출자 범위 결정에 남긴다.
5. 이름 붙은 조회가 필요하면 새 의미가 아니라 canonical Intent의 별칭/manifest ID다. 표준 대수로 표현 불가능한 읽기만 명시적 확장으로 분류한다.

이 안은 “화면별 서버 조회 정의”를 되살리지 않으면서 운영 검토와 캐시·관측 가능성을 확보한다. DD-01은 이 안을 독립 대안으로 비교하거나, 최소한 대안 2의 실행 하위안으로 명시해야 한다. 현재처럼 DD-03으로 완전히 미루면 대안 2의 실제 보안·운영 비용을 평가할 수 없다.

### 3.3 대안 2의 새 비용은 크게 과소평가됐다

DD-01 C.2의 “플래너와 비용 모델, 노출·허용 범위, 실행 계획 도구” 외에도 다음이 필요하다.

- 선택·필터·정렬·관계·집계를 분리한 capability/정책 모델과 조건부 필드 권한의 합성 규칙
- 관계 경로 전체의 행·필드·테넌트 정책 삽입과 서브쿼리·집계까지 포함한 권한 보존 증명/테스트
- 동치 요청 정규화, 안정적 해시, plan cache 키, 정책·스키마 버전 무효화
- null, 빈 목록, 다중 정렬, tie-breaker, cursor, 집계의 정확한 의미와 DB별 capability 차이
- 인덱스 유무가 아니라 실제 예상 스캔·조인·정렬·결과 바이트를 보는 비용 추정과 admission control
- 사용자·테넌트별 rate/concurrency budget, 취소, timeout, DB statement limit
- 타입 생성·SDK·스키마 탐색·오류 redaction·감사 로그·실행 계획 설명 도구
- 조합 결과의 캐시 키와 쓰기 뒤 무효화, 실시간 동기화 범위
- 계약 버전 관리와 필드/관계 제거 시 호환성, 승인 manifest의 재검증
- 정책 조합 회귀 테스트와 공격 요청 corpus

공통 엔진에 한 번 구현해 앱별 중복을 흡수할 수 있다는 장점은 여전히 크다. 그러나 이것이 “총량 감소”인지 “고비용 공통 플랫폼 선투자”인지는 E2만으로 판단되지 않는다. 개발량뿐 아니라 운영·보안 비용도 비교해야 한다.

## 4. 보안 비판

아래 예시는 모두 **개념 공격 요청**이며 실제 문법이 아니다.

### 4.1 결과 행 상한은 인덱스 없는 필터·정렬 비용을 제한하지 않는다

C.3은 인덱스 없는 필터·정렬을 “결과 행 상한 안”에서 허용한다고 한다(`DD-01:117`). DB는 `take: 1`을 반환하기 전에도 전 테이블 스캔과 정렬을 수행할 수 있다.

```ts
aip.read("Recruitment", {
  where: { title: { contains: "%a%" } },
  orderBy: { body: "asc" },
  take: 1,
})
```

공격자는 결과 1건만 요청하면서도 큰 텍스트 검색과 sort spill을 유발할 수 있다. 결과 행이 아니라 AST 노드 수, 연산별 가중치, 예상 스캔 행, 조인 fan-out, 정렬 메모리, 결과 바이트, 실행 시간, 동시 요청 예산을 함께 제한해야 한다. 실행 중 취소와 DB statement timeout도 필요하다.

### 4.2 “읽을 수 있으면 필터·정렬 가능”은 권한을 잘못 합친다

필드 선택 권한과 비교·순서화 권한은 같지 않다. 조건부로 보이는 필드를 다른 행의 필터에 쓰거나, 민감한 순서를 ID 목록으로 관찰할 수 있다.

```ts
aip.read("Member", {
  where: { clubId: targetClub },
  orderBy: { lastActiveAt: "desc" },
  select: { id: true },
})
```

`lastActiveAt`가 일부 화면에서 읽히는 필드라는 이유만으로 전체 구성원의 활동 순위를 허용해서는 안 된다. `select/filter/sort/group/aggregate` capability를 별도로 선언·파생하고 기본 거부해야 한다. 행별 조건부 필드 권한이 쿼리 계획 단계에서 어떻게 평가되는지도 정해야 한다.

### 4.3 대상 리소스 가시성만 다시 적용하면 관계 **간선**의 비밀이 샌다

C.3은 관계 단계마다 “대상 리소스의 가시성”을 다시 적용한다고 한다(`DD-01:118`). 그러나 관계 자체가 민감할 수 있다. 공개 Member와 공개 Recruitment 사이의 `RecruitmentBookmark` 연결은 개인 행동 정보다.

```ts
aip.read("Recruitment", {
  where: { bookmarks: { some: { member: { id: victimId } } } },
  select: { id: true },
})
```

Member와 Recruitment 각각을 볼 수 있어도 피해자가 무엇을 북마크했는지는 볼 수 없어야 한다. 대상 노드 정책뿐 아니라 관계 간선의 탐색·존재·개수 정책, 역방향 탐색 정책, 중간 리소스 정책을 모두 적용해야 한다. 각 단계 적용이 재귀 중첩과 서브쿼리에도 닫혀 있는지도 검증해야 한다.

### 4.4 `count` 기본 허용은 차분·존재 추측 공격을 연다

C.3은 `count`를 기본 허용한다(`DD-01:119`). 합계·평균만 막아도 작은 집단을 0/1로 좁히면 존재와 관계를 알아낼 수 있다.

```ts
aip.read("Recruitment", {
  where: {
    club: { school: { id: targetSchool } },
    bookmarks: { some: { member: { id: victimId } } },
  },
  aggregate: { count: true },
})
```

필터를 조금씩 바꾼 두 count의 차이로 개인 행동을 추론할 수 있다. count도 capability별 기본 거부가 안전한 기준이다. 공개 통계가 제품 요구라면 최소 집단 크기, 차분 질의 예산, 응답 버킷/노이즈, 동일 주체의 질의 상관 추적 중 필요한 통제를 별도 설계해야 한다. 어떤 통제가 필요한지는 데이터 민감도에 따라 검증해야 한다.

### 4.5 “보이지 않는 행은 없음”만으로 존재 오라클이 사라지지 않는다

동일한 404/빈 결과를 주어도 다음 차이가 남을 수 있다.

- 존재하지만 금지된 ID와 존재하지 않는 ID의 응답 시간·DB 접근 패턴
- 금지 필드, 알 수 없는 필드, 금지 관계의 오류 코드·메시지 차이
- 목록 count, cursor 유무, total count, 정렬 위치 차이
- rate limit·감사 로그·캐시 hit 여부의 외부 관찰 차이

예를 들어 공격자가 `club.internalMemo`를 요청했을 때 “필드는 존재하지만 금지”와 “없는 필드”를 다르게 답하면 스키마 오라클이 된다. C.3의 존재 노출 규칙(`DD-01:121`)은 행뿐 아니라 필드·관계·집계·오류·타이밍 정책까지 확장해야 한다. 타이밍 완전 동일화가 현실적으로 가능한지는 `확인 필요`지만, 최소한 오류 shape과 목록 메타데이터는 통제할 수 있다.

### 4.6 깊이·행·조인·시간 상한만으로 조합 폭발과 테넌트 우회를 못 막는다

다음 요청은 깊이가 얕아도 많은 OR, 문자열 연산, 관계 fan-out으로 비쌀 수 있다.

```ts
aip.read("Recruitment", {
  where: { or: thousandsOfPredicates },
  select: { club: { school: { name: true } } },
  take: 20,
})
```

또 `Recruitment -> Club -> School` 경로의 중간 스캔·서브쿼리·집계마다 테넌트 제약이 자동 삽입되지 않으면 다른 테넌트 존재나 통계를 볼 수 있다. T07도 모든 스캔에 테넌트 필터를 넣어야 한다고 한다(`plan-docs/topics/T07-security.md:34-39`). C.3은 테넌트 불변식을 누락했다. plan cache가 사용자, 역할, 테넌트, 정책 버전을 키에 포함하지 않아 권한이 다른 plan을 재사용하는 위험도 검증 항목에 넣어야 한다.

## 5. F 질문 비판

### F1 — **창시자 결정 사항이 맞다**

읽기 기본 모델은 호출자의 표현 범위와 AIP 정체성을 바꾸므로 창시자 승인 대상이다. 다만 현재 대안 2가 C.3의 넓은 기본 허용까지 포함하는지, 아니면 “호출자 조합”이라는 상위 방향만 뜻하는지 분리해서 물어야 한다. 지금 문구에 동의하면 안전하지 않은 기술 기본값까지 묶여 승인된 것처럼 읽힐 수 있다.

### F2 — **제품 위험 수용은 창시자 사항이지만, 현재 이분법은 부적절하다**

기본 공개 대 기본 거부는 보안 책임에 영향을 주므로 최종 승인은 창시자에게 있다. 그러나 에이전트는 먼저 `select/filter/sort/traverse/aggregate`를 분리한 capability 모델과 안전한 기술 권고를 내야 한다. “필드는 기본 공개하고 숨길 것만 표시”는 필드 추가 시 조용히 노출되는 실패를 정상 경로로 만든다. 데이터 필드 선택은 기본 거부를 기술 기본안으로 제안하고, 반복 선언을 줄일 안전한 묶음/규칙 파생을 함께 제시한 뒤 예외 허용 여부만 물어야 한다.

### F3 — **지원할 호출자 범위는 창시자 결정 사항이 맞지만 선택지가 뭉쳐 있다**

자사 프론트, 자사 AI 에이전트, 신뢰된 파트너, 불특정 서드파티는 발견 가능성, rate limit, 승인 경로, 호환성 약속이 다르다. “자사 프론트만 / AI·서드파티까지 같은 방식”의 2분법은 제품 범위와 신뢰 모델을 섞는다. 공통 Intent 의미 모델을 쓸지와 동일한 승인·예산 경로를 쓸지는 별도다. 제품이 지원할 1차 호출자와 각 호출자의 신뢰 등급을 창시자에게 묻고, 등급별 기술 통제는 에이전트가 제안해야 한다.

### F4 — **창시자 결정 사항이 아니다**

E1~E4는 코드 변경 없는 사실 확인·문서 실험이다. 운영 규칙은 문서 초안, 사실 확인, 선택지 비교, 추천을 승인 없이 할 수 있다고 한다(`plan-docs/00-rules.md:58-62`). 가역적이고 저비용인 검증을 할지 창시자에게 묻는 것은 불필요한 선택지를 늘린다. 에이전트가 수행하고 결과를 판단 자료로 제출해야 한다.

### 빠진 창시자 질문

1. **canonical read Intent의 지위:** JS/TS, Python, `.aip` 등 작성 표면이 여러 개여도 서버가 받는 의미 구조는 하나여야 하는가, 공식 작성 방식도 하나로 제한할 것인가. 작성 언어 자체는 미결정이므로 여기서 확정하지 말아야 한다.
2. **자연어 문법화의 읽기 연결:** 목적·전제·기대 결과 같은 구조화 정보가 읽기 Intent의 실행 계약, 검증 메타데이터, AI 탐색 정보 중 어디에 속하는가. 현재 의미가 미결정이므로 후보와 영향만 제시해야 한다.
3. **표준 조합과 확장 읽기의 경계:** 표준 읽기 대수로 표현할 수 없는 조회를 어떤 원칙으로 JS/Python 확장에 보내며, 이름 붙은 별칭이 새 의미를 만들 수 있는가. “한 의도 한 구조”에 직접 영향을 주는 제품 규칙이다.

### 에이전트가 기술적으로 제안·검증했어야 할 질문

- capability를 선택·필터·정렬·관계·집계별로 어떻게 분리하고 어떤 안전한 기본값을 둘 것인가
- 동일 요청의 canonicalization과 해시, 별칭, plan cache, 정책 버전 무효화를 어떻게 정의할 것인가
- 결과 제한이 아니라 예상 실행 비용을 어떤 지표로 계산하고 런타임 예산을 어떻게 강제할 것인가
- 관계 간선 정책, 조건부 필드 권한, 테넌트 필터가 중첩·집계·서브쿼리에서도 보존되는가
- 오류와 목록 메타데이터가 존재·스키마 오라클이 되지 않는가
- DB별 capability 차이를 어떻게 구조화된 오류로 드러낼 것인가. DB 범위 자체는 아직 미결정이다.

## 8. 결론

내 추천은 **현재 문서의 대안 2 그대로가 아니라, capability가 분리된 canonical 조합 읽기 모델인 수정 대안 2**다. 호출자가 필요한 데이터 모양·조건·정렬·관계를 한 가지 읽기 Intent로 표현하고, 서버는 행·필드뿐 아니라 필터·정렬·관계·집계를 각각 허용하며 canonical plan과 비용 예산을 최종 통제해야 한다. 자사 프론트의 빌드 승인 manifest와 동적 호출자의 런타임 검증은 같은 의미 모델 위의 실행 하위안으로 남겨 DD-03에서 비교할 수 있다.

Claude/DD-01의 추천도 대안 2이므로 방향은 같다. 차이는 **현재 C.3을 포함한 대안 2는 추천 가능한 상태가 아니라는 점**이다. 필드 선택 권한을 필터·정렬 권한으로 자동 승격하고 count를 기본 허용하며 결과 행 상한으로 비용을 통제하는 안은 “요청의 자유와 실행 권한 분리”를 구현하지 못한다. 또한 한 의도 한 구조, GraphQL과의 차별점, 자연어 문법화의 열린 연결, 운영 비용이 빠져 있다. 이 조건을 보강하고 E1~E4 및 확장 위협 실험을 수행한 뒤 창시자에게 상위 방향을 묻는 것이 맞다.
