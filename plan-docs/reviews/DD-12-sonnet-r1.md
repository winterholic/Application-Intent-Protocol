## 2. 철학 정합성과 DD-01~10 불일치

### 2-1. 유지보수 최소화 대 데이터 안전

- C.3-1·2(의도 선언 없으면 거부, 같은 정의 = 같은 DB)는 운영 규칙 6과 PRINCIPLES §2(보안·서버 통제)에 맞다. 이 두 줄은 유지해도 된다.
- D절 표의 "S1이 가장 직접. 아리아리의 손 DDL이 사라진다"는 맞지만, 사라지는 것은 DDL 작성이지 **검토 책임**이 아니다. S1에서도 `removed field`를 쓰는 순간 사람이 데이터 삭제를 결정한다. DD-12는 이 책임이 누구에게 있는지(앱 개발자, 리뷰어, 배포 담당)를 적지 않았다. PRINCIPLES §4-3("서버 쪽에 써야 할 것이 늘어나는가 줄어드는가")에 대한 답이 "줄어든다"로만 돼 있고, `was`/`removed` 선언이 소스에 남는 비용(`grammar.md` 220행: 배포 뒤에도 남겨도 됨)은 언급이 없다.
- F1의 에이전트 의견("개발은 (가), 운영은 (나), 낮은 위험은 (가) 허용")은 아래 3절에서 보듯 **기준 없는 혼합**이다. 운영 규칙 6을 지키는 것인지 판정할 수 없다.

### 2-2. 개발 S1 / 운영 S2 분리는 DD-03의 "로컬과 운영 일치"와 부딪친다

- DD-03 88행 "배포 전 일치 검사": "로컬에서는 되는데 운영에서 거부가 정상 개발 흐름이 되지 않게 한다."
- 개발 DB는 보통 비어 있거나 작다. `DataCheck`(NULL 행, 중복 행, 길이 초과, enum 값 사용 중)는 **행이 있어야** 걸린다. `evolve_e2e.rs` 221~250행의 거부 시험도 행을 직접 INSERT하고 나서야 거부가 나온다. 개발에서 S1이 통과했다는 사실은 운영 데이터에서의 통과를 말해 주지 않는다.
- 그래서 개발 S1 / 운영 S2에서는 운영 경로(파일 검토 + 데이터 검사)가 **처음 실행되는 곳이 운영**이다. 제안: 운영 DB(또는 스냅숏)에 대한 읽기 전용 `--plan`을 배포 전 단계로 필수화하는 쪽이 모드를 나누는 것보다 일관된다. PoC `aip migrate --plan`은 이미 "데이터베이스에 붙어 SQL, 분류, 검사 결과를 출력만 하고 아무것도 바꾸지 않는다"(`grammar.md` 245행). 즉 S2가 하려는 "사람이 보고 승인"의 재료는 변경 파일 없이도 이미 있다. 이것이 3절의 빠진 대안이다.

### 2-3. DD-01·02의 새 개념이 스키마 진화에서 다뤄지지 않는다

DD-12 E1이 "대조"를 미뤘고 본문에는 capability 축소 한 줄(C.3-3, 범위 4행)만 있다. PoC 코드와 DD-01~03을 맞춰 보면 빈칸은 다음과 같다.

| 개념 | DD 근거 | PoC가 지금 하는 일 | 빈칸 또는 위험 |
|---|---|---|---|
| 새 필드는 자동 공개 안 됨 | DD-01 I1, preset 1·4번(150~155행), DD-02 W-I1(150행) | 새 필드는 DB에 자동으로 `safe` 추가(`grammar.md` 228행). 공개 여부는 별개 | 정의에서 필드를 추가하면 DB는 즉시 바뀌지만 capability에서는 안 열린다는 점이 DD-12에 없다. 반대로 **이름 변경 시 capability·preset의 닫힌 목록이 옛 이름을 가리킨다**. `was`가 목록 안 이름도 따라가는지는 정해지지 않았다. 따라가지 않으면 호출자가 깨지고(안전하지만 시끄러움), 따라가는 규칙이 불명확하면 DD-01 I1을 우회할 수 있다. 확인 못함: `was`가 policy·allow 식의 이름까지 다시 쓰는지 코드로 끝까지 추적하지 않음 |
| 이름 재사용 | 같음 | E111은 "아직 선언된 이름이 `was`"를 막는다(`grammar.md` 221행). 이미 사라진 이름을 나중 배포에서 **다른 의미의 새 필드**로 재사용하는 것은 막지 않는다 | `X`를 `Y`로 옮기고 다음 배포에서 새 `X`(예: 내부 메모, 민감 필드)를 만들 때, 호출자가 등록해 둔 옛 `X` 요청이나 allow 목록의 `X`가 **새 필드에 붙는다.** DD-03 T-I4(권한 축소 유예 없음)는 축소만 다루고 이 "같은 이름, 다른 의미"는 다루지 않는다. 확인 못함: 등록 요청이 이름으로 식별되는지 구조(스키마 digest)로 식별되는지 DD-03 층 1에 명시가 없다 |
| preset | DD-01 154~155행 "preset 정의가 바뀌어도 기존 앱의 노출이 조용히 넓어지지 않는다", "펼친 결과를 사람이 보고 변경 diff를 검토" | 계약 diff는 "그 밖의 추가와 완화"를 호환으로 본다(`grammar.md` 247행) | **추가형 노출 확대는 `aip diff`에서 호환(통과)이 될 수 있다**(PoC 계약 모델 기준. 새 조합 모델에서의 분류는 정의 안 됨). DD-01이 말한 "펼친 노출 diff 검토"가 DD-12에 들어오지 않았다. DD-01 E2의 지표 "검토해야 할 권한 확대 수"(195행)가 증거이므로 DD-12도 확대를 1급 개념으로 다뤄야 한다 |
| 불변식 추가·변경 | DD-02 W-I5(154행) | 유일성·`CHECK`·`ExactlyOne`의 부분 unique 인덱스는 `Checked` 단계로 기존 행을 먼저 센다(`evolve.rs` 777~800행 부근, e2e 199행). 그러나 트리거로 구현되는 불변식(`ddl.rs` 539~558행의 `__least` 지연 트리거, 행 국소가 아닌 `Invariant`의 `inv_` 트리거 572~587행)은 `evolve.rs`가 "트리거와 함수는 비교하지 않고 현재 텍스트로 교체"(`evolve.rs` 12~13행) | **트리거형 불변식을 새로 추가하면 기존 위반 행은 검사 없이 통과하고 이후 쓰기에서만 막힐 수 있다.** 확인 못함: 실제 DB에서 재현하지 않았다. 코드 읽기만의 추정이며, 시험 `evolve_e2e.rs`에는 이 경우가 없다(grep으로 `invariant`·`exactly` 0건). W-I5가 "모든 경로에서"를 약속하는 만큼 "기존 데이터에도"를 같은 약속 안에 넣을지 정해야 한다 |
| 상태 전이 | DD-02 W-I2 | enum 값 삭제는 사용 중이면 거부, 순서 변경은 `UNSUPPORTED`(`grammar.md` 233·234행) | 전이 간선(from→to)이 바뀌거나 상태 값이 의미를 바꾸는 경우(값 이름은 같고 뜻이 다름)는 IR 비교에 없다. 상태 필드의 허용 값 삭제 때 진행 중인 행의 처리(PoC는 거부)와 전이 계약 변경 시 이미 중간 상태인 행 처리가 DD-12에 없다 |
| 테넌트·게시·이력 trait | PoC | `history`, `publishable`, `tenant via` 추가·삭제는 `AIP.SCHEMA.UNSUPPORTED` 거부(`diff.rs` 188~192행, `evolve.rs` 482~486행, `grammar.md` 241행) | 보안상 거부는 안전하지만 **막다른 길**이다. 해결책이 "다른 이름으로 새로 만들고 migration으로 옮기기"(`evolve.rs` 485행)라서 "유지보수 0에 가깝게"와 멀다. 나중에 멀티테넌트를 붙이는 앱은 수동 이전이 된다. DD-12는 이 거부 목록(트레이트, 필드 종류, 암호화, ordered enum, 다른 기본 타입)을 C.3-1의 "데이터를 잃거나 다르게 해석하는 변경"으로 뭉뚱그려 PoC 원칙을 실제보다 단순하게 보이게 한다 |
| 확장 동작·소유 선언 | DD-02 W-I10, DD-06 | 확장 코드는 엔진을 거쳐 DB를 쓴다. 엔진이 모르는 스키마 의존은 `migration` 본문 | 필드를 바꿀 때 확장 코드(JS/Python)가 그 필드를 참조하는지 정적으로 알 수 없다. DD-12의 "호출자" 정의(화면, 등록된 요청)에 **확장 동작**이 빠져 있다. 확장은 DD-06 (가)(다)에서 별도 프로세스이고 배포 시점이 다를 수 있다 |

### 2-4. DD-06 배포 형태와의 불일치

- DD-06 40~45행: 서버 N대로 늘릴 수 있다(75행: "호스트를 N개로 늘리면"). PoC `aip run`은 **기동할 때** 마이그레이션을 같은 advisory lock 안에서 적용한다(`grammar.md` 245행, `aip-runtime/src/lib.rs` 50행).
- 롤링 배포에서는 새 인스턴스가 기동하며 `RENAME COLUMN`을 적용하는 순간 **옛 인스턴스는 아직 옛 컬럼 이름으로 SQL을 만든다**. 이름 변경이 한 트랜잭션 한 단계라서(1-8) 이 틈에 옛 인스턴스의 요청이 실패한다. DD-12는 호출자(프론트) 쪽 깨짐만 보고 **같은 서버 정의의 옛 버전 인스턴스**를 보지 않았다. "배포 중 전환"(의제 11 항목)의 핵심이 이것인데 B절 시나리오에 없다. 확인 못함: 현재 PoC가 옛 인스턴스를 어떻게 막는지(버전 digest 불일치 시 거부 등)는 `aip-runtime`에서 끝까지 확인하지 않았다.
- 그래서 C.3-5(확장→전환→축소)는 "호출자 때문에"만이 아니라 **서버 자신의 롤링 배포 때문에도** 필요하다. 그런데 PoC는 이름 변경에서 이것을 하지 않는다.

### 2-5. 롤백은 DD-12가 의제 11 항목을 조용히 빠뜨렸다

- 5행 "기준 원문"에 "롤백"을 적었지만 C절·F절·G절 어디에도 롤백이 없다. T12 25행은 `[미정]`.
- 코드 확인: `crates/aip-pg/src/*.rs`, `crates/aip-cli/src/*.rs`, `spec/grammar.md`에서 DB 단계 롤백(down)을 지원하는 흔적이 없다(grep에서 나온 rollback은 NOTIFY/업로드/`migration` 실패 시 트랜잭션 롤백뿐). "적용 중 실패 시 전체 롤백"은 있으나 **적용 후 되돌리기**는 없다.
- `removed field`는 DB에서 컬럼을 지운다(`evolve.rs` 593~595행 `DROP COLUMN`). 코드를 되돌려도 값은 돌아오지 않는다. 롤백 절차가 없다면 `removed`를 쓰는 배포의 안전장치는 사람이 사전에 백업하는 것뿐이다. 운영 규칙 6(운영 가능성)에 비춰 이 공백은 DD-12가 "미결정"이라고라도 적어야 한다.

## 3. 대안 비판

### 3-1. S1 / S2 / S3 (C.1)

1. **S3는 비교 대상이 아니다.** "지금 아리아리"는 AIP가 DB를 정의에서 파생한다는 전제(PRINCIPLES §1)와 양립하지 않는다. 손으로 바꾼 DB는 "같은 정의 = 같은 DB"(C.3-2)를 깨고, PoC는 이를 `AIP.SCHEMA.UNRECORDED` 또는 불일치로 거부하거나 기록만 남긴다(`grammar.md` 199행). S3를 대안 열에 두면 S1/S2의 우월함이 부풀려 보인다. 기준선(현재 상태)으로 옮기고 대안은 S1/S2 둘로 줄이는 편이 정직하다.
2. **S2의 "변경 파일(SQL 또는 계획)"이 둘로 갈린다.** 이 둘은 안전 성질이 정반대다.
   - **SQL 파일을 사람이 고칠 수 있는 형태**로 두면 정의 외의 두 번째 서술이 생긴다. `evolve.rs` 9~11행은 바로 이것을 피하려고 "두 번째 서술을 따라가지 않고" 옛/새 DDL을 생성기로 다시 만들어 비교한다. 손으로 고친 SQL은 C.3-2의 불변식(기존 DB + 단계 = 새로 만든 DB)을 깨뜨린다. PoC e2e는 카탈로그 덤프 비교로 이 불변식을 검증한다(`evolve_e2e.rs` 45~80행). 손으로 고친 파일에도 같은 검사가 가능한지 DD-12는 말하지 않는다.
   - **계획 파일(기반 digest + 새 digest에 묶인 읽기 전용 산출물)** 이면 위 문제는 없다. 단 데이터 검사(`DataCheck`)는 검토 시점과 적용 시점 사이 데이터가 바뀌면 결과가 달라진다. 계획 파일에는 "적용 시 검사 재실행, 배포 기록 digest 불일치면 거부"가 들어가야 한다. PoC는 적용 시 같은 트랜잭션에서 검사를 돌린다(`grammar.md` 245행)는 점에서 이미 반쯤 갖췄다.
3. **S2에서 "사람이 검토"의 대상은 SQL이 아니라 결과 요약이어야 한다.** PoC는 단계마다 분류와 이유를 사람 말로 낸다(`grammar.md` 224행, `evolve.rs`의 `step(..., why)`). 비전문 개발자가 SQL을 읽어야 한다면 PRINCIPLES §4-5(새 언어를 배우지 않고)와 긴장한다. D절 표에서 이 항목이 빠졌다.
4. **S1의 "거부 규칙이 완전해야 한다"는 말은 진실하지만 측정 기준이 없다.** 현재 거부는 `AIP.SCHEMA.UNDECLARED/TYPE_CHANGE/UNSUPPORTED/DATA_CONFLICT`(`crates/aip-ir/src/codes.rs` 202~210행)이지만 2-3절의 트리거형 불변식처럼 구멍이 있을 수 있다. 완전성은 시험 목록으로 정의해야 한다(예: "정의 변경 유형 × 데이터 상태" 매트릭스 시험).

### 3-2. 호출자 쪽 세 안 (C.2)

세 안은 대안이 아니라 **서로 보완하는 층**이다. 표가 택일처럼 쓰여 있어 G절 "별칭 유예"가 어느 층의 선택인지 흐려진다.

| 안 | 실제 역할 | 빠진 점 |
|---|---|---|
| 배포 전 거부 | 탐지(항상 켜야 함) | 거부가 **무엇에 대해** 가능한가. `aip diff`는 IR 대 IR이고 배포된 프론트가 실제로 쓰는 필드를 모른다. "등록된 요청 중 깨지는 목록"(C.3-3)은 등록 기능을 켠 경우에만 존재한다(DD-03 78행: T-I2~T-I4는 등록 시에만 적용). 런타임 단일 경로(R)에서는 이 목록이 없다. 필드 사용량 관측(서버가 모든 요청을 보므로 가능)이 같은 목록을 줄 수 있으나 DD-12는 쓰지 않았다 |
| 별칭 유예 | 호환 | **보안 성질이 없다.** 옛 이름 요청이 새 필드의 capability·정책·행 정책·감사 선언을 그대로 받는지, 옛 이름이 닫힌 목록(DD-01 I1, DD-02 W-I1)에 암묵 추가되는 것은 아닌지 정해야 한다. 별칭은 **계약 수준 이름 해석**(요청 canonical화 때 옛 이름 → 새 이름)이어야 하고 DB 뷰나 이중 컬럼이면 안 된다. 만료 시각과 만료 후 거부 코드, 이름 재사용 금지 기간도 필요하다(2-3절 "이름 재사용") |
| 계약 버전 분리 | 공존 | DD-12는 비용만 적었다. 버전마다 capability·정책 표면이 따로 생겨 검토량이 곱절이 되는 **보안 비용**이 크다. 이미 `docs/DECISIONS.md` OI-P2(91행)가 "계약 버전 공존"을 Open으로 둔다. DD-12가 이를 건드리려면 창시자 결정 사항이므로 이 안은 "하지 않음, OI-P2로 위임"으로 못박는 것이 안전하다 |

### 3-3. 빠진 대안

| 대안 | 내용 | 왜 후보인가 |
|---|---|---|
| S1' 자동 + 계획 승인 게이트 | 항상 계획을 먼저 계산하고(`--plan`), 분류에 따라 자동 적용할 수 있는 것과 **승인 토큰이 있어야 적용되는 것**을 나눈다. 승인은 계획 digest를 가리킨다 | 변경 파일 형식을 새로 만들지 않고 PoC 자산(`StepClass`, `--plan`, digest)만 쓴다. "혼합"이 이것으로 구체화된다 |
| S4 export | AIP 계획을 SQL로 내보내 Flyway/Prisma/DBA 도구로 적용하게 하는 탈출구 | 조직에 DBA 승인 절차가 있는 경우(운영 규칙 6의 운영 가능성). JS/Python 생태계 존중(PRINCIPLES §2). 단 export는 "읽기 전용 산출"이며 AIP가 소유한 DB의 정본이 아님을 명시해야 한다 |
| 온라인 변경 도구 위임 | 큰 테이블의 NOT NULL·인덱스·컬럼 변경은 락 없이 하는 외부 도구에 맡김 | 확인 못함: pgroll 등 구체 도구의 현재 상태를 이번에 조사하지 않았다. 개념만 후보로 둔다 |
| 사용량 기반 축소 판정 | 서버가 요청에서 본 필드별 마지막 사용 시각으로 "이 별칭/필드는 N일간 쓰이지 않았다"를 알려 줌 | 호출자 이행 완료를 사람이 추측하지 않게 한다. 별칭 만료·`removed` 안전 확인에 직접 쓰인다 |
| 정의 변경 의도 분리 | 이름 변경(`was`)과 삭제(`removed`)는 이미 있으나 "의미 변경 (같은 이름, 다른 뜻)"이 없다 | 2-3절 이름 재사용 위험. 예: `was`/`removed` 이후 같은 이름 재사용은 새 이름 강제 또는 대기 기간 |

### 3-4. "위험 등급" 기준은 정의돼 있는가

**없다.** C.3-4가 "큰 테이블 잠금, NOT NULL 추가, 인덱스 생성 같은 것을 단계마다 위험 등급으로"라고만 쓰고, F1 의견이 "위험 등급이 낮은 변경은 (가)"로 이를 의존한다. 정의되지 않은 값에 자동/수동 경계를 거는 구조다. 구체적 문제:

1. **PoC `StepClass`는 운영 위험이 아니라 데이터 안전 등급이다.** `Safe/Relaxing/Checked/Refresh/Declared`(`aip-plan/src/lib.rs` 558~569행). 이 등급으로는 "낮은 위험"을 가를 수 없다. 예: 비유일 인덱스 생성은 `Safe`인데 `evolve.rs` 785행 메시지가 "writers wait"라고 적는다. `SET NOT NULL`은 `Checked`지만 전체 테이블 스캔이 두 번(검사 쿼리 + 제약 검증) 일어나는 것으로 읽힌다(코드 읽기 기준, 실행 확인 못함). 잠금 수준·소요 시간 축이 없다.
2. **계획기는 테이블 크기를 모른다.** `crates/*/src`에서 `reltuples`, `lock_timeout`, `statement_timeout`, `ACCESS EXCLUSIVE` 검색은 `pg_class` 한 건(트리거 조회, `evolve.rs` 850행)뿐이다. 크기 입력이 없으니 "큰 테이블"을 판정할 수 없고, F1이 S1의 단점으로 든 "사람이 못 본다"가 등급으로도 해소되지 않는다.
3. **모든 단계가 한 트랜잭션이다**(`grammar.md` 198·245행). 원자성은 안전하지만 먼저 잡은 잠금이 커밋까지 유지되므로 잠금 시간은 단계 시간의 합이다. 이 설계 선택은 장점(실패 시 전부 롤백)이면서 운영 위험이다. DD-12에 트레이드오프로 기록돼야 한다.
4. **권한 축이 없다.** 등급이 DB 측면(잠금, 시간)만 말하고 **노출 확대, 정책 완화**를 포함하지 않는다. 4절 참고.
5. **설계 이름 불안정(OI-IR4)이 등급을 무력화한다.** `docs/DECISIONS.md` 81행: 제약 이름이 선언 위치에 의존해, 멤버 순서만 바꿔도 객체가 바뀐다. `evolve.rs` 9~11행대로 이름이 움직인 제약은 "낡은 것 삭제 + 새로 생성"이 된다. 의미 없는 편집이 unique 인덱스 재생성(`Checked`, 큰 테이블에서 쓰기 대기)이라는 높은 등급 단계로 번역될 수 있다. 확인 못함: 순서만 바꾼 예를 실제로 돌리지 않았다.

**제안 정의(초안, 창시자 결정 아님):** 등급은 직교하는 세 축의 최댓값이다. (a) 데이터 축: PoC `StepClass` 그대로. (b) 운영 축: 단계가 잡는 잠금 수준 × 대상 테이블 추정 행 수(`pg_class.reltuples` 등, 계획 때 읽기 전용 조회). 임계값은 설정값이고 기본값은 보수적으로. (c) 권한 축: 노출·정책이 넓어지는가. 자동 적용 허용 = 세 축이 모두 낮을 때만. 이 한 줄이 F1의 혼합 추천을 시험 가능하게 만든다.

## 4. 보안·운영 검토

### 4-1. 불변식·제약을 새로 추가했는데 기존 데이터가 위반할 때

- **PoC가 하는 것:** unique, check, 필수 전환, enum 값 목록 축소는 적용 전에 기존 행을 센다. 위반이 있으면 개수와 id 예시를 내며 아무것도 바꾸지 않는다(`grammar.md` 230~232행 표, e2e `a_unique_rule_over_duplicate_rows_is_refused_with_the_count`, `rules_the_rows_already_break_are_refused`). 이 방향은 운영 규칙 6에 맞다.
- **빠진 것 1: 트리거형 불변식.** 2-3절 표대로 `ExactlyOne`의 "최소 1개"(`__least` 지연 트리거)와 행 국소가 아닌 `Invariant`는 `DataCheck`가 붙지 않는 구조로 읽힌다(코드 읽기 기준, 실행 확인 못함). 결과는 "기존 위반은 침묵, 이후 해당 그룹을 건드릴 때만 거부"다. 정확히 W-I5가 막으려는 상태(깨진 채 커밋)와 비슷하다. 제안: 불변식 종류별로 "추가 시 기존 데이터 검사 가능한가"를 표로 만들고, 불가능한 종류는 불변식 추가를 거부하거나 별도 검사 쿼리를 생성기가 만들게 한다(P0).
- **빠진 것 2: 거부 이후 길.** 위반이 있을 때 PoC는 거부만 한다. 수정은 `migration` 본문을 직접 써서 값을 고치는 것이다(`grammar.md` 222행). DD-12 4행 "백필 문법은 후속"은 이 둘을 같은 문제로 보지 않았다. DD-02 W-I5가 `repair` 규칙을 불변식과 함께 선언하라고 요구하므로(`DD-02` 154행) 불변식 추가 때의 기존 데이터 수선도 같은 `repair` 어휘여야 "한 의도 한 표현"(PRINCIPLES §4-6)이 선다. 수선은 데이터를 바꾸는 배포 단계이므로 그 자체가 `Declared`급 위험이다.
- **중간 단계 선택지(정책 판단은 창시자):** 신규 쓰기에만 먼저 강제하고 기존 위반을 센 뒤 나중에 완전 검증으로 올리는 "점진 강제"는 PostgreSQL의 `NOT VALID` 제약과 같은 발상이다. 단 W-I5("깨진 채 커밋되지 않는다")를 기존 데이터에 대해 약화시키는 것이므로 기본값이 되어서는 안 되고, 켜면 "미검증 상태"가 계약과 진단에 보여야 한다. 확인 못함: PoC 생성기가 이 방식을 지원하는지.

### 4-2. 롤백

1. **적용 중 실패는 안전하다.** 계획 전체가 한 트랜잭션이라 중간 실패 시 전부 되돌아가고 기록되지 않는다(`grammar.md` 198·245행, e2e `a refused change changes nothing`). 좋은 성질이므로 C.3에 불변식으로 올릴 만하다(P1).
2. **적용 후 코드만 되돌리면 서버가 기동하지 않을 가능성이 높다(코드 읽기 기준).** 이전 버전 프로그램을 다시 배포하면 `recorded IR`(새 필드 포함) 대 `옛 프로그램`의 차이는 "필드 삭제 + 선언 없음"이다. `evolve.rs` 439~460행 `FieldRemoved { declared: false }`가 `AIP.SCHEMA.UNDECLARED`로 거부하고, `aip run`은 거부 대상이 있으면 기동하지 않는다(`grammar.md` 245행). e2e `removing_a_field_needs_a_declaration...`(148행)가 같은 논리를 검증한다. 즉 **추가만 있었던 배포도 서버 바이너리 롤백이 막힌다.** 확인 못함: "옛 프로그램 재배포"를 그대로 시험한 사례는 없다. 이것이 사실이면 긴급 롤백 절차가 PoC에 없다는 뜻이다. 의제 11의 "롤백" 항목에 대한 핵심 질문은 "DB를 되돌리는가"보다 "**새 스키마 위에서 옛 서버가 뜰 수 있는가**"다.
3. **`removed`는 되돌릴 수 없다.** 컬럼/테이블이 삭제된다. 현재 안전장치는 `Declared` 표시와 사람의 의도 선언뿐이다(`evolve.rs` 593~595행, 단계 분류 `Declared`). 배포 기록(`_aip_deployment`: digest, ir, steps, `applied_at`, `schema.rs` 69행)에 **누가 어떤 승인으로 적용했는지 컬럼이 없다.** DD-02 W-I11의 "고위험 동작은 감사 없이 커밋되지 않는다"를 스키마 배포에도 적용하면 `Declared` 단계를 포함한 배포는 행위자와 영향 행 수가 기록돼야 한다(P1).
4. **삭제를 둘로 쪼개는 안**(expand/contract의 계약 측 적용): `removed field` 하나가 "호출자에게서 숨김"과 "DB에서 지움"을 동시에 하지 말고, 첫 배포에서 capability에서만 빼고(되돌릴 수 있음) 관찰 기간 뒤에 DB 삭제를 별도 선언으로 하게 한다. 이 안은 현재 `removed field`의 의미(`grammar.md` 204행 EBNF 주석 "이 필드의 컬럼과 값을 일부러 버린다")를 바꾸므로 창시자 판단이 필요한 문법 변경 후보다. 문서에는 후보로만 남긴다.

### 4-3. 큰 테이블과 잠금

- 근거는 3-4절 그대로: 크기 입력 없음, 타임아웃 설정 없음, 한 트랜잭션에 모든 잠금이 누적, 비동시 인덱스(`evolve.rs` 785행), 파생 컬럼은 `Safe`로 분류되지만 "테이블이 한 번 다시 쓰인다"고 스스로 적음(`evolve.rs` 777~779행).
- **기동 시 적용(`aip run`)과 결합하면 더 나빠진다.** 여러 프로세스는 advisory lock으로 순서대로 기다린다(`aip-runtime/src/lib.rs` 50행). 마이그레이션이 길어지면 나머지 인스턴스 전부가 기동을 못 한 채 대기하고, 오케스트레이터의 헬스체크가 프로세스를 죽여 재시작 루프가 생길 수 있다. 확인 못함: 재시작 시 advisory lock 해제 타이밍과 재진입 동작은 실행해 보지 않았다.
- 제안: 운영에서는 "기동"과 "마이그레이션"을 분리한 실행 단위(별도 배포 작업)를 기본으로 하고, 잠금 대기 한도(`lock_timeout`)와 문장 한도를 계획에 명시한다. 한도를 넘으면 실패(전부 롤백)가 기본이다.

### 4-4. 정의 변경으로 권한이 넓어질 때 (capability 확대)

DD-12는 **축소만** 본다(범위 4행 "capability 축소", C.3-3, DD-03 T-I4 연결). 보안 위험은 대칭이 아니다. 축소는 호출자를 깨뜨려 눈에 띄지만, 확대는 조용히 통과한다.

| 확대 경로 | 현재 PoC 처리 | DD-12 | 문제 |
|---|---|---|---|
| `allow` / `requires` 완화 | `aip diff`에서 경고(`compat.rs` 386~410행, 종료코드 0) | 없음 | 누가 호출할 수 있는지가 넓어져도 배포는 통과한다 |
| 새 필드가 select/filter/sort 목록(또는 preset)에 포함 | 출력 추가는 호환 | 없음 | DD-01 I1(정렬 가능이 곧 순위 노출)이 막으려는 것. DD-01 155행 "preset이 바뀌어도 노출이 조용히 넓어지지 않는다"와 154행 "펼친 결과를 사람이 보고 diff 검토"를 DD-12가 이어받지 않았다 |
| 필드 이름 변경 후 목록의 옛 이름 | 불명 | 없음 | 2-3절 |
| enum 값 추가(상태·역할) | 출력에 쓰이면 경고(`grammar.md` 247행) | 없음 | DD-02 W-I1 "새 값 자동 허용 안 됨"과 일치해야 한다. `ordered` enum의 중간 삽입은 비교 의미를 바꾼다(`evolve.rs` 492행 노트만 남김) |
| 정책이 참조하는 필드의 타입·의미 변경 | 타입 변경은 거부 | 없음 | 허용 규칙 의미가 바뀌는 변경을 정책 쪽에서 재검토하는 지점이 없다 |

제안(P0): **노출 diff를 DB 위험 등급과 별개의 1급 출력**으로 둔다. 정의 변경 때마다 "호출자가 할 수 있는 일이 늘어나는 항목" 목록을 만들고(펼친 preset 포함), 비어 있지 않으면 S1이든 S2든 사람의 확인을 요구한다. 축소는 호출자 보호, 확대는 서버 보호다. 둘 다 서버 소유 판정이어야 한다(PRINCIPLES §2 "서버가 최종 권한").

### 4-5. S1을 운영에서 쓸 때의 권한 분리

- 기동 시 적용(`aip run`)은 **요청을 받는 프로세스가 DDL 권한이 있는 DB 계정을 쥔다**는 뜻이다. `removed entity`는 `DROP TABLE`이다(`evolve.rs` 404행).
- DD-06은 확장의 우회 차단을 "확장에 DB 자격증명을 주지 않는다"로 구조화한다(DD-06 66·83·93행). 그런데 배포 형태 E(앱 프로세스 안에 엔진 내장, DD-06 45행)는 호스트가 DB URL을 가지며 확장과 같은 프로세스다. 여기서 S1을 켜면 확장 코드가 DDL 가능 자격증명에 닿을 수 있다(DD-06 66행이 이미 "구조로는 막을 수 없다"고 인정). 이는 DD-06 보안 논증을 약하게 한다.
- 제안(P1): 마이그레이션 계정(DDL)과 서비스 계정(DML만)을 분리한다. 개발은 하나로 쓰되 운영 기본은 분리. 이 점이 "개발 S1 / 운영 S2"를 정당화하는 **더 강한 근거**다. 현재 F1 의견이 내세운 "큰 테이블 잠금을 사람이 본다"보다 보안 논거가 단단하다.

### 4-6. 그 밖의 운영 사실

- **암호화 필드 이름 변경은 거부**된다(`evolve.rs` 20행, 365·420·469행 `SCHEMA_ENCRYPTION_CHANGE`; 암호문이 엔티티·필드 이름에 묶임). `was`는 만능이 아니다. DD-12 B.3 예시(`externalUrl` → `applyUrl`)가 암호화 필드가 아닌 것은 다행이지만 "이름 변경은 데이터 보존"이라는 서술(B.3)은 조건부다.
- **기존 DB 채택**(아리아리는 MariaDB, 1-9)은 DD-12 밖이지만 "스키마 진화"의 첫 번째 실제 사례다. 이를 T12 또는 별도 DD로 분리해 기록하지 않으면 E2(아리아리 변경 이력 분석)가 PostgreSQL 전제로만 해석될 위험이 있다.

## 5. F1은 창시자 질문이 맞는가

운영 규칙 F: "제품 철학이나 사용자 경험에 영향을 미치는 선택만 질문한다. 내부 구현 세부 사항은 근거를 제시한 뒤 기술적으로 제안한다."

### 5-1. 판정: 질문의 **주제**는 맞고 **형식**은 맞지 않는다

- 주제(배포가 위험한 변경을 사람의 확인 없이 해도 되는가)는 철학 문제다. 유지보수 최소화(PART I §1)와 데이터 안전(운영 규칙 6)이 직접 부딪히기 때문이다.
- 그러나 (가) 자동 적용 / (나) 변경 파일 검토는 **구현 방식의 이름**이다. 창시자가 "변경 파일"이 무엇인지, 파일을 사람이 읽어서 무엇을 판단하는지 모른 채 고르면, 고른 결과는 철학 선택이 아니라 용어 선택이 된다. 비전문가가 답할 수 있는 질문이 아니다.
- 에이전트 의견("개발 (가), 운영 (나), 낮은 위험은 (가)")이 **(가)와 (나) 어느 쪽도 아닌 세 번째 안**이다. 창시자에게 이분법을 묻고 의견은 혼합을 내놓으면, 어느 답을 해도 추천과 다르게 되어 창시자가 "혼합"으로 답하게 유도된다. 혼합을 선택지로 올리고 위험 등급 정의(3-4절)를 같이 보여 줘야 한다.
- (가)는 안전 장치를 설명에 포함("의도를 적지 않으면 거부")하는데 (나)는 같은 장치를 적지 않았다. C.3-1은 어느 쪽이든 적용되므로, 설명이 비대칭이라 (가) 쪽이 더 안전해 보이는 편향이 생긴다.

### 5-2. 이 질문이 실제로는 창시자 결정이 아닐 수도 있는 이유

- 적용 타이밍(언제, 누가 승인하나)은 환경마다 다른 **운영 설정**으로 둘 수 있다(예: 환경별 `auto`/`require-approval`). 그렇게 하면 엔진은 두 방식을 모두 지원하고, 창시자가 정할 것은 "기본값이 무엇인가"로 좁혀진다. 이 좁힌 형태가 비전문가가 답할 수 있는 질문이다.
- 위험한 변경(데이터 삭제, 권한 확대)에서 **AI가 쓴 `removed field`로 사람 확인 없이 배포된다**는 점(6절 3번)은 "AI First"와 "서버 최종 권한"의 충돌이라 철학 질문이다. F1이 이 질문을 해야 한다.

### 5-3. 대체 F1 문구 제안 (일상어, 창시자 결정 대신 질문 후보)

**F1'. 배포할 때 두 종류의 변경은 사람이 한 번 확인한 뒤에만 반영되길 원하나요?**
1. 저장된 데이터가 사라지는 변경(필드·테이블 삭제 등)
2. 호출자가 할 수 있는 일이 늘어나는 변경(보여 주는 필드 추가, 접근 허용 확대 등)
- (가) 둘 다 확인한 뒤에만 반영한다
- (나) 데이터 삭제만 확인하고, 권한 확대는 알림만
- (다) 확인 없이 자동 반영하고, 문제는 거부 규칙으로 막는다
- 에이전트 의견 칸에 (가)를 적고, 근거로 4-4·4-5절(권한 확대는 조용히 통과, AI가 삭제 의도를 선언문으로 우회 가능)을 붙인다.

**F2' (DD-12에는 없고 있어야 하는 질문). 배포 뒤 문제가 생기면 이전 버전으로 되돌릴 수 있어야 하나요?** 데이터 삭제는 되돌릴 수 없다는 사실을 먼저 알리고, 되돌림 기대 수준을 묻는다(의제 11 "롤백").

**F3' (OI-P2와 겹침, 창시자 결정 사항).** G절이 "이름 변경은 별칭 유예"를 추천하지만, 구버전 호출자를 얼마나 오래 받을지는 `docs/DECISIONS.md` OI-P2(91행)가 Open이다. PRINCIPLES §4-8("창시자의 결정이 필요한 사항을 임의로 정하고 있지 않은가")에 걸린다. 별칭은 F에서 묻거나 G에서 빼야 한다.

### 5-4. 문서 크기

운영 규칙 3("하나의 토론에서 하나의 주요 의사결정")에 비추어 DD-12는 DB 적용(C.1)과 호출자 호환(C.2)을 한 문서에 담았다. C.2의 상당 부분은 OI-P2와 DD-03 층 2에 속하므로 DD-12a(DB), DD-12b(호출자/공존)로 나누거나, 최소한 F를 DB 쪽으로 한정하고 C.2는 "층 2 후보"로 낮추는 편이 맞다.

## 6. 이탈 방지 점검 재평가

원문 규칙(`design-operating-rules` 53~64행)의 여섯 질문에 대한 DD-12 답을 다시 판정한다.

| # | DD-12의 답 | 재평가 | 근거 |
|---|---|---|---|
| 1 | "예. 손 DDL과 엔티티-DB 어긋남이 사라진다" | **조건부 예.** PostgreSQL 신규 프로젝트에 한함 | 아리아리는 MariaDB(1-9). 기존 운영 DB 채택 경로는 DD-12에 없다. 또 새로 생기는 유지보수가 있다: `was`/`removed` 선언 관리, 승인 절차, 롤백 수동 절차(4-2). 줄어드는 양을 E2(아리아리 변경 이력, git 로그 가용)로 재기 전까지 "예"는 가설이다 |
| 2 | "호출자를 깨는 변경을 미리 보여 준다" | **부분 예** | 등록 기능이 꺼진 R 경로에서는 "깨지는 요청 목록"이 없다(DD-03 78행). 계약 diff 수준 경고만 가능. 사용량 관측이 대안(3-3) |
| 3 | "해당 적음. 데이터 보존 규칙은 서버가" | **틀렸다. 해당 있음, 현재는 미충족(검증 필요)** | 권한 확대 무통제(4-4), DDL 계정 분리 없음(4-5), 이름 재사용(2-3), 감사 컬럼 없음(4-2-3). 서버가 최종 권한을 통제하는지는 스키마 진화에서 가장 중요한 점검 중 하나다 |
| 4 | "예. 의도 선언 형식이 하나" | **오히려 위험.** 아래 설명 | 선택지(S1/S2/혼합, 별칭/버전)가 늘었다. 더 중요하게는 AI가 거부 메시지의 `fix` 문장대로 `removed field`를 써 넣으면 거부가 풀린다(`evolve.rs` 460행 근처 메시지: "Removed (its values are deleted): write `removed field ...`"). 즉 **의도 선언은 실수 방지이지 사람의 승인이 아니다.** AI가 소스를 쓰는 전제(AI First)에서는 선언문 존재가 "사람이 데이터 삭제를 원했다"의 증거가 되지 못한다 |
| 5 | "Prisma migrate 등과 비슷한 경험(확인 필요)" | **검증 안 됨** | 이번에도 확인하지 못했다: 확인 못함(외부 도구 동작을 조사하지 않음). 또 `was`/`removed`는 PoC DSL 문법이고 작성 형식(T02, DD-04)이 정해지면 다시 쓴다(T12 20행: "문법은 T02에 따라 다시 씀"). 다시 쓴 뒤에도 JS/Python 개발자가 새 문법을 배워야 하는지는 미정 |
| 6 | "엔진에 비교·위험 판정이 있다(PoC 자산 재사용 후보)" | **절반만 맞다** | 비교와 데이터 안전 분류는 PoC 자산이다. **운영 위험 판정(잠금, 크기, 시간, 권한 확대)은 PoC에 없다**(3-4절). 복잡성을 옮긴 것이 아니라 새로 만들어야 하는 부분이 있다. 이를 "재사용 후보"로 적으면 일의 크기를 과소평가한다 |

**종합:** 2번 질문(호출자)과 5번 질문(생태계)은 보강, 3번은 정정, 4번과 6번은 "예"를 철회하고 이유를 쓰는 것이 맞다. 중대한 충돌은 숨기지 말라는 규칙(원문 64행)에 따라 3번을 DD-12 본문에 명시해야 한다.

| # | 제안 | 이유 |

## 8. 결론과 추천

1. **방향은 맞다.** PoC 원칙(데이터를 잃는 변경은 거부, 같은 정의 = 같은 DB)은 철학과 운영 규칙 6에 부합하고 이미 구현·시험돼 있다. C.3-1·2는 그대로 유지한다.
2. **그러나 DD-12는 "DB 데이터 안전"만 보았고 "서버 권한 안전"을 보지 않았다.** 이탈 방지 점검 3번의 "해당 적음"은 정정해야 한다. 정의 변경은 DB를 바꾸는 동시에 호출자의 권한 범위를 바꾸는데, 확대는 현재 어떤 경로에서도 사람에게 보이지 않는다. 이것이 가장 큰 구멍이다.
3. **혼합 추천은 위험 등급이 정의되지 않아 시험할 수 없다.** 정의 후에 제시해야 한다. PoC의 등급은 데이터 안전용이고 잠금·크기·권한 축이 없다.
4. **expand/contract는 구현이 없다**(규약과 거부 메시지 안내뿐). "PoC에 설계가 있음"이라는 표현은 과대하다. 롤링 배포와 구버전 인스턴스 문제는 이름 변경에서 지금 그대로 생긴다.
5. **롤백은 의제 11에서 조용히 빠졌다.** 적용 후 서버 코드 되돌리기가 막힐 가능성(4-2-2)을 시험으로 확인하고 DD에 올려야 한다.
6. **추천 수정 방향(창시자 결정 아님):** S1/S2 이분법 대신 "항상 계획 먼저, 자동 허용은 세 축(데이터·운영·권한) 모두 낮을 때만, 그렇지 않으면 계획 digest에 묶인 사람의 승인" 구조(S1')를 후보로 제시하고, 운영에서는 마이그레이션 계정 분리를 기본으로 한다. F는 5-3절의 F1'(데이터 삭제·권한 확대의 사람 확인), F2'(롤백 기대 수준)로 바꾼다. 별칭 유예는 OI-P2로 넘긴다.

가장 중대한 지적 3가지는 최종 응답에 요약한다.
