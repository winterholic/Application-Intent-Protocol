**함의.** (1) "프론트 무효화 34곳이 사라진다"는 약속은 **이미 React Query를 쓰는 부분**에 대해서만 성립한다. 나머지 읽기·쓰기는 로컬 state와 직접 재호출이라 M2의 SDK가 가져가려면 아리아리가 SDK 캐시로 읽기 전체를 옮겨야 한다. 이것은 이탈 방지 점검의 "JS/Python 생태계" 항목에 걸린 비용이다. (2) 반대로 낡음 문제의 실제 규모는 34곳보다 크다(2장의 "빠짐").

**1-8 `writes.rs`는 변경 집합 수집기가 아니다.** `crates/aip-pg/src/writes.rs`는 "프로그램 전체에서 어떤 엔티티 필드가 절대값으로 대입되는지"를 정적 분석해 버전 트리거의 동시성 판단에 쓴다(`writes.rs:1~5` 모듈 주석, `absolute_fields`/`delta_fields` 11~18행). 실행 시 어떤 행이 바뀌었는지가 아니라 **선언된 command 본문의 대입 구문**만 훑는다. DD-11이 "선례"라고 쓴 C.2 71행과 E3는 근거가 약하다. 실제로 PoC에서 "무엇이 바뀌었나"에 가장 가까운 장치는 `crates/aip-pg/src/plan/subscribe.rs:73~91`의 **테이블 단위 문장 트리거**(`AFTER INSERT OR UPDATE OR DELETE OR TRUNCATE ... FOR EACH STATEMENT` → `pg_notify('aip_changed', TG_TABLE_NAME)`)다. 페이로드는 테이블 이름뿐이고 행 id·필드는 없다. 구독이 읽는 테이블 집합은 컴파일된 질의에서 뽑는다(`aip-pg/src/plan/subscribe.rs:20` `tables_in(&query)`). 즉 PoC의 선례는 "읽기가 어느 테이블을 보는가"(읽기 쪽 의존)이며 "쓰기가 어느 행·필드를 바꿨나"가 아니다.

**1-9 보완.** 구독의 재실행은 구독자 권한으로 질의를 다시 돌려 이전 결과와 값 비교 후 다를 때만 보낸다(`subscribe.rs:430~455`). 이것은 "변경 집합"이 아니라 **재조회 후 비교(diff)**이며 변경 집합 노출 문제(I5)가 구조적으로 생기지 않는다. 4장에서 대안으로 다시 쓴다.

**기타 사실.**
- 문서 22행 "34곳, 10-03 grep 기준"은 재현됨. 다만 `setQueryData` 2곳과 컴포넌트 직접 호출을 세지 않았다.
- B.2의 "클라이언트 캐시와 무효화 정보 전달은 없다(인계 기록, T13)"는 `T13-frontend-sync.md` 표의 "없음"과 일치한다. 코드로 별도 확인하지 않았다(확인 못함: PoC 전체에서 SDK 디렉터리 유무는 이번 범위 밖).

### 집계

- 백엔드 코드로 **빠짐이 확인된 것**: 8, 9, 12, 13, 16, 17, 25 (그리고 6·18의 알림). 알림은 `staleTime 0`이라 증상이 작고, `myClubList`(8, 9)와 모집 계열(16, 17)은 실제 낡은 화면을 만들 수 있다.
- **과잉**: 10(실패 시·수정 시 무효화). 거친 단위(18의 전체 일정 페이지)는 과잉이 아니라 정밀도 한계.
- **프론트가 서버 파생을 재구현**: 17(`"CLOSED"` 직접 대입), 26(북마크 로컬 state).
- 정확: 1, 2, 7, 11, 15, 19, 20, 22, 24 및 6의 목록·`myClubList`.
- 한 줄 평가: 확인한 26개 쓰기 경로 중 7개가 빠짐을 가졌다. 문서 E1이 상정한 "M1은 빠뜨린다"는 가설은 **이 코드에서도 확인된다**. 다만 이것은 **"쓰기가 무엇을 바꾸나"를 안다고 해서 해결되는 종류가 아니다**(아래 3장, 8·9·13·25번은 *파생 값*과 *연쇄*가 원인).

### 이 표가 M2에게 던지는 시험

M2가 맞히려면 엔진이 다음을 알아야 한다.
1. 8·9: 쓰기가 삭제한 행이 어느 *파생 읽기*(`MAX(createdDateTime)`)의 입력인가. 이 의존은 쓰기 쪽에 적혀 있지 않고 **읽기 쪽 식**에 있다.
2. 13·25: 선언된 작업의 연쇄 UPDATE(작성자 NULL 처리). 아리아리는 서비스 메서드 안의 JPQL 4개다. AIP에서는 FK 동작으로 선언되거나 확장 동작 안의 SQL이 된다.
3. 12: 쓰기가 *다른 리소스의 행을 지움*(알림). 변경 집합에 `delete` 연산이 필요하다.
4. 6·18·19: 알림 생성은 `@TransactionalEventListener` + `REQUIRES_NEW`로 **본 쓰기와 별개 트랜잭션**에서 일어난다(`club/alarm/ClubAlarmService.java:50~51`, `member/alarm/MemberAlarmService.java:36~37`). 요청 트랜잭션에서 수집한 변경 집합은 이 행을 보지 못할 수 있다(확인 못함: 이벤트 리스너 실행이 응답 직렬화 전에 끝나는지는 Spring 설정 의존이며 이번에 확인하지 않음).

## 3. 철학 정합성과 DD-01~10 불일치

### 3-1. DD-10 VV-5와의 정면 충돌(가장 큰 불일치)

- DD-10 VV-5: "viewer 값이 든 응답은 HTTP·CDN 공유 캐시에 넣지 않는다(`private`). **viewer 값 결과 캐시는 T13 설계 전에는 쓰지 않는다**"(`DD-10-viewer-derived-values.md:98`). T13의 최신 결정 문서가 DD-11이라고 `T13-frontend-sync.md:4`가 말한다.
- 그런데 DD-11 본문에는 viewer 값, `VV-5`, 행위자별 캐시 분리에 대한 언급이 **한 줄도 없다**(DD-11 전체 133행에서 DD-10은 참조 목록에도 빠짐. 6행 "관련"에 DD-01·02·07·08만 있음). 결과적으로 DD-10이 걸어 둔 조건("T13이 설계되면 viewer 값 캐시 허용")이 **어느 문서에서도 닫히지 않는다**.
- 아리아리의 실제 비중: DD-10 B.1은 보는 사람 기준 값이 11개라고 했고 K1~K5가 9개다(`DD-10:20~35`). 모집 상세·목록, 동아리 정보, 댓글 등 **화면 핵심 읽기에 들어 있다**. viewer 값을 뺀 M2는 아리아리 읽기 상당수를 설명하지 못한다.

viewer 값이 든 읽기에서 M2가 깨지는 구체 경로:

1. **의존이 읽기 정의 안에 숨는다.** DD-10은 `isBookmarked: "exists bookmarks b where b.member = actor"`처럼 viewer 값을 *서버 리소스 선언*에 두고 호출자는 이름만 고르게 한다(`DD-10:B.3`). 그러면 "모집 목록" 읽기의 canonical 형태에는 `isBookmarked`라는 이름만 있고, 이 값이 `RecruitmentBookmark` 테이블에 의존한다는 사실은 **서버 정의에만 있다**. DD-11 C.2 71행이 "SDK: 읽기의 canonical 형태가 어느 리소스·필드를 보는지 알아야 함"이라 했지만, canonical 형태만으로는 알 수 없다. 북마크 쓰기의 변경 집합(`RecruitmentBookmark`)은 `Recruitment` 읽기와 대조되지 않아 **낡은 `isBookmarked`가 남는다**. 해결은 **읽기 응답에 서버가 계산한 의존 집합(footprint)을 실어 보내는 것**뿐이다. PoC도 이미 그렇게 한다(구독의 `reads`를 컴파일된 질의에서 뽑음, `aip-pg/src/plan/subscribe.rs:20`). 즉 M2는 "쓰기 응답에 변경 집합"만으로 서지 않고 **읽기 응답에도 의존 집합이 필요**하다. DD-11은 한쪽만 설계했다.
2. **의존 집합 자체가 존재를 새게 할 수 있다(I5).** footprint에 행위자가 열람할 수 없는 리소스(예: viewer 식이 참조하는 소유 간선, 행 정책이 참조하는 리소스)가 그대로 나오면 "열리지 않은 관계는 없는 것과 같은 모양"(DD-01 I5, `DD-01:145`)을 어긴다. 열린 리소스 이름만 노출하거나, 불투명 태그로 접어야 한다.
3. **행위자 전환.** 로그아웃, 토큰 만료(VV-6: 무효·만료 인증은 오류, 조용한 비로그인 전환 금지, `DD-10:99`), 대리 접속(DD-02 W-I11 감사 대상)에서 클라이언트 캐시를 비워야 한다. 캐시 키가 행위자를 포함하는지, 전환 시 폐기하는지가 문서에 없다. 아리아리에서는 `useMyClubListQuery`가 `enabled: isSignIn`으로만 막는다(`hooks/club/my/useMyClubListQuery.tsx:12~15`)이며 로그아웃 시 캐시 폐기는 확인 못함(이번 범위 밖).
4. **남의 쓰기로 낡는 공개 집계.** F1 (가)가 남의 쓰기를 범위 밖으로 두는 것은 의도된 선택이다. 다만 DD-01 I7의 공개 집계(북마크 수 등)는 *남의 쓰기*로 계속 낡는다. 내가 북마크를 누르면 내 `isBookmarked`와 집계는 재조회로 서버 값에 맞춰지지만, 화면을 열어 둔 사이 다른 사람의 변경은 반영되지 않는다. 이것은 오류가 아니라 (가)의 귀결이다. 문서가 "자기 쓰기로 낡는 viewer 값"과 "남의 쓰기로 낡는 공개 집계"를 구분해 (가)가 무엇을 포기하는지 적어야 창시자가 (가)를 고를 때 근거가 된다.

### 3-2. 변경 집합은 "엔진이 다 아는가". 경로별 판정

DD-11 C.2는 "불변식·전이·연쇄 삭제로 바뀐 것까지 포함 가능"(69행)이라 했지만 조건을 달지 않았다. 경로별로 보면 다음과 같다.

| 경로 | 엔진이 아는가 | 근거·문제 |
|---|---|---|
| 표준 create/update/delete/transition | 안다 | 엔진이 대상 행을 고른다(DD-02 W-I1·W-I3) |
| bulk, 전체 단위 U4 | 안다. 실패 시 빈 집합 | `DD-07` U4 |
| **bulk, 항목별 U7** | **일부만 성공** | DD-11 C.3-3 "전부 아니면 전무이므로 무효화할 것이 없다"는 U4에서만 참. U7 예외(예: 이미지 업로드, `DD-07:B.2`)에서는 항목별 `ok`에 따라 변경 집합이 나뉜다 |
| 연쇄 삭제·`ON DELETE SET NULL` 대용 | 선언했다면 안다. 아니면 모른다 | 아리아리 탈퇴·회원 삭제가 작성자 참조를 일괄 UPDATE(2장 13·25번, `ClubMemberService.java:170~175`). AIP에서 FK 동작으로 선언되면 엔진이 알고, 확장 동작 안의 SQL이면 엔진이 SQL을 해석하지 않는 한 모른다 |
| 불변식 repair(W-I5의 "복구 규칙") | 엔진이 실행하면 안다 | `DD-02:W-I5`. repair가 만든 변경도 같은 변경 집합에 합쳐야 한다는 말이 DD-11에 없다 |
| 확장 동작(JS/Python) | **DD-06 선택에 달림** | 확장이 DB 자격 증명을 갖지 않고 엔진 API로만 쓰면 안다. DD-06 F2 (나)(엔진이 앱 프로세스 안, 확장이 DB 직접 접근 가능)는 "개발 규약과 감사로" 막는다고 했다(`DD-06:133`). 그 경우 **변경 집합 보장이 없다**. DD-11이 DD-06 F2 답에 종속됨을 적지 않았다 |
| DB 트리거·직접 SQL 마이그레이션 | 모른다 | DB 수준 캡처만 본다 |
| **반응(reaction)·outbox가 만드는 변경** | **응답 시점에 모른다** | DD-02 W-I7은 알림 같은 외부 효과를 outbox로 두고 DD-06 백그라운드 루프가 처리한다(`DD-06:33`: outbox 디스패치, 스케줄, 잡 워커). 아리아리 알림도 별도 트랜잭션(`REQUIRES_NEW`)으로 생성된다. 응답에 담긴 변경 집합은 이 행을 포함할 수 없다 |
| **시간 경과** | 쓰기가 없다 | `Recruitment.isRecruiting()`과 `getRecruitmentStatusType()`이 `LocalDateTime.now()`로 SCHEDULED→OPEN→CLOSED를 정한다(`commons/entity/Recruitment.java:108~120`). 아무 쓰기도 없이 모집 상태가 바뀐다. 변경 집합 방식은 원리상 못 잡는다 |

**진단.** M2가 "정확하다"는 주장은 *동기 경로*에서만 참이다. 비동기 효과, 시간, 불확실한 결과, 확장 우회 가능 구성은 별도 장치(재검증 주기 `validUntil`, 불확실 결과 시 쓰기 capability의 정적 영향 집합, 수동 `invalidate`)가 필요하다. 이때 `writes.rs`류 정적 분석은 **불확실한 결과에서 "이 capability가 건드릴 수 있는 리소스 집합"을 얻는 데** 쓸 수 있다. 문서는 이 용도를 쓰지 않았고 대신 변경 집합 수집이라는 부정확한 선례로 인용했다.

### 3-3. 변경 집합이 존재를 노출하는 경로(I5, W-I9)

C.3-1은 "볼 수 없는 행·필드는 뭉뚱그리거나 빼라"고만 했다. 목록으로 풀면 다음 경로가 열린다.

1. **연쇄·반응 행의 id.** 회원을 삭제하면 그 회원의 출석·알림이 바뀐다. 삭제자(MANAGER)는 남의 알림 행을 읽을 수 없다. 변경 집합에 `MemberAlarm` 이름과 id가 나오면 "상대에게 알림이 갔다"를 알게 된다. 규칙은 "행위자가 읽을 수 없으면 제외"인데, 제외하면 SDK는 *그 리소스에 의존하는 읽기*를 낡게 두므로 정확성과 I5가 서로를 깎는다(아래 3-4).
2. **필드 이름.** B.3의 `fields: ["balance"]`는 행위자에게 `select` capability가 없는 파생 필드의 존재·변경을 알린다. 필드 열람 정책(DD-01 I1·I2)을 통과한 필드만 나와야 한다.
3. **개수와 길이.** bulk 응답의 `ids` 길이, U7 항목별 `ok` 배열은 정책 필터 이후 대상 수를 드러낼 수 있다. DD-07이 "대상 수 상한, 실행 전 실제 대상 수 검사"를 두므로(`DD-02:W-I4`) 이미 호출자에게 보이는 값인지 확인해야 한다.
4. **쓰기 후 정책(W-I3).** 행위자가 소유권을 넘기는 update는 쓰기 *후* 행위자가 못 보는 행을 낳는다. 변경 집합에 그 id를 싣는지, "무언가 바뀜"으로만 싣는지 정해야 한다.
5. **의존 집합(3-1의 2).** 읽기 응답의 footprint.
6. **구독/푸시 경로(M3).** 변경 집합을 구독자에게 밀면 *구독자가 못 보는 행의 변경*이 타이밍으로 샌다. PoC 구독은 이를 피한다. 테이블 NOTIFY는 이름만 전달하고 구독자 권한으로 *질의를 다시 돌려 값이 다를 때만* 보낸다(`subscribe.rs:8~11, 430~455`). M3를 변경 집합 푸시로 설계하면 PoC보다 후퇴한다.
7. **버전 토큰 대안(4장 A).** 리소스별 단조 증가 카운터는 숨은 행의 쓰기 빈도를 오라클로 만든다. 행위자에게 보이는 결과의 해시(ETag)가 안전하지만 질의를 한 번 돌려야 한다.

### 3-4. DD-11 C.3-4, B.3 예시의 사실 오류

- **C.3-4 "처음에는 리소스·행 단위로 시작해도 정확성은 같다"는 틀렸다.** 행 단위는 *수정·삭제된 행이 이미 캐시에 있을 때*만 맞는다. **생성**은 id가 어떤 캐시에도 없으므로 행 id 대조로는 목록·집계에 닿지 못한다. 필터에 새로 들어오거나 나가는 행, 정렬 때문에 다른 쪽 페이지로 밀리는 행도 마찬가지다. 아리아리의 회계 목록은 최신순 페이지에 "페이지 마지막 기록 이전 누계"를 싣는다(`FinancialRecordService.java:73`). 새 기록이 한 건 들어오면 *모든 페이지의 누계*가 달라진다. 정확한 하한은 **리소스 단위(+ 파티션 키 예: 동아리)**이고, 행·필드 단위는 *상세(id로 읽기) 읽기에서만 안전한 선택적 최적화*다. 문서 순서(행 단위 먼저, 필드 단위는 선택)를 뒤집어야 한다.
- **B.3 `Club.balance`.** 아리아리 잔액은 컬럼이 아니라 합계 질의다(`FinancialRecordService.java:42`). AIP에서도 집계(DD-01 aggregate capability)일 것이다. 변경 집합이 `{resource:"Club", fields:["balance"]}`를 내려면 엔진이 "FinancialRecord가 바뀌면 Club.balance가 바뀐다"는 역방향 의존을 *모든 파생 필드에 대해* 유지해야 한다(물질화 뷰 유지와 같은 복잡도). 자연스러운 설계는 변경 집합에는 `FinancialRecord`만 싣고, 읽기의 footprint에 `FinancialRecord`가 있어서 잔액 읽기가 낡는 것이다. 예시가 설계를 잘못 유도한다.
- **8·9번(2장)은 "파생 읽기 의존"의 증거다.** `myClubList`는 `findFirstByClub...CreatedDateTimeDesc`(최신 공지·활동 시각)이라 *삭제*가 낡음을 낳는다(`ClubListService.java:86~87`). 변경 집합에 `ClubNotice delete`가 있어도 SDK가 `myClubList` 읽기의 footprint(`ClubNotice`, `ClubActivity`)를 모르면 소용없다. 이 사례는 읽기 쪽 footprint가 M2의 *필수 절반*임을 보여 준다.

### 3-5. DD-01 canonical과의 정합

C.3-2 "SDK의 캐시 키는 읽기의 canonical 형태에서 만든다"는 DD-01의 canonical 정리와 의미가 다르다. DD-01의 canonical은 "같은 의미의 요청(중첩 where와 관계 필터, 저장된 조회와 원형)이 하나의 형태로 정리되어 같은 정책을 받는다"는 **서버 내부 수단**이다(`DD-01:158`). 정책·스키마를 아는 정리를 클라이언트가 똑같이 구현하면 이중 구현이다(AIP가 없애려는 바로 그것). 현실적 선택은 (가) SDK가 호출자가 쓴 요청을 결정적으로 직렬화한 값을 키로 쓰고 의미가 같은 요청의 중복 캐시를 허용하거나, (나) 서버가 응답에 canonical 키를 실어 주고 SDK는 그것으로 *저장 후* 공유한다. 둘 다 DD-08(요청 형식)의 직렬화 규칙과 "응답 형식은 후속 문서"(`DD-08:5`)에 종속된다. DD-11은 이 종속을 표시하지 않았다.

### 3-6. 그 밖의 불일치·누락

## 4. 대안 비판

### 4-1. M1/M2/M3는 같은 축의 대안이 아니다

M1은 *누가 정하나*(사람), M2·M3는 *변경 정보를 어떻게 전달하나*다. M2와 M3는 같은 "변경 태그"를 서로 다른 채널로 보내는 것이다. M2는 *쓰기 응답*이라는 채널이고, M3는 *구독 푸시*라는 채널이다. 진짜 설계는 "변경 정보의 형식과 의존 집합의 형식"이고, 채널은 후속으로 붙일 수 있다. 문서가 M2·M3를 병렬 선택지로 놓은 탓에 F1이 "형식이 다른 두 안"처럼 읽힌다. 또 C.2의 M3 열이 M2와 거의 같은 이유는(정확도·구현 "M2 + ...") 이를 증명한다. 형식을 공통으로 만들면 M3는 M2에 "구독 연결 + 팬아웃"만 더한 것이고 F1은 *형식 결정이 아닌 채널 추가 시점*의 질문이 된다.

## 5. F1이 창시자 질문이 맞는지

**판정: 창시자 질문이 될 자격은 있으나 현재 문장으로는 답하기 어렵고, 지금 막혀 있는 결정도 아니다.**

1. **사용자 경험 질문이라 자격은 있다.** 운영 규칙 F는 "제품 철학이나 사용자 경험에 영향을 미치는 선택만" 묻는다. 남의 변경이 화면에 언제 보이는가는 사용자 경험이다. 또 실시간을 고르면 DD-06이 말한 상시 프로세스가 필요해져 배포 선택(DD-06 F1 서버리스 여부, `DD-06:126`)과 엮인다. 이 연결은 DD-11에 적혀 있지 않다.
2. **그러나 근거가 없다.** 아리아리에는 실시간 데이터 화면이 없다. 백엔드 `src/main`에 WebSocket·SSE 사용이 없고(`grep -rnlE "WebSocket|SseEmitter|SimpMessaging|@EnableWebSocket"` 결과 없음), 프론트에도 `refetchInterval`·`WebSocket`·`EventSource`가 없다(`setInterval` 5곳은 `dayFloatinBar.tsx:35` 등 UI 타이머로 보이나 각 파일 목적은 확인 못함). 문서는 "실시간이 필요한 화면은 E1로 찾는다"(110행)고 했지만 **E1은 무효화 호출 대 서버 변경 대조이므로 실시간 필요를 찾아낼 수 없다**. 근거가 필요하면 별도 실험(화면 목록에서 "여러 사람이 같은 데이터를 동시에 열어 두는" 화면 찾기)이 필요하다.
3. **비전문가가 답하기 어려운 문장이다.** "자동으로 반영", "화면을 다시 열거나 새로고침할 때"는 몇 초 안에인지, 어떤 화면에서인지 정하지 않았다. (가)의 설명도 부정확하다. 지금 아리아리에서 다른 사람의 변경이 보이는 시점은 React Query의 `staleTime`과 재마운트에 달려 있어 새로고침 없이도 보이는 경우가 있다(전역 60초, `providers/QueryClientProvider.tsx:19`). 창시자가 "새로고침해야 보이는 화면"을 상상하고 (가)를 고르면 실제 동작과 달라질 수 있다.
4. **중간 선택지가 빠졌다.** "화면이 열려 있는 동안 몇십 초마다 다시 가져오기"(주기적 재조회)가 (가)와 (나) 사이에 있다. 비용은 거의 없다.
5. **형식이 같다면 지금 안 물어도 된다.** 4-1처럼 변경 정보의 형식을 하나로 두면 M3는 *채널 추가*이고 기본값 (가)를 그대로 두고 화면 요구가 생길 때 열면 된다. 즉 F1은 "지금 필요한 제품 결정"이 아니라 "미룰 수 있는 범위 질문"이다. 에이전트가 기본값 (가)로 가고 근거를 달아 제안하는 쪽이 운영 규칙의 "내부 구현 세부 사항은 근거를 제시한 뒤 기술적으로 제안"에 맞다.

**수정안.** F1을 지금 묻는다면 아리아리의 실제 화면으로 바꾼다. 예: "운영진 두 명이 같은 지원자 목록을 열어 두었습니다. 한 명이 한 지원자를 승인했을 때, 다른 운영진의 화면은 (가) 그 사람이 화면을 다시 열 때까지 그대로여도 된다 (나) 몇십 초 안에 저절로 바뀌어야 한다 (다) 즉시 바뀌어야 한다." 지원자 목록은 2장 23번에 있는 실제 화면이다. 기본값은 (가), 에이전트 근거는 "아리아리에 실시간 화면이 없음(위 2번)".

**더 중요한, 아직 묻지 않은 질문 후보 하나(필수 아님, 확정 아님).** "AIP가 프론트 캐시까지 직접 제공해야 하는가, 아니면 아리아리가 이미 쓰는 React Query 같은 도구와 연결하는 어댑터면 되는가." 이것은 인계 의제 14의 "프론트엔드 라이브러리와 통신 규약까지 포함하는 통합 개발 체계"를 어느 범위로 읽는지에 걸린다. 1장 근거(읽기 상당수가 이미 React Query 밖)를 보면 어느 쪽이든 아리아리 이전 비용이 다르다. 비전문가에게는 "지금 앱이 쓰는 도구 위에서 돕는 것인가, 새 도구로 바꾸게 하는 것인가"로 풀어 쓸 수 있다.

## 8. 결론과 추천

**방향은 맞고 형식이 덜 익었다.** 서버가 아는 변경 지식을 프론트가 손으로 다시 적지 않게 하자는 DD-11의 목표는 PRINCIPLES §2의 존재 목적(이중 유지보수 최소화)과 의제 14의 "통합 개발 체계"에 맞는다. 아리아리 코드도 M1의 실패를 확인해 준다. 확인한 26개 쓰기 경로 중 7개에서 낡은 읽기가 생기고, 1개는 과잉 무효화다(2장). 프론트가 서버의 파생 상태를 재구현하는 곳(`"CLOSED"` 직접 대입, 북마크 로컬 복제)도 나왔다.

**그러나 초안의 M2는 지금 상태로 추천하기 어렵다.** 이유 셋.
1. DD-10 VV-5가 "T13 전에는 viewer 값 캐시를 쓰지 않는다"고 걸어 둔 조건을 DD-11이 닫지 않았다. 그리고 viewer 값과 파생 값은 쓰기의 변경 집합만으로는 맞히지 못하고, **읽기가 의존하는 리소스 집합(읽기 쪽 footprint)**이 있어야 맞다. 문서는 쓰기 쪽만 설계했다.
2. "행 단위로 시작해도 정확성은 같다"는 틀렸고(생성이 닿지 않는다), `Club.balance` 예시와 `writes.rs` 선례는 사실과 다르다.
3. 정확도 주장이 동기 경로에서만 참인데 조건 없이 쓰였다. 반응·outbox, 시간 경과, 불확실한 결과, 확장 우회 구성은 별도 장치가 필요하다.

**추천.**
- 결정 상태는 **미결정 유지**. 창시자에게 바로 올릴 새 결정은 없다.
- 설계 방향은 **B(리소스+파티션 태그를 쓰기 응답과 읽기 응답 양쪽에 서버가 계산해 싣는 방식)를 기본, C(활성 읽기 전체 재조회)를 폴백·기준선, 시간·반응은 `validUntil`**로 수정한다. 행·필드 단위, 구독 푸시는 후속 최적화로 둔다.
- F1은 아리아리 실제 화면 문장으로 바꾸고 기본값 (가)로 비차단 처리한다. 창시자 질문으로 가치가 더 큰 것은 "AIP가 프론트 캐시를 직접 제공하나, 기존 도구의 어댑터인가"이며 필수는 아니다(5장).
- 다음 라운드 전에 P0-1~P0-8을 반영하고 E4(빠짐 7건이 태그로 잡히는지)를 돌려 B의 실효를 숫자로 확인한다.

**확인 못함(이번 검토의 한계).** (1) `ApplyFormService`와 임시 지원 목록 DTO의 필드를 읽지 않아 2장 5·21번은 판정 보류. (2) 알림 리스너가 응답 직렬화 전에 끝나는지(3-2) 스프링 설정 미확인. (3) 로그아웃 시 React Query 캐시 폐기 여부, 화면당 활성 쿼리 수. (4) `setInterval` 5곳의 목적. (5) PoC에서 문장 트리거 외에 행 단위 변경 캡처가 있는지는 `aip-pg`·`aip-runtime` 전체를 훑지 않음(확인한 범위는 `subscribe.rs`, `plan/subscribe.rs`, `writes.rs`).
