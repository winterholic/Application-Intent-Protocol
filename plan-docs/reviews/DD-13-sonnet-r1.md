방법: 22개 파일의 `export interface/type` 선언 119개를 읽고 성격별로 손으로 분류. 선 단위 근사이고 분류 경계는 판단이므로 ±5%p 오차를 가정한다. (분류 명령: `grep -h "^export (interface|type)" app/types/*.ts`, 선언명 목록은 스크래치패드에 보관.)

해석:
- 계약과 무관한 화면 전용 약 17%. 나머지 약 83%는 "서버 모양을 손으로 옮긴 것"이라 DD-13 B.1의 서술("백엔드 DTO를 손으로 다시 적은 타입")은 맞다.
- 단 83%는 "T2가 생성한다"가 아니다. T2가 만드는 것은 엔티티 DTO와 열거형(약 52%)이고, 봉투 19%는 타입이 아니라 **요청 모양 자체가 사라지는 부분**이다. 요청 본문 11%는 T2가 아니라 T1(커맨드별 입력 타입)이 만든다. DD-13은 T1을 "저장된 조회에만 맞음"으로 읽기에 한정했지만(C.1) 쓰기 입력 타입은 T1/PoC 방식이 그대로 맞는다. 그러면 T2의 정확한 범위는 "읽기 쪽 결과 타입"이고 쓰기는 T1이다. G절은 이 구분을 "저장된 조회는 T1도 함께"로만 적어 쓰기를 빠뜨렸다.
- 화면이 그 봉투를 이미 그대로 소비한다는 점이 중요하다. `RecruitmentResponse` 같은 큰 봉투 타입을 쓰는 화면은 `select`로 바꾸면 컴포넌트 props도 바뀐다. 타입이 없어지는 이득은 화면 코드 수정 비용(이 연구에서 미측정)과 맞바꾼다. 확인 못함: 화면 코드 수정량은 측정하지 않았다.
- **수작업 복제의 표류가 실제로 일어나고 있다(사실).** 같은 이름이 중복 선언된 것: `ApplyQuestionData`(`types/recruitment.ts:58`은 `id: number`, `types/application.ts:62`는 `id: string`), `ClubData`(`api.ts:49`, `club.ts:33`), `PageInfo`(`api.ts:128`, `pageInfo.ts:1`), `SchoolData`(`api.ts:124`, `club.ts:29`), `ClubMemberData`(`member.ts:26`, `clubActivity.ts:56`), `ProcedureType`(`review.ts:53`, `recruitment.ts:11`), `ClubActivity`, `ClubActivityComment`. `ClubRecruitmentListResponse`는 같은 파일 `recruitment.ts:35`와 `:73`에 두 번 선언돼 TS 인터페이스 병합으로 조용히 합쳐진다. 119개 선언에서 이름 중복이 9쌍 이상이다. DD-13은 B.1에서 "고치지 않으면 컴파일러도 모른다"라고 일반론으로만 말했지만, 이 표류 증거가 가장 강한 근거인데 인용하지 않았다.
- `isMyBookmark`/`isMyClub`/`isMyApply` 같은 viewer 값이 `types/` 안에 9곳. DD-10의 viewer 파생 값과 직접 대응하며 T2 생성 타입이 이를 `bookmarks: { mine: ... }` 형태로 줄지 이름으로 줄지는 DD-10이 닫지 않았다. 생성 타입의 모양이 DD-10 V안(`DD-10:53~57` 두 표기 병존)에 종속된다.

결론: E1은 DD-13에서 "완료 가능"한 검증이다. 위 표를 DD-13 E1에 결과로 기입하고 "생성되는 비율"이 아니라 "손으로 쓰는 코드에서 사라지는 비율"로 질문을 바꿔야 한다.

### 3.2 의제 14와의 범위 불일치 (가장 큰 철학 문제)

의제 14 원문(`founder-intent-handoff-2026-10-03.md:695~703`)은 9개를 논의 대상으로 둔다: 프론트 데이터 캐시, 변경 후 무효화, 재조회, **낙관적 업데이트, 실시간 동기화, 일관성 수준, 구독 모델, 여러 호출자 간 상태 반영**, 서버와 클라이언트 계약. DD-13 A는 "타입을 얻는 방식"과 "캐시를 누가 갖나" 둘로 줄였고, 둘 다 9개 중 첫째·둘째·마지막에만 닿는다. 나머지 5개는 DD-11이 "후속"(`DD-11:4`)으로 미뤘고 DD-13도 다루지 않는다. 그 사이에서 의제 14의 후반부가 어느 문서에도 소유자가 없다. 이 공백은 교차 검토 3-4가 지적한 SDK 공백과 같은 종류인데 DD-13이 일부만 메운다. 최소한 "이 DD가 다루지 않는 의제 14 항목"을 표로 명시하고 소유 문서를 지정해야 한다.

또 의제 14의 핵심 문장 "프론트엔드 라이브러리와 통신 규약까지 포함하는 통합 개발 체계"는 AIP가 **프론트 라이브러리를 직접 가진다**는 방향으로 읽히는데, 추천 C2는 AIP의 프론트 라이브러리를 "기존 캐시 도구 위의 얇은 어댑터"로 낮춘다. 이것이 원문에 맞는지가 진짜 창시자 질문이다. 다만 원문이 "프론트엔드 라이브러리"의 모양을 확정하지 않았고(원문 의제 14는 "상태: 미확정"), PART I §3은 "JS 생태계를 자연스럽게 활용"을 요구하므로 C2 쪽이 더 가깝다는 DD-13의 판단은 타당하다. 문제는 그 판단이 맞는지가 아니라, 그 판단을 근거(에이전트 의견 한 줄, `DD-13:116`)만으로 창시자에게 넘기고 "AIP 소유로 남는 것"을 말하지 않는 점이다. 4절 S 목록이 사실상 그 답인데 F1에 연결되어 있지 않다.

### 3.3 계약 노출: 생성 타입이 무엇을 클라이언트에 싣는가 (DD-01 I5, OI-P3와 충돌 소지)

- T2는 "계약에서 리소스 타입을 생성"한다(`DD-13:39`, `:58~63`). 그러면 클라이언트 번들/저장소에 리소스·필드 목록이 들어간다. DD-01 I5는 "운영 런타임에서 볼 수 없는 행은 없음, 열리지 않은 필드·관계는 없는 것과 같은 오류 모양"을 요구하고(`DD-01:146`), DD-01 B.3(`:100`)은 "권한이 반영된 계약을 가진 빌드·개발 도구는 정확한 진단을 준다"고 쓴다. 이 둘이 합쳐지면 질문이 생긴다: **생성에 쓰는 계약은 전체 계약인가, 호출자 역할별 가시 계약인가.** 전체 계약으로 만든 타입은 닫힌 필드의 이름을 프론트 번들에 싣고(존재 노출), 가시 계약이면 역할마다 SDK 빌드가 달라져 생성물이 복수가 된다(S6의 "개발 도구는 정확, 운영은 감춤"을 어느 산출물이 구현하는지 불명).

## 4. 대안 비판 (T/C), 빠진 대안, S1~S7 누락·과잉

### 4.1 T1/T2/T3

- **T1 대 T2 구분이 틀에 맞지 않는다.** 2절에서 보인 대로 쓰기 입력 타입(약 11%)은 T1 방식이 그대로 맞고, 읽기만 T2가 필요하다. 표는 읽기 하나만 놓고 두 방식을 경쟁시켰다(`DD-13:58~63`). 올바른 분해는 "읽기 결과 타입: 추론(T2) / 쓰기·저장된 조회: 생성 함수(T1)"이고 둘은 대안이 아니라 한 SDK의 두 층이다. G절이 이미 이 조합으로 결론을 내므로 C.1은 대안 비교처럼 보이게 쓴 정당화 표다.
- **T3은 허수아비다.** "타입 없음"은 PoC 이전의 아리아리 프론트(API 호출 129곳 중 64곳만 타입 인자)가 현재 상태라 "현 상태"로 라벨을 바꾸는 쪽이 정직하다. 반대로 T3의 변형인 "T3'=런타임 검증은 서버 응답을 클라이언트에서 스키마로 파싱(zod 등)"은 서버 변경의 **런타임 드리프트 탐지**로 T2와 병용 가능한데 언급이 없다(Python 호출자에게는 사실상 이것만 남는다. C.1 마지막 행).
- **T2의 "컴파일 성능 한계, 확인 필요"는 추천의 핵심 위험인데 E2는 문서 조사로만 끝난다**(`DD-13:106`). TS select-추론은 Prisma 등의 선례가 있다고 알려져 있으나(확인 필요: 웹 미확인) 그 선례의 스키마 규모와 컴파일 비용은 확인 못함. DD-01의 표현 범위(where/orderBy/traverse/aggregate/viewer 값)가 Prisma보다 넓어질수록 타입 레벨이 깊어진다. **PoC 없이 추천하지 말고 "아리아리 계약 규모 + DD-01 B.1 요청 10개"로 타입체크 시간을 재는 E를 추가**하는 것이 맞다.
- **빠진 대안 T4: 같은 언어 직접 타입 공유(생성 없음).** 서버 정의가 JS/TS(OI-L1이 JS/Python 정형 API로 가는 중)라면 tRPC식으로 정의 객체의 타입을 프론트가 import해 추론하는 방식이 있다. 생성 단계·`.aip/client` 디렉터리가 없어 PRINCIPLES §4-5(새 단계 없이 쓴다)에 더 가깝다. 한계: 서버가 Rust 엔진 + 정의는 "데이터"이면(DD-04 결정 전) 타입이 정의에서 나오지 않고, 프론트·백엔드가 다른 레포·다른 언어(아리아리 백엔드는 JS가 아닌 것으로 보임. 확인 못함)면 불가. 그래서 **T4는 보조 경로**이지 T2의 대체는 아니나, 후보에서 지운 근거를 문서에 남겨야 한다.
- **빠진 대안 T5: 계약을 기계 판독 스키마(describe)로 노출하고 범용 클라이언트가 읽는다.** PoC는 이미 `/aip/describe`를 두었고 tsgen의 주석(`tsgen.rs:2`)도 "describe를 가져올 수 있는 어떤 소비자도 같은 클라이언트를 만든다"고 쓴다. T2의 생성기를 JS/Python/에이전트가 공유하는 중립 층(계약 JSON) 위에 두면 Python 호출자(F3의 자사 AI 에이전트)와 TS가 같은 입력을 쓴다. DD-13은 생성 입력이 무엇인지(서버 정의? describe? 빌드 산출물?) 명시하지 않았다. 3.3의 가시 계약 문제와 같은 뿌리.

### 4.2 C1/C2/C3

- **F1의 이분법 (나) C1은 아무도 주장하지 않는 허수아비에 가깝다.** C1은 "캐시 구현을 AIP가 계속 유지"인데 DD-11은 B(태그 대조)를 위해 필요한 것이 **캐시 전부가 아니라 "무효화 판정과 키 직렬화"**라고 이미 좁혔다(CI-3). 현실 선택지는 (가) C2: RQ 위에 얹기, (나') **프레임워크 중립 코어(캐시 없음, 태그/키/구독 이벤트만 방출) + 공식 어댑터 여러 개**다. 이 코어는 Python 호출자와 서버 사이드 호출자(Next 서버 컴포넌트, 에이전트)도 같이 쓰므로 어차피 필요하다. 코어 위에 RQ 어댑터를 첫 어댑터로 두는 구조가 C2를 포함하면서 C1의 위험(캐시 유지)을 지지 않고 "RQ가 바뀔 때만 어댑터 비용"을 한정한다.
- 현재 추천 C2는 `useRead`/`useApply` 훅으로만 표현돼 **React 전용으로 읽힌다.** 원문은 "JavaScript 생태계 우선"이지 React 우선이 아니다(`founder-intent-handoff:152`). TanStack Query가 React 외 어댑터(Vue, Solid, Svelte, Angular)를 제공한다는 것은 알려져 있으나 확인 필요(웹 미확인). 어느 쪽이든 DD-13은 "코어 클라이언트"와 "프레임워크 어댑터"의 층을 나누지 않아 3.4-1이 생긴다.
- **C2의 이점 서술 중 "AI가 이미 아는 도구"(`:72`)는 과장이다.** 호출 표면은 `aip.useRead("Recruitment", {where, select...})`라는 AIP 고유 API이고 AI가 RQ를 아는 것은 `data`, `isLoading`, `invalidateQueries` 같은 주변부에 한정된다. 학습 비용은 어차피 AIP API에 있다. C2의 진짜 이점은 (1) 이미 쓰는 devtools·Suspense·SSR 하이드레이션·재시도·중복 제거를 공짜로 얻는 것, (2) 아리아리처럼 이미 RQ를 쓰는 앱의 **점진 이주**다(아리아리 hooks 23개 파일이 RQ를 쓰는 사실, 5절 참고). 이 두 가지를 쓰면 근거가 사실에 맞는다.
- **C2의 숨은 비용을 표에 쓰지 않았다**: (a) RQ 메이저 버전 상승에 AIP 어댑터가 종속(`:71`에 한 줄 있음), (b) 3.4-6의 구조적 보장 상실, (c) 낙관적 업데이트·구독을 RQ의 `onMutate`/`setQueryData`에 맡기면 서버 태그 규칙과 충돌하는 쓰기 경로가 열림, (d) RQ 쿼리 키 해시가 객체 키 순서에 둔감하다고 알려져 있으나(확인 필요) DD-11 CI-3의 "결정적 직렬화"를 AIP가 별도로 보장해야 하는지 불명.
- C3(캐시 없음): 비교 기준선으로 쓰는 것이 맞고 열을 채워 넣어야 한다(3.4-9). 아리아리의 `staleTime`/`placeholderData` 사용이 5건(hooks)뿐이고 화면당 활성 읽기 수는 DD-11 E6이 미측정이므로 **"C3 + 쓰기 뒤 전체 재조회(DD-11 C안)"가 충분한지는 아직 모른다.** DD-11이 "E6에서 C로 충분하면 B는 후속"이라 했는데 DD-13의 어댑터 필요성도 같은 E6에 종속된다는 점이 적혀 있지 않다.

## 5. F1이 창시자 질문인가, 비전문가가 답할 수 있는가

### 5.1 창시자 질문인가: 대부분 아니다. 단 숨은 진짜 질문이 있다

운영 규칙 F: "제품 철학이나 사용자 경험에 영향을 미치는 선택만 질문한다. 내부 구현 세부 사항은 근거를 제시한 뒤 기술적으로 제안한다." 그리고 DD-13 C.3 제목은 스스로 "`[추천]` (창시자 질문 아님)"이다.

- "React Query에 붙일까 AIP 전용 캐시를 만들까"는 PART I §3(JS 생태계 우선, 개발자가 새 도구를 배우지 않게)이 이미 방향을 정한 **구현 선택**에 가깝다. 에이전트 의견(가)가 원문 문장 하나로 닫히는 질문이면(`DD-13:116`) 창시자에게 묻는 대신 DD-08처럼 "창시자 질문 없이 기술 제안으로 낸다"가 규칙에 맞다(DD-08:3 헤더가 그 선례). 하나의 DD에 창시자 질문이 하나면 과하게 묻는 것이다.
- 반면 **창시자가 실제로 답해야 할 질문은 F1 밑에 가려져 있다**: (1) AIP의 프론트 라이브러리는 얼마나 AIP 소유여야 하는가(의제 14의 "프론트엔드 라이브러리와 통신 규약까지 포함하는 통합 개발 체계"에서 "라이브러리"의 무게), (2) 1차 지원 프레임워크 범위(React만? 프레임워크 중립?). (1)은 F1(가)/(나)로 번역되면서 "도구가 바뀌면 AIP 어댑터도 따라가야 한다"는 유지보수 부담의 문제로 변형되어 철학 질문이 사라진다. (2)는 문서에 전혀 없다. 창시자 질문은 이 둘이어야 한다.

### 5.2 비전문가가 답할 수 있는가: 불가능한 문장이 섞여 있다

- 질문 본문(`:113`)의 "캐시할 때 AIP 전용 도구 대 이미 널리 쓰는 도구(React Query 등)"에서 창시자는 "React Query가 무엇이고 현재 아리아리가 이를 쓰는지"를 모르면 판단할 수 없다. B.1이 "React Query 훅"이라고 한 줄 적었지만 운영 규칙 9("창시자가 이해하기 어려운 기술 개념은 실제 AIP 사용 예시와 연결해 설명")대로라면 "아리아리 프론트에서 지금 `useClubNoticeMutation` 같은 훅이 쓰는 그것"이라고 짚어야 한다.
- (가)의 "도구가 바뀌면 AIP 어댑터도 따라가야 한다"와 (나)의 "동작을 AIP가 완전히 통제하지만 새로 배워야 한다"는 서로 다른 축의 비용을 각각 한 문장씩 줬을 뿐이다. 창시자가 비교할 수 있는 같은 축(누가 무엇을 얼마나 오래 고치는가)이 없다. 아래처럼 바꿔야 한다.
- 실제로 필요한 사용자 시나리오 문장이 없다. 질문 앞에 "프론트 개발자가 공지 삭제 버튼을 만든다. (가)는 삭제 후 무엇이 다시 불러와지는지를 AIP가 자동으로 정하고, 개발자는 이미 쓰던 React Query의 로딩/에러 상태 값을 그대로 쓴다. (나)는 …" 같은 한 장면.
- 선택에 필요한 **실측**이 빠졌다. "이미 널리 쓰는 도구"가 아리아리에서 hooks 23개 파일/1,359줄이라는 사실, 손 무효화 34곳 중 DD-11 E1이 찾은 빠짐 7건이라는 사실(`DD-11:104` E1 완료)을 질문에 붙이면 창시자가 "지금도 쓰는 도구를 유지한다"의 이득을 숫자로 안다.

### 5.3 F1 개정안 (창시자 몫 확정 아님, 제안 문구)

**F1. 프론트 개발자가 AIP로 데이터를 불러올 때, 지금처럼 이미 쓰는 도구(아리아리는 React Query)를 그대로 쓰고 AIP가 그 위에서 자동으로 처리해 주길 원하나요, 아니면 AIP가 프론트용 도구를 따로 제공해 그것만 쓰게 하길 원하나요?**
- (가) 이미 쓰는 도구 위에서. 아리아리라면 훅 이름과 호출 방식만 AIP 것으로 바뀌고 로딩/에러 처리는 그대로. 단, 도구의 큰 개편이 있으면 AIP도 따라가야 함
- (나) AIP 전용 도구. 다른 프레임워크에서도 같은 방식으로 동작하고 AIP가 끝까지 책임지지만 개발자가 새로 배워야 함
- 답이 없으면 (가)로 진행(다른 결정을 막지 않음). 에이전트 의견: (가)이되, 프레임워크와 무관한 코어를 먼저 두고 React Query 연결은 그 위의 첫 어댑터로.

그리고 **F2(제안): 첫 출시에서 지원할 프론트 환경은 React 하나인가, 아니면 다른 프레임워크도 같은 방식으로 되어야 하나?** (DD-01 F3와 묶어 "누가 호출하나"의 일부로 다룰 수 있음.)

이것은 DD-13이 창시자 질문 수를 늘리자는 제안이 아니다. 현 F1을 위 (나') 구조로 바꾸면 F1은 기술 제안으로 내리고 F2만 창시자에게 남길 수 있다. 규칙 F("철학/UX에 영향을 주는 선택만")에는 이쪽이 맞다.

## 8. 결론과 추천

- DD-13의 방향(SDK를 DD로 세워 공백을 메우고, 읽기 결과 타입은 요청 모양에서 추론하며, 캐시는 기존 도구와 병행)은 철학에 맞고 교차 검토 3-4를 정확히 겨냥했다. 아리아리 `types` 실측에서도 약 83%가 서버 모양의 수작업 복제이고 이미 표류가 있어 "이중 유지보수 감소" 근거는 DD-13이 쓴 것보다 강하다.
- 그러나 현 초안은 (1) 층 구조 없이 C2를 `useRead`/React 훅으로 쓴 점, (2) 생성 입력과 계약 노출을 정하지 않은 점, (3) S 목록이 다른 DD의 "SDK가" 문장 모음에 그쳐 실제 SDK의 필수 책임(인증, 멱등 키, 파일, 페이지네이션, 오류, 버전)을 놓친 점, (4) F1이 구현 선택을 창시자에게 묻고 진짜 창시자 질문을 가린 점 때문에 **합의 문서가 되기엔 이르다.**
- 추천: 7-1~7-7을 반영해 2라운드로 보낸다. T2/C2 방향은 유지하되 "잠정"으로 표기하고, 코어/어댑터 분리와 계약 가시 범위를 먼저 못 박는다. 창시자에게는 F1을 기술 제안으로 내리고, 5.3의 "1차 지원 프론트 환경" 질문과 "AIP 프론트 라이브러리의 소유 범위" 질문만 남기는 것을 권한다(확정 아님).
