# 비-primary `Id<T>` 컬럼 연결

> 상태: V1 의미 검사를 이미 통과하는 타입의 V2 DDL 누락 보완. 타입 체계나 최종 작성 형식의 새 결정을 뜻하지 않는다.

V1은 필드 `next: Order.Id?`를 `Id<Order>?`로 기록한다. 이 타입은 Order를 식별하는 값이며 `Ref<Order>`와 달리 DB 외래키나 행 탐색을 뜻하지 않는다. V2 읽기·V3 값 검사·SDK·마이그레이션의 물리 타입 표는 이를 bigint로 다루지만, 초기 V2 DDL은 기본키 이름 `id`인 경우만 처리하고 나머지 `Id<T>`를 미지원 타입으로 거부한다. 테이블 생성 순서에서도 `Id<T>`를 Ref 의존성으로 잘못 계산해 상호 식별자 필드가 있는 두 리소스를 순환으로 판단할 수 있다.

## 설계 관문

1. **원칙:** §2의 2·3·4·6에 따라 이미 선언 가능한 값을 실행 환경까지 일치시킨다. 새 DSL 표면과 런타임 권한은 늘지 않는다.
2. **표현 범위:** 성공 facts인데 배포할 수 없던 nominal ID 보관·필터·읽기가 작동한다. 기존 Ref 관계 표현과 필드 정책 범위는 바뀌지 않는다.
3. **서버 작성량:** 단순 식별자 보관에 가짜 관계 resource나 별도 SQL이 필요하지 않다. 새 서버 설정은 없다.
4. **최종 권한과 신뢰:** `Id<T>` 값도 기존 입력·wire 검사를 거친다. DDL은 bigint 컬럼만 만들고 FK 권한이나 관계 탐색을 부여하지 않는다. `Ref<T>`만 실제 FK와 생성 순서 의존성을 갖는다.
5. **생태계:** TS SDK의 기존 `Id<"T">` brand와 세 ID wire를 유지한다. Python 등 호출 계약도 변하지 않는다.
6. **중복 표현:** `Id<T>`를 `Ref<T>`로 암묵 변환하지 않는다. 이미 다른 의미로 쓰인 두 타입의 DDL만 분리한다.
7. **수단과 목적:** V2 DDL 타입·의존성 분기 두 곳을 보완하며 공통 path helper의 기존 의미는 유지한다.
8. **OPEN:** ID 입력 wire나 보관 방식의 최종 제품 결정을 새로 하지 않는다. 기존 `id` 기본키 DDL·facts 지문은 그대로 둔다.

## 검증

- V1이 허용한 nullable/non-null 비-primary `Id<T>`가 bigint 컬럼으로 생성되고 실제 값으로 저장·필터·읽기된다.
- `Id<T>`만으로 서로 가리키는 두 테이블은 생성 가능하며, `Ref<T>`는 FK를 유지한다. 기존 기본키 DDL 문구는 변하지 않는다.
- 세 ID wire에서 조회 값의 변환·정밀도를 확인한다. 마이그레이션에서 신규 `Id<T>` 컬럼의 물리 타입과 nullable 보강을 확인한다.

## PoC 확인 결과

V2 단위 테스트에서 누락된 bigint 분기와 잘못된 상호 의존성의 RED를 확인한 뒤, DDL의 `Id<T>` 컬럼 타입과 실제 `Ref<T>` 의존성만 좁게 고쳤다. 새 V2 단위 테스트 3개와 PostgreSQL 테스트 1개가 통과했다. DB에는 존재하지 않는 대상 ID도 `Id<T>` 컬럼에 저장되며, 반대로 `Ref<T>`는 없는 부모를 SQLSTATE 23503으로 거부한다. Legacy·SafeNumber·DecimalString 읽기와 `i64::MAX`의 문자열 wire, nullable 값도 확인했다. 새 마이그레이션 PostgreSQL 테스트는 기존 행에 nullable `Id<T>` 컬럼을 bigint로 추가하고 값 없는 행을 보존한 뒤, FK 없이 숫자를 대입한다.
