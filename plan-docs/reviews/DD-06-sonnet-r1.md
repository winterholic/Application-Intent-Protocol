DD-06이 인용하지 않았지만 판단에 중요한 코드 사실(E1을 지금 읽기만으로 일부 답할 수 있다):

- `engine.rs`는 axum/http를 import하지 않는다. 의존은 crypto, error, exec, objects, validate, aip_plan, deadpool_postgres뿐이다(`engine.rs` 4~16행). HTTP에 묶인 모듈은 `http.rs`와 `subscribe.rs`뿐이다(`grep -ln axum *.rs` 결과). `subscribe.rs` 17행이 `crate::http::AppState`를 쓰고 `axum::extract::ws`(21행)를 쓴다. 즉 DD-06 C.3-1의 "HTTP와 엔진이 한 크레이트라 분리가 필요"는 사실이지만, 얽힘 정도는 낮다. 분리 비용 추정(E1)은 승인 없이 이미 가능하고, 결과는 "엔진 본체는 이미 HTTP 비의존, 구독(WebSocket)만 HTTP 계층에 묶임"이다.
- 백그라운드 작업은 `lib.rs` 116~123행에서 `tokio::spawn`으로 4개를 띄운다(outbound, dispatch, schedule, jobs). `Options.workers` 플래그(88~89행)가 이미 있어 워커를 끌 수 있다. 워커들은 `FOR UPDATE SKIP LOCKED`로 행을 잡는다(`dispatch.rs` 34행, `jobs.rs` 50행, `outbound.rs` 235행). 여러 프로세스가 동시에 돌아도 안전한 구조다.
- 구독 변경 감지는 PostgreSQL `LISTEN/NOTIFY`이고 전용 연결이 하나 필요하다(`subscribe.rs` 7행, 132행, `http.rs` 29행 주석).
- HTTP 계층은 라우트 8개를 가진다: `/aip/describe`, `/aip/health`, `/aip/objects/*`, `/aip/webhooks/{name}`, `/aip/subscribe`(WebSocket), `/aip/{intent}` 등(`http.rs` 44~52행). 즉 "HTTP는 호스트가 받아 엔진에 넘긴다"(DD-06 B.3 E)에는 intent 호출 외에 웹훅 서명 검증, 객체 다운로드, WebSocket 업그레이드, 프록시 신뢰(`trusted_proxies`)가 따라온다.
- 서버는 `127.0.0.1`에 고정 바인드한다(`lib.rs` 126행). 컨테이너 배포(DD-06 C.2 "컨테이너 하나에 바이너리 두 개")는 지금 그대로는 외부에서 못 닿는다. 사소하지만 S의 "지금 형태 그대로"가 완전하지 않다는 증거다.
- CLI `aip run`은 `.aip` 파일을 매번 컴파일해서 `(core, program)`을 얻고(`aip-cli/src/main.rs` 233행 `compile_full`), 계약은 Core에서 계산해 런타임에 넘긴다. 주석: "the runtime serves the contract as computed from Core IR; it never sees the IR itself"(236행). 런타임이 받는 것은 `aip_plan::Program`(`lib.rs` 99행)이지 Core IR이 아니다. DD-06은 B.3 E 예시에서 `ir from "./.aip/app.ir.json"`로 "검증된 Core IR"을 엔진에 넣는 것처럼 쓰지만(53행), 현 구현에서 엔진 입력은 Plan Program + 별도 contract JSON 두 개다. 아래 §7 P1-4.

### 2.2 몰래 확정한 것

1. **B.3 E 예시의 "HTTP는 호스트 앱이 받는다"(55행)와 D의 "HTTP 수신은 호스트에 맡길 수 있다(E)"(98행).** 원문 PART I §15는 "Rust가 모든 일을 수행하는 것이 반드시 최적은 아니다"라고 했지만 구체적으로 무엇을 호스트에 맡길지는 정하지 않았다. 인증(토큰 검증), 웹훅 서명 검증, WebSocket, 객체 다운로드가 현재 http.rs 안에 있다(위 §1 마지막 목록). 호스트가 HTTP를 받는다는 것은 "서버가 최종 권한을 통제"(PRINCIPLES §2 보안)의 입구 코드(신원 추출)를 호스트에 두는 결정이다. 선택지로 서술했으니 확정은 아니나, 비교표에서 E의 불리한 점으로 한 번도 드러나지 않는다.
2. **C.2 "철학 정합성" 행의 "E가 'JS/Python 생태계에서 자연스럽게'에 가장 가깝다"(75행)와 이탈 점검의 "E가 가장 자연스럽다"(143행).** 원문은 "JS/Python 환경에서 AIP의 표준 인터페이스를 통해 기능을 사용할 수 있어야 한다"(원문 159행)고만 했고, 이를 만족하는 방법이 임베드뿐이라고 하지 않았다. S에서도 `@aip/client` 같은 JS 클라이언트가 같은 인터페이스를 줄 수 있다. 이 문장은 사실상 E를 선호 방향으로 프레이밍한다. "자연스러움"을 임베드와 동일시한 것은 DD-06의 해석이고 원문 근거는 없다.
3. **C.3-2 "운영 엔진은 정의 모듈을 실행하지 않는다"를 DD-06이 `[추천]`으로 자기 문서에 재선언.** DD-04 C.3 공통 조건 1(DD-04 253~254행)이 같은 내용이다. DD-04가 아직 창시자 판단 전이라면 DD-06이 이를 전제로 삼는 순간 DD-04의 선택지를 좁힌다(범위 문단 4행이 스스로 인정). 문제는 크지 않으나 "DD-04가 먼저 결정된 뒤에만 유효"를 명시해야 한다.

## 3. 대안 비판

### 3.1 S / E / S+E 비교의 공정성

DD-06 C.2 표를 행별로 본다.

| 행 | DD-06 서술 | 비판 |
|---|---|---|
| 철학 정합성 | E가 가장 가깝다 | §2.2-2 참조. S도 JS 클라이언트로 같은 "표준 인터페이스"를 줄 수 있다. 비교 축이 "개발자가 `npm install` 한 줄로 시작하나"로 암묵 환원됐다 |
| 보안 | S는 격리하기 쉽다, E는 막기 더 어렵다 | 방향은 맞으나 정도를 줄여 말했다. "더 어렵다"가 아니라 "같은 프로세스에서는 구조로 막을 수 없다"에 가깝다(§4.1). 반대로 S의 이점도 과대: 사이드카가 데이터를 읽어야 하면 엔진에 콜백해야 하고, 사이드카에 DB 자격증명을 주지 않아야 효과가 있다. 그 약속은 설정 문제이지 S의 본질적 속성이 아니다 |
| 구현 난이도 | S: 엔진은 지금 형태, 확장 IPC 신규. E: 분리 + 바인딩 + 비동기 연동 | S의 "지금 형태" 서술이 틀리지는 않으나 불완전. 확장 IPC뿐 아니라 사이드카 수명 관리(기동·재시작·헬스체크), 127.0.0.1 고정 바인드(`lib.rs` 126행) 정리가 따른다. E는 반대로 엔진 본체가 HTTP 비의존이어서(§1) 분리 자체는 싸다. 난이도 비교의 양쪽이 정확한 코드 사실 없이 작성됐다 |
| 확장성(배포) | S: 서버리스는 어렵다(확인 필요), E: 기존 Node/Python 배포 그대로 | **불공정. 가장 중대.** E가 "기존 Node 배포 그대로"는 호스트가 장수 프로세스일 때만 맞다. B.3 E 예시가 "Next.js API 라우트"(47행 주석)인데, 엔진은 outbox 폴링, 타이머, 잡 워커, 구독 LISTEN 연결 등 상시 백그라운드 루프를 `tokio::spawn`으로 돌린다(`lib.rs` 116~123행, `subscribe.rs` 132행). 요청 단위로 실행되고 멈추는 환경(서버리스 함수)에서는 이 루프들이 돌 곳이 없다. 따라서 F2의 "서버리스까지" 답이 예이면 S뿐 아니라 E도 워커를 별도 장수 프로세스로 빼야 한다. DD-06은 F2를 "S의 적합성이 달라진다"고만 쓰고(124행) E에 대한 영향은 쓰지 않았다. 일반 지식이며 웹으로 확인하지 않았다: 확인 필요(특정 호스팅의 장수 프로세스 지원 여부) |
| 디버깅 | S: 프로세스 둘이라 추적을 이어야 함. E: 한 프로세스 | E에서 Rust 패닉이 Node 프로세스에 어떻게 전파되는지, 네이티브 스택이 JS 에러로 어떻게 보이는지는 미평가. "한 프로세스라 쉽다"는 낙관 |
| AI 개발 경험 | S: 서버 하나 더 띄우는 절차. E: npm install 후 몇 줄 | S도 `npx aip dev`처럼 SDK가 사이드카를 자동 기동하면 같은 몇 줄이다(§3.2의 빠진 대안). 비교가 "최악의 S(수동 기동) 대 최선의 E"로 놓였다 |
| 성능 | S: IPC 비용, E: 바인딩 비용 작음 | E4(확장 호출 빈도 추정)로 검증 예정이라 OK. 다만 E의 JS to Rust 호출 비용에 JSON 직렬화(Program·요청·응답이 `serde_json::Value`, `engine.rs` 13행)가 있다는 점은 빠짐. 확인 필요 |

### 3.2 빠진 대안

DD-06의 대안은 S, E, S+E 셋이고 모두 "엔진을 어디에 두나" 한 축이다. 원문 PART III 의제 9(599~611행)가 논의 대상으로 든 "실행 프로세스 구조, 비동기 실행, 메모리와 자원 관리, 런타임 장애 격리"는 이 축에서 갈리지 않는다. 다음 대안은 서로 다른 축이므로 S/E 비교를 풀어놓는다.

| 대안 | 내용 | 왜 비교에 필요한가 |
|---|---|---|
| H. 호스트 SDK가 서버를 자동 기동 | npm/pip 패키지가 Rust 바이너리를 같이 배포하고 개발 시 자식 프로세스로 띄워 localhost로 통신. 앱 코드는 `createAip(...)`만 본다 | E의 "설치 한 줄" 경험을 S의 프로세스 격리와 함께 얻는다. 근거: 외부 사례로 네이티브 바이너리를 npm 패키지에 포함하는 패턴이 있다(예: esbuild 류, 확인 필요). 다만 사례 이름을 근거로 삼지 말 것 |
| X. 확장을 별도 서비스(HTTP/gRPC)로 | 확장 함수를 웹훅처럼 엔진이 HTTP로 부르는 서비스로 배포 | 서버리스와 가장 잘 맞고, 확장과 엔진의 배포 주기를 분리한다. 이미 엔진에 outbound HTTP·웹훅 인프라가 있다(`outbound.rs`, `http.rs` 48행 웹훅 라우트). 대신 지연과 트랜잭션 참여 불가 |
| W. WASM으로 확장 실행 | 확장을 WASM 샌드박스로 엔진이 직접 실행 | 격리·자원 상한·결정성이 가장 좋다. PoC에 `fn … wasm` 문법이 이미 있으나 실행 경로는 없다(T09 52행, `DECISIONS.md` 88행 OI-E2). 단점: npm/PyPI 생태계 사용이 막혀(JS/Python 패키지 상당수가 WASM 안에서 못 돈다, 확인 필요) 원문 "확장은 JS/Python을 자연스럽게"(PRINCIPLES §2)와 긴장. 따라서 "순수 계산 확장" 등급 한정으로만 검토할 후보 |
| D. 엔진 본체 서버 + 워커 분리 | `Options.workers`(`lib.rs` 88행)를 이미 끌 수 있으니 API 프로세스와 워커 프로세스를 나눠 띄움 | 백그라운드 루프 문제(§3.3)의 직접적 해법이고 SKIP LOCKED 덕에 프로세스 수를 늘려도 안전. S·E 어느 쪽과도 조합되는 별개 축인데 DD-06이 선택지로 올리지 않았다 |

세 번째 열의 외부 사례 주장은 모두 확인 필요이다. 위 대안은 "이것을 추천한다"가 아니라 "비교표에 올라야 F1이 정직해진다"는 주장이다.

### 3.3 백그라운드 작업이 E(임베드)에서 어디서 도는가 (숨은 비용)

DD-06 본문에 한 줄도 없다. 사실 정리:

1. 엔진은 시작 시 outbox 디스패치, 아웃바운드 웹훅 전달, 스케줄(타이머), 잡 워커 4개 루프를 `tokio::spawn`한다(`lib.rs` 116~123행). 모두 `Arc<Engine>`을 공유하고 DB 풀을 쓴다.
2. 구독은 별도 DB 연결로 `LISTEN`하고 WebSocket 세션을 유지한다(`subscribe.rs` 7, 132행; `http.rs` 49행). 호스트가 Next.js API 라우트라면 WebSocket 업그레이드를 받을 수 있는지 자체가 호스트 의존이다(확인 필요: Next.js 14 라우트 핸들러의 WebSocket 지원 범위).
3. E에서 이 루프들은 호스트 프로세스 안의 tokio 런타임 스레드에서 돈다(napi-rs가 별도 런타임을 제공하는지, 직접 만들어야 하는지는 확인 필요: DD-06 E2가 이미 조사 항목으로 잡음). 즉 "호스트 앱 하나를 재시작하면 잡 워커도 같이 죽는다", "스케일아웃으로 앱을 N개 띄우면 워커도 N개가 된다"(SKIP LOCKED 덕에 정확성은 유지되지만 DB 부하와 웹훅 중복 전송 위험을 평가해야 함).
4. 잡은 `heartbeat` + 재개 모델(`jobs.rs` 1~4행)이어서 호스트가 자주 죽는 환경에서도 정확성은 견딘다. 이 점은 E에 유리하며 DD-06이 활용하지 않았다.
5. 정리: E는 "엔진을 호스트에 끼운다"가 아니라 "호스트 프로세스가 앱 서버이자 잡 러너, 웹훅 전송기, 구독 허브까지 겸한다"이다. DD-06 B.3 E의 `export const POST = aip.handler`(56행) 한 줄로는 이 사실이 보이지 않는다.

### 3.4 트랜잭션·확장 쓰기의 S/E 차이 (누락)

DD-02 W-I10은 확장 동작도 불변식·멱등·감사를 통과한다고 했다. 확장 쓰기가 엔진 트랜잭션 안에서 돈다면: E는 같은 프로세스 함수 호출이라 콜백이 쉽다. S는 사이드카가 쓰기 요청을 IPC로 엔진에 되돌려야 하고, 트랜잭션을 연 채 프로세스 경계를 오가면 타임아웃·교착 위험이 있다. T09 41행이 이를 `[미정] T11`로 두었으나 DD-06 C.2는 이를 비교 축으로 올리지 않았다. 이는 S의 보안 이점과 E의 편의 사이의 실제 trade-off이므로 한 행 추가가 필요하다.

## 4. 보안·운영

### 4.1 E에서 "확장의 DB 직접 접근 차단"은 실제로 어떻게 강제하나

DD-06은 C.3-3에서 "E에서는 확장에 DB 연결을 직접 주지 않는 구조가 필요하다"(88행)고, 이탈 점검에서 "E는 확장의 DB 직접 접근을 구조로 막아야 함"(141행)이라 썼다. 강제 수단은 어디에도 없다.

- DD-06 자신의 E 예시가 문제를 보여준다. `createAip({ ..., extensions: ext, database: process.env.DATABASE_URL })`(53행). DB 자격증명이 확장 코드와 같은 프로세스의 환경에 있다. 확장은 `process.env.DATABASE_URL`을 읽고 자기 pg 클라이언트를 열 수 있다. 일반 Node 프로세스 안의 모듈끼리는 권한 경계가 없다(일반 지식. Node의 permission 모델 등 완화책은 확인 필요).
- 엔진이 `Pool`을 내부에 숨기는 것(현재 `Engine.pool`은 `pub`, `engine.rs` 20행)은 API 모양의 약속이지 강제가 아니다.
- 따라서 E에서 DD-01 I6·DD-02 W-I10(146행·159행)이 요구하는 "확장도 같은 통제"는 **악의 또는 실수에 의한 우회를 구조로 막지 못하고, 약속·린트·코드 리뷰·감사 로그로만 관리**된다. S는 사이드카에 자격증명을 주지 않고 네트워크로도 DB에 닿지 않게 하면 구조로 막을 수 있다. 이 차이가 S/E 비교의 보안 행에서 가장 큰 사실인데 "더 어렵다" 한 마디로 축소되었다.
- 더 근본 문제: **위협 모델이 정의되지 않았다.** 확장은 앱 개발자(또는 AI)가 쓴 코드이고 오늘의 Spring 백엔드 코드와 같은 신뢰 수준이다. 막으려는 대상이 (a) 실수로 정책을 건너뛰는 코드인지, (b) 서드파티 확장 모듈의 악의인지에 따라 답이 다르다. T09 31행은 "1st-party와 서드파티가 같은 계약"을 말해 (b)도 범위에 둔다. (a)라면 E는 충분히 현실적이고(엔진이 제공하는 데이터 API가 유일하게 편한 길이면 된다), (b)라면 E는 사실상 불가하다. 원문은 "확장 기능이 서버 권한과 보안 규칙을 우회해서는 안 된다"(원문 §8)만 말한다. 이 질문은 창시자 결정은 아니고 설계 전제이므로 문서가 먼저 서술해야 한다(§7 P0-2).
- 대안으로 DB 쪽 방어(Postgres 롤·RLS)는 엔진 자신도 같은 자격증명으로 접속하는 E에서는 확장과 엔진을 구별하지 못한다. 구별하려면 확장 실행 시 `SET ROLE`을 하는 식이 필요한데, 이는 동일 연결에서 확장이 `RESET ROLE`을 호출하면 무력화될 수 있다(확인 필요, 설계 후보 수준).

### 4.2 장애 격리

| 상황 | S | E | 비고 |
|---|---|---|---|
| 확장이 예외를 던짐 | 사이드카가 오류 응답, 엔진 정상 | 바인딩 경계에서 JS 예외 변환 필요 | 둘 다 가능. 계약(C.3-4)에서 오류 코드로 감쌈 |
| 확장이 무한 루프(동기) | 시간 초과 시 사이드카 kill/재시작 | 호스트 이벤트 루프가 막혀 앱 전체가 멈춤. 엔진 워커 스레드(tokio)는 계속 돌지만 HTTP를 받는 호스트가 응답 불가 | 일반 지식, 확인 필요(Python은 GIL 점유 여부에 따라 다름) |
| 확장이 메모리를 폭주 | 사이드카만 OOM | 호스트 프로세스 전체 OOM, 엔진 워커도 함께 소멸 | C.3-4 "시간 제한"만 있고 메모리 제한이 없다. DD-01 I6은 자원 상한을 요구 |
| Rust 쪽 패닉 | 서버 프로세스만 | 호스트 프로세스 중단 가능(napi-rs의 패닉 처리는 확인 필요) | 반대 방향 위험. 확장 격리와 별개로 엔진 안정성이 호스트에 번진다 |
| 호스트 재시작/배포 | 엔진 영향 없음 | 4개 워커 루프와 구독 세션이 함께 종료 | §3.3. 잡은 heartbeat로 재개(`jobs.rs` 1~4행) |

C.2 보안 행은 첫 줄만 쓰고 나머지를 생략했다.

### 4.3 버전 호환

DD-06은 버전 호환을 다루지 않는다(원문 의제 12는 "버전 호환성"을 논의 대상으로 명시, 원문 657~672행 부근).

- S: 엔진 바이너리 버전, 확장 SDK(JS/Python) 버전, IR 버전 세 개를 맞춰야 한다. 프로세스 경계가 있어 프로토콜 버전 협상이 필요하다.
- E: 엔진 버전 = 호스트 앱의 npm 패키지 버전. 네이티브 바이너리를 플랫폼(OS/CPU/libc, Node ABI)별로 배포해야 한다(확인 필요). Python은 wheel을 별도로 만든다. 즉 E를 JS와 Python 둘 다 하려면 바인딩 제품이 두 개이고, S+E는 세 개(서버 + Node 바인딩 + Python 바인딩)다. DD-06 C.2 "구현 난이도"에 이 릴리스 매트릭스 비용이 없다.
- 공통: DD-04 C.3-5가 "서명이 맞지 않으면 빌드 오류"를 요구하므로, 확장 서명을 IR의 기호 참조와 대조하는 단계는 S/E와 무관하게 존재한다. 호환 정책 자체는 DD-06이 아니라 T09의 `[미정]`이다. 단 S/E 선택이 호환 방식의 비용을 바꾼다는 점은 DD-06에 한 줄 필요.

### 4.4 운영 상의 기타 사실

- `aip run`은 서버 시작 전에 `migrate_deployed`를 호출한다(`aip-cli/src/main.rs` 253~254행; `lib.rs` 43행 주석). E에서 마이그레이션을 누가, 언제 돌리는가(앱 부팅 때인지 배포 단계인지)가 정해져 있지 않다. 스키마 변경은 advisory lock으로 직렬화되므로(`lib.rs` 50행) 여러 호스트 인스턴스가 동시에 부팅해도 안전하지만, 이 사실은 DD-06이 사용하지 않았다.
- 비밀: `AIP_SECRET`, `AIP_ENCRYPTION_KEYS`는 환경 변수로 읽혀 `Options`에 들어간다(`aip-cli/src/main.rs` 239~245행, `lib.rs` 95행). E에서 이 비밀이 확장 코드와 같은 프로세스 메모리에 있다는 점은 4.1과 같은 계열의 위험이다.

## 5. F 질문

### 5.1 F1·F2가 창시자 결정이 맞는가

- F1: **맞다.** 원문이 "아직 확정하지 않았다"고 명시한 것이고(원문 167~169행), 운영 규칙 F절의 "제품 철학이나 사용자 경험에 영향을 미치는 선택"에 해당한다. 한편 바인딩·FFI 구조(원문 171행)는 창시자가 아니라 기술 제안으로 처리하는 것이 맞는데 DD-06도 그렇게 처리했다.
- F2: **부분적으로만 맞다.** "첫 출시 배포 대상"은 제품 범위 결정이라 창시자 몫이지만, 서버리스 포함 여부는 창시자의 원문에 근거가 전혀 없다(`grep` 결과: 원문·PRINCIPLES에 서버리스/Vercel/Lambda 언급 없음). 그리고 F2를 묻기 전에 먼저 확인할 사실이 있다: 아리아리 현재 배포는 컨테이너 기반으로 보인다(`ariari-backend/Dockerfile` 존재). 프론트의 배포 위치는 확인 못함. 이 사실로 F2의 기본 답을 "일반 서버·컨테이너"로 제안하고 변경하고 싶을 때만 묻는 편이 규칙 F("내부 구현 세부는 근거를 제시한 뒤 기술적으로 제안")에 맞다.

### 5.2 비전문가가 답할 수 있는가

- F1 (가)/(나)/(다)는 개발자 경험을 묻는 질문이라 방향 선호는 답할 수 있다. 그러나 이 선택이 실제로 바꾸는 것 세 가지가 질문에 보이지 않는다: (1) 확장 코드가 보안 규칙을 구조로 지켜지는가, 약속으로 지켜지는가(§4.1), (2) 잡·웹훅·구독 같은 백그라운드 작업이 어느 프로세스에서 도는가(§3.3), (3) 서버리스에 올릴 수 있는가. 창시자가 (나)를 고르면 이 셋을 같이 고른 셈인데 모른 채로 고른다.
- (다)에 "구현·시험 비용이 가장 크다"를 붙인 것은 선택을 한쪽으로 끌 수 있는 서술이다. 비용 설명이 필요하면 (가)(나)에도 각각 같은 밀도로 써야 한다. 또 (다)는 "둘 다 제공"인데 §3.2의 H(기동을 자동화한 S)와의 차이가 독자에게 보이지 않는다.
- F2의 "서버리스·엣지"는 용어 설명이 없다. 운영 규칙 9항("창시자가 이해하기 어려운 기술 개념은 실제 AIP 사용 예시와 연결해 설명")에 어긋난다.
- F1과 F2는 독립 질문이 아니다. F2의 답이 F1의 선택지를 지운다("S의 적합성이 달라진다"). 순서·묶음이 필요하다.

### 5.3 고칠 문장 (제안, 확정 아님)

F1 현재: "개발자가 AIP를 처음 쓸 때 어떤 모습이길 원하나요?" 이후 (가)(나)(다).

F1 제안:
```
F1. 앱을 운영할 때 AIP 엔진이 어디에서 돌길 원하나요?
 (가) 별도 서버로 돌고, 프론트와 확장 코드는 네트워크로 그 서버를 부른다
 (나) 기존 Node(또는 Python) 앱 안에서 같이 돈다
 (다) 개발 중에는 (나)처럼 한 줄로 시작하되, 운영에서는 (가)처럼 따로 돌 수 있게 한다 (설치 도구가 서버를 알아서 띄움)
 (라) 가·나를 모두 정식 지원한다
 이 선택이 바꾸는 것:
  - 확장 코드가 DB 규칙을 우회하지 못하게 하는 방법: (가)(다)는 구조로 막을 수 있음, (나)는 개발 규약과 감사로 관리
  - 메일 발송·예약 작업·실시간 구독 같은 백그라운드 일이 도는 곳: (가) 엔진 서버, (나) 앱 서버 안
 어느 쪽이든 핵심 엔진은 Rust이고 권한·정책 판단은 엔진이 합니다.
```
(다)는 DD-06이 올리지 않은 대안 H를 반영한 것이고, 이 문장이 창시자 의사에 맞는지는 창시자가 판단한다.

F2 제안:
```
F2. 첫 출시에서 아래 환경에 올릴 수 있어야 하나요?
 (가) 일반 서버·컨테이너(예: 지금 아리아리 백엔드처럼 Docker로 올리는 방식)만
 (나) 요청이 올 때만 잠깐 켜지는 서비스(예: Vercel 함수, AWS Lambda)까지
 (나)를 고르면 예약 작업이나 실시간 구독 같은 상시 일을 돌릴 별도 서버가 한 대는 반드시 필요해집니다.
```
위 (나)의 마지막 문장은 §3.1 확장성 행의 일반 지식 기반이며 확인 필요. F2는 F1의 앞에 두거나 묶어서 묻기를 권한다.

## 6. 이탈 방지 점검 6문항 재평가

| 질문 | DD-06 답 | 재평가 |
|---|---|---|
| 백엔드 개발·이중 유지보수를 줄이는가 | E는 배포물을 하나 줄인다. S는 AIP 서버 하나 | 부분. "배포물이 준다"는 E가 장수 프로세스 호스트일 때만이다. 서버리스 호스트면 워커 서버를 따로 둬야 해서 줄지 않는다(§3.1). S/E는 어느 쪽도 백엔드 코드 양을 직접 바꾸지 않으므로 이 질문의 답은 "직접 관계 없음, 운영 배포 수에만 영향"이 정확하다 |
| 호출자 표현에 도움이 되는가 | 직접 관계 없음 | 동의. 단 호스트가 HTTP를 받는 E에서는 호출자 요청이 호스트 미들웨어를 먼저 통과하므로 요청 변형 위험 한 줄은 필요(인증 헤더, 프록시 신뢰 `trusted_proxies`는 현재 http.rs 소유) |
| 서버가 최종 권한을 통제하는가 | 어느 형태든 엔진이 판단. E는 구조로 막아야 함 | **문제 있음.** "어느 형태든 엔진이 판단"은 맞지만 "E는 구조로 막아야 함"은 요구사항을 적은 것이지 달성 방법이 아니다. §4.1처럼 같은 프로세스에서는 구조로 막을 수 없다. 이 항목은 "E: 중대한 충돌 가능, 해법 미정"으로 명시해야 한다(운영 규칙 64행 "중대한 충돌이 있으면 숨기지 말고 명시") |
| AI의 불필요한 선택을 줄이는가 | S+E는 "어느 형태로 실행할까"라는 선택을 만든다 | 부분 동의. 선택지가 늘어나는 건 맞다. 반대로 S든 E든 하나만 고르면 AI에게 선택이 사라진다는 반론은 성립한다. 그러나 H(자동 기동)나 워커 분리(D) 같은 하위 선택이 새로 생기는 것은 어느 쪽이든 마찬가지다. 점검이 S+E만 언급해서 E 단독 선택도 "워커를 어디서 돌릴까" 선택을 만든다는 점이 가려졌다 |
| JS/Python 생태계와 사람의 사용성 | E가 가장 자연스럽다 | 과대. 사용성은 설치 절차뿐 아니라 디버깅·배포·장애 대응 포함. E의 Rust 패닉/네이티브 스택 디버깅, 바이너리 호환 문제는 사용성 비용이다(§4.2~4.3). 또한 Python은 GIL·PyO3 비동기 문제가 있어 "E가 JS/Python 모두에 자연스럽다"고 하기 어렵다(확인 필요). 원문이 JS를 우선한다고 했으므로(원문 §3) E는 JS 먼저, Python은 S로 시작이라는 비대칭 가능성이 열려 있는데 문서는 다루지 않았다 |
| 복잡성을 옮기기만 했나 | E는 바인딩·비동기 연동 복잡성을 엔진 쪽에 두고 앱 개발자에게는 줄어든다 | 부분. 옮기는 곳이 엔진 쪽만이 아니다. E는 (1) 확장 보안 강제 문제를 호스트 규약으로, (2) 워커·구독·마이그레이션 실행 책임을 호스트 운영자에게, (3) 릴리스 매트릭스(플랫폼×언어)를 AIP 릴리스 팀에 옮긴다. "앱 개발자에게는 줄어든다"는 앱 개발자가 운영자를 겸하는 소규모 상황에서는 거짓이다 |

## 8. 결론

### 내 추천

1. **지금 결정할 수 있는 것은 F1이 아니라 "먼저 결정할 질문의 순서"다.** F2(배포 대상)와 위협 모델(P0-2)이 F1의 답을 대부분 정한다. 서버리스까지가 범위가 아니라면 S와 E의 배포 차이는 크지 않고, 확장이 신뢰 코드라면 E의 보안 약점도 감수할 만하다. 반대로 서드파티 확장이나 서버리스가 범위라면 E 단독은 어렵다.
2. **한 형태를 고른다면 S 계열(별도 프로세스)을 기본으로 하고, 설치 경험은 SDK가 서버를 띄워 주는 방식(H)으로 보완하는 안을 F1의 선택지로 올리는 것을 추천한다.** 이유는 (a) 확장의 DB 직접 접근 차단과 자원 상한을 구조로 강제할 수 있는 유일한 형태이고(§4.1, 4.2), (b) 백그라운드 작업의 거처가 명확하며(§3.3), (c) 이미 있는 코드가 이 형태이고 엔진 분리 비용이 낮다(§1), (d) JS 생태계 정합성은 H와 JS 클라이언트로 상당 부분 얻을 수 있다. 단 (d)는 가설이며 E3/E2 스파이크로 임베드의 실제 경험을 확인하기 전까지 확정하지 않는다. E의 가치를 부정하는 것이 아니고, "E가 가장 자연스럽다"는 서술이 증거 없이 앞서 있다고 보는 것이다.
3. **C.3-1(엔진 라이브러리 분리)은 모든 경우의 선행 작업이므로 문서 추천에 동의한다.** E1을 읽기만으로 지금 끝낼 수 있고(P1-3), 분리 크기도 작다는 증거가 있다.

### 문서 추천과의 차이

| 항목 | DD-06 G절 | 내 의견 |
|---|---|---|
| C.3-1 엔진 분리 | 먼저 한다 | 동의. 증거 보강(E1 결과) |
| E 쪽 가치 | "원문이 JS 우선이므로 E 쪽 가치가 크다. E2·E3 결과 전에는 추천하지 않는다" | 가치 방향은 동의, 단 "E가 가장 자연스럽다"는 비교 서술은 근거 부족. 또 E2·E3(바인딩 기술 검증)보다 먼저 **배포 환경(F2)과 위협 모델**이 E 적합성을 가른다. 순서가 다르다 |
| 첫 포장 | F1·F2 답에 따른다 | 질문 표현을 고친 뒤 F2→F1 순서. S+H를 선택지로 포함 |
| 보안 평가 | "E는 막기 더 어렵다" | "E는 같은 프로세스에서는 구조로 못 막는다"로 상향. 이탈 점검의 해당 칸을 충돌로 표기 |
| 백그라운드 작업 | 언급 없음 | 필수 비교 행. E의 숨은 비용 |
