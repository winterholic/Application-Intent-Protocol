### 1.1 DD-14가 쓰지 않은, 확인된 추가 사실

1. **아리아리 필터 경로**: 인증 실패(`ExpiredToken`·`NotValidToken`)는 `ExceptionControllerAdvice`가 아니라 필터가 직접 쓴다(`JwtAuthenticationFilter.java:67-85`). RE-5("응답 모양은 하나")는 **디스패치 이전에 나는 오류(인증, 본문 파싱, 알 수 없는 경로, 본문 크기, 속도 제한)**도 같은 봉투를 써야 한다고 명시해야 한다. 지금 문구는 "검증·권한·위반·서버 오류"뿐이다.
2. **`DuplicateDataCreateException`은 호출 지점이 메시지를 넘긴다**(생성자 `String message`, `throw new` 3곳). 안정 코드로 옮기려면 "메시지가 곧 의미"인 예외라 코드를 새로 정해야 한다.
3. **일반 `RuntimeException` 11곳**(`grep "throw new RuntimeException"`) → 모두 `ADV:23-32`의 500 + `getMessage()`로 간다. 이 11곳은 코드가 아예 없는 "코드 없는 실패"다.
4. 일부 Spring 내장 예외(예: JSON 파싱 실패)가 `Exception` 핸들러로 떨어져 파서 메시지가 노출되는지는 **확인 못함: 실행하지 않았고 Spring 해석 순서를 코드로 증명하지 않음**. 가설로만 둔다.

### 1.2 PoC 사실 정정: "재사용 가능"은 조건부

DD-14 E3은 PoC 레지스트리 재사용을 검증 항목으로 남겨 뒀지만, 읽기만으로 이미 다음이 확인된다. 이 때문에 B.2의 "가까움"은 낙관적이다.

- **PoC가 RE-3을 어긴다.** `aip-runtime/src/exec.rs:89-112`(`db_error`)은 `23505`/`23514`(93행 `CONFLICT_UNIQUE`, 94행 `INVARIANT_VIOLATED`)와 `22P02`(112행) 등에서 **`db.message()`를 그대로 `message`에 넣는다**. Postgres 메시지에는 제약 이름(`duplicate key value violates unique constraint "…"`)이 들어 있다. `exec.rs:274`는 `format!("object store: {e}")`, `webhook.rs:86`은 `e.to_string()`을 `INTERNAL`의 `message`로 낸다. `exec.rs:116`의 알 수 없는 SQLSTATE만 "internal error"로 정리된다(원문은 로그로, 114-115행).
- **PoC가 RE-2를 어긴다.** `codes.rs:1039-1046`의 `TENANT_MISMATCH`는 "404 like NOT_FOUND so a caller cannot tell another tenant's row from a missing one **by the status**"라고 쓴다. 상태는 같지만 **본문 `code`는 `AIP.TENANT.MISMATCH` 대 `AIP.NOT_FOUND`로 다르다**(`error_response`가 코드를 그대로 직렬화, `http.rs:77-80`). 상태만 맞추고 코드는 노출한 사례이고, DD-14 RE-2 "같은 코드"가 정확히 이 구멍을 막는다. DD-14는 이 반례를 자기 근거로 쓰지 않았다.
- **PoC `AipError`는 `intent`, `path`, `reason`을 응답에 싣는다**(`error.rs:7-19`). DD-14의 B.3 예시는 `code`와 `trace`만 있어 이 필드들의 운명이 불명확하다(아래 4절).
- 알 수 없는 코드는 409로 응답(`codes.rs:223-225`). 레지스트리 누락이 조용히 409가 된다는 뜻이라, RE-4("본문 코드와 HTTP 상태가 어긋나지 않는다")를 강제하려면 **누락을 오류로 만드는 검사**가 필요하다(`codes.rs:10-11` 주석은 `tests/codes.rs`가 소스에서 남은 문자열 리터럴을 스캔한다고 하지만, 레지스트리에 없는 코드를 막는지는 확인 못함: 테스트 파일을 열지 않음).

## 2. E1(가능한 만큼): 62개 커스텀 예외를 안정 코드로 옮길 때

방법: `grep -rlE "extends CustomException"`로 62개 파일, 각 파일의 `MESSAGE`와 `HTTP_STATUS`를 뽑아 의미 단위로 수작업 분류. **분류 기준이 내 판단이라 묶음 수는 ±3 정도의 추정이다.** 실행·테스트는 하지 않았다.

### 2.1 상태 분포(코드로 확인)

400×45, 401×4, 403×5, 404×1, 409×1, 415×1, 422×2, 500×3 = 62. 클라이언트에게 "권한 없음"을 말하는 `No*Auth*`·`NoClub*` 계열도 대부분 **400**이다(예: `NoApplyAuthException`, `NoClubManagerException`, `NoClubAdminException`). 같은 의미의 `ExistingClubMemberException`(400)과 `ExistsClubMemberException`(403)이 따로 있다. 그래서 "HTTP 상태를 코드에서 정한다"(RE-4)만으로는 부족하고, **옮길 때 상태를 새로 판정해야 한다**(기존 상태를 승계하면 어긋남이 코드로 굳는다).

### 2.3 규모 추정과 읽는 법

- **62개 → 대략 25~35개**로 줄어든다고 추정한다(위 표에서 학교 인증 3→1, 이미 있음 10→규칙 1+앱 몇 개, 소속 3→1~2, 권한 부족 10→규칙 이름으로 흡수). 숫자는 분류 기준에 따라 크게 움직이므로 **"확인 필요(근거 약함)"**. DD-14 E1의 질문("몇 개 코드가 되는지")에 대한 답은 "중복 제거로 절반 안팎, 하지만 줄어드는 폭의 대부분이 *정책 거부의 reason 흡수*와 *유일 제약에서 파생*에서 온다"이다.
- 이 감소는 **레지스트리가 공짜로 만들어 주는 것이 아니라 엔진이 만들어 주는 것**이다. 권한 거부는 `allow`가 내고, 유일성 위반은 제약이 내고, 형식 위반은 타입이 낸다. 앱 개발자가 직접 이름을 붙이는 코드는 "상태 불가" 한 묶음(대략 10개 안팎)이다. 이것이 DD-14의 "복잡성을 옮기기만 했나" 답(레지스트리 관리가 생기지만 예외 처리기가 사라진다)을 강화하는 **구체적 증거**인데 DD-14는 쓰지 않았다.
- 반대로 위험 신호: 권한 거부 10개를 `AUTH.FORBIDDEN` 하나로 접으면 프론트가 보여 주던 구분 문구("최고 관리자 권한이 없습니다" 대 "관리자 권한이 없습니다")가 사라진다. 이것은 **존재 누설이 아니라 역할 정보**이므로 `reason`(코드와 구분되는 하위 사유)을 남길지, 별도 코드를 둘지를 정해야 한다(4절 RE-2 구멍과 연결).
- 아리아리 외 공통 컨트롤러 에러(`NoResourceFoundException` 404, 검증 `Map`, DB `DataAccess`)는 E1의 62개에 포함되지 않았다. 매핑 대상이 **62 + CustomException 외 핸들러 6종(`ADV`의 7개 핸들러 중 CustomException 제외) + 일반 `RuntimeException` throw 11곳**이다.

## 3. 철학 정합성과 DD-01~13 불일치

### 3.1 철학(PRINCIPLES §4 관문)과의 관계

| 관문 | 평가 |
|---|---|
| §4-1 어느 원칙을 실현/긴장 | DD-14 D절은 AI First 8번과 "서버 최종 통제"를 든다. **긴장 쪽을 쓰지 않았다**: AI First 8번("명확하고 구조화된 오류")과 "존재를 드러내지 않음"(I5)은 정면으로 긴장한다. 정확한 오류일수록 오라클이 된다. DD-14는 "개발 진단에서만 구분"으로 풀었는데 그 메커니즘이 비어 있다(아래 3.3) |
| §4-2 호출자 표현 범위 | 변화 없음. 이탈 점검 "간접"은 정직하다 |
| §4-3 서버 쪽 작성량 | 줄어든다는 주장(예외 처리기·응답 DTO 제거)은 E1 증거(2.3)로 **부분 입증**되지만, "앱이 코드와 reason을 선언하는 양"과 **로케일 메시지 작성량**이 새로 생긴다(4절) |
| §4-4 신뢰/검증 | RE-2·RE-3이 맡음. 다만 오류 *필드*(경로, 위반 인덱스, 파라미터)가 신뢰되지 않는 호출자 입력의 반사(echo)라는 점은 다루지 않았다 |
| §4-5 새 언어 없이 | 오류는 JSON이라 문제 없음 |
| §4-6 같은 의도 여러 방식 | **위반**: R1 안의 `NOT_FOUND`/`FORBIDDEN`/`APPLY.NOT_MEMBER` 사이에서 앱 개발자(AI)가 "어떤 코드를 내야 하나"를 고를 여지가 남는다. 거부의 *종류*를 엔진이 정하는 규칙이 없다 |
| §4-7 수단을 목적처럼 | R3(problem+json) 호환 검토는 "표준 도구와 호환(확인 필요)" 하나가 이유다. **호환될 도구를 한 개도 지목하지 못한 채** 대안으로 올렸다. 수단이 목적처럼 올라온 후보 |
| §4-8 창시자 결정 임의 확정 | 6.절에서 다룬다 |

### 3.2 DD-14 내부의 모순

1. **R1과 R3이 대안인 척하지만 직교한다.** C절 표는 R1 대 R3을 대안으로 비교하고, G는 "R1을 기본으로 하고 표현은 R3 호환을 검토"라고 한다. 그런데 B.3 예시는 `{ "error": { "code": ... } }`처럼 **`error` 객체로 감싼 형태**다. RFC 9457의 problem details는 `type`·`title`·`status`·`detail`·`instance`를 **최상위 멤버**로 쓰고 `application/problem+json` 매체 유형을 쓴다(확인 필요: 웹으로 확인하지 않았다. RFC 9457이 7807을 대체했고 확장 멤버를 허용한다는 것은 내가 아는 바이며 검증 못함). B.3 모양은 그 모양이 아니다. 둘을 동시에 만족할 수 없으니 **"R3 호환 검토"는 B.3을 바꿔야 한다는 뜻**이다. 문서가 이 충돌을 숨기고 있다.
2. **RE-4와 B.3의 `NOT_FOUND`**: RE-4는 "레지스트리가 본문 코드와 HTTP 상태를 함께 정한다"고 했는데, 일괄(`BULK.REJECTED`)에 HTTP 상태가 무엇인지 어디에도 없다. DD-07의 U7(항목별 부분 성공)이 서면 한 HTTP 응답이 "일부 성공 + 일부 실패"인데 **단일 코드에서 하나의 상태를 정한다**는 RE-4가 성립하지 않는다.
3. **RE-5 "응답 모양은 하나" 대 RE-6 "성공 봉투"**: 성공도 `data` 봉투를 쓴다고 했다. 그런데 DD-13 33행·126행은 "응답 봉투(페이지 정보 등, 약 19%)는 select 기반 요청으로 소멸"한다고 썼다. DD-14 RE-6은 `page`를 봉투 메타로 다시 세운다. 소멸의 의미(타입 선언이 필요 없다)와 재도입(와이어에 봉투가 있다)은 다른 층의 이야기라 모순은 아닐 수 있지만, **DD-13의 이 수치를 쓰는 사람이 오해하지 않게 한 줄 정리가 필요**하다. 이것이 P1이다.

## 4. 대안 비판과 RE-1~RE-7의 구멍

### 4.1 대안(R1/R2/R3)

- **R2는 허수아비다.** 현 아리아리 방식을 "대안"으로 두었지만 운영 규칙 1("기존 구현을 정답으로 가정하지 마라")을 의식한 대조군일 뿐 실제로 고를 사람이 없다. 대안 비교를 "서로 다른 대안 2~3개"(운영 규칙 C)로 채우려면 **축이 다른 진짜 대안**이 필요한데 빠져 있다.
- **R1과 R3은 같은 축이 아니다.** R1은 "무엇을 담나(코드+구조화 세부)", R3은 "어떤 껍데기에 담나(RFC 9457 매체 유형·멤버)"다(3.2-1). 비교 표에서 R3의 AI 처리·보안 칸이 "R1과 같음"인 것이 증거다. 실제 결정은 두 개다: (a) 담는 내용, (b) 껍데기/전송 의미(HTTP 상태를 어디서 쓰나).
- **빠진 대안(실질적으로 다름):**
  - **R4 GraphQL식 "항상 200 + errors 배열 + 부분 data".** 읽기 조합이 한 요청에 여러 뿌리를 가질 수 있으면 의미가 있다. DD-14는 읽기가 *전부 성공 또는 전부 실패*라고 한마디도 하지 않았다. AI가 `data`와 `error`가 동시에 올 수 있는지 추측하게 둔다. 최소한 **"읽기는 부분 데이터 + 오류를 섞지 않는다"를 RE로 명시**해야 한다(DD-01의 구조에서 확인 못함: 다중 뿌리 읽기를 허용하는지 DD-01 전체를 읽지 않음).
  - **R5 HTTP 의미를 전송에 맡기고 본문은 코드만(JSON-RPC식).** OI-P1(프로토콜 의미와 전송 분리, `docs/DECISIONS.md:89`)과 맞고, 구독(WebSocket, D-P24)이나 한 연결의 여러 호출에서는 HTTP 상태가 없다. DD-14는 RE-4를 HTTP 전제로 썼고 구독을 "후속"으로 밀었는데, **상태 필드가 의미 층인가 전송 층인가**를 정하지 않으면 구독 때 RE-4가 다시 열린다.
  - **R6 메시지 없이 코드+매개변수만(문장 생성은 클라이언트).** 4.3 로케일 항목에서 자세히.

### 4.2 RE-1~RE-7의 구멍

**RE-1 안정된 코드.**
- "공개된 코드는 의미를 바꾸지 않는다"는 PoC의 선언(`codes.rs:13-14`)을 가져왔다. 하지만 **앱 정의의 코드(`APPLY.ALREADY_MEMBER` 등)는 레지스트리 하나가 아니라 앱마다 있다.** PoC 레지스트리는 엔진/컴파일러 코드 목록이고 `rt()`로 `AIP.*`만 담는다. 앱 선언 코드가 공개 계약에서 어떻게 *안정성이 강제*되는지(DD-12 `aip diff`가 코드 삭제·의미 변경을 잡는가)가 빠졌다. "한 코드 한 의미"는 사람이 지키는 약속인데 의미 검사는 영구 과제라고 DD-10이 이미 적었다(확인 못함: DD-10 해당 행 정확한 위치를 인용하지 못함, 'V2 제외(표면 셋·의미 검사 영구 과제)', DD-10 changelog).
- **코드 목록 자체가 정보를 흘린다.** 공개 계약에 모든 capability의 오류 코드(`MEMBER.ROLE_LOCKED`, `CLUB.ADMIN_ONLY_DELEGATE`…)를 실으면 관리자 전용 기능과 그 업무 규칙이 번들에 들어가 비로그인 호출자에게도 보인다. 이것은 **OI-P3(Open)의 쓰기·효과 공개 문제와 같은 부류**이고 DD-13 71행이 "공개 계약에 호출자에게 공개된 것만"이라 했으니, 코드도 **호출자 등급별로 계약에서 걸러야 하는지**가 질문이다. DD-14는 이 질문 자체를 안 한다. 걸러내면 SDK 타입 `ErrorOf<capability>`가 호출자 등급마다 달라진다.
- **알 수 없는 코드의 계약**: 서버가 새 코드를 추가했는데 옛 SDK/AI가 모르는 경우 클라이언트가 무엇을 하는지가 없다(이전 호환의 핵심). 최소 규칙: 알 수 없는 코드는 *category*와 *retry* 힌트로 처리, 없으면 서버 오류로 취급하지 않는다. PoC는 알 수 없는 코드를 409로 응답(`codes.rs:223-225`)하는데 이것을 *클라이언트 쪽*에 그대로 적용하면 안 된다.

**RE-2 존재를 드러내지 않음.** 가장 중대한 구멍이 여기 있다.
1. **정책 거부 vs 존재 없음의 경계 정의가 없다.** "볼 수 없음과 없음은 같은 코드"는 볼 수 없는 *대상*에 대한 규칙이다. 반대로 대상은 보이지만 *동작할 권한이 없는* 경우(관리자가 아니라서)는 `FORBIDDEN`(역할 정보)과 `NOT_FOUND` 중 무엇인가. 아리아리의 `NoClubManagerException` 같은 10개가 정확히 이것이고, 프론트가 이 구분 문구를 쓰고 있다. 규칙 문장이 필요하다: **"호출자가 대상을 볼 수 있을 때만 상세 사유 코드를 준다"**(DD-07 C.3-1은 일괄에 대해서만 적었다).
2. **제약에서 파생되는 코드는 정책을 거치지 않는다.** PoC는 `23505` 유일 위반을 `CONFLICT.UNIQUE`로 낸다(`exec.rs:93`). 숨은 행의 유일 값(예: 다른 사용자의 비공개 이메일)을 입력하면 `UNIQUE` 대 성공으로 **존재를 확인**한다. `CONFLICT.IN_USE`(`exec.rs:105-106`, "still referenced")는 숨은 참조 행의 존재를, `INPUT.REFERENCE_NOT_FOUND`(`exec.rs:108`, `codes.rs` 상 422)는 `NOT_FOUND`(404)와 **다른 코드·상태**로 FK 대상의 존재를 가른다. DD-02 W-I9가 "묶음 중 어느 단계에서 거부됐는지도 포함"이라 했지만 DD-14 RE-2는 이 *제약 파생 코드*를 말하지 않는다. DB가 정책을 보지 않고 존재를 판정하기 때문에 구조적으로 새는 지점이다. 확인 못함: PoC가 FK 대상 행에 대해 가시성 검사를 선행하는지(코드 추적을 하지 않음).
3. **닫힌 필드의 이름이 오류 *본문*으로 되돌아온다.** 검증 오류에 `path: "recruitment.secretScore"`를 반사하면 호출자가 보낸 문자열을 되돌려 줄 뿐이라 *그 자체*로는 새지 않는다. 새는 경우: (a) "열린 필드 X를 닫힌 필드로 필터했다" 대 "없는 필드 Y로 필터했다"가 다른 `code`를 낸다(I5 위반), (b) 오류가 **서버가 아는 후보를 제안**한다("did you mean `scoreSummary`?"), (c) 허용 목록(허용되는 연산자·필드) 전체를 `INVALID` 세부에 싣는다. AI First 8번(추측 없는 오류)이 (b)(c)를 유혹한다. RE-2에 **"제안·허용 목록은 *호출자에게 공개된* 계약 안의 것만"**을 넣어야 한다.
4. **capability/intent 이름의 존재.** PoC는 알 수 없는 intent는 404 `REQUEST.UNKNOWN_INTENT`, `allow`가 거짓이면 403 `AUTH.FORBIDDEN`(`codes.rs:767-773`의 `AUTH_FORBIDDEN`, `codes.rs:1016`의 `REQUEST_UNKNOWN_INTENT`)이다. 공개 계약에 열린 capability가 나열된다면 존재는 비밀이 아니지만, 등급별로 닫힌 capability가 있다면 403 대 404가 오라클이다. 이것은 4.2-RE-1의 "계약을 호출자 등급별로 거르는가"와 같은 뿌리다(결정 대기, OI-P3).
5. **응답 시간·크기·메타데이터.** I5는 total count·cursor를 언급했는데 RE-2 문장에는 없다. 응답 크기(`violations` 길이), 지연 시간(존재하는 행만 정책 평가), `depends`의 "리소스 전체 태그로 접음"(DD-11 CI-1)이 *접혔는지 여부*가 숨은 의존 존재를 드러낸다. DD-01이 "응답 시간 균일화 없음"을 층 1 단순 구현에서 허용했으므로 시간은 인정하되 **DD-14에 "층 1에서 시간 채널은 닫지 않는다"를 명시**하는 편이 정직하다.
6. **운영/개발 구분 메커니즘 없음**(3.3 DD-01 행).

**RE-3 내부 내용은 나가지 않음.** 방향은 맞다. 구멍:
- **`message` 필드가 존재하는 한 누출 위험이 남는다.** PoC가 `db.message()`를 그대로 `message`에 넣는 것이 증거다(1.2). RE-3을 "원문은 응답에 안 넣는다"로 쓰면 `message`를 누가 채우는지가 문제다. 가장 단순한 보장: **서버 생성 문장은 고정 사전(코드별 정적 문자열)에서만 나오고 예외 메시지·DB 메시지는 어떤 경로로도 합성되지 않는다.** 이것을 *검사 가능한 규칙*(정적 분석/테스트로 `AipError::new(…, db.message())` 형태 금지)으로 두어야 한다. 지금 문장은 약속에 가깝다.
- **`trace`**: 무작위·추측 불가여야 한다(순차 ID는 요청량을 흘린다). 또한 `trace`로 로그 조회 권한이 누구에게 있는지, 호출자가 trace를 알려 주면 운영자가 서버 로그를 열어 보는 흐름이 사실상 *유일한 서버 오류 디버깅 경로*가 되므로 **AI 개발 경험**(AI가 오류를 보고 스스로 고친다)과 충돌한다. 개발 환경의 서버 오류 디버깅 경로를 별도로 언급해야 한다.
- 오류 본문의 `intent`·`path`·`reason`(PoC `error.rs:7-19`)이 RE-3의 "내부 내용"인지 아닌지 정의가 없다. `intent`는 호출자가 보낸 이름의 반사라 무해하지만 `reason`이 "앱 선언 코드"인지 "내부 제약 이름"(PoC에서는 제약 이름으로 `constraint_errors`를 조회, 응답에는 `spec.code`)인지 분리해야 한다.

**RE-4 HTTP 상태는 코드에서 결정.**
- 방향은 맞고 PoC가 이미 한다. 구멍: (a) 단일 HTTP 호출이 *여러 코드*를 낼 수 있는 경우(U7 부분 성공, 한 요청의 여러 조합 읽기). (b) **상태는 정보 채널**이다. 401/403/404/409/422/429를 가르면 그 자체가 분류 정보이며, I5가 요구하는 "같은 오류 모양"에는 **같은 HTTP 상태**도 들어간다. RE-2와 RE-4가 서로 의존하는데 문장은 따로 있다. (c) 레지스트리에 없는 코드가 나왔을 때 PoC는 409(`codes.rs:223-225`). 이것을 계약으로 삼으면 안 된다. 미등록 코드는 *빌드/테스트 실패*여야 한다.
- 아리아리 사례(F4)가 보여 주듯 **방향 오류(클라이언트 잘못인지 서버 잘못인지)**가 가장 큰 오분류다. RE-4에 "4xx는 호출자가 바꿔서 해결 가능, 5xx는 불가"를 명시하면 `DataAccessException→400` 같은 사례를 규칙으로 막는다.

**RE-5 응답 모양은 하나.** 디스패치 이전 오류 포함 여부(1.1-1)와 위 R4 대안(부분 성공)이 빠졌다. 그리고 "세부는 코드별로 정의된 필드"는 `violations`처럼 코드마다 다른 모양을 허용하는데, 그러면 SDK가 *코드→세부 모양* 매핑을 알아야 한다(타입 생성의 입력이 되려면 공개 계약에 코드별 세부 스키마가 있어야 한다). 이 요구를 DD-13과 연결해 한 줄 쓰라.

**RE-6 성공 봉투.** `validUntil`은 뷰어 의존·시간 의존 값이 *있는지*를 드러낸다(숨은 뷰어 값의 유무?). 낮은 위험으로 보이나 `depends`와 함께 "접힌 태그" 신호가 된다. `page.next` 커서 불투명성(서명/암호화로 내부 키 값 노출 금지)은 DD-01 I5 "cursor"에 이미 있으므로 인용만 하면 된다.

**RE-7 재시도 가능 여부.**
- **PoC의 `retryable`은 조건부 의미다.** `codes.rs:55-57`: "Whether the caller may send the same call again **with the same idempotency key**". `CONCURRENCY_CONFLICT`의 fix가 "Send the same call again with the same idempotency key"(`codes.rs:789`)이다. DD-14 RE-7은 "다시 보내도 되나"로 줄여 이 전제를 떨어뜨렸다. 멱등 키 없는 쓰기를 "재시도 가능"이라 알려 주면 W-I8(재시도 안전)을 SDK가 어기게 만든다. 그리고 멱등 키 전달 방식은 DD-08이 후속으로 넘겼고 DD-14 범위 밖이다. **고리가 닫히지 않았다.**
- `Retry-After`/대기 시간 같은 *동적* 힌트가 없다(`RATE_LIMITED`, `UNAVAILABLE`).
- "응답을 받지 못함"(네트워크 중단)은 코드가 없는데 SDK 재시도의 제일 흔한 경우다. 이 경우 *결과를 모르는 쓰기*를 어떻게 다루는지는 DD-13 S9 쪽 문제라 한 줄 위임을 쓰라.

### 4.3 로케일 메시지

- RE-1은 "사람 문장은 보조이고 로케일별로 바뀔 수 있다"고만 썼다. 이것은 **누가 문장을 만드는가**를 정하지 않은 문장이다. 선택지: (A) 서버가 `Accept-Language`로 번역(서버 측 작성량 증가 = 철학 §4-3 위반 후보, 앱마다 번역 카탈로그), (B) 서버는 영어 진단 문장만, 사용자용 문장은 프론트가 코드로 매핑(아리아리의 "프론트가 고정 문구로 덮음"과 같은 구조가 되살아난다 — DD-07 B.1 관찰 6), (C) 코드+매개변수만 보내고 문장은 전혀 안 보냄. B.3 예시에 `message`가 하나도 없는 것은 (C)처럼 읽히고, RE-1 문장은 (A)처럼 읽힌다. **문서 안에서 서로 다른 안을 가정한다.**
- (C)는 RE-3(내부 내용 비노출)을 구조적으로 해결하고 AI가 다루기 쉽다. 단 사람이 개발 중 응답을 읽는 경험(JS/Python 개발자 사용성, 이탈 점검 5번)이 약해지므로 *개발 환경에 한해* 코드 설명(`explain-code` 유사, PoC B.2)으로 보완하는 안이 설득력 있다. 이는 3.3의 "개발 진단 메커니즘"과 같은 설계 항목이다.
- 문장에 호출자 값이 들어가면(예: "닉네임 'abc'는 이미 있습니다") 반사된 값이 로그/화면에서 XSS·로그 주입의 매개가 된다. (C)면 값은 구조화 `params`로 가고 이스케이프 책임이 클라이언트 렌더에 있음을 명시.

## 5. "창시자 질문 없음"이 정당한가

**대체로 정당하나, 조건 하나가 어긋난다.** 운영 규칙 F는 "제품 철학이나 사용자 경험에 영향을 미치는 선택만 질문하고 내부 구현 세부는 근거를 제시한 뒤 기술적으로 제안"하라고 한다. 응답 봉투 모양, JSON 필드 이름은 내부 구현 세부이므로 질문 없음이 맞다.

그러나 DD-14 안에는 창시자 영역에 걸치는 항목이 둘 숨어 있다. 이것을 "기술 제안"으로 처리하면 운영 규칙 8·10(미결정 사항 임의 확정 금지)에 걸린다.

1. **존재를 어디까지 감추는가의 사용자 경험 비용.** 아리아리의 `NoClubManagerException` 같은 "역할 부족" 구분 문구를 프론트가 쓰는데(DD-07 B.1 관찰 6), 이를 `NOT_FOUND`로 접으면 최종 사용자가 "왜 안 되는지" 못 본다. RE-2가 이 경계를 정하지 않아서 4.2-RE-2-1이 비어 있다. 경계를 *더 많이 감춘다*로 정하면 사용자 경험이 달라지므로 **창시자의 이해가 필요한 선택**이다(비전문가 문장: "권한이 없는 사람이 눌렀을 때 '권한이 없습니다'라고 알려 줄까, '없는 페이지입니다'라고만 할까?"). DD-01 I5를 창시자가 이미 승인했다는 증거는 이 문서에서 확인하지 못했다(`DD-01`은 "에이전트 합의", 창시자 판단 전). **이미 확정된 철학이 아니라 에이전트 합의 위에 서 있는 RE-2다.**
2. **메시지의 소유(서버 대 프론트, 4.3).** 로케일 메시지를 누가 만드는지는 "서버 쪽에 써야 할 것이 늘어나는가"(PRINCIPLES §4-3)에 직결되는 *개발자 경험*이다. 창시자 질문까진 아니라도 DD-07의 F1·DD-10의 F처럼 **"비전문가가 이해하는 두 문장 선택"**으로 올릴 가치가 있다.

또한 R3 채택 여부는 "JS/Python 생태계 호환"(PRINCIPLES §2 구현 행)에 걸친 선택이라, 확인 필요 항목이 풀리기 전에는 "기술 제안"의 근거도 부족하다. 최소한 F절에 **"창시자 질문 없음, 단 RE-2 경계(역할 정보)와 메시지 소유는 DD-01 I5·DD-13 결정에 종속"**이라고 의존을 쓰는 편이 정직하다. 현재 F절 "없음"은 이 종속을 가린다.

## 7. 수정 제안

### P0 (결정 문서가 서려면 필요)

1. **RE-2를 세 층으로 쪼개고 제약 파생 코드를 포함시킨다.** (a) 볼 수 없는 대상 = `NOT_FOUND`와 동일 *코드·상태·모양*, (b) 보이는 대상에 대한 동작 거부 = 상세 사유 허용, (c) **DB 제약/FK/유일 위반에서 나오는 코드는 가시성 검사를 통과한 후에만 낼 수 있거나, 통과 못 하면 `NOT_FOUND`/일반 코드로 접는다.** 한 줄: "코드는 호출자가 볼 수 있는 행에 대해서만 달라진다."
2. **개발 진단 메커니즘을 정한다.** 운영 서버에 "개발 모드 응답"을 두지 않고, 정확한 사유는 *진단용 계약 + 요청의 오프라인 재현* 또는 *개발자 인증 맥락의 별도 엔드포인트*로만 계산한다고 못 박는다(DD-13 73행과 정합).
3. **R1/R3 충돌을 푼다.** B.3 모양을 problem+json 호환으로 바꿀지(최상위 `type`·`status`·`code`·...), R3을 대안에서 빼고 "필요 시 어댑터"로 후속할지 정한다. 지금처럼 "R1 기본 + R3 호환 검토"는 B.3을 건드리는 결정을 숨긴다. (RFC 9457 세부는 확인 필요.)
4. **RE-7에 멱등 키 전제를 복원한다.** PoC `codes.rs:55-57`의 의미 그대로 "같은 멱등 키로 다시 보내도 되나". 멱등 키 전달이 비어 있다는 DD-08 위임을 DD-14 의존으로 명시.
5. **F절을 "없음"에서 "종속 있음"으로 고친다**(5절). RE-2 역할 정보 경계와 메시지 소유를 비전문가 문장 2개로 올릴지 coordinator가 판정.

### P1

6. **RE-3을 검사 가능한 규칙으로.** "어떤 경로에서도 외부 오류 메시지가 `message`로 합성되지 않는다"를 PoC `db_error`·`INTERNAL` 경로 수정 항목(1.2)과 함께 E 검증으로 추가(E4: PoC `message` 합성 지점 감사).
7. **RE-4에 "5xx는 서버 책임, 4xx는 호출자가 바꿔서 해결 가능" 방향 규칙과 "미등록 코드는 빌드 실패"를 추가.** 일괄/부분 성공의 상태(U7), 필터 bulk의 식별자 지시, 커밋 시점 위반을 B.3에 예시로 추가.
8. **오류 category(S12)와 알 수 없는 코드 처리**를 RE에 추가하고 DD-13 S12와 연결한다. 레지스트리가 공개 계약에 얼마나 들어가는지는 OI-P3 종속으로 명시.
9. **RE-5 범위를 디스패치 이전 오류(인증, 파싱, 라우팅, 크기, 속도 제한)까지 확장.** 아리아리 필터 사례(1.1-1) 인용.
10. **읽기는 `data`와 `error`를 동시에 주지 않는다(부분 성공 없음)**를 RE에 명시하거나, 허용한다면 모양을 정의.
11. **메시지 소유(4.3 A/B/C)를 정하고 B.3 예시와 RE-1 문장을 일치**시킨다. 추천 시작점은 (C)+개발 환경의 `explain-code` 유사 도구(추천일 뿐 확정 아님).
12. **DD-13 33행의 "응답 봉투 소멸"과 RE-6의 관계 한 줄 정리.**

### P2

13. E1 후속: 62개를 실제로 코드 후보 표로 만들어 중복 제거 수치를 근거 있게 확정(지금 2.3의 25~35는 추정).
14. E2를 구체 공격 목록으로: (i) 비공개 유일 값 존재 확인, (ii) 닫힌 필드 필터 대 없는 필드 필터, (iii) 일괄 위반의 `index` 길이/집합, (iv) 숨은 FK 대상, (v) intent 403 대 404.
15. `trace` 형식(무작위), 오류 본문 `params` 이스케이프, 커서 불투명성 인용.
16. 오류 코드의 deprecated/삭제를 `aip diff`(DD-12)의 호환 검사 대상으로 묶는지 질문 목록에 추가.
17. E3 선행: PoC 레지스트리 재사용은 "코드 구조(CodeInfo·http_status·retryable)는 재사용, `message` 합성·`TENANT.MISMATCH` 코드는 수정"으로 구체화.

## 8. 결론과 추천

**추천: R1의 방향은 맞지만 현재 문서는 "결정 가능한 상태"가 아니다. P0 5개를 반영한 v2가 필요하다.**

- 맞는 것: 안정 코드(RE-1), 서버 내부 비노출(RE-3), 상태는 코드에서(RE-4), 오류 모양 통일(RE-5)의 방향. 아리아리 사실 서술은 대체로 정확하다(F1~F4, F6).
- 틀리거나 비어 있는 것: ① 존재 비노출(RE-2)이 정책 거부·제약 파생 코드·개발 진단 메커니즘을 정하지 않았다. ② R3 호환 검토가 B.3 모양과 충돌한다. ③ RE-7이 멱등 키 전제를 잃었다. ④ 로케일 메시지의 소유가 문서 안에서 모순이다(RE-1 대 B.3). ⑤ F절 "없음"이 RE-2 경계(사용자 경험)를 가린다. ⑥ PoC가 이미 RE-2·RE-3을 어긴다는 사실이 E3 전에 읽기만으로 확인된다.
