## 2. 새 모순, 임의 확정, 과잉 설계

### 2-1. V1의 "선언한 상세 형태"가 DD-01 저장된 조회 정의와 맞지 않는다 (새 문제)

- DD-09:60은 센다고 선언하는 대상을 "DD-01의 저장된 조회 또는 리소스의 `detail` 형태"로 적는다.
- DD-01은 저장된 조회를 "표준 조합 요청에 이름만 붙인 것. 새 의미가 없다"(`DD-01:117`)로 정의하고, F4에서 "같은 조합 요청의 별칭으로만 쓴다"(`DD-01:243`)고 묶었다. 또 "저장된 조회와 원형"은 하나의 canonical 형태로 정리돼 같은 정책을 받는다(`DD-01:158`).
- 저장된 조회에 "센다"를 붙이면 새 의미가 생긴다. 같은 요청을 이름 없이 조합 형태로 보내면 세지 않거나, 이름이 canonical 정리에서 사라져 세는 근거가 없어진다. 한 의도가 두 표현에서 다른 부수 효과를 낳는다. 이는 DD-09:101이 스스로 근거로 삼은 "한 의도 한 구조"와 `DD-01:158` 양쪽에 걸린다.
- "리소스의 `detail` 형태"는 DD-01에 정의가 없다. `detail`이라는 용어는 DD-01에서 찾지 못했고(grep), 상세는 아리아리 예시로만 나온다(`DD-01:206`). 존재하는 개념처럼 적혀 있다.
- 따라서 V1의 판정 장치는 DD-01의 어느 개념에도 얹히지 않았다. 방향(선언 기반)은 맞지만 DD-09:60의 문구는 DD-01과 충돌하는 주장이다.
- 심각도: F1(허용 여부)의 답은 이 문제에 의존하지 않는다. 그러나 추천 V1의 정의(DD-09:127 "선언한 상세 형태")가 미정의 개념이라 에이전트 간 합의로는 닫히지 않는다. 고칠 문구는 §4 P1-1.

### 2-2. 임의 확정 여부

- 창시자 결정을 확정한 곳은 없다. 상태는 "미결정"(DD-09:3,127), VC-1~VC-7은 `[추천]`이고 창시자 질문이 아님을 밝혔다(DD-09:78). 운영 규칙 F(기술 제안은 에이전트)와 맞다.
- 다만 VC-5의 "일 단위로 바뀌는 해시"와 B.1에서 가져온 "하루/14일"은 값을 정한 것이다. 추천 성격이라 허용하되 "아리아리 기존 값 그대로 가정"이라는 표시가 있으면 더 낫다(P2).

### 2-3. 과잉 설계

- 없다. 층 1은 성질 7개로 관찰 가능한 보장만 적었고 구현 선택(인라인/큐/로그)은 DD-06으로 미뤘다(DD-09:76). DD-06이 이미 백그라운드 루프 위치를 다루므로(`DD-06:17`) 중복도 없다.
- 일관성: VC-3은 `DD-01:145`(I5 존재를 드러내지 않음)와 같은 방향이고, VC-6은 `DD-02` W-I8(`DD-02:157`)과 충돌하지 않는다. VC-1·VC-2와 아리아리의 `@Transactional(readOnly)` 덮어쓰기는 r1에서 확인한 사실로 DD-09:13에는 직접 인용이 없지만 주장 자체는 틀리지 않는다.

## 3. F1은 비전문가 창시자가 답할 수 있는가

- 가능하다. 질문이 "서버가 자동으로 올려도 되는가"로 하나이고, (가)와 (나)가 각각 화면이 무엇을 하는지로 서술된다(DD-09:117-120). 기술 결정(키, 저장, 일관성)은 질문에서 빠졌다.
- (가)의 "같은 접속은 하루 한 번"과 "학교 공용망은 여러 명을 1명으로 센다"는 약속 범위를 정직하게 낮췄다. r1 §6.2의 우려는 해소됐다.
- 남는 흠 두 가지, 둘 다 P2다.
  1. "조작에 어느 정도 강한"은 모호하다. 바로 뒤 괄호가 설명하므로 답은 가능하다.
  2. 에이전트 의견의 이유 "화면마다 신호를 빠뜨리는 실수가 없다"(DD-09:121)는 아직 근거 없는 추정이다(r1 3.5). 에이전트 의견은 창시자 선택을 기울이므로 "추정"을 붙이거나 (나)의 비용(화면이 빠뜨리면 숫자가 줄어듦)을 같은 무게로 적는 편이 낫다.

## 4. 잔여 수정 제안

### P0
- 없음.

### P1
1. DD-09:60과 DD-09:127의 "선언한 상세 형태"를 DD-01과 맞춘다. 택일 후보를 문서에 `미결정`으로 적는다.
   - (a) 세는 선언은 저장된 조회가 아니라 리소스가 선언하는 별도 항목(예: 리소스의 "열람 집계" 선언)이며, 어떤 표현으로 읽든 그 리소스의 지정된 읽기가 같은 canonical로 정리되면 같은 결과를 낸다.
   - (b) 저장된 조회에 붙이려면 DD-01의 "이름만 붙인 것, 새 의미 없음"(`DD-01:117,243`)을 고치는 일이므로 DD-01에 명시적으로 요청한다.
   - 어느 쪽이든 `detail`은 DD-01에 없는 용어이므로 새 개념임을 밝히고, "DD-01에 통지 필요"를 열린 점에 추가한다.

### P2
2. F1 에이전트 의견(DD-09:121)에 "추정"을 붙이거나 (나)의 비용을 병기한다.
3. 하루·14일·일 단위 해시가 아리아리 기존 값 승계임을 표시한다(§2-2).
4. 창(14일)이 랭킹 의미 요건이라는 점(r1 #11)과 변하는 카운터 정렬·커서 상호작용(r1 #13)을 DD-01 후속 목록에 한 줄씩 남긴다.

## 5. 결론

**미합의 1개.**

1. V1의 "선언한 상세 형태"가 DD-01의 저장된 조회 정의(이름만 붙인 별칭, 새 의미 없음)와 어긋나고 `detail`은 DD-01에 없는 용어다 (§2-1, P1-1). 문구 수정으로 닫히는 크기이며, 나머지 13개 제안은 반영 또는 허용 가능한 후속이다. 사실 정정, VC 성질, F1은 합의 가능하다. P1-1이 반영되면 합의 도달로 본다.
