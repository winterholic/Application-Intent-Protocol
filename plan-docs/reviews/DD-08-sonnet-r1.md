## 2. 철학 정합성과 DD-01~07과의 불일치

### 2.1 원문 기준 평가

| 원문 | DD-08 처리 | 평가 |
|---|---|---|
| "HTTP를 반드시 버리는 것이 아니다. 요청·응답을 어떤 **의미 단위**로 정의하고 서버가 어떻게 검증·실행하나가 중요" (handoff 103~107행) | C.2-1에서 HTTP 유지. 의미 단위는 "구조화된 Intent" (D표 102행) | 방향은 맞다. 다만 **의미 단위의 정의가 와이어 문서에 없다.** DD-08은 읽기 조합 한 예만 보이고, 쓰기·전이·bulk·확장 호출·저장된 조회 호출이 어떤 모양인지 하나도 보이지 않는다. 그런데 C.2-2는 "하나의 진입점이 이 모두를 받는다"고 확정 어조로 쓴다. 보이지 않는 것을 받는다고 약속한 셈이다 |
| "Intent는 명확한 문법, 계약, 타입, 정책을 갖춘 구조화된 요청" (handoff 115행) | W1을 "구조화된 요청 그대로"로 평가 (C.1 77행) | **"구조화"를 JSON과 동일시한 것은 약하다.** 원문은 문법·계약·타입·정책 4요소를 말한다. JSON 트리 자체는 문법이 아니라 컨테이너다. 어떤 키가 어떤 의미를 가지는지(`where`/`gte`/`$today`/`select: true`)의 **문법 정의**가 W1의 실질인데 문서에 없다. 아래 2.3 |
| "REST를 다른 이름으로 바꾸는 데 그쳐서는 안 된다" (handoff 638행) | D표 104행 "C.2-2(의도별 엔드포인트 없음)로 충족" | **근거가 얇다.** 엔드포인트를 하나로 합치고 본문에 `read`/`where`를 넣는 것은 REST의 이름 바꾸기보다 RPC·단일 엔드포인트 패턴(GraphQL이 바로 이 모양)에 가깝다. 이 원칙의 실질 충족은 DD-01의 capability·정책·canonical에서 나오며 와이어 형식에서 나오지 않는다. "와이어 형식이 이 원칙을 충족한다"고 쓰면 과장이다. "와이어 형식이 이 원칙을 해치지 않는다"가 정확하다 |
| 프로토콜 이름 Application Intent Protocol | D표 102행 "W1·W2 모두 충족" | W1·W2 모두 충족한다는 말은 이 축에서 변별력이 없다는 뜻이다. 문서가 이를 알고 있다면 근거 축으로 쓰지 말아야 한다 |

### 2.2 DD-01~07과의 불일치·긴장

1. **"canonical 정본 표현은 하나"와 W1의 비결정성 (DD-01 158행, DD-08 C.2-4).** DD-01 canonical은 "중첩 where와 관계 필터, 저장된 조회와 원형"처럼 *의미*가 같은 요청을 한 형태로 정리한다고 했다. DD-08 C.1(79행)은 "트리를 그대로 정렬·해시하기 쉽다"고 하는데, JSON 트리 해시가 쉬운 것은 **구문 정규화**(키 순서, 숫자 표기, 중복 키)일 뿐이다. DD-01의 의미 정규화(`a AND (b AND c)` = `AND[a,b,c]`)와는 다른 층이다. 이 구분을 쓰지 않으면 "W1이 canonical에 유리"가 의미 정규화까지 쉽다는 뜻으로 읽힌다.
2. **DD-03 S 등록과의 연결 부재.** DD-03 26행·T-I3은 빌드가 canonical 요청을 **명시 등록**하고 식별자를 가진다고 했다. DD-08 B.3은 요청 본문에 *식별자로 호출*하는 형태(등록 ID만 보내기)를 전혀 다루지 않는다. 등록이 있으면 와이어에는 (a) 전체 트리, (b) 등록 ID + 변수 두 형태가 필요한데, 이는 곧 "정본 표현이 둘"이다(C.2-4와 충돌 가능). 3.1에서 대안으로 다룬다.
3. **DD-03 T-I5 "경로는 서버가 정한다"와 단일 진입점.** 헤더·파라미터로 `runtime`을 주장하지 못해야 한다. 단일 `POST /aip` 본문에 `read` 외 다른 필드가 늘수록, 본문 어느 필드도 입장 경로에 영향을 주면 안 된다는 규칙이 와이어 스키마에 명시돼야 한다. DD-08은 이를 언급하지 않았다.
4. **DD-02 W-I6와 W1 확장성.** 쓰기에서 "순서·잠금·격리 힌트가 요청에 없다"가 층 1이다. W1이 "새 연산은 새 키"(C.1 83행)라는 확장 방식을 장점으로 쓰는데, **새 키가 늘수록 W-I6·DD-01 I3(힌트 금지)가 스키마의 거부 목록(allow-list)에 의존**한다. 알 수 없는 키를 무시하는 JSON 관행(forward compat)과 충돌한다. "미지의 키는 무조건 거부"를 와이어 규칙으로 못박아야 한다. 현재 문서에 없다.
5. **DD-07 위반 응답과 응답 형식.** DD-07(108~112행)이 정한 위반 응답(항목 index, 안정 코드, 오라클 제거)은 **응답** 쪽 형식이다. DD-08은 제목이 "요청을 서버에 어떤 형태로"라서 범위 밖이라 해도, T06 3절은 요청·응답을 한 항목으로 묶었다. 요청만 먼저 정하고 응답(select 모양 보존, 오류 필드 위치, `page`/`items` 메타)을 나중에 정하면 **select 기반 타입 추론**(B.3 66행)이 응답 모양 규칙에 의존하므로 순서가 거꾸로다.
6. **DD-04와의 연동 서술이 한쪽만 맞다.** DD-08 86행은 "E가 채택되면 서버 정의는 AIP 문법이므로 W2가 계열 일관"이라 했다. 그러나 DD-04 E의 *선언 블록*은 *개발자가 쓰는 소스*이고 요청 W2는 *런타임 전송 문자열*이다. 소스 문법과 와이어 문법은 목적이 다르다. 일관성의 실익은 (a) 학습 비용 (b) 에디터 도구 공유 정도이고, DD-04 146행이 스스로 인정했듯 **B-data에서도 조건식은 고유 문법**이다. 즉 W1을 택해도 `where` 안의 *식*을 문자열로 받을지 JSON 트리로 받을지 결정이 남는다(2.3).

### 2.3 W1의 "순수 구조화" 주장의 허점

W1 예시에서 `{ "periodEnd": { "gte": { "$today": true } } }`는 이미 **표현식**이다. `$today`는 JSON이 가진 의미가 아니라 *서버가 해석하는 함수 표기*다. 조건이 `OR`, 관계 경유 필터(`club.school`), `now()` 기준 상대 날짜, 주체(`actor`) 참조로 늘면 JSON 트리는 사실상 **JSON으로 쓴 AST**가 된다. 이 경우 두 가지가 같이 성립한다.
- 파서가 사라지지 않는다. 대신 "스키마 검증기 + 표현식 의미 검사기"가 파서 자리에 선다(이탈 방지 6번 "파서 대신 스키마 검증, 엔진 쪽 비용이 작다"는 낙관).
- 사람 가독성 문제가 모든 where 식에서 생긴다.

문서의 E1이 "표현 불가능한 것 비교"를 실험으로 두었으니 이 점은 E1에서 검증 대상이지만, 현재 본문은 W1 쪽에 유리한 비교 표를 이미 완성했다(3.2).

## 3. 대안 비판

### 3.1 W1/W2/W3 비교의 공정성

비교표 C.1(75~84행)은 W1에 기울어 있다. 구체적으로:

| 행 | DD-08 서술 | 반박 |
|---|---|---|
| 보안 | W2 "프론트에서 문자열을 이어 붙이면 주입 위험" | 이것은 W2의 약점이 아니라 **사용 방식의 약점**이다. 파라미터화된 질의(`$param` 자리표시자 + 별도 값)를 쓰면 SQL의 prepared statement와 같은 이유로 막힌다. DD-08 자신이 C.2-3에서 "W2를 택해도 `$param` 자리표시자"를 규칙으로 두었으므로, 같은 표의 W2 칸에서 이 위험을 지워야 공정하다. 즉 보안 행은 C.2-3 적용 후 W1과 W2가 **주입 면에서 동등**하다. 남는 차이는 파서 자체의 취약점(재귀 폭주, 정규식 DoS)이지만, JSON 파서도 깊이 폭탄에 같은 문제가 있다(4.1) |
| 보안 | W1 "스키마 검증이 쉽다" | JSON Schema로 *깊이·분기*는 표현할 수 있어도 `where` 식의 **의미** 검증(필드가 filter capability에 열려 있나)은 스키마가 못한다. 이건 W2도 같은 의미 검사기를 쓴다. 따라서 이 장점은 구문 단계에 한정된다 |
| 디버깅·로그 | W1 "길고 중첩돼 읽기 불편", W2 "짧고 읽기 쉬움", W3 "표시용으로 W2 출력 가능" | G절 추천은 "W1 정본 + 사람용 표기는 출력 전용"이다. 그러면 사실상 **W2를 만들어야 한다**(출력기, 왕복 불가능한 표기이지만 문법 정의는 필요). W3의 변환기 비용(C.1 80행 "변환기 하나 더")을 W3의 단점으로 쓰면서, 추천안이 같은 문법 정의 비용을 "출력 전용"이라는 이름으로 숨기고 있다. DD-04 E4가 "출력기 시제품이 필요, 비용은 검증 못함"이라 한 것과 같은 비용이다 |
| AI 경험 | W2 "문법을 틀리기 쉬움", W1 "구조를 틀리면 스키마 오류로 바로 잡힘" | 근거 없음(E3 미실행). LLM이 JSON을 틀리는 빈도와 짧은 DSL을 틀리는 빈도는 모델·도구(구조화 출력 모드, JSON Schema 제약 디코딩)에 달렸다. 확인 필요. 오히려 AI가 생성 시 *토큰 수*와 *오타 표면*은 W1이 더 크다. 이 비교 행은 `확인 필요`로 표시해야 한다 |
| 확장성 | W1 "새 연산은 새 키", W2 "새 문법" | W1의 "새 키"도 서버 스키마와 SDK 타입이 갱신돼야 하고 문서가 갱신돼야 한다. 문법 확장 비용과 구조가 같다. 비대칭이 아니다 |
| 생태계 | W2 "전용 파서·에디터 지원 필요" | 맞다. 이건 W2의 실제 약점이다. 다만 프론트는 SDK가 만들므로 에디터 지원은 *사람이 와이어를 직접 쓸 때*만 필요하다. 문서가 "프론트는 어차피 SDK"(F1 125행)라고 하는 만큼, 이 약점의 무게는 작다 |

요약: W1이 이기는 축은 (a) 구문 정규화·해시 (b) 파서 구현량 (c) 도구 생태계 3가지로 보이고, **보안 행의 우위는 사용 규칙으로 상쇄된다.** 추천 결론 자체(W1)는 합리적일 수 있지만, 근거 표현이 실제보다 강하다. 이 정도면 P1 수정 사유다.

W3 평가도 불공정하다. W3를 "표현이 둘"로 규정했는데 D표 105행은 이를 "한 의도 한 구조"와 충돌로 본다. 그러나 W3의 설계안 자체(61행)는 "W1 정본, W2는 입력 편의, 서버 안에서는 하나"로 canonical이 하나다. PRINCIPLES §4-6("같은 의도를 여러 방식으로 쓸 여지를 만들지 않는가")의 쟁점은 **서버 내부 정본이 하나인가**와 **사람·AI가 쓰는 방식이 여럿인가** 두 가지로 갈린다. DD-08은 후자만 W3의 단점으로 쓰고, 정작 DD-04가 여러 작성 방식(C2)을 평가 보류한 것과의 일관성을 설명하지 않았다.

### 3.2 빠진 대안

| 대안 | 내용 | 왜 비교에 들어와야 하나 |
|---|---|---|
| **W4. 저장된 조회/등록 ID만 전송 (registered-only의 와이어 형태)** | 호출자가 `{ "id": "q_9f3a...", "vars": {...} }`만 보낸다. 트리 전체는 빌드 때 서버에 등록돼 있다 | DD-03 S는 `registered-only`를 정식 입장 정책으로 추천했다. 이 정책에서는 **운영 와이어의 90%가 W4**일 것이다. 그러면 와이어 형식의 "본체"는 트리/문자열이 아니라 *식별자 + 변수*이고, 트리 전송은 개발·`runtime` 모드용이 된다. 이 경우 W1/W2 논쟁의 중요도가 낮아지고, 대신 변수 타입 검증, 식별자 위조(T-I3), 구버전 식별자 처리(T-I4)가 와이어 핵심이 된다. DD-08에 이 형태가 없는 것은 DD-03 추천과의 통합 누락이다. |
| **W5. 혼합: 트리 + 이름 있는 변수(prepared) 분리** | 정본은 트리, 값은 `vars`로 분리. 서버가 *트리 모양(구조)* 과 *값*을 따로 취급 | C.2-3이 사실상 이를 요구(값을 이어 붙이지 않는다)하는데 W1 예시(B.3 38~47행)는 값이 트리 안에 인라인(`"take": 5`, `"gte": {...}`)이다. 구조 해시/등록/plan cache(DD-03·DD-01 층 2)를 값 변화와 분리하려면 `vars` 분리가 **와이어 구조에 들어가야 한다.** 이게 빠졌다 |
| **W6. 바이너리 직렬화 (CBOR, MessagePack, Protobuf)** | JSON과 같은 트리를 바이너리로 | D-P13이 "커스텀 바이너리 wire protocol"을 금지했으나 이는 *자체 설계*에 대한 금지다. 표준 직렬화는 별개다. 다만 지금 단계에서 이득이 없으므로 **기각 근거를 한 줄 적는 것으로 충분**하다. 현재 C.2-1은 "커스텀 바이너리는 만들지 않는다"만 쓰고 표준 바이너리는 침묵한다. 기각이어도 이유(디버깅·브라우저 도구·JSON 우선)를 적어야 한다 |
| **W7. GET + 쿼리 문자열/URL 인코딩** | 읽기는 `GET /aip?q=<encoded>` | HTTP 캐시(CDN, 브라우저)와 프록시 가능성이 있다. 반대로 URL 길이·로그 유출·캐시 키 문제가 있다(4.4). DD-08은 읽기를 POST로 가정하고 이유를 쓰지 않았다. HTTP 의미(안전·멱등·캐시 가능)를 쓸지는 원문 "HTTP를 반드시 버리는 것이 아니다"가 *HTTP 의미를 활용할 수 있다*는 쪽으로도 읽힌다. 비교에서 빠뜨리면 안 된다 |
| **W8. GraphQL 호환 (그대로 채택/호환 레이어)** | 요청을 GraphQL 문서로 받음 | 철학 §1이 "복제하려는 것이 아니다"라 했으므로 기각은 자연스럽다. 그러나 W2가 사실상 GraphQL 모양이므로 *기각 사유와 W2 평가가 같은 근거*임을 한 줄로 밝히는 편이 좋다. 외부 기술 사실(GraphQL persisted queries, APQ 동작)은 웹 확인 없음: **확인 필요** |

### 3.3 "쓰기와 읽기를 같은 진입점에 둘 때의 문제" (C.2-2)

C.2-2가 "하나의 진입점이 읽기·쓰기·전이·bulk·저장된 조회·확장 호출을 받는다"고 추천한다. 이 추천은 **창시자 질문이 아니라고 했지만 사실상 큰 설계 결정**이다. 문제:

1. **HTTP 의미 상실.** 읽기도 POST이면 브라우저·CDN·프록시·모니터링이 안전/멱등을 구분하지 못한다. 단 DD-08은 이를 인지했다는 서술이 없다. 반대로 읽기는 GET, 쓰기는 POST로 나누면 "엔드포인트가 둘"이 되어 C.2-2와 충돌하나, **의도별 엔드포인트가 아니라 *종류별* 2~3개**이다. REST 이름 바꾸기와는 다르다. PoC가 이미 `/aip/query/`·`/aip/command/` 별칭(`http.rs` 51~52행)을 둔 것은 이 분리의 흔적이다. 그것을 버리는 이유가 문서에 없다.
2. **운영 통제.** WAF·게이트웨이·레이트 리밋은 경로로 읽기/쓰기를 구분하는 게 일반적이다. 본문 안 `read`/`write` 키로만 구분되면 L7 정책이 본문 파싱을 요구한다. 본문 크기·깊이 제한을 게이트웨이가 못 건다.
3. **권한 오분류 위험.** 한 진입점이 읽기·쓰기를 가르는 기준이 본문 필드이면, 본문 필드 오기·누락이 쓰기를 읽기로 취급(예: 읽기 타임아웃·읽기 복제본으로 라우팅)하는 사고가 된다. DD-03 T-I3("읽기 등록이 쓰기·확장 경로로 쓰일 수 없다")과 정면으로 관련되는데 와이어에서 연산 종류를 어떻게 구분하는지 안 쓰였다.
4. **CSRF**(4.5).
5. 반대 방향 이점: 단일 진입점은 인증·오류·버전·멱등 처리의 중복을 줄인다. 이는 AIP 목적(중복 제거)에 부합한다. 그러므로 "하나냐 둘이냐"의 결정은 **창시자 질문까지는 아니되 기술 제안 근거를 써야 하는 항목**이다.

### 3.4 "결과 타입을 select에서 추론" 주장의 현실성

B.3 66행. 문제는 크게 4가지다.

1. **현 자산에 없다.** 생성 클라이언트는 intent 이름별 고정 출력 타입(`ClubListOutput`)이다(`aip.ts` 1030행 이후). select 기반 추론은 TS의 조건부·매핑 타입으로 가능한 기법이지만 *이 프로젝트에서 구현·검증된 적 없음*이다. 확인 필요(TS 타입 계산 성능, 깊은 중첩에서 컴파일 지연).
2. **Python은?** PRINCIPLES §2는 "JS/Python 생태계"를 말한다. TS식 select 추론은 Python에서 동일하게 성립하지 않는다(TypedDict/Protocol 한계 또는 코드 생성 필요). DD-08은 TS만 예시.
3. **와이어와 무관한 약속.** 추론은 SDK의 일이지 와이어 형식의 성질이 아니다. 그러므로 W1/W2 비교의 근거로 쓰면 안 된다. 쓴다면 "W1이든 W2든 SDK가 추론할 수 있다"가 올바른 문장이다.
4. **서버 응답이 select와 일치한다는 계약 필요.** DD-01 I5(열리지 않은 필드는 없는 것과 같은 오류 모양)에서 거부되는 필드가 있을 때 응답 타입은 어떻게 되나. "select한 필드는 모두 있다 또는 요청 전체 거부"가 타입의 전제인데, 필드 정책에 따라 *필드별 마스킹*이 생기면 추론 타입이 거짓이 된다. DD-01에서 필드 정책이 거부인지 마스킹(null)인지가 와이어에 영향을 주는데 DD-08이 이 의존을 적지 않았다. 확인 못함: DD-01이 필드 정책 위반을 *요청 전체 거부*로 정했는지는 본문에서 확정 문장을 찾지 못했다.

## 4. 보안

DD-08의 보안 서술은 "주입 표면이 작다"(C.1 78행, D표 105행) 한 줄이다. E2(111~117행)가 공격 예를 만들겠다고 했으나 아직 실행 전이다. 아래는 실행 전에 알 수 있는 약점이다. 증명이 아니라 점검 항목이다.

### 4.1 깊이 폭탄
- JSON 중첩 깊이 폭탄은 **파서 단계**에서 먼저 터진다(재귀 파서의 스택). 서버의 의미 검사(DD-01 I4 "요청 복잡도 상한")는 *파싱이 끝난 뒤* 작동하므로 이를 막지 못한다. 와이어 규칙에 "본문 최대 바이트, 최대 JSON 중첩, 최대 노드 수를 *파싱 중에* 제한"이 들어가야 한다. `http.rs`에서 본문 크기 제한·깊이 관련 문자열은 grep에 없었다(`body_limit`·`depth` 검색 무결과). 프레임워크 기본값에 의존하고 있는지는 확인 못함(axum 기본 제한 값은 외부 사실이라 확인 필요).
- 반대로 W2 파서도 같은 문제를 갖는다. W1이 구조적으로 안전하다는 근거는 없다. `serde_json`은 기본 재귀 한도를 갖는 것으로 알려졌으나 정확한 값과 이 프로젝트의 사용 방식은 확인 필요.
- select 중첩(`club { ... }` 관계 경유)과 where 중첩은 **서로 다른 한도**여야 한다. 관계 경유 깊이는 조인 비용(DD-01 I4), 불리언 중첩은 파서 비용이다. 하나의 "depth" 숫자로 퉁치면 둘 중 하나가 어긋난다.

### 4.2 거대 OR / 조합 폭발
- DD-01 E3가 "OR 폭발"을 공격 모음에 넣었지만 와이어에서의 한도(배열 길이, 분기 수)는 DD-08에 없다. `IN [수만 개 값]`, `OR` 수천 개, 다중 정렬 키는 **크기** 문제와 **비용** 문제가 겹친다. 와이어 상한(바이트·노드 수)이 1차, DD-01 I4 비용 추정이 2차 방어라는 층 구분을 쓸 것.
- W1에서 이는 JSON 배열 길이 문제, W2에서는 토큰 길이 문제로 형태만 다르다. 비교표에서 W1 우위 근거가 되지 못한다.

### 4.3 값 주입
- C.2-3 "값을 문자열로 이어 붙이지 않는다"는 **SDK를 쓸 때의 규칙**이다. 서버는 SDK를 신뢰할 수 없다. 서버가 보장해야 하는 것은 "어떤 입력이 오더라도 값은 SQL 문자열이 아니라 바인딩 파라미터로만 간다"이다. 이건 DD-01 I3(raw SQL 금지)과 같은 층이며, 와이어 문서가 서버 쪽 보장으로 쓰지 않고 *프론트 규칙*으로 쓰면 책임이 잘못 놓인다. **PRINCIPLES §4-4 "호출자가 보낸 것 중 무엇을 신뢰하고 무엇을 검증하는가"에 대한 답이 와이어 문서에 없다.**
- **필드 이름·정렬 키가 값이 되는 경우.** 이 문제의 *현 실물 증거*가 이미 아리아리에 있다. `RecruitmentRepositoryImpl.java` 50~53행은 정렬 속성명을 문자열 그대로 `pathBuilder.get(o.getProperty())`에 넣는다. W1의 `"orderBy": [{ "periodEnd": "asc" }]`에서 키 `periodEnd`가 같은 구조(필드명이 데이터)다. 필드명은 *식별자*이므로 반드시 계약의 열린 목록(sort capability)과 대조해야 하고, 값 바인딩 규칙으로는 막히지 않는다. 문서는 "값 주입"만 말하고 **식별자 주입(필드명·관계명·연산자명)** 을 말하지 않았다.
- **`$` 접두 규약.** `$today` 같은 서버 해석 토큰이 일반 문자열 값과 섞이면, 사용자 입력 문자열 `"$today"`가 토큰으로 오해되는 혼동이 생길 수 있다(NoSQL 연산자 주입류). 연산자와 리터럴 값이 같은 JSON 위치에 올 수 있는 설계(`{"gte": {"$today": true}}` vs `{"gte": "2026-10-03"}`)는 값 슬롯 안에서 *객체=연산자, 스칼라=리터럴*이라는 규칙이 필요하고, 사용자 데이터가 객체일 때(JSON 컬럼 값) 충돌한다. 확인 필요: 이 프로젝트에 JSON 컬럼 타입이 있는지.

### 4.4 캐시 키·로그
- **캐시 키.** 요청이 POST 본문이면 HTTP 캐시는 쓸 수 없다(기본). 서버 쪽 plan cache/결과 캐시(DD-01 164~166행, DD-03 층 2)의 키는 "구조 해시"여야 하고 **actor·tenant·정책 버전이 키의 일부**여야 한다(DD-03 T-I1, DD-01 층 2 "판정 결과 공유 금지"). W1의 `vars` 분리(3.2 W5)가 없으면 값이 섞인 해시가 되어 plan cache hit이 낮고 반대로 값을 뺀 해시를 쓰면 키 충돌 위험이 생긴다. 와이어 설계가 캐시 안전성의 전제다.
- **캐시 오염.** 사용자 입력이 포함된 응답을 공유 캐시(CDN)가 보관하면 다른 사용자에게 전달된다. 읽기에 GET을 도입(W7)한다면 `Vary: Authorization`, `Cache-Control: private` 규칙이 와이어 계약이 된다.
- **로그에 남는 민감 값.** E1이 "길이·가독성"을 보기 위해 W2 출력 표기를 로그에 쓰자는 서술이 있다(C.1 81행). 로그에 요청 *전체*를 남기면 `where` 값(이메일·전화번호·검색어)이 그대로 남는다. 요청 로그는 (구조 해시 + 구조의 값 마스킹판)을 정본으로 하고, 원문 로그는 개발 모드 한정이어야 한다. DD-02 164행이 "감사 연결(민감 값 가림)"을 층 2에 두었다. 같은 규칙이 요청 로그에도 있어야 하며 DD-03 60행 "canonical 해시로 추적")과 일관된다. 현재 DD-08에 규칙 없음.
- **URL이 아니라 본문**이므로 접근 로그에 값이 덜 남는다는 이점은 있다. W7(GET)을 택하면 이 이점이 사라진다. 비교에 필요한 사실.

### 4.5 CSRF·GET/POST
- PoC 클라이언트는 `Authorization: Bearer` 헤더를 쓴다(`aip.ts` 1016~1017행). 브라우저가 자동으로 붙이는 쿠키가 아니므로 전형적 CSRF에는 강하다. `http.rs`에서 쿠키·CSRF 관련 문자열은 grep 무결과(확인함). 그러나 DD-08은 *인증 전달 방식*을 정하지 않았다. 세션 쿠키로 가면 `POST /aip` 단일 진입점은 **모든 쓰기가 한 URL**이라 CSRF 방어(SameSite, Origin 검사, 커스텀 헤더 요구)를 한 곳에 몰아 걸 수 있다는 장점이 있고, 반대로 `Content-Type: text/plain`으로 단순 요청이 되어 사전 요청 없이 통과하는 경로를 막는 규칙(`application/json`만 수락)이 필요하다. 이 요건을 와이어 규칙으로 쓸 것.
- 읽기를 POST로 보내는 설계에서 *읽기도 상태를 바꾸는 요청처럼* 취급되어 CSRF 토큰이 읽기에도 필요해진다. 읽기 GET을 허용(W7)하면 반대로 URL이 로그·Referer에 노출된다. 어느 쪽이든 DD-08이 현재 선택을 *근거 없이* POST로 고정했다.
- `text/plain`·`multipart/form-data`도 받는 현재 PoC(`http.rs` 136~138행 multipart 분기)는 JSON 외 본문 형식을 이미 받는다. W1을 "정본"으로 선언해도 업로드가 있는 한 *본문 형식이 둘*이다. 이 존재가 DD-08에서 빠졌다(파일 첨부 요청의 와이어, 즉 `aip.ts` 1021~1028행 `FormData` 분기).

### 4.6 W1 보안 우위 주장의 재평가

| 주장 | 평가 |
|---|---|
| "주입 표면이 작다" | 문자열 이어 붙이기 면에서는 맞다. 식별자 주입, 연산자 토큰 혼동, 중복 키, 깊이, 크기는 W1에도 있다 |
| "스키마 검증이 쉽다" | 구문 단계에 한정 |
| "W2는 파서가 공격 표면" | 맞다. 대신 W1도 JSON 파서와 의미 검사기가 표면이다. 표면의 *크기*는 비교한 적 없음(E2 실행 후 판정) |

W1 선택을 뒤집을 정도의 약점은 아니다. 다만 "보안상 W1"을 주된 근거로 삼는 건 약하고, 진짜 근거는 **canonical 해시·검증·생태계**여야 한다.

## 5. F 질문

### 5.1 F1은 창시자 결정이 맞나

운영 규칙 F절은 "제품 철학이나 사용자 경험에 영향을 미치는 선택만 질문한다. 내부 구현 세부 사항은 근거를 제시한 뒤 기술적으로 제안한다"이다(`design-operating-rules` F절).

DD-08 자신이 F 첫 줄(122행)에서 "이 선택은 대부분 기술 판단이지만"이라고 인정했다. 그런데도 질문을 하나 남겼다. 판정:

- **전송 표현(JSON 트리 vs 문자열)은 기술 판단이다.** 근거를 제시해 제안하고 끝내야 한다. F1이 이 부분을 창시자에게 넘긴 것은 규칙 위반에 가깝다. 실제 문장도 "차이는 네트워크·로그·디버깅 도구에서 보이는 모양과 보안 검사 방식입니다"(F1 125행)라 *창시자가 답할 근거가 없는 영역*이다.
- **그러나 창시자 의도와 닿는 부분이 하나 있다.** PRINCIPLES §2 표현 방식 "자연어의 구조화·문법화"와 handoff 266~281행 "자연어로 표현하던 목적·의도를 AIP의 공식 구조나 문법으로". 호출자의 요청이 이 *문법화* 철학의 표면에 속하는지(호출자에게 AIP 문법이 보이는가)는 철학 질문일 수 있다. 다만 이 질문은 **DD-04 F1("AIP 고유 문법을 공식 작성 형식으로 남겨야 하나", DD-04 291행)과 사실상 같은 질문의 호출자 쪽 버전**이다. DD-04 F1 답이 정해지면 DD-08 F1은 (a) 같은 답을 기계적으로 적용 (b) 다르게 답할 이유를 별도로 묻기 둘 중 하나로 줄어든다.
- 따라서 F1은 **조건부 질문**으로 바꾸고 DD-04 F1 뒤로 순서를 둬야 한다. 지금 형태는 두 결정이 따로 창시자에게 도착해 모순된 답이 나올 수 있다(예: DD-04에서 "고유 문법 필수", DD-08에서 "JSON 요청").

### 5.2 비전문가가 답할 수 있나

F1 문장: "호출자 요청에도 AIP 고유 문법(사람이 읽는 질의 문장)을 쓰길 원하나요, 아니면 요청은 기계가 다루기 쉬운 구조화 데이터(JSON)로 두고 프론트에서는 SDK 함수로만 다루면 되나요?"

문제:
1. **두 선택지의 비용이 질문에 없다.** 선택지가 "원하나요 / 되나요"로 한쪽은 *선호*, 다른 쪽은 *충분성*이다. 대칭이 아니다. "원하나요"에 "아니오"는 쉽고 "예"는 비용이 크다(파서·에디터 지원·학습). 비용을 모르는 상태에서 "원한다"고 답하기 쉽다.
2. **"JSON"이 비전문가에게는 철학 후퇴처럼 보일 수 있다.** 창시자는 이미 "REST를 다른 이름으로" 경계가 있고 DD-04에서 "고유 문법을 제거하지 마라" 원문을 인용한다(DD-04 18행). JSON을 고르면 *문법이 사라진다*고 읽힐 수 있다. 실제로는 사라지지 않고 서버 정의(DD-04)에 남는다. 이 구분을 질문에 적어야 한다.
3. **AIP 사용 예시와 연결 부족.** 운영 규칙 9번("이해하기 어려운 기술 개념은 실제 AIP 사용 예시와 연결해 설명")에 따라, 화면 개발자가 *어디서* 이 차이를 마주치는지(디버깅 중 네트워크 탭에서 요청을 봤을 때 JSON 덩어리 vs 한 줄 문장)를 보여주는 두 줄 예시가 F1 밑에 있어야 한다. B.3에 예시는 있지만 F1과 연결되지 않았다.

### 5.3 제안하는 F 처리
- F1 삭제. G절에 "W1 정본, 사람용 표기는 출력으로(기술 제안)"로만 두고 근거 표를 명시.
- 단, DD-04 F1에 **한 줄 연동 조건**을 추가: "DD-04 F1에서 '예'이면 호출자 요청에도 같은 문법을 노출하는지는 DD-08에서 다시 연다."
- 이 문서가 창시자에게 새로 물을 것은 없다. 와이어 형태(전체 트리 vs 등록 ID)는 DD-03 F1(`registered-only` 기본 입장) 답에 종속되므로, DD-08은 DD-03 F1 뒤로 순서를 둔다.

## 7. 수정 제안

### P0 (확정 전 반드시)
1. **F1을 삭제하거나 DD-04 F1에 종속시킨다.** 기술 판단을 창시자에게 넘긴 상태이며 DD-04 F1과 모순 답이 나올 수 있다(5.1).
2. **범위 선언과 내용을 일치시킨다.** 제목·C.2-2는 읽기·쓰기·전이·bulk·확장·저장된 조회를 한 진입점이 받는다고 하나 예시는 읽기뿐이다. 쓰기·전이·bulk 요청의 와이어 예시를 최소 하나씩 추가하거나, C.2-2를 "읽기 조합 요청의 형식만 정하고 진입점 통합은 별도 결정"으로 낮춘다(2.1, 3.3).
3. **와이어 층 보안 규칙을 층 1 불변식으로 적는다.** 본문 크기·중첩 깊이·노드 수는 파싱 중 제한, 미지의 키 거부, 필드명·연산자 allow-list 대조, JSON 외 content-type 처리, 중복 키 거부(4.1~4.3, 4.5). 지금 보안 근거는 "W1이 표면이 작다" 한 줄이다.
4. **D표의 "REST 이름 바꾸기 금지 충족"과 이탈 방지 3번 인용(C.2-3)을 정정한다.** 와이어 형식이 아니라 DD-01·DD-02가 실질 충족이다(2.1, 6절 3번).

### P1 (추천을 유지하려면)
5. **C.1 보안 행에서 C.2-3을 W2 칸에도 적용**해 공정하게 다시 쓴다. AI 경험 행은 `확인 필요`(E3 전)로 표시(3.1).
6. **W4(등록 ID만 전송)와 W5(트리와 값 `vars` 분리)를 대안에 추가**한다. DD-03 S와의 통합이 없으면 두 문서가 서로 다른 와이어를 가정한다(2.2-2, 3.2).
7. **읽기 GET 가능성(W7)과 POST 고정 근거**를 비교 표에 넣는다. `/aip/query`·`/aip/command` 별칭이 PoC에 있었다는 사실(`http.rs` 51~52행)을 B.2에 더한다(1절 1번, 3.3).
8. **canonical 구분**: 구문 정규화(JSON 키 순서·숫자 표기)와 의미 정규화(DD-01 158행)를 구분해 W1의 이점을 정확히 쓴다(2.2-1).

## 8. 결론과 추천

**결론: W1(JSON 트리 정본)이라는 방향은 현 시점에서 합리적인 기본값이다.** 반박 의견은 방향이 아니라 **근거의 품질과 문서 범위**에 있다. 문서가 "대부분 기술 판단"이라고 쓰고도 창시자 질문을 만들었고, 보안 우위를 W2에 불공정하게 적용했으며, DD-03 S의 등록 흐름(실제 운영 와이어의 주류가 될 수 있다)과 읽기/쓰기 단일 진입점의 HTTP 비용을 다루지 않았다.

**추천:**
1. 현 상태로 창시자에게 보내지 말고 P0 4건을 반영한 v2를 만든다.
2. F1은 삭제하고 DD-04 F1·DD-03 F1 뒤에 둔다. G절은 "에이전트 기술 제안: W1 정본(미확정)"으로 쓴다.
3. 확정 문장은 쓰지 않는다. 운영 규칙에 따라 창시자가 승인하기 전에는 확정 표기 금지이고, W1은 "검증 필요"가 적절하다(E1·E2·E3 미실행).
4. 이 문서는 DD-01~07이 낸 *와이어에 영향을 주는 합의*(canonical, 등록, 위반 응답, 힌트 금지)를 한 장에 모으는 것으로 가치가 커진다. 현재는 그 통합이 약하다.
