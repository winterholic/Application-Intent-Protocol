## 2. v2의 새 문제

**새 모순: 없음.** 점검한 연결 3개: WI-3(목록 대조)와 DD-01 I5(열리지 않은 필드는 없는 것과 같은 오류), DD-03 T-I2(등록은 권한이 아님)와 W4, DD-03 F1·DD-04 F1 종속 조건. 모두 방향이 맞다.

**"창시자 질문 없음"은 정당한가: 정당하다.** 근거: 운영 규칙 F절은 철학·사용자 경험에 영향을 주는 선택만 질문하라고 한다(`design-operating-rules` F절). 전송 표현은 내부 구현이다. 철학과 닿는 부분(호출자에게 AIP 문법이 보이는가)은 DD-04 F1(DD-04 291행)에 이미 묻혀 있고, v2가 D절 123행과 F절 139행에서 조건부로 연결했다. 질문을 다시 만들 필요가 없다. 확정 표기도 없다(3행, 145행 "미결정").

**미결정 사항 임의 확정: 문제 되는 것은 없다.**
- "전송은 HTTP"(108행)는 D-P13(Accepted, DECISIONS 48행)의 재진술이다.
- "프로토콜 버전과 IR 버전 분리"(111행)는 "후보"로 표기돼 OI-P1(Open)을 확정하지 않는다.
- W5 추천은 G절 145행에서 E2·E3 전 미확정으로 표기됐다.

**과잉 설계 여부: 경미.** 대안 5개(W1·W5·W2·W4·W7)는 1라운드 요구를 따른 것이고, 비교표가 한 장에 들어 있다. 번호가 W1·W2·W4·W5·W7로 비어 있어 독자에게 어색할 뿐이다(선택적 다듬기).

**사소한 불일치(선택적 다듬기)**
- 52행 `"select": { ... }`는 유효한 JSON이 아니다. 개념 예시임을 한 줄 표시하면 된다.
- 쓰기·bulk 예시(41~43행)는 W1(값 섞임)만 있다. 추천이 W5인데 쓰기 쪽 `vars` 표기는 안 보인다. WI-4가 쓰기에도 적용되는지 한 줄이 필요하다.
- bulk 키가 `targets`(43행)인데 DD-07은 SDK 호출에서 `ids`를 쓴다(DD-07 65행). 와이어와 SDK 이름이 달라도 되지만 같은 뜻을 두 이름으로 쓰는 인상을 준다. DD-02 91행은 `id`.
- WI-3의 "계약 허용 목록"이 호출자(actor)가 볼 수 있는 계약인지 전체 계약인지 불명확하다. 전체이면 존재 노출(I5)과 어긋날 수 있다. 문서가 I5와 연결해 한 줄로 못 박으면 좋다.
- C.1 표 W7 열(83~88행)에 빈 칸이 있다.
- B.1의 `RecruitmentRepositoryImpl.java` 50~53행: 실제 파일(`ariari/ariari-backend/.../RecruitmentRepositoryImpl.java`) 49~52행이 `pathBuilder.get(o.getProperty())`로 정렬 속성을 그대로 쓴다. 한 행 차이이며 의미는 맞다.

## 3. 잔여 수정 제안

- P0: 없음.
- P1: 없음.
- P2(후속 문서로 충분):
  1. WI-3의 허용 목록 범위(actor 가시 계약)를 I5와 맞춰 한 줄 명시.
  2. 취소·멱등 키 헤더를 5행 범위 제외 목록에 한 줄 추가(제안 16의 누락분).
  3. 응답 형식 DD를 이 문서와 같은 라운드 또는 앞에 두는 순서 표기(제안 12).
  4. 쓰기·bulk 예시를 W5 표기로도 한 건 추가하거나 "쓰기에서도 vars 사용 여부는 후속"이라고 표시.

## 4. 결론

**에이전트 간 합의 도달.** 미합의 0개. 1라운드 P0·P1은 전부 반영(부분 1건은 선택적 다듬기), P2는 후속으로 넘긴 범위가 5행에 명시돼 있다. "창시자 질문 없음"은 운영 규칙 F절과 DD-04 F1·DD-03 F1 종속 조건 덕에 정당하다. 확정 표기가 없고 창시자 Open(OI-P1)을 임의로 닫지 않았다.

확인 못함: `serde_json` 재귀 한도·axum 본문 제한 기본값 등 WI-1 상한의 실제 구현 수치(v2도 값을 정하지 않아 합의에는 영향 없음). 외부 사실(GraphQL 호환)은 웹 확인을 하지 않았다.
