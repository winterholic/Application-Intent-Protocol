# AIP 1.0 지원 범위 매트릭스와 출시 차단 목록 감사

- 감사 기준: `origin/main` `723fb474ca7891180c87edfb08ed7a689e1b2001` (2026-11-18 00:41 KST, PR #15 병합). 감사일 2026-11-21. 이후 main에 새 커밋과 새 Actions 실행은 없다.
- 감사 브랜치: `release/1.0-audit-20261121`. 이 문서 하나만 추가했고 코드는 바꾸지 않았다.
- 제품 코드 기준 SHA: `a0fa27294fa9a1867fe67e9861079e256dfd0d24`. `git diff --stat a0fa2729 723fb474`는 `plan-docs/reviews/2026-11-17-1.0-cycle-results.md` 한 파일(156줄 추가)뿐이다. 그래서 a0fa2729의 CI 실행은 "같은 코드의 실행"으로 인용하되 723fb474 자체의 실행으로 세지 않는다. 723fb474 자체의 실행은 아래 5개 워크플로뿐이다.
- 이 문서는 1.0 출시 승인이 아니다. 기획 세션이 Phase 2 결함 수정을 나누기 위한 근거 목록이다.

## 0. 결론

1. **1.0 사용자 정식 경로는 `aip service`(`.aip`, spike-v1~v6 엔진을 path dependency로 쓰는 제품 조립)다.** Core `.aipoc`(aip-syntax/sema/ir/pg/runtime)는 PoC이며 `poc-runtime` feature 없이는 `run/migrate/rekey/token`이 동작하지 않는다. Core 결과를 제품 지원 근거로 쓰지 않았다.
2. 19개 후보 중 **지원 11, 조건부 7, 제외 1**이다(§4). 제외는 자동 tenant 격리다. 제품 경로 소스에 `tenant` 구현이 0건이고 Core PoC에만 있다.
3. **출시 차단 P0는 4건**이다(§8). 버전 0.1.0, 공개 count와 callerFilter의 숨은 행 노출 정책, 출시 후보 SHA에서 돌지 않은 CI, main Verify의 반복 실패(분류만)다.
4. P1은 14건이다. 대부분 문서·CI 연결·패키징 정리이며 코드 의미 변경은 count 정책 한 건에 모인다.
5. 이번 감사에서 직접 확인한 것: 제품 binary로 숨은 행 값을 `callerFilter read` count로 추정하는 재현(§6.2), 선언형 표현력 반례 7개(§7), 제품 경로 테스트 재실행(§11).

## 1. 방법과 증거 등급

| 표기 | 뜻 |
|---|---|
| 실행(이번) | 이 감사에서 723fb474 소스로 직접 실행한 명령과 출력 |
| CI(같은 코드) | `gh`로 조회한 GitHub Actions 실행. 대상 SHA와 723fb474의 코드 차이를 `git diff`로 확인한 것만 인용 |
| 코드 확인 | 소스·문서를 읽고 위치를 확인했다. 실행하지 않았다 |
| 미검증 | 확인하지 못했다. 지원 근거로 쓰지 않았다 |

과거 보고서(`2026-11-17-1.0-cycle-results.md`, `2026-11-17-core-service-semantic-matrix.md`, `product/RELEASE-GATE.md`, `product/VERIFICATION.md`)의 수치는 근거로 복사하지 않았다. 필요한 곳은 같은 Run을 `gh`로 다시 조회했다.

환경 한계: 이번 로컬 실행은 macOS arm64 Mac Studio, rustc/cargo 1.98.1, node 26.9.0, 전용 PostgreSQL 17 컨테이너(감사 전용, 고포트)다. CI는 Linux다. macOS Seatbelt와 Linux Bubblewrap 격리, 외부 IdP, 실 AWS/GCS는 이번에 실행하지 않았다.

### 6.2 노출 위험 (이번 재현, 제품 binary)

조건: 정의 작성자가 (a) 원본에 `rows read`가 있고 (b) 집계에 `where`가 없고 (c) `sourceAccess`가 넓고 (d) `callerFilter read`를 선언한다. `service_flow.rs:40-70`의 정책 fixture에 아래 한 줄을 더했다.

```
aggregate oracleCount: Int { source Vote; sourceAccess publicVotes(actor); groupKey record; callerFilter read; rowOutput none; release count }
```

실행(이번): `aip service init/serve`(PostgreSQL 17 컨테이너), 사용자 42의 토큰으로 호출.

```
Vote 읽기(rows read when owner = actor) → 보이는 행 id 1(amount 10), id 2(amount 20)
oracleCount filter amount eq -900   → {"ok":true,"rows":[1]}   # 다른 사용자(99)의 숨은 행
oracleCount filter amount eq -5000  → {"ok":true,"rows":[1]}   # 다른 조직(100)의 숨은 행
oracleCount filter amount eq -1234  → {"ok":true,"rows":[0]}   # 없는 값
```

호출자는 읽을 수 없는 행의 필드 값을 `eq` 필터로 한 값씩 확인할 수 있다. `callerFilter none`인 `publicVoteCount`(where 없음)는 필터 오라클은 없지만 숨은 행이 늘면 숫자가 바뀐다(`service_flow.rs:717` 단언 5, 숨은 행 삽입 뒤 6, `:744`). 이는 문서화된 공개 예외다.

추가로 확인한 점:
- `aip service check`(옵션 없음)는 `oracleCount` 정의를 `ok:true`, `advisories:[]`로 통과시킨다. `--dev-checks`를 줘야 경고가 나온다. 반면 `spec/definition-syntax.md`는 "생략하면 … 정의 검사에서 경고한다"고 쓰는데 `callerFilter` 생략은 경고가 아니라 `DEF.MISSING_ITEM` 오류다. 문서와 동작이 다르다(P1-2).
- `callerFilter none`이며 `where` 없는 count(`publicVoteCount`)에는 어떤 경고도 없다.
- 이 오라클은 문서화된 계약 안의 동작이다(`product/SDK.md`). 결함이 아니라 정책 결정이 필요한 위험이다.

### 6.3 호환성 영향 (저장소 안 정의 정적 스캔, 정규식 기반이라 근사치)

| 정의 | count 집계 수 | 원본에 rows read | where 없음 | callerFilter read + where 없음 |
|---|---|---|---|---|
| `porting/flaskbb/app.aip` | 4 | 4 | 0 | 0 |
| `product/tests/fixtures/facereview-mysql/facereview.aip` | 9 | 9 | 3 (`User.watchCount`, `User.commentCount`, `Video.likeCount`) | 0 |
| `spikes/spike-v1-fixture/fixture/recruitment.aip` | 1 | 1 | 1 (`Recruitment.bookmarkCount`) | 0 |

`callerFilter read`이면서 `where`가 없는 count는 저장소 정의에 없다. 기본값을 "rowRead 상속"으로 바꾸면 위 where 없는 4개(FaceReview 3, recruitment 1)의 출력이 호출자별로 줄어든다. FaceReview의 세 값은 의도적으로 넓은 `sourceAccess`를 쓴다(`product/SDK.md`). 생성 계약의 fingerprint, TS/Python 타입은 변하지 않지만 응답 값이 바뀐다.

### 6.4 대안 (정책 결정은 기획 몫)

| 대안 | 내용 | 호환 영향 | 작업 |
|---|---|---|---|
| A. 현행 유지 + 경고 강화 | advisory를 `--dev-checks` 없이 기본 출력으로. `callerFilter none`·where 없는 count에도 "공개 count" 경고 | 없음 | S |
| B. 오라클만 닫기 | rows read가 있는 원본에서 `callerFilter read`는 `where`에 같은 정책을 요구하는 것을 오류로 승격(`sema.rs:1655-1670`) | `callerFilter read`·where 없음 정의만 깨짐(저장소 0건) | S + 마이그레이션 진단 |

## 12. 반례 probe 정의

모두 아래 머리말을 공유한다. 파일은 저장소에 두지 않았다.

```
resource Member { fields { id: Id; score: Int; flag: Bool; name: Text } rows read when id = actor.id }
actor Member
```

| 이름 | 추가 정의 | 결과 |
|---|---|---|
| p_effect_ok | `resource Post {… transition fin { from done = false; to done = true; allow author = actor; update Member where id = author { score = 5 } } }` | ok |
| p_effect_arith | 위에서 `score = score + 1` | `DEF.PARSE_EXPECTED 이름 필요, + 발견` |
| p_effect_semicolon / comma | 효과 `{ score = 5; flag = true }` / `{ score = 5, flag = true }` | ok / `DEF.PARSE_EXPECTED` |
| p_to_semicolon / comma | `to done = true; views = views + 1` / `to done = true, views = views + 1` | `DEF.PARSE_UNKNOWN_KEY views` / ok |
| p_to_arith_by_field | `to views = views + bonus` | `DEF.ARITH_NOT_ALLOWED` |
| p_avg | `release avg(views)` | `DEF.UNSUPPORTED` |
| p_sum_decimal | `Decimal(10,2)` 필드에 `release sum(price)` | `DEF.TYPE_MISMATCH` (추가로 내 probe의 `groupKey`도 오류이나 sum 거부는 독립) |
