## 2. v2의 새 모순·과잉 설계·임의 확정

### 2.1 T-I1은 그대로는 성립하지 않는다

T-I1은 개발·빌드·운영과 두 입장 정책에서 “같은 요청은 같은 결과와 같은 오류 코드”를 요구한다(`DD-03 v2:80`). 그러나 같은 문서가 빌드는 구조 검사와 prewarm만 하고 실제 actor·최신 정책이 없다고 전제한다(`:13-15`). 빌드는 데이터 결과를 내지 않으며, 개발과 운영은 데이터·시각·actor·tenant·정책 버전이 다르면 결과가 달라지는 것이 정상이다. 따라서 현재 문장은 관찰 가능하지만 **잘못 정의된 성질**이고 A절과 모순된다.

보장해야 할 것은 다음이다.

> 동일한 canonical 요청, actor·tenant, 데이터 스냅샷, capability·정책·스키마 버전, 자원 한도에서 runtime과 registered-only는 같은 결과·오류를 낸다. 빌드·개발 도구의 구조 판정은 운영의 같은 구조 판정과 일치하며, 실행 시점에만 알 수 있는 권한·데이터·비용 판정을 성공으로 가장하지 않는다.

### 2.2 T-I1~T-I5의 “관찰 가능한 성질” 여부

| 조건 | 판정 |
|---|---|
| T-I1 | **부분.** 비교 맥락을 고정하면 관찰 가능하지만, 현재의 무조건적 “같은 결과”는 시간·데이터·actor 차이를 무시하고 빌드가 실행 결과를 낸다고 읽힌다(`:80`). |
| T-I2 | **대체로 관찰 가능.** 등록 ID만으로 권한이 생기지 않고 현재 actor·tenant·정책 변화가 다음 실행에 반영되는지는 시험할 수 있다. 다만 “정책 판정 결과를 굳혀 재사용하지 않는다”는 내부 구현 금지문이므로, “정책 변경 뒤 같은 ID도 새 판정에 따라 거부된다”라는 외부 성질로 바꾸면 더 정확하다(`:81`). |
| T-I3 | **관찰 가능.** 미승인 주체의 등록·활성화 거부와 앱·환경·연산·capability·스키마 간 ID 치환 거부로 시험할 수 있다. “결박”은 구현을 암시하지만 요구되는 거부 행위가 충분히 명확하다(`:82`). 서명 형식을 층 2로 둔 것도 적절하다(`:86`). |
| T-I4 | **부분이며 내부 모순.** 정책·capability 축소가 다음 입장에 반영되고 stale 오류가 나는 것은 관찰 가능하다. 그러나 제목의 “즉시”와 같은 문장의 “유예 기간”은 범위를 구분하지 않으면 충돌한다. 최대 보존 기간은 안전 불변식보다 rollout 운영 정책/수단이다(`:83`). |
| T-I5 | **관찰 가능.** 클라이언트가 헤더·파라미터를 바꿔 registered-only를 우회하지 못하는지 시험할 수 있다(`:84`). |

T-I4는 두 층으로 나누는 편이 맞다. **층 1:** 권한·정책·capability가 축소된 등록분은 다음 입장부터 유예 없이 거부한다. **층 2:** 아직 현재 계약과 호환되는 구 프론트 등록분을 얼마나 공존시킬지, 최대 보존·롤백 절차를 운영 정책으로 정한다. 보안 폐기와 호환성 유예는 같은 대상이 아니다.

### 2.3 PART V 과잉 설계 여부

v2는 과잉 설계 위험을 충분히 낮췄다. S는 런타임 파이프라인에서 시작하고 등록 체계는 선택했을 때만 추가하며(`:44-49`, `:98`), 정적 추출과 서명 형식·cache 세부도 층 2로 내렸다(`:86`). 등록 기능을 실제로 선택한다면 T-I2~T-I5는 장식이 아니라 권한 우회와 운영 실패를 막는 최소 계약이다. 다만 T-I2~T-I4의 내부 수단 표현을 관찰 결과로 정리하고, 등록 기능을 쓰지 않는 R에는 해당 조건이 공집합임을 적으면 PART V와 더 선명하게 맞는다.

### 2.4 미결정 사항 임의 확정 여부

**없다.** 문서는 S를 에이전트 추천으로 표시하고 기본 입장 정책은 E1·E3 및 F1 뒤로 미뤘으며(`:115-126`), 작성 방식도 DD-04 이후 확인 필요로 둔다(`:30-32`, `:138`). DD-01의 변경도 “대체 검토 중”이라고만 썼다(`DD-01:113-114`). 창시자 결정을 몰래 확정한 것으로 보이지 않는다.

## 3. F1 최종 검토

F1은 **비전문가 창시자가 답할 수 있는 제품 선택**으로 거의 충분하다. A는 화면 변경 때 등록 목록도 함께 배포되는 비용을, B는 처음 보는 요청도 받되 매번 검사하는 차이를 설명하고(`DD-03 v2:115-118`), 호출자 범위와 별개라는 점도 사례로 풀었다(`:118-120`). Manifest 형식이나 cache 같은 내부 구현은 묻지 않는다.

다만 B의 “서버 계약”은 앞 문서를 읽지 않은 사람에게 추상적이다. 다음 한 문장만 다듬으면 된다.

> **B. 서버가 허용한 데이터·조건·정렬 범위 안이면, 배포 때 등록하지 않은 새 요청 모양도 운영 중 받아 줍니다.** 별도 등록 배포는 없지만 서버가 매번 요청 구조·권한·비용을 검사합니다.

또한 선택 시점은 현재 문서처럼 E1·E3 이후로 유지해야 한다. 이것은 F1을 기술팀에 넘기는 것이 아니라, 창시자가 실제 추가 작업과 보안 차이를 보고 제품 기본값을 고르게 하는 순서다.

## 4. 잔여 수정 제안

### P0

1. **C.4 T-I1:** 무조건적인 “같은 요청은 같은 결과”를 §2.1의 통제된 동일 맥락 조건으로 바꾸고, 빌드는 실행 결과가 아니라 구조 판정의 동등성만 보장한다고 분리한다.

### P1

2. **C.4 T-I4:** 보안 축소의 즉시 폐기와 호환 가능한 구 프론트의 rollout 유예를 분리한다. 전자는 층 1, 최대 보존 기간·롤백·공존은 층 2로 옮긴다.
3. **B.1·C.4 또는 E:** 1라운드 제안 5의 남은 부분인 CI/로컬 production-parity 검사를 한 문장으로 명시한다. 로컬 즉시 실행과 별도로 배포 전 같은 canonical 구조 판정·등록 적격성 검사를 수행해야 한다.

### P2

4. **C.4 T-I2:** “정책 판정 결과를 굳혀 재사용하지 않는다”를 “actor·tenant·현재 정책이 달라지면 같은 등록 ID도 새 판정 결과를 낸다”라는 관찰 가능한 문장으로 바꾼다.
5. **C.4 도입문:** T-I2~T-I4는 등록 기능이 켜진 경우에만 적용되고, R에서는 공집합임을 밝힌다.
6. **F1 B:** “서버 계약”을 “서버가 허용한 데이터·조건·정렬 범위”로 풀어 쓴다.

## 5. 결론과 합의 상태

**미합의 2개.** 남은 이견은 다음과 같다.

1. T-I1이 빌드·개발·운영의 데이터·actor·정책 맥락을 고정하지 않은 채 같은 결과를 요구해 A절과 모순한다.
2. T-I4가 보안상 즉시 폐기와 호환 rollout 유예·최대 보존이라는 다른 층의 요구를 한 불변식에 섞었다.

그 밖의 핵심 방향에는 합의했다. 단일 canonical 런타임 파이프라인, 선택적 명시 등록/prewarm, registered-only를 입장 정책으로만 취급, 등록과 권한의 분리, S 추천, F1 전 E1·E3 검증은 1라운드 비판과 일치한다. 위 두 문장을 바로잡으면 에이전트 간 합의 도달로 판단할 수 있다.

### 선택적 다듬기

- T-I2를 내부 구현 금지보다 외부 관찰 결과로 쓴다.
- T-I2~T-I4의 조건부 적용 범위를 밝힌다.
- F1 B의 “서버 계약”을 일상어로 풀어 쓴다.
