# 신규 리소스 참조 마이그레이션 순서

> 상태: 이미 허용된 `Ref<T>` 정의의 마이그레이션 실행 순서 보완. 상호 `Ref<T>` 순환의 DDL 지원은 별도 과제로 남긴다.

기존 `Member`에 nullable `team: Team?`을 추가하면서 새 `Team` 리소스를 정의하면 V1 facts와 V2 전체 DDL은 생성된다. 제품 마이그레이션은 기존 테이블의 `ADD COLUMN team_id bigint REFERENCES team(id)`을 새 `Team`의 `CREATE TABLE`보다 먼저 실행해 실패한다. 새 리소스 생성은 전체 DDL의 참조 의존 순서를 이미 갖고 있으므로, 계획 단계에서 그 순서를 보존한 채 기존 테이블 변경보다 먼저 놓는다.

## 설계 관문

1. **원칙:** 성공한 선언의 배포 실행을 완성한다. 참조 관계의 의미나 접근 권한은 바꾸지 않는다.
2. **표현 범위:** 기존 테이블이 새 리소스를 참조하는 비순환 `Ref<T>` 변경과 새 리소스 간 비순환 참조 연쇄를 다룬다. 순환 참조는 현재 V2 DDL이 거부하므로 이번 범위 밖이다.
3. **서버 작성량:** 테이블 생성과 열 추가의 순서만 자동으로 조정한다. 사용자 migration 지시를 새로 요구하지 않는다.
4. **최종 권한과 신뢰:** FK 생성과 기존 데이터 검증은 PostgreSQL이 계속 강제한다. 실패하면 기존 apply 트랜잭션이 전부 롤백된다.
5. **생태계:** facts, SQL 스키마, 클라이언트 wire, 승인 digest 형식은 유지한다. 변경된 단계 순서는 새 계획 digest에 반영된다.
6. **중복 표현:** `Ref<T>`를 별도 타입이나 임시 관계로 표현하지 않는다. 기존 V2 생성 DDL의 순서를 사용한다.
7. **수단과 목적:** 제품 `derive`에서 새 `CREATE TABLE` 단계를 기존 테이블의 `ADD COLUMN` 및 FK 추가보다 앞에 배치한다. 오래된 제약 삭제, 새 부가 객체 생성, 삭제 테이블의 역순 처리 규칙은 유지한다.
8. **OPEN:** 실제 상호 FK 순환과 두 단계 DDL은 여기서 결정하지 않는다. 기본값·임의 CRUD 범위도 넓히지 않는다.

## 검증 표면

- 기존 행이 있는 `Member`에 새 nullable `Team` 참조를 추가하면 계획은 승인 필요로 표시되며, 적용 후 기존 행의 값은 NULL이다.
- 새 `Organization` → 새 `Team` → 기존 `Member`의 참조 연쇄는 대상 테이블을 먼저 생성한다. 유효한 참조 대입은 성공하고 없는 대상은 FK 오류를 낸다.
- 존재하지 않는 대상 ID로 backfill하는 계획을 적용하면 트랜잭션이 실패하고 새 테이블·열·metadata가 모두 이전 상태로 남는다.
