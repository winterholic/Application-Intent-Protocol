# Bounded update effects 검토

> 상태: 제품 사양 확정이 아닌 구현 검토. 기존 전이 효과 `update`의 기본 정확히 한 행 의미를 유지하면서, 서버가 선언한 효과 하나가 제한된 여러 자식 행을 바꾸는 후보를 평가한다.
> 기준: `docs/PRINCIPLES.md` §4, `plan-docs/decisions/DD-02-write-scope.md` C.3 W-I4~W-I9, W2(서버 정의 전이 효과).

## 제안 범위

InvenTree 주문 취소처럼 한 주문 전이가 여러 `Allocation` 행을 같은 목표 상태로 바꾸는 실용 패턴을 표현한다. 후보 A 문법은 다음과 같다.

```aip
update many Allocation maxRows 100 where order = this.id and status = ACTIVE {
  status = RELEASED
}
```

후보 H-map은 다음과 같다.

```json
{
  "update": "Allocation",
  "many": true,
  "maxRows": 100,
  "where": { "order": "this.id", "status": "ACTIVE" },
  "values": { "status": "RELEASED" }
}
```

`many`는 기존 update를 넓히는 명시 표식이며 기존 효과는 계속 대상별 정확히 한 행을 요구한다. `maxRows`는 효과 호출 전체에 대한 상한이고 부모별 상한이 아니다. 후보 범위는 1..1000이며, 1000은 현재 실행 상한 계열을 따른 임시 상한으로 사양 확정값이 아니다. 일치 행 0개는 성공으로 본다. 전체 선택 행 수가 상한을 넘으면 어떤 행도 바꾸지 않고 효과 전체를 거부한다.

다중 행 효과의 범위는 대상의 non-null `Ref<Source>` 필드가 현재 전이 대상 `this.id`와 같은 조건을 반드시 포함해야 한다. 해당 부모 참조는 효과에서 바꿀 수 없고, many 효과를 가진 전이는 부모 `id`를 바꿀 수 없다. 따라서 호출자가 제공하는 필터나 추가 대상 선택은 없다. 효과는 서버 선언에만 있고, W2 의미에 따라 대상 자식의 `rowRead`를 새로 적용하지 않는다. 부모 접근 정책은 전이의 기존 판정에 그대로 적용한다.

## 설계 관문

1. **원칙:** §2의 1·2·4·6·7을 돕는다. 반복적인 업무 동작을 서버에 한 번 선언하고 프론트에서 표현하게 하며, 실행 권한·범위·비용은 서버가 가진다. 더 넓은 쓰기 표면과 잠금 복잡도는 긴장 요소다.
2. **표현 범위:** 하나의 부모 전이에서 여러 관련 자식 행을 갱신할 수 있어 넓어진다. 대상은 서버 선언의 비-null 부모 참조와 조건으로 제한되고 `maxRows`를 넘길 수 없다.
3. **서버 작성량:** 화면별 API·반복 전이를 줄일 수 있다. 서버 작성자는 자식 변경 규칙과 상한을 선언해야 하므로 계약 자체가 사라지지는 않는다.
4. **최종 권한과 신뢰:** 서버 정의의 테이블·조건·대입·부모 참조·상한만 신뢰한다. 호출자 입력에는 기존 부모 전이 대상만 있고 임의 자식 ID, SQL, 순서, 잠금 힌트가 없다. 컴파일러는 Ref 타입·null 불가·필드·값 타입·범위를 검증하고 런타임은 실제 선택 수와 최종 DB 제약·불변식을 확인한다.
5. **확장 생태계:** A 문법과 H-map이 같은 AST/의미 경로를 사용한다. 런타임 계약을 JS/TS·Python SDK에 노출할 필요는 없으며 SDK 호출 모양은 변경하지 않는다.
6. **중복 표현:** 새 임의 bulk API나 호출자 지정 child IDs를 추가하지 않는다. 현재 `update`는 exact-one, 명시적인 `update many ... maxRows ...`만 bounded-many를 뜻하게 해 기본 동작의 암묵적 변화를 피한다. A/H-map parity는 사실 JSON으로 검증한다.
7. **수단과 목적:** AST/H-map/SQL은 동일한 서버 효과를 안전하게 실행하는 구현 수단이다. 목표는 주문 취소 같은 단일 업무 전이의 관련 행 동기 갱신이며 별도 bulk 프레임워크가 아니다.
8. **OPEN 확인:** 이 후보는 W-I4의 고정 최대 대상 수와 W-I5/W-I6의 서버 최종 검사·실행 계획에 맞춘다. 다만 정확한 상한값 및 기존 트랜잭션의 성공 단위 질문(T11)은 확정하지 않는다. 효과 하나의 상한 초과는 실행 전 전체 거부로 제안하며 항목별 성공·부분 처리는 도입하지 않는다. 새 public write API, CRUD 조합, HTTP 응답 형식은 바꾸지 않는다.

## 동시성 및 실패 경계

단일 apply와 compose 초기 판정은 부모 행을 ID 오름차순으로 잠그고, 잠금 뒤 별도 READ COMMITTED 문장에서 조건에 맞는 자식 후보를 ID 오름차순으로 잠근다. 실제 자식 수는 `maxRows + 1`까지 확인해 초과를 감지하고, 초과 시 전체 트랜잭션을 rollback한다. 갱신은 잠근 ID 집합으로 제한하고 조건을 재평가한다. 여러 부모를 함께 변경해도 전역 상한은 합산된 선택 행 수에 적용한다. W0 bundle의 여러 연산은 요청 순서로 실행하므로 bundle 전체의 잠금 순서까지 정렬하는 보장은 하지 않는다. 교착 시 기존 DB 오류·rollback 경계를 따른다.

자식의 non-null FK는 부모 `FOR UPDATE`와 삽입의 FK `FOR KEY SHARE`가 충돌한다. 부모 잠금 후 별도 READ COMMITTED 문장을 사용하면 먼저 커밋한 삽입은 새 스냅샷에서 보이고, 후속 삽입은 부모 잠금 뒤 진행한다. 자식의 부모 참조 변경도 해당 자식 잠금과 최종 조건 재평가를 거쳐야 한다. 효과 결과가 포함된 전이의 `run_checks`는 동일 트랜잭션에서 자식 갱신까지 검사해야 한다.

정책 정보 누설을 막기 위해 대상 미발견·중복·상한 초과 등 내부 이유를 외부 오류에서 구분하지 않고 기존 exact-one 효과의 opaque 오류 수준을 따른다. DB check/invariant 실패는 기존 안정 오류 정책에 따라 전체 rollback한다. 확장 효과는 기존 W-I10 통제를 그대로 따른다.

## 검증 계획

- A 문법 및 H-map이 같은 facts를 만들고 기존 exact-one facts는 변하지 않는지 확인한다.
- 거부: `many` 누락/중복, 0·1001 상한, 대상의 nullable 또는 잘못된 Ref, 부모 범위 조건 누락, 상수/actor/호출자 자식 ID 범위 확장, 미지원 필드·타입을 검사한다.
- PostgreSQL에서 0개와 2개 대상이 성공하고, 지정한 부모 범위만 바뀌는지 확인한다.
- 여러 부모에 걸친 총 대상 수가 상한을 초과하면 전부 rollback되는지 확인한다.
- 업데이트된 자식의 check/invariant 실패가 부모 전이까지 되돌리는지 확인한다.
- 경쟁 부모/자식 삽입 및 자식 부모 이동을 대상으로 FK 잠금·별도 READ COMMITTED 조회의 범위 보장을 실제 DB로 검증한다.
- 기존 단일 update 효과의 exact-one 성공/0개/중복 동작과 facts·DDL·HTTP 응답 모양을 회귀 검사한다.

제품의 공통 parser/sema와 v3 실행 경로에서 후보를 구현했다. 다섯 작성 형식 parity, H-map 모호한 상한 거부, 기존 exact-one facts 보존, 부모 ID 변경 거부를 검사한다. 실제 PostgreSQL 시나리오는 0개·2개·상한 3개 성공, 다중 부모의 총 4개 거부, 부모 권한 거부, 자식 check·정원 invariant 실패, 선행 notify 효과 rollback, 오래된 취소 재시도, 선행 삽입의 FK 경합, 자식이 범위 밖으로 이동할 때 조건 재검사, 잠긴 부모로 들어오는 이동의 FK 대기를 포함한다. W0 bundle은 후속 효과 실패가 선행 부모·자식·outbox 변경을 되돌리는지 검사하고, W1 compose는 합산 상한 초과 거부와 단일 부모 성공을 검사한다. 결과가 새 문법 표준이나 최종 상한 결정을 뜻하지 않는다.
