## 2. 문제

지금 PoC에서는 화면이 새 데이터를 원하면 서버 정의에 query를 추가해야 한다. 이것은 Java 컨트롤러를 `.aip` 한 블록으로 바꾼 것일 뿐, "매번 API를 추가하지 않는다"는 목적을 이루지 못한다.

반대로 호출자에게 아무 요청이나 허용하면 권한 우회, 정보 유출, 비용 공격의 문이 열린다. 원문의 답은 "요청의 자유와 실행 권한을 분리한다"이다. 이 문서는 그 분리를 구체적인 경계로 바꾼다.

## 3. 어떤 선택지든 지켜야 할 불변식 `[추천]`

1. 서버는 모든 요청을 매번 정책(허용, 행 가시성, 필드 가시성, 테넌트, 상태)으로 판단한다. 호출자가 보낸 권한 규칙이나 실행 계획은 신뢰하지 않는다.
2. 호출자는 읽을 수 없는 필드로 필터, 정렬, 집계도 할 수 없다. 결과에 안 나와도 조건으로 쓰면 값이 샌다.
3. 실행 전에 비용 상한(깊이, 행 수, 조인 수, 시간, 결과 크기)을 검사한다. 상한은 서버가 정한다.
4. 노출은 기본 거부. 서버가 열지 않은 리소스, 필드, 관계, 동작은 요청할 수 없다.
5. 원시 SQL과 임의 코드는 호출자 요청에 들어갈 수 없다.
6. 같은 의도는 같은 요청 형식으로 쓴다.
7. 거부와 부재를 구분해 존재를 노출하지 않는다(보이지 않는 행은 "없음"으로 응답).
8. 조합된 쓰기가 비즈니스 불변식(상태 전이, 제약, 수량)을 깨지 못한다. 불변식은 DB와 런타임이 강제한다.

원문 PART I §2 보안 원칙 8개와의 대응은 T07 §2.

## 4. 원문의 세 안

| 안 | 내용 |
|---|---|
| A | 읽기는 조합 가능, 쓰기는 사전 선언된 Command만 |
| B | 읽기와 단순 쓰기를 모두 정책 안에서 조합 가능 |
| C | 더 일반적인 Intent 기반 실행 모델. 안전한 의미 체계와 실행 제한을 둔다. 자연어 추론 엔진이나 무제한 명령 실행이 아니다 |

C는 아직 형태가 없다. 아래 §5에서 C를 구체화한 후보 하나(C1)를 만들어 비교하지만, 이것이 창시자가 말한 C인지는 확인이 필요하다(질문 Q1-b).

### C1 후보 (에이전트 구체화, 확인 필요)
호출자가 한 Intent 안에 "읽기 조합 + 쓰기 동작 여러 개 + 동작 사이의 값 전달"을 담는다. 각 쓰기 동작은 리소스 정책이나 선언 Command 중 하나에 대응해야 하고, 서버가 묶음 전체를 한 트랜잭션 경계와 비용 상한 안에서 검증·실행한다. 동작의 종류는 서버가 열어 둔 것으로 닫혀 있다.

## 5. 비교 (원문의 8개 축)

| 축 | A | B | C1 |
|---|---|---|---|
| 철학 정합성 | 읽기 쪽 "매번 API 추가"를 대부분 없앤다. 쓰기는 여전히 선언 위주 | 단순 쓰기까지 서버 추가 없이. 작동 모델에 더 가깝다 | 호출자 표현이 가장 넓다 |
| 서버 작성량 | 리소스·정책 + 모든 쓰기 Command | 리소스·정책(쓰기 정책 포함) + 복잡한 쓰기 Command | B와 비슷하거나 적다. 대신 경계 정의가 늘 수 있다 |
| 보안 위험 | 읽기 조합의 정보 유출·비용 공격 | A + 쓰기 정책 구멍(필드 단위 쓰기 권한, 상태 조건 누락) | B + 트랜잭션 경계와 동작 순서를 호출자가 사실상 설계. "실행 권한 분리"와 긴장 |
| 비즈니스 규칙 | Command 안에 모인다. 찾기 쉽다 | 규칙이 정책과 Command로 나뉜다. 정책 표현력이 부족하면 규칙이 새는 곳이 된다 | 규칙이 호출자 쪽 조합에 흩어질 위험. 서버가 강제하는 불변식만 남는다 |
| 구현 난이도 | 런타임 읽기 계획기 + 비용 상한 | A + 쓰기 정책 평가기 | B + 다단계 실행·값 전달·부분 실패 의미 |
| 확장성 | 쓰기 요구가 늘면 Command가 쌓인다 | 단순 쓰기는 늘어도 서버 무변경 | 가장 넓다 |
| 디버깅 | 쓰기는 이름으로 추적 쉬움. 읽기는 계획 출력 필요 | 쓰기도 계획 출력 필요 | 묶음 단위 추적 필요. 가장 어렵다 |
| AI 작성 편의 | 쓰기 때마다 "Command를 추가할까"를 판단 | 대부분 판단 불필요. "정책으로 되나 Command가 필요한가" 경계 규칙이 명확해야 한다 | 표현 자유가 커서 같은 의도를 여러 모양으로 쓸 위험(관문 6) |

### 읽기 경로의 실행 시점 (A·B·C 공통 하위 결정)

| 선택지 | 내용 | 장점 | 단점 |
|---|---|---|---|
| R-런타임 | 런타임이 요청마다 검증·계획·실행 | 동적 호출자(AI 에이전트, 서드파티) 지원 | 실행 SQL을 미리 볼 수 없다. 비용 공격 표면이 넓다 |
| R-빌드 승인 | 빌드가 프론트 코드의 조합 요청을 추출해 계약 범위 검사 후 승인 목록 생성. 운영은 승인된 요청만 실행 | 실행 계획을 미리 고정·검토 가능(지난 PoC의 SQL 사전 고정 자산 재사용) | 빌드 도구가 프론트 코드를 이해해야 한다. 배포 절차가 하나 는다 |
| R-혼합 | 같은 요청 형식. 개발 중엔 런타임, 운영 기본은 빌드 승인, 동적 호출자는 별도 경로 | 둘의 장점 | 경로가 둘이라 같은 요청이 다르게 동작할 위험. 차이를 시험으로 막아야 한다 |

이 하위 결정은 옛 OI-C2(SQL 컴파일 시점 고정)와 같은 문제다.

## 6. 선언 Intent와 조합 Intent가 공존할 때의 규칙 `[추천]`

관문 6(한 의도 한 표현)을 지키려면 둘의 역할이 겹치지 않아야 한다.

- 조합 Intent로 표현할 수 있는 읽기는 선언 query로 따로 만들지 않는다. 선언 query는 "재사용 이름이 필요한 조합"의 별칭일 뿐, 다른 의미를 갖지 않는다.
- 선언 Command는 정책만으로 표현할 수 없는 규칙(여러 리소스에 걸친 불변식, 외부 효과, 상태 기계)이 있을 때만 만든다. 이 기준을 기계로 판정할 수 있는지가 B안의 성패다.

## 7. 결정 전 검증 실험 `[추천]`

1. 아리아리 프론트 API 호출 약 115곳과 백엔드 엔드포인트 159개를 하나씩 대응시킨다.
2. 각 호출을 A, B, C1에서 "서버 추가 없음 / 정책 추가 / Command 추가 / 확장 필요"로 분류한다.
3. 안마다 서버 추가량(지표 S1)을 집계한다.
4. §3 불변식을 깨려는 요청 예를 안마다 만들어 막히는지 따진다(T07 위협 모델).
5. 결과표를 창시자에게 낸다.

코드 변경이 없는 작업이라 승인 없이 할 수 있다(`../00-rules.md` §6). 단 착수 여부는 창시자에게 묻는다.

## 8. 현재 판단

`[추천 보류]` 감사 보고서는 A를 추천했지만 10-03 원문이 그것을 "창시자 결정이 아니다"라고 명시했다. 실험(§7) 전에는 추천하지 않는다. 지금 말할 수 있는 것은 하나다. 지난 PoC의 `expose`(생성·수정·삭제 + 정책 + 필드 목록)는 B의 씨앗이고, 서버 권한 층은 세 안 모두에서 재사용된다.
