# T08. 공통 의미 모델 (Canonical Typed IR)

> **2026-10-03 기준 정본:** [창시자 통합 지침](../sources/founder-integrated-directive-2026-10-03.md)과 [B 결정 상태 재분류](../alignment/B-decision-reclassification.md)가 우선한다. 아래 초안·후보·미정·자료 요청은 이전 기준의 기록이며 전체 승인으로 보지 않는다. 이전 기준의 질문이 B에서 해결·대체된 경우 재질문하지 않는다.
> 이전 기준의 초안 상태: v0 (2026-10-03). 기준 원문: PART II §9.4, PART V, 의제 2. 당시 검토 대상으로 표시했고 T01~T03 뒤 결론을 내리기로 했으며, 현재 처리 상태는 B를 따른다.
> **관련 기술 기록:** `../decisions/DD-04-authoring-model.md` — 기존 리뷰는 이전 지침의 검토 이력이다. 현재 결정 상태는 [B](../alignment/B-decision-reclassification.md)를 따른다.

## 1. 설계 관문 (원문 PART V의 여섯 질문으로 답한다)

| 질문 | 현재 답 |
|---|---|
| 왜 필요한가 | 작성 방식(T02)이 여럿이거나, 정의와 호출 요청을 같은 검증기로 다뤄야 할 때 의미를 한 곳에 모은다 |
| 호출자 중심 실행에 어떤 도움 | 조합 Intent를 서버가 받으면 "요청 → 의미 표현 → 정책 검사 → 계획"의 중간 표현이 필요하다. 정의와 요청이 같은 타입 체계를 쓰면 검사가 단순해진다 |
| 보안 통제에 어떤 도움 | 정책 평가와 비용 검사를 작성 방식이나 요청 형식과 무관하게 한 곳에서 한다 |
| JS/Python과 어떻게 연결 | TS/Python 정의가 이 표현을 만든다(B·C안). JSON 직렬화로 언어 경계를 넘는다 |
| 없으면 무엇이 실제 문제 | 작성 방식이 하나(TS)이고 요청 형식이 단순하면, 엔진이 정의를 직접 읽어도 된다. 그때는 별도 IR이 과할 수 있다 |
| 더 단순한 대안 | 정의 스키마(JSON Schema 수준) + 요청 스키마만 두고 내부 표현은 엔진 구현 세부로 숨긴다 |

결론 `[추천 보류]`: IR의 필요성은 T02(작성 방식 수)와 T01(조합 요청 유무)이 정한다. 지금 IR 설계를 먼저 하면 지난번처럼 수단이 앞선다.

## 2. 원문의 제약

- 공통 내부 표현으로 정규화하는 방향은 논의했지만 구조와 역할은 미확정.
- IR을 쓴다는 이유로 AIP를 범용 언어나 컴파일러 프로젝트로 만들지 않는다.
- 단일 Canonical IR + 목적별 파생 모델을 제안했지만 확정하지 않았다.

## 3. 다룰 항목 (원문 의제 2)

타입 정보 / 실행 의미 / 정책과 부작용 / 기본값의 정규화 / JS/Python 연결 / Runtime이 쓰는 정보 / 통신 계약과의 관계 / AI가 탐색할 메타데이터 / 버전 관리.

## 4. 기존 자산

`crates/aip-ir`: 위치 정보 없는 언어 독립 표현, 결정적 JSON과 digest, 검증(validate), 의미 규칙(analyze), diff, 진단 코드 레지스트리. IR JSON만으로 같은 진단이 나오는 테스트가 있다(감사 보고). 지금 IR은 "선언 Intent 정의"만 담고, 호출자 요청은 담지 않는다. 조합 Intent를 다루려면 요청 쪽 표현이 추가되거나 별도로 필요하다.

## 5. 결정 순서

1. T01, T02 결정
2. 위 여섯 질문을 다시 답한다
3. 필요하면 범위를 정한다(정의만 / 정의 + 요청 / 계약 파생까지)
4. 기존 `aip-ir` 처분(D8)
