## 2. 원문의 정의

통합 지침 §2 원칙 6의 책임 구분을 기준으로 한다.

| 영역 | 역할 |
|---|---|
| Specification | 서버 측 데이터 모델, 허용 범위, 권한, 정책, 업무 규칙, 확장 계약 등을 정의 |
| Presentation | 프론트엔드가 필요한 데이터와 동작을 AIP 문법으로 표현 |
| Runtime | 요청을 검증하고 정책에 따라 안전하게 실행 |

SPR은 책임을 이해하기 위한 개념 모델이다. 구체 패키지 구성이나 내부 구현을 SPR 이름만으로 고정하지 않는다. 공개 가능한 계약과 내부 정책을 구분해야 하며 공개 범위·타입/권한 노출은 기술 검증 대상으로 남는다(B Q6, T06).

흐름: Presentation → Application Intent Protocol → Specification 기반 검증 → Runtime 실행 → 결과 반환.

## 3. MVC와 무엇이 다른가 `[추천 초안]`

| | MVC | SPR |
|---|---|---|
| 나누는 기준 | 코드의 역할(화면, 흐름, 데이터) | 누가 무엇을 결정하나(무엇을 원하나 / 무엇이 허용되나 / 어떻게 실행하나) |
| 화면이 새 데이터를 원할 때 | Controller와 Model 쪽 코드 추가 | Presentation이 표현. Specification이 이미 허용하면 서버 변경 없음 |
| 권한 | Controller·Service 코드에 흩어짐 | Specification에 선언, Runtime이 강제 |

SPR이 실질적인 역할을 하는지 보는 시험: "새 화면 추가 시 S가 바뀌지 않는 경우가 대부분인가". 지난 PoC에서는 S가 매번 바뀐다. 이것이 감사가 "구조는 일치, 역할은 불일치"로 본 이유다.

## 4. 공개 계약의 기술 검증 항목 (이전 초안 질문의 현재 처리)

아래는 창시자에게 중복 질문할 목록이 아니라 통합 지침과 B에서 기술 검증으로 분류한 공개 계약 세부다.

| 질문 | 선택지 | 메모 |
|---|---|---|
| Specification은 서버에만 있나 | (a) 서버만 / (b) 공개 계약 부분을 클라이언트와 공유 / (c) 전체 공유 | (b)가 타입 있는 호출의 전제. 무엇이 공개되나는 T06의 공개 계약 범위와 같은 문제(옛 OI-P3) |
| 클라이언트와 어떤 정보를 공유하나 | 리소스·필드·관계 이름과 타입 / 정책의 존재 여부 / 비용 상한 / 오류 코드 | 정책 내용은 공유하지 않는 것이 기본 후보. 공유하면 공격자에게 지도를 준다 |
| 계약 배포와 버전 | 빌드 산출물 / 런타임 발견(introspection) / 둘 다 | T06, T01 §5 실행 시점 결정과 묶임 |
