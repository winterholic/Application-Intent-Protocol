## 2. Query Planner (의제 7)

T01이 조합 읽기를 허용하면 플래너가 새로 필요하다. 지금 PoC는 컴파일 시점에 SQL을 고정하고 비용 기반 계획이 없다.

| 항목 | 설계 질문 | 초안 |
|---|---|---|
| 해석 | 호출자 요청을 무엇으로 받나 | T06 요청 형식 → 내부 표현(T08) |
| 관계 탐색 | 중첩 관계를 어떻게 SQL로 | 조인 / 관계별 배치 조회(N+1 방지) / JSON 집계 중 선택 `[미정]` |
| 필터·정렬 | 허용 연산자, 인덱스 요구 | 노출 필드만, 인덱스 없는 큰 테이블 정렬은 거부 후보 |
| 페이지 | keyset / offset | PoC는 keyset. 유지 후보 |
| 집계 | 허용 범위 | 리소스별 명시 허용 후보(T07 TH3) |
| 비용 상한 | 깊이, 행 수, 조인 수, 시간 | 실행 전 정적 검사 + 실행 중 타임아웃 |
| 권한 적용 | 정책을 계획에 넣는다 | 행 가시성은 WHERE로, 필드 가시성은 선택 단계에서. PoC 방식 재사용 |
| 실행 시점 | 런타임 / 빌드 승인 / 혼합 | T01 §5 |

## 3. 자동 CRUD 범위 (의제 8)

| 항목 | 초안 |
|---|---|
| 기본 조회 | 조합 읽기로 흡수(T01) |
| 생성·수정·삭제 | 정책 아래 표준 쓰기(B안) 또는 선언 Command(A안). T01 결정 |
| 관계 변경 | 연결·해제를 표준 쓰기로 둘지 `[미정]` |
| 일괄 처리 | 항목별 결과(부분 성공) 의미는 PoC에 있음(`each … partial`). 재검토 |
| 비즈니스 규칙이 필요한 변경 | Command 또는 확장(T09) |

원문: 지난 에이전트의 "읽기 조합 + 선언 Command만" 추천은 창시자 결정이 아니다.

## 4. DB 추상화 (의제 6)

| 선택지 | 내용 | 장점 | 단점 |
|---|---|---|---|
| D-PG | PostgreSQL 전용으로 깊게 | 행 수준 기능, 제약, 트리거, FTS, LISTEN/NOTIFY를 다 쓴다. PoC 자산 그대로 | 다른 DB를 쓰는 팀 배제 |
| D-Cap | 공통 데이터 모델 + DB별 capability 선언, 미지원 기능은 명시적 오류 | 여러 DB. 원 설계 초안이 요구한 방향 | 기능마다 대체 구현 또는 거부 판정. 비용이 크다 |
| D-PG 먼저 + Cap 경계만 | 지금은 PG만 구현하되 PG 고유 기능 사용 지점을 capability 이름으로 표시 | 나중에 확장할 자리 | 표시가 형식만 남을 위험 |

`[추천 보류]` 존재 목적에 직접 걸리지 않으므로 T01 실험 뒤 정해도 늦지 않다.
