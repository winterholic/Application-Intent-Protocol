## 1. 설계 관문

| # | 답 |
|---|---|
| 1 원칙 | 구현(Rust 엔진 + JS/Python)과 확장(JS/Python 자연 활용)을 실현 |
| 2 호출자 범위 | 직접 영향 없음 |
| 3 서버 작성량 | 배포·운영 구성 부담에 영향 |
| 4 서버 권한 | 확장 코드가 엔진의 권한 판단을 우회하지 못하게 경계를 둔다 |
| 5 JS/Python | 개발자가 Rust를 쓰지 않는다(원문) |
| 6 한 의도 한 표현 | 실행 형태가 여럿이면 같은 정의가 형태마다 다르게 동작하지 않아야 한다 |
| 7 수단 | Rust는 수단이다(원문). 모든 일을 Rust가 하는 것이 최적은 아니다 |
| 8 현재 기준 | 자체 포트 AIP 서버와 프론트엔드 전용 SDK라는 제품 구조는 확인됐다. 자동 기동·추가 임베딩·worker/IPC 등 실행 편의와 경계는 기술 검증 대상이다(B 질문 16·17, Q4). |

## 2. 원문의 사실과 미정

- `[확인된 제품 구조]` 설정 뒤 자체 포트에서 실행하는 AIP 서버 프레임워크와 별도의 프론트엔드 전용 호출 라이브러리를 제공한다. 둘은 서로 대체하는 선택지가 아니다(통합 지침 §3.1~3.2, B 질문 16·24).
- `[확인된 방향]` Rust 기반 핵심 엔진을 구상하며 JS/TS·Python 생태계를 지원하고, 특히 JS/TS 개발 경험을 중요하게 본다(통합 지침 §2 원칙 3, B Q4).
- `[기술 검증]` 패키지의 자동 서버 기동, 추가 임베딩 편의, 확장 worker와 IPC/FFI 경계, 배포 방식은 제품 구조와 별도로 검증한다. worker나 사이드카는 확정 구조가 아니다(B 질문 16·17, 24).
- 현재 구현이 독립 서버라는 것은 구현 사실이며, 임베딩을 포함한 제품 선택이 승인됐다는 뜻은 아니다.

## 4. 이전 선택지·추가 지원 비교 (기본 제품 구조의 양자택일 아님)

아래 표는 확인된 자체 서버+프론트 SDK 구조를 바꾸는 비교가 아니다. 실행·확장 편의로 추가 지원할 수 있는 선택지를 이전 초안에서 비교한 기록이다. 특히 별도 확장 worker는 아직 검증 대상이다.

| 축 | S. 자체 서버 + 별도 확장 프로세스 후보 | E. 추가 임베딩 편의 후보(N-API, PyO3 등) | 둘 다 지원 |
|---|---|---|---|
| 개발 경험 | 별도 바이너리 실행. 확장은 다른 프로세스 | `npm install` 후 같은 프로세스. 기존 앱 서버에 붙이기 쉽다 | 선택 부담 |
| 확장 호출 비용 | 프로세스 경계(IPC) | 함수 호출 수준 | |
| 장애 격리 | 확장이 죽어도 엔진 생존 | 확장 문제가 엔진 프로세스에 영향 | |
| 배포 | 컨테이너 하나 + 사이드카 | 기존 Node/Python 배포 그대로 | 두 배포 경로 시험 |
| 기존 자산 | 지금 구현 그대로 | 엔진을 라이브러리로 분리해야 함(`aip-runtime`이 HTTP와 엔진을 같이 가짐) | |
| Python 동시성 | 영향 적음 | GIL과 비동기 연동 설계 필요 | |

`[확인 필요]` N-API, PyO3의 비동기·스레드 제약은 버전별로 다르다. 결정 전 스파이크로 확인한다.

## 5. 어느 안이든 `[추천]`

엔진 핵심을 HTTP 서버와 분리된 라이브러리로 두면 S, E 모두로 갈 수 있다. 결정 전에 할 수 있는 구조 정리이지만, 코드 변경이므로 승인 후에 한다.
