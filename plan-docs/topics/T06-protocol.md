# T06. Application Intent Protocol

> **2026-10-03 기준 정본:** [창시자 통합 지침](../sources/founder-integrated-directive-2026-10-03.md)과 [B 결정 상태 재분류](../alignment/B-decision-reclassification.md)가 우선한다. 아래 초안·후보·미정·자료 요청은 이전 기준의 기록이며 전체 승인으로 보지 않는다. 이전 기준의 질문이 B에서 해결·대체된 경우 재질문하지 않는다.
> 이전 기준의 초안 상태: v0 (2026-10-03). 기준 원문: PART I §2, 의제 10. 당시 새 프로토콜의 의미 변경을 창시자 승인 사항으로 표시했으며, 현재 답과 남은 세부는 B를 따른다.
> **관련 기술 기록:** `../decisions/DD-08-request-wire-format.md` — 기존 리뷰는 이전 지침의 검토 이력이다. 현재 결정 상태는 [B](../alignment/B-decision-reclassification.md)를 따른다.

| # | 답 |
|---|---|

| 2 호출자 범위 | 요청 형식이 T01이 정한 범위를 그대로 표현해야 한다 |
| 3 서버 작성량 | 영향 적음 |

| 8 창시자 결정 | 의미 변경은 승인 사항 |

## 2. 원문의 요점

- 핵심은 HTTP를 버리는 것이 아니라 **요청과 응답을 어떤 의미 단위로 정의하고 서버가 어떻게 검증·실행하나**이다.
- 호출자는 엔드포인트를 부르지 않고 필요한 결과와 동작을 표준 방식으로 표현한다.
- Intent는 문법, 계약, 타입, 정책을 갖춘 구조화된 요청이다. 자연어 무제한 해석이 아니다.
- REST를 다른 이름으로 바꾸는 데 그치면 안 된다.

## 4. 요청 형식 설계 원칙 `[추천 초안]`

1. 하나의 요청 형식이 읽기 조합, 쓰기 동작, 선언 Intent 호출을 모두 담는다. 의도별로 다른 엔드포인트를 만들지 않는다.
2. 요청은 직렬화된 데이터다. 문자열로 된 질의 언어를 둘지(GraphQL처럼), 구조화된 JSON 트리로 둘지는 `[선택지]`. 문자열은 사람이 읽기 좋고, JSON 트리는 생성·검증이 쉽고 주입 표면이 작다.
3. TS 쪽은 타입이 있는 빌더나 객체로 만들고, 결과 타입이 요청 모양에서 추론되게 한다.
4. 계약 공개 범위: 클라이언트와 AI 에이전트가 무엇을 볼 수 있나(옛 OI-P3). 정책 내용은 기본 비공개 후보.
