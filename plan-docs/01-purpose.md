# 01. 존재 목적

> 상태: 통합 지침 반영 (2026-10-03). 기준: [창시자 통합 지침](sources/founder-integrated-directive-2026-10-03.md) §1~3·13. 상세 설계/지표는 제안이다.

## 1. 한 문장

AIP는 프론트엔드와 백엔드의 개발 경계를 다시 설계한다. 호출자가 필요한 데이터와 동작을 정형화해 표현하면 반복되는 서버 구현을 공통 엔진이 흡수한다. 목표는 애플리케이션별 백엔드 구현과 프론트·백엔드 계약의 이중 유지보수를 구조적으로 최소화하는 것이다. 서버 코드 0이나 모든 업무 로직 제거를 약속하지 않는다.

## 2. 풀려는 구조적 문제

새 화면 하나를 만들 때 일반적인 웹 서비스에서 일어나는 일:

1. 프론트가 필요한 데이터와 동작을 정한다.
2. 백엔드가 그에 맞는 API를 설계한다.
3. Controller, Service, Repository, DTO, 직렬화, 검증을 쓴다.
4. 프론트가 호출 코드를 쓴다.
5. 화면이 바뀌면 1부터 다시 한다. 양쪽 계약도 같이 고친다.

문제는 코드 양 자체가 아니라 **화면의 요구가 바뀔 때마다 서버 변경이 따라붙는 구조**다. 서버 쪽 작업의 대부분은 비즈니스 판단이 아니라 "이 화면이 이 모양의 데이터를 원한다"를 옮겨 적는 일이다.

아리아리 실측(10-02, 어노테이션 개수 기준, 확인 필요: 공유 경로 중복 미제거): 컨트롤러 41개, 엔드포인트 159개(GET 63, POST 55, DELETE 22, PUT 13, PATCH 6), 프론트 API 호출 약 115곳. GET 63개 중 상당수가 화면 단위로 추가된 조회라는 것이 가설이다. 엔드포인트별 분류는 아직 하지 않았다(T01 §7 실험).

## 3. AIP가 하려는 것과 하지 않으려는 것

| 한다 | 하지 않는다 |
|---|---|
| 호출자가 필요한 데이터와 동작을 표현할 수 있는 범위를 기존보다 넓힌다 | 서버를 없앤다 |
| 서버가 요청의 의미와 권한을 매번 판단하고 실행 방법을 정한다 | 인증, 인가, 비즈니스 규칙, 데이터 무결성의 책임을 프론트로 넘긴다 |
| 반복 구현(조회, 검증, 권한, 트랜잭션, 비동기 작업, 승인 흐름 등)을 표준 기능으로 흡수한다 | 모든 비즈니스 규칙과 서버 설정이 사라진다고 약속한다 |
| 표준 밖은 JS/Python으로 자연스럽게 확장하게 한다 | 확장에 승인 절차나 복잡한 의식을 붙인다 |
| 백엔드, 프론트엔드 라이브러리, 통신 규약을 하나의 체계로 설계한다 | GraphQL 복제, REST를 다른 문법으로 감싸기, 이름 붙은 서버 함수 호출에 그치기, CRUD 자동 생성에 머물기 |

## 4. 이상적인 개발 경험 (원문 PART I §1)

1. AIP 서버와 필요한 정책·데이터 정의를 준비한다.
2. 프론트엔드에서 필요한 데이터와 동작을 표현한다.
3. AIP가 요청의 의미와 권한을 검증한다.
4. AIP가 적절한 실행 방법을 결정한다.
5. 서버가 실제 작업을 수행한다.
6. 프론트엔드는 필요한 형태의 결과를 받는다.

이 흐름에서 3, 4, 5는 프레임워크의 공통 책임이다. 앱 개발자는 모델·정책·불변식·확장 계약과 표준으로 처리되지 않는 JS/TS·Python 로직을 작성한다. 자체 포트 서버와 공식 프론트 호출 라이브러리가 기본 경험이며, 화면별 plumbing을 얼마나 줄이는지가 성패다.

## 5. 성공 지표 (초안)

| 지표 | 정의 | 재는 법 | 상태 |
|---|---|---|---|
| S1 서버 추가량 | 새 화면이나 기능을 만들 때 서버 쪽에 추가해야 하는 정의의 양 | 아리아리 프론트 호출 115곳을 하나씩 "서버 추가 없음 / 정책 추가 / command 추가"로 분류 | `[추천]` 핵심 지표로 제안 |
| S2 보안 불변식 | 조합 요청이 권한, 가시성, 테넌트를 우회하지 못함 | 위협 모델(T07)의 공격 요청을 선택지마다 만들어 막히는지 확인 | `[추천]` |
| S3 AI 작성 일관성 | 같은 요구에 대해 AI가 만드는 정의가 같은 모양으로 수렴하는 정도 | 같은 요구를 여러 번 생성해 정규화 후 비교 | `[추천]`, 측정 방법 미정 |
| S4 확장 비율 | 표준 기능으로 못 덮어 JS/Python 확장으로 빠진 비율 | 아리아리 재구현 시 집계 | `[추천]` |
| S5 실서비스 성능 | 원본 대비 p50/p95 | 부하 측정 | `[추천]`, 우선순위 미정 |

옛 전략 문서(`../docs/design/00-strategy.md` §7)의 "뒤집을 신호" 수치는 그대로 쓰지 않는다. 핵심 측정 대상은 이번 지침으로 확인됐고 목표값은 아직 없다. [D](alignment/D-development-experience.md)에서 초기 설정 비용·실제 변경 파일·계약 중복·AI 선택·실행 성능을 함께 측정하는 방법을 정리했다.
