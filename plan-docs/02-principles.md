# 02. 원칙과 설계 판단 우선순위

> 상태: 통합 지침 반영 (2026-10-03). [통합 지침](sources/founder-integrated-directive-2026-10-03.md)의 FOUNDER가 기준이다. [A](alignment/A-founder-intent-matrix.md)에 코드/설계 반영을 연결한다.

## 1. 원칙표

최초 7가지 원칙은 이번 통합 지침 §2에 있다. 아래 9행은 책임별 탐색을 위한 표현이며 원문 원칙 개수를 대신하지 않는다.

| 구분 | 원칙 | 10-03 원문 위치 | 비고 |
|---|---|---|---|
| 존재 목적 | 백엔드 개별 개발과 유지보수의 극단적 최소화 | PART I §1 | |
| 작동 모델 | 호출자가 원하는 데이터와 동작을 표현한다 | PART I §1 | 범위는 T01 |
| 보안 | 서버가 최종 권한과 실행을 통제한다 | PART I §2 보안 철학 | 8개 세부 원칙은 T07 |
| 프로토콜 | Application Intent Protocol | PART I §2 | Intent는 구조화된 요청. 자연어 무제한 해석이 아니다 |
| 아키텍처 | SPR: 정의·프론트 표현·정책 실행 | 통합 지침 §2 원칙 6 | 책임 확인. 패키지 구성은 기술 설계, T05 |
| 구현 | Rust 핵심 엔진, JS/TS 중요, Python 지원 | 통합 지침 §2·3 | 자체 포트 서버+공식 프론트 SDK 확인. 자동 기동/추가 임베딩은 검증 |

Q0 최초 원칙과 Q5 metadata 역할은 답변됐다. 독립 파일 여부·정확 문법·언어 초기 동등 지원·Typed IR 필요성은 미정 또는 기술 검증으로 남는다.

## 2. 설계 판단 우선순위 (원문 PART VI)

구현 순서가 아니라 **두 설계가 부딪칠 때 무엇을 먼저 지키느냐**의 순서다.

| 단계 | 내용 |
|---|---|
| P0 존재 목적 | 프론트·백엔드 개발 경계 재정의 / 백엔드 개별 구현·유지보수 극단적 최소화 / 호출자 중심 데이터·동작 표현 / 서버의 최종 권한과 실행 통제 |
| P1 핵심 제품 구조 | Application Intent Protocol / SPR / 안전한 요청 조합 / Rust 핵심 엔진 / JS/TS 우선, Python 지원 / 기존 생태계 활용 |
| P2 AI 개발 경험 | AI First / 선택지 최소화 / 문법 정형화 / 명확한 실행 의미 / 풍부한 기본 기능 / 자연어의 문법화 / 예측 가능한 프로젝트 구조 |
| P3 기술 구현 | DSL / IR / Parser / Planner / ABI / DB Adapter / Migration / Cache / Code Generation |

P3는 P0~P2를 위한 수단이다. P3 항목을 도입하려면 그것이 어느 P0~P2를 실현하는지 문서에 적어야 한다.

P0 안에서도 긴장이 있다. "호출자 표현"과 "서버 최종 통제"는 서로 당긴다. 원문의 답은 "요청의 자유와 실행 권한을 분리한다"이다. 즉 자유를 줄여서 안전을 얻지 않고, 자유는 넓히되 실행 판단을 서버가 매번 한다. 지난 PoC는 자유를 없애는 방식으로 안전을 얻었고, 그래서 충돌로 판정됐다(`../docs/design/11-founder-intent-audit.md` §B).

## 3. AI First 세부 원칙 (원문 PART I §4)

1. 일반적 개발 패턴을 최대한 표준 기능으로 제공한다.
2. 같은 의도는 같은 구조로 표현한다.
3. 기본값을 풍부하게 둔다.
4. 불필요한 설정과 선택지를 없앤다.
5. 문법과 계약을 명확히 한다.
6. 모호한 관습보다 기계로 검증할 수 있는 규칙을 우선한다.
7. 프로젝트 구조와 기능의 위치를 예측할 수 있게 한다.
8. 오류를 명확하고 구조화된 형태로 준다.
9. AI가 외부 문서나 내부 구현을 추측해야 하는 상황을 줄인다.
10. 사람도 이해하고 유지보수할 수 있어야 한다.

핵심은 자유를 없애는 것이 아니라 **불필요한** 자유와 구현 다양성을 줄이는 것이다. 9.3 "기본값과 명시적 재정의"가 이 균형을 잡는다: 기본은 표준 방식, 필요하면 명시적으로 재정의.

## 4. 자주 혼동되는 것

- 호출자가 표현한다는 것은 무제한 요청이 아니다. 서버가 허용한 계약 안에서 요청한다.
- 백엔드 개발을 줄이는 것과 백엔드의 보안 책임을 없애는 것은 다르다.
- GraphQL을 복제하지 않는 것과 GraphQL에서 영감을 받은 호출자 중심 데이터 선택을 금지하는 것은 다르다.
- Rust는 엔진 구현 언어다. 개발자가 정의를 무엇으로 쓰는지와 별개다.
- "독립적인 표현 체계"와 "새 소스 언어 + 컴파일러"는 같은 말이 아니다. 다만 10-03 원문은 고유 문법을 없애는 쪽도 단정하지 말라고 한다(T02).
- 자연어 메타데이터의 핵심은 설명의 구조적 소속이다. 이를 자연어 의미 검사·실행 규칙 생성 의무로 확대하지 않는다.
- 문서화 표준 제공과 문서 작성 강제는 다르다. 표준은 주되 의무는 만들지 않는다.

## 5. 설계 관문 8문항

`../docs/PRINCIPLES.md` §4를 그대로 쓴다. 10-03 원문 PART V의 여섯 질문을 7번에 붙였다.

1. 원칙표의 어느 원칙을 실현하는가? 어느 원칙과 긴장하는가?
2. 호출자가 표현할 수 있는 범위가 넓어지는가, 좁아지는가?
3. 애플리케이션 개발자가 서버 쪽에 써야 할 것이 늘어나는가, 줄어드는가?
4. 서버의 최종 권한이 유지되는가? 호출자가 보낸 것 중 무엇을 신뢰하고 무엇을 검증하는가?
5. JS/TS·Python의 개발 경험과 확장 생태계를 자연스럽게 활용할 수 있는가?
6. 같은 의도를 여러 방식으로 쓸 여지를 만들지 않는가?
7. 수단을 목적처럼 다루고 있지 않은가? (왜 필요한가 / 호출자 중심 실행에 어떤 도움 / 보안 통제에 어떤 도움 / JS/Python과 어떻게 연결 / 없으면 실제로 무엇이 문제 / 더 단순한 대안은)
8. 창시자 결정이 필요한 사항을 임의로 정하고 있지 않은가?

관문 5는 특정 파일 형식을 선결하지 않는다. 고유 정형 표현은 지향하지만 독립 `.aip` 파일은 OPEN이다.

## 6. 검증·오픈소스 추가 기준

선택적 개발 검사는 공식 지원 목표다. 서버의 타입·입력·인증·인가·무결성·트랜잭션·자원 검증은 그 선택과 독립적으로 필수다. 자연어 내용의 의미 판정은 기본 요구사항이 아니다.

오픈소스·외부 기여 환영은 FOUNDER다. 구체 라이선스·초기 서드파티 패키지/클라이언트 범위는 OPEN이다.
