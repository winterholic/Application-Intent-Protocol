# EE 경계와 "MIT만 포팅" 분모 (WBS 7.3.3.8 재분석, 2026-10-18)

이전판은 "EE 77 서비스·122 라우터 파일을 제외하면 MIT 범위만 포팅할 수 있다"고 비준했다. 독립 검증이 이 전제에 이의를 제기해 소스를 다시 셌다. **이 문서는 법적 결론을 내리지 않는다.** 사실, 대안, 그리고 사용자가 판단할 항목을 정리한다. 원본은 실행하지 않았고 소스 판독과 파일 집계만 했다. revision은 `47246becc445869ba73077baa0a53a683e3508ce`.

## 확인한 사실

| 사실 | 수치 | 근거 |
|---|---|---|
| 라이선스 구분은 디렉터리다. `ee/` 아래는 Enterprise License, 나머지는 MIT | `backend/src/ee`(서비스 77개, 라우터 파일 122, 라우트 정의 533), `backend-go/internal/ee` | `LICENSE`, `backend/src/ee/LICENSE.md` |
| Enterprise License 조건(요지): production 사용에는 구독 동의가 필요하다. 개발·테스트 목적의 복사·수정은 구독 없이 허용한다. 수정과 패치의 권리는 Infisical에 귀속된다. 복사·병합·게시·배포·재라이선스·판매는 금지한다 | — | `backend/src/ee/LICENSE.md` 전문. 해석은 하지 않는다 |
| 권한 평가의 핵심이 EE 디렉터리에 있다 | `backend/src/ee/services/permission/` 파일 20개, 약 10,044줄(테스트 포함). 역할 정의 `default-roles.ts` 1,324줄, 프로젝트 권한 `project-permission.ts` 2,115줄(Subject 열거와 행동 열거 수십 종), 서비스 `permission-service.ts` 1,553줄, DAL 1,072줄, 조직 권한 `org-permission.ts` 699줄 | `ee/services/permission` 판독(줄 수만, 로직은 읽지 않음) |
| MIT 쪽에는 CASL 보조 코드가 있다 | `lib/casl/`(경계 계산, glob 부분집합, 필터 유틸 등) 약 1,900줄 | `lib/casl` |
| MIT 파일이 EE 모듈을 import한다 | `ee/` 밖 `.ts` 3,332개 중 **446개**가 `@app/ee/...` 또는 `ee` 디렉터리 상대 경로를 import한다(테스트 제외 407개). import 문은 1,334개 | `infisical-inventory.json`의 `ee_coupling`, `tools/infisical_inventory.py` |
| 그중 `ee/services/permission` import | 테스트 제외 **133**개 파일 | 위와 같음 |
| 가장 많이 import되는 EE 모듈(import하는 파일 수) | audit-log 164, permission 153, license 80, gateway-v2 78, gateway-pool 57, group 27, dynamic-secret 24 | `ee_coupling.top_imported_ee_modules` |

검증 보고서의 "EE를 import하는 MIT 파일 803개"는 이 세션이 같은 정의(alias와 상대 경로 import)로 세어 **446개**(문 단위 1,334)가 나와 재현하지 못했다. 803이 나온 집계 정의를 알 수 없어 `확인 필요`다. 어느 쪽이든 결론은 같다. 상당수의 MIT 파일이 EE 모듈에 의존한다.

## 판정할 수 있는 것과 없는 것

판정할 수 있다: 이전 비준의 전제("EE를 빼면 MIT 범위가 독립적으로 성립한다")는 코드 의존도로는 성립하지 않는다. 특히 I04(조직·RBAC)는 서비스의 31/71, 라우터의 23/27이 EE를 import하고 권한 평가의 본체가 EE에 있다. I03 시크릿 라우터도 12/19가 EE를 import한다. 그래서 "MIT만 포팅" 분모에 인가가 들어 있는지가 불분명하다.

판정하지 않는다(사용자 판단): (a) EE 소스를 읽고 그 동작을 다시 구현하는 것이 허용되는지, (b) 허용되는 범위, (c) AIP 오픈소스(MIT, D-A27) 산출물과의 관계, (d) 업스트림이 EE를 뺀 배포물을 따로 제공하는지(`확인 필요`, 이 세션은 확인하지 않았다).

## 이 세션의 EE 소스 노출 범위

클린룸 같은 분리가 사용자에게 중요하면 필요한 정보다. 이 세션이 EE 디렉터리에서 한 일은 다음뿐이다.

- 디렉터리 이름과 파일 이름, 파일별 줄 수를 나열했다.
- `ee/services/permission/project-permission.ts`와 `org-permission.ts`에서 `export enum` 선언 줄 이름만 나열했다(내용은 읽지 않음).
- `ee/LICENSE.md`를 읽었다.
- 큐(`QueueName`)와 MIT 파일의 `@app/ee/` import 문자열을 집계했다.

권한 평가 로직, 기본 역할의 구체 규칙, 조건식 처리 코드는 읽지 않았다. 포팅 산출물 `porting/infisical/app.aip`의 권한 규칙(admin, member, viewer, no-access, 조직 admin의 암묵적 프로젝트 접근, 조직 구성원만 사용자 가시)은 AIP 쪽 설계 판단이며 EE 코드를 옮긴 것이 아니다. 다만 역할 이름(admin, member, viewer, no-access)은 작성자의 사전 지식에서 가져왔고 Infisical 문서나 코드로 대조하지 않았다(`확인 필요`). 원본의 기본 역할이 실제로 이 이름과 의미를 갖는지는 확인된 바 없다.

## 대안

| 안 | 내용 | 얻는 것 | 잃는 것·위험 |
|---|---|---|---|
| A. 분모를 MIT 소스로 한정하고 인가는 AIP가 독자 설계 | 현재 접근. 역할 기반 권한을 predicate로 표현하고 실DB로 검증한다 | 라이선스 접촉면이 가장 작다 | "Infisical 전체 포팅"이 아니라 "Infisical 형태의 앱을 AIP로 새로 만든 것"이 된다. 원본 권한 동작과의 동등성은 주장하지 못한다 |
| B. 관찰 기반 클린룸 범위 | 원본의 권한 동작을 EE 소스가 아니라 공개 문서, 공개 API 응답, 화면, 블랙박스 시험으로 관찰해 사양(입력→허용/거부)을 만들고, 그 사양만 보고 AIP predicate로 구현한다. 사양 작성자와 구현자를 나눈다 | 동등성 주장이 가능해진다 | 관찰은 원본 실행이 필요해 EE 코드가 실행될 수 있고(개발·테스트 허용 범위인지는 사용자 판단) 사양 작성자가 EE 소스를 보지 않았음을 증명하는 절차가 필요하다. 이 세션은 이미 위 범위로 노출됐으므로 구현자 역할을 맡길지 정해야 한다 |
| C. 공개 API 계약(OpenAPI)을 분모로 재정의 | MIT 라우터 정의와 응답 스키마를 계약으로 보고 인가는 계약상 보이는 부분까지만 다룬다 | 분모가 문서로 고정된다 | 인가 의미가 계약에 없는 부분은 비어 있다 |
| D. EE 포함(라이선스 구독 전제) | 구독 계약 하에 EE도 분모에 넣는다 | 분모가 완전해진다 | production 사용이 구독에 묶인다. AIP 오픈소스 산출물과 양립하는지는 사용자 판단 |
| E. 범위 축소 | 인가가 단순한 모듈(예: I10 일부, I05)부터 EE 비의존 경로만 먼저 | 법적·기술적 위험이 작다 | 앱의 핵심 가치(프로젝트·시크릿 접근 제어)가 빠진다 |

이 세션의 권고는 없다. 안 A로 이미 진행했고 그 한계를 문서화하는 것이 현재 상태다. 안 B로 가려면 사용자가 노출 범위와 역할 분리를 먼저 정해야 한다.

## 사용자 판단 항목

1. EE 디렉터리 소스를 읽고 같은 동작을 AIP로 다시 구현해도 되는가. 안 된다면 이 세션의 노출을 어떻게 취급할 것인가.
2. 안 B(관찰 기반 클린룸)를 택한다면 사양 작성자와 구현자를 누가 맡고, 원본을 실행해 관찰하는 것이 개발·테스트 허용 범위인지 누가 판단하는가.
3. 포팅의 목표를 "Infisical 동등성 증명"으로 둘 것인가, "Infisical 형태의 비밀 관리 앱을 AIP로 만들기"로 둘 것인가. 후자면 안 A로 충분하다.
4. 업스트림이 EE 없는 배포물을 제공하는지 확인할 것인가(`확인 필요`).
5. 이전의 "EE 제외 비준"을 공식으로 철회하고 위 판단이 날 때까지 잠정으로 둘 것인가(이 문서는 잠정으로 취급한다).
