# AIP 원칙 (정본)

> 상태: 창시자 기준 확인. 최신 정본은 [2026-10-03 통합 지침](../plan-docs/sources/founder-integrated-directive-2026-10-03.md)이다. 이 문서는 탐색용 원칙표이며 충돌하면 원문 표식을 따른다.
> [FOUNDER] 목적·원칙과 [DIRECTION]·[OPEN] 기술 설계를 분리한다. 현재 상세 결정 상태는 [B](../plan-docs/alignment/B-decision-reclassification.md).

## 1. AIP를 만드는 이유

> 서버는 안전한 실행 환경을 제공하고, 프론트엔드에서 필요한 데이터와 동작을 표현하면 백엔드에 매번 API를 추가하지 않고도 처리할 수 있어야 한다.

> 요청의 자유와 실행 권한을 분리한다.

GraphQL과 CQRS에서 영감을 받았지만 그것을 복제하려는 것이 아니다. 서버를 없애려는 것도, 인증·인가·비즈니스 규칙·데이터 무결성의 책임을 프론트엔드로 넘기려는 것도 아니다.

## 2. 절대 잃으면 안 되는 원칙

| 번호 | 원칙 |
|---|---|
| 1 | 애플리케이션별 백엔드 반복 구현·유지보수 최소화 |
| 2 | Application Intent Protocol. 호출자는 필요한 데이터·동작을 표현하고 서버가 권한·실행을 최종 결정 |
| 3 | Rust 핵심 엔진과 자연스러운 JS/TS·Python 생태계 |
| 4 | AI를 위한 정형화·근거 없는 구현 선택 최소화. 인간 이해·검증 가능성 유지 |
| 5 | 선언에 귀속된 선택적 자연어 metadata. 의미 검사 비필수, 실행·보안 근거 아님 |
| 6 | SPR: 서버 계약/정책 정의·프론트 표현·Runtime 안전 실행. 패키지는 미정 |
| 7 | 표준 밖 JS/TS·Python 공식 확장. 계약·권한·비용·트랜잭션 통제 유지 |

자체 포트의 AIP 서버 프레임워크와 공식 프론트 호출 라이브러리는 함께 제공하는 제품 구조다. 임베딩·자동 기동·언어 첫 출시 동등성은 추가 검증 대상이다.

선택적 개발 검사와 필수 서버 안전성 검사를 구분한다. 오픈소스와 외부 기여 환영은 확인됐고 구체 라이선스는 미정이다.

## 3. 자주 혼동되는 것

- AIP 고유의 정형 표현을 지향하며 JS/TS·Python 생태계와 연결한다. 독립 `.aip` 파일 필요성은 OPEN이다. 고유 문법을 자동 폐기하거나 현재 parser를 최종 사양으로 확정하지 않는다.
- 호출자가 표현한다는 것은 **무제한 요청**을 뜻하지 않는다. 서버가 허용한 최종 계약 안에서 필요한 데이터와 동작을 요청한다.
- DSL, IR, 컴파일러, 타입 시스템은 **수단**이다. 특히 IR은 호출자의 Intent를 서버가 안전하고 일관되게 실행하는 데 실제로 도움이 될 때만 정당화되는 내부 도구다.
- Rust를 쓴다는 것은 핵심 엔진의 구현 언어 이야기다. 개발자가 무엇으로 정의를 쓰는지(JS/Python)와 별개다.

## 4. 설계 관문 (모든 설계·구현 단위가 통과해야 한다)

새 기능, 문법, 구조를 제안하거나 구현하기 전에 아래를 문서에 답한다. 답하지 못하면 진행하지 않는다.

1. §2의 어느 원칙을 실현하는가? 어느 원칙과 긴장하는가?
2. 이것 때문에 호출자가 표현할 수 있는 범위가 넓어지는가, 좁아지는가?
3. 이것 때문에 애플리케이션 개발자가 서버 쪽에 써야 할 것이 늘어나는가, 줄어드는가?
4. 서버의 최종 권한이 유지되는가? 호출자가 보낸 것 중 무엇을 신뢰하고 무엇을 검증하는가?
5. JS/TS·Python의 개발 경험과 확장 생태계를 자연스럽게 활용할 수 있는가?
6. 같은 의도를 여러 방식으로 쓸 여지를 만들지 않는가?
7. 수단(IR, 컴파일러 단계 등)을 목적처럼 다루고 있지 않은가?
8. 창시자의 결정이 필요한 사항을 임의로 정하고 있지 않은가? (`docs/DECISIONS.md`의 Open을 확인)
