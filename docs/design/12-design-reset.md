## 2. 꼼꼼하게 설계하는 규칙

지난 설계가 흐려진 원인은 수단(언어, IR, 컴파일러)을 설계하면서 매번 원칙으로 돌아가 확인하지 않은 것이다. 이번에는 다음을 지킨다.

1. **관문 먼저.** 모든 설계 문서는 첫 절에 `PRINCIPLES.md` §4 관문 8문항의 답을 쓴다.
2. **한 문서에 한 결정.** 결정마다 `docs/design/decisions/<id>.md`: 문제, 선택지(최소 2개), 원칙별 영향, 보안 영향, 실험 또는 근거, 추천, 창시자 승인 여부.
3. **실제 자료로 검증.** 추상 예제가 아니라 아리아리 실제 코드로 판단한다. 기준 자료: 프론트엔드(`ariari/ariari/ariari-frontend/app`, API 호출 약 115곳), 백엔드(컨트롤러 41개, 엔드포인트 159개: GET 63, POST 55, DELETE 22, PUT 13, PATCH 6 — 어노테이션 개수 기준, 확인 필요: 공유 경로 중복 미제거).
4. **측정 가능한 성공 기준.** 핵심 지표: "새 화면·기능을 만들 때 서버 쪽에 추가해야 하는 것의 양". 아리아리의 각 API 호출이 새 모델에서 서버 추가 없이 처리되는지 하나씩 분류한다.
5. **창시자 승인 지점을 미리 표시.** Open 항목을 임의로 닫지 않는다. 추천은 하되 결정은 하지 않는다.
6. **구현은 설계 승인 뒤.** 실험용 스파이크는 허용하되 `spikes/`에 두고 본 구현과 섞지 않는다.

## 4. D2 착수안: 호출자 표현 모델

### 4.1 문제
아리아리 백엔드 엔드포인트 159개 중 GET이 63개다. 대부분 "어떤 화면이 어떤 데이터를 어떤 모양으로 필요로 하는가"에 따라 하나씩 추가된 것이다(확인 필요: 엔드포인트별 분류 전). 현재 AIP PoC도 같은 구조다. 화면이 새 데이터를 원하면 서버 명세에 query를 추가해야 한다. 이것이 없애야 할 반복이다.

### 4.2 어떤 선택을 하든 지켜야 하는 불변식
1. 서버는 호출자가 보낸 요청을 매번 정책(allow, 행 가시성, 필드 가시성, 테넌트)으로 다시 판단한다. 호출자가 보낸 권한 규칙이나 실행 계획은 신뢰하지 않는다.
2. 호출자는 읽을 수 없는 필드로 **필터·정렬·집계도 할 수 없다.** 결과에 안 나와도 조건으로 쓰면 값이 새어 나간다(존재 여부 추측 공격).
3. 실행 전에 비용 상한(깊이, 행 수, 조인 수, 시간)을 검사한다. 상한은 서버가 정한다.
4. 노출은 기본 거부. 서버가 열지 않은 엔티티·필드·관계는 요청할 수 없다.
5. 원시 SQL이나 임의 코드는 호출자 요청에 없다.
6. 같은 의도는 같은 요청 형식으로 쓴다(AI가 고를 선택지를 늘리지 않는다).

### 4.3 읽기 선택지

| 선택지 | 내용 | 원칙 부합 | 위험·비용 |
|---|---|---|---|
| R-A 선언 intent만 (현재) | 서버가 query를 하나씩 선언 | 존재 목적·작동 모델과 충돌 | 기각(D-R5) |
| R-B 런타임 자유 조합 | 호출자가 필드·관계·조건·정렬·페이지를 조합, 런타임이 정책·상한 검사 후 계획·실행 | 작동 모델에 가장 충실 | 런타임 계획기 필요. 비용 공격 표면이 넓다. 실행 SQL을 미리 볼 수 없다 |
| R-C 빌드 시점 승인 조합 | 프론트 코드에 쓴 조합 요청을 빌드가 추출, 서버 계약 범위 안인지 검사해 승인 목록을 만든다. 운영 런타임은 승인된 요청만 실행. 개발 모드는 즉시 실행 | 작동 모델 충족(서버 코드 추가 없음) + 실행 SQL을 미리 고정·검토 가능 | 빌드 도구가 프론트 코드를 이해해야 한다. 승인 목록 배포 절차가 생긴다. 서드파티·AI 에이전트 같은 동적 호출자는 별도 경로 필요 |
| R-D 엔티티 단위 표준 조회 | 엔티티별 목록/단건 조회에 필드 선택과 허용된 필터만 | 일부 충족 | 표현력이 낮아 결국 서버 query 추가로 돌아간다 |

메모: R-B와 R-C는 요청 형식이 같을 수 있다. "같은 요청 언어, 실행 시점만 다름"으로 설계하면 개발 중에는 R-B, 운영에서는 R-C를 기본으로 하는 조합도 가능하다. 이 조합이 SQL 사전 고정(OI-C2)의 장점(예측 가능성, `explain`)을 살리면서 서버 코드 추가를 없앨 수 있는지 실험할 가치가 있다.

### 4.4 쓰기 선택지

| 선택지 | 내용 | 위험 |
|---|---|---|
| W-A 선언 command만 | 비즈니스 규칙이 있는 쓰기는 서버 정의 command | 단순 쓰기(프로필 수정, 댓글 작성)도 하나씩 선언해야 한다 |
| W-B 엔티티 정책 아래 표준 쓰기 + 선언 command | 생성·수정·삭제를 엔티티 정책(누가, 어떤 필드를, 어떤 상태에서)으로 열고, 규칙이 복잡한 동작만 command | 정책 표현력이 부족하면 구멍이 된다. 불변식·상태 전이·제약은 DB와 런타임이 계속 강제해야 한다 |
| W-C 호출자 조합 다단계 쓰기 | 여러 쓰기를 호출자가 묶어 보냄 | 트랜잭션 경계·권한 판단을 호출자가 사실상 설계하게 된다. "실행 권한 분리"와 긴장 |

현재 판단(추천 아님, 실험 대상): W-B가 원칙에 가장 가깝다. PoC의 `expose`(생성·수정·삭제 + 정책 + 필드 목록)가 W-B의 씨앗이다. W-C는 기본 제외 후보.

### 4.5 검증 실험 (결정 전에 수행)
1. 아리아리 프론트 API 호출 115곳과 백엔드 엔드포인트 159개를 하나씩 대응시킨다.
2. 각 호출을 R-B/R-C/R-D × W-A/W-B 조합별로 "서버 추가 없이 처리 가능 / 서버 정책 추가 필요 / 서버 command 필요"로 분류한다.
3. 결과표로 선택지별 "서버 쪽 추가량"을 비교한다. 이것이 존재 목적의 직접 지표다.
4. 보안 불변식(§4.2)을 깨는 요청 예를 선택지마다 만들어 막히는지 따져 본다(설계 단계의 위협 모델링).

## 5. D3 예고: JS/Python에서 정의 쓰기

- 질문: 서버 쪽 정의(엔티티, 정책, 규칙, command)를 TS/Python으로 어떻게 쓰나. 후보: 정형 객체 스키마, 빌더 API, 데코레이터/클래스.
