# 00. 전략: AIP는 무엇을 이기려 하는가

> 2026-10-02: 이 문서는 창시자 원칙 정정 이전에 작성됐다. `docs/PRINCIPLES.md`와 충돌하는 부분은 그 문서를 따른다(감사: `11-founder-intent-audit.md`).

> 상태: Proposed · 작성 2026-09-30 · 렌즈: biz-product-strategy(Rumelt 커널), dev-chief-architect
> 원문 맥락: `../origin/full_context_handoff.md`, `../origin/design_draft.md`

## 1. 한 문장

AIP는 **백엔드의 의미(semantics)를 언어로 선언하면 컴파일러가 검증하고 런타임이 실행하는 애플리케이션 모델**이며, 동시에 클라이언트가 서버에 "의도(Intent)"만 보낼 수 있게 하는 **새 클라이언트-서버 규약**이다.

목표 상태는 "백엔드 유지보수가 거의 필요 없는 백엔드"다. 여기서 유지보수가 사라진다는 말은 코드가 없어서가 아니라, 사람이 유지하던 것(계층 간 일관성, 권한 누락 점검, 트랜잭션 경계, 재시도 안전성, 클라이언트 타입 동기화, 마이그레이션)을 컴파일러가 소유한다는 뜻이다.

## 2. 진단: 진짜 장애물

"선언형 백엔드"는 새 발상이 아니다. 실패한 시도와 부분 성공한 제품이 많다. 그것들이 멈춘 지점이 곧 AIP의 진단이다.

| 장애 | 기존 시도가 멈춘 지점 | AIP가 이 장애를 못 넘으면 |
|---|---|---|
| **신뢰 격차** | 자동 생성 API는 권한·N+1·트랜잭션을 사람이 짠 것보다 "모르게" 만든다. 그래서 진지한 서비스는 결국 손으로 짠다 | Spring 사용자가 옮겨 오지 않는다 |
| **표현력 절벽** | CRUD는 쉽고 그다음 한 걸음(상태 전이, 관계 경유 권한, 외부 결제)에서 escape hatch가 전부 먹는다 | "결국 코드 짜는 BaaS"가 된다 |
| **분산 부작용의 거짓말** | `transaction` 한 단어로 DB, 캐시, 브로커, 외부 API를 원자적이라고 가장한다 | 운영 첫 장애에서 신뢰를 잃는다 |
| **블랙박스 공포** | 실행되는 SQL과 효과를 설명하지 못한다 | 성능 문제를 디버깅할 수 없어 버린다 |
| **잠금(lock-in)** | 빠져나갈 수 없는 런타임 | 도입 결정 자체가 안 난다 |

핵심 진단: **AIP의 적은 "코드량"이 아니라 "신뢰"다.** 사람이 짠 백엔드보다 더 많은 것을 실행 전에 증명하고, 증명하지 못하는 것은 정직하게 말해야 이긴다.

근거는 사용자의 실제 운영 코드에 있다. 아리아리 백엔드(Spring, Java 477파일, 1년 운영)에서 이번에 확인한 결함 몇 가지다. 전부 "사람이 매번 기억해야 하는 규칙"이 한 곳에서 빠진 경우다. 상세는 `01-reality-test.md`.

- 동아리 관리자가 자기 자신에게 관리자 위임(`entrustAdmin`)을 호출하면 같은 엔티티에 ADMIN을 넣었다가 GENERAL로 덮어써 **관리자 0명인 동아리**가 된다. "동아리당 관리자는 정확히 1명"이라는 규칙은 README와 컨트롤러 한 곳에만 있다.
- 회계 기록 수정/삭제(`modifyFinancialRecord`, `removeFinancialRecord`)는 기록이 요청한 동아리 소속인지 확인하지 않는다. 다른 동아리의 관리자가 id만 알면 수정할 수 있다(IDOR). 해당 기능은 코드상 "비활성화" 구간이라 운영 노출 여부는 확인 필요.
- 조회수 Redis 키(`resolveViewsKey`)가 콘텐츠 타입이 아니라 **현재 조회수 값**으로 만들어져, 조회수가 바뀔 때마다 키가 달라지고 14일 창 차감이 동작하지 않는다.
- 지원서 제출은 "이미 지원했는지 조회 후 저장"인데 unique 제약이 없어 동시 요청 시 중복 지원이 생길 수 있다.
- 회원 탈퇴는 DB 트랜잭션 안에서 카카오 연결 해제(외부, 되돌릴 수 없음)를 먼저 호출한다. 이후 DB 삭제가 실패하면 상태가 갈라진다.

이 결함들은 개발자가 부주의해서가 아니라, 규칙이 코드 여러 층에 흩어져 있고 그 규칙을 아는 주체가 사람뿐이기 때문에 생긴다. AIP는 규칙을 아는 주체를 컴파일러로 바꾼다.

## 3. 방침 (Guiding Policy)

> **"사람이 짠 백엔드보다 더 많은 것을 실행 전에 증명한다. 증명할 수 없는 것은 계약에 적는다."**

세부 방침 네 가지:

1. **증명 가능한 것만 자동화한다.** 모든 자동 동작은 정적 보장, 시작 시 검증, 런타임 검증, 보장 불가 중 하나로 분류되어 `aip verify`와 계약에 드러난다(`04-safety-matrix.md`).
2. **반복 코드를 "문법"으로 승격한다.** 사용자의 비유 그대로다. 기계어 위에 어셈블리, 그 위에 C가 올라갔듯, 백엔드에서 수천 번 반복된 패턴(소유권 검사, 상태 전이, 카운터, 탈퇴 익명화, 보존 기한, 재고 예약)을 검증 가능한 언어 구성요소로 만든다. 상위 구성요소는 반드시 하위 Core IR로 내려가고, 검증은 Core IR에서 한다(`02-language.md`).
3. **Extension이 문법과 의미를 함께 가져온다.** Postgres, Redis, Kafka, S3, 결제, 메일은 함수 라이브러리가 아니라 타입, 효과 서명, capability, 검증 규칙, 런타임 어댑터의 묶음이다. Core의 안전 모델은 extension이 우회할 수 없다(`06-extensions.md`).
4. **탈출구는 열어두되 잠금은 없다.** 생성된 SQL, 마이그레이션, 계약은 읽을 수 있는 산출물이다. 어느 날 AIP를 버려도 DB와 스키마는 남는다.

## 4. 일관된 행동

| 행동 | 방침과의 연결 |
|---|---|
| 아리아리 전체를 AIP로 옮겨 원본 Spring과 코드량, 결함 검출, 성능(k6)을 나란히 비교 | 신뢰 격차를 숫자로 닫는다 |
| Reality Test 케이스를 실행 가능한 conformance suite로 만든다 (진단 코드와 런타임 동작 기대값) | 언어가 팽창해도 의미가 흔들리지 않는다 |
| 1st-party extension 7종을 Core와 동시에 개발 (postgres, redis, kafka, s3, http, mail, payments) | 표현력 절벽을 CRUD 다음 단계에서 넘는다 |
| 컴파일러 진단을 LLM이 읽고 고칠 수 있는 구조(JSON, 고칠 위치, 제안 패치)로 설계하고 자가수정률을 측정 | AI-native 주장을 검증한다 |
| `aip explain`, `aip verify`를 1급 기능으로 | 블랙박스 공포 해소 |

## 5. 하지 않을 것

- 멀티 DB 동시 지원. PostgreSQL을 깊게 쓴다. MySQL/SQLite는 capability 모델이 증명된 뒤다.
- 호스팅 클라우드, 비주얼 빌더, 관리자 UI 생성기.
- ~~클라이언트가 임의 쿼리를 보내는 모든 형태 (GraphQL식 자유 선택 포함). 클라이언트는 선언된 Intent만 호출한다.~~ **철회(2026-10-02)**: 창시자 원칙 "호출자가 원하는 데이터·동작을 표현"과 충돌(`docs/PRINCIPLES.md`, `DECISIONS.md` D-R5). 호출자 표현 범위는 OI-C1.
- 커스텀 바이너리 wire protocol. 초기 transport는 HTTP/JSON과 WebSocket(구독)이다. protocol은 semantics가 안정된 뒤 결정한다.
- 범용 프로그래밍 언어 기능(임의 루프, 재귀, 예외, 가변 변수). 필요가 증명되면 escape hatch(샌드박스 함수)로 해결한다.

## 6. 포지셔닝: 정확히 어느 층이 다른가

"Hasura가 이미 한다"로 끝내지 않고 층별로 본다. `○` 지원, `△` 부분, `×` 없음. 타 제품의 세부 동작은 공개 문서 기준 이해이며 셀별 정밀 검증은 확인 필요.

| 축 | GraphQL | Hasura / PostgREST / Supabase | Convex | Encore | Ash (Elixir) | Temporal | Cedar / SpiceDB | **AIP 목표** |
|---|---|---|---|---|---|---|---|---|
| 데이터 접근 자동화 | △ (resolver 필요) | ○ | ○ | △ | ○ | × | × | ○ |
| 비즈니스 행위를 선언으로 표현 | × | × (로직은 SQL 함수/웹훅) | × (명령형 TS) | × | ○ (actions/changes) | × | × | ○ |
| 권한 규칙을 컴파일러가 이해 | × | △ (행 단위 규칙) | × | × | △ (policies, 런타임 평가 중심, 확인 필요) | × | ○ (정책만) | ○ (정책 + 그 정책을 바꾸는 명령까지) |
| 상태 전이·불변식 검증 | × | △ (DB 제약) | × | × | △ | × | × | ○ |
| 부작용·일관성 등급 모델링 | × | × | △ (action 분리) | △ (인프라 선언) | △ | ○ (durable execution) | × | ○ |
| 재시도·멱등 정적 분석 | × | × | × | × | × | △ | × | ○ |
| 생성 계약·클라이언트 | ○ | ○ | ○ | ○ | ○ | × | × | ○ (에러 reason·효과·보장까지) |
| LLM canonical 생성 목표 | × | × | × | × | × | × | × | ○ |

가장 가까운 선행 사례는 **Ash Framework**(선언형 resource/action/policy + extension)와 **Convex**(DB와 함수의 통합 런타임)다. AIP의 차이는 세 가지로 좁혀진다.

1. **검증 범위**: 권한, 상태 전이, 불변식, 부작용 일관성, 잠금 순서, 데이터 삭제 완결성을 하나의 IR 위에서 정적으로 교차 검증한다. 예를 들어 "관리자 역할을 바꾸는 명령이 관리자 1명 불변식을 깨는가"는 권한 모델과 불변식을 동시에 아는 컴파일러만 답할 수 있다.
2. **언어 중립 IR과 단일 바이너리 런타임**: 호스트 언어(Elixir, TS)의 런타임에 묶이지 않는다. 정의는 IR로 내려가고 런타임은 그 IR만 신뢰한다.
3. **AI를 1급 저자로 가정**: 표현이 하나뿐인 문법, 기계가 읽는 진단, 계약에 포함된 보장 목록.

## 7. 핵심 전제와 뒤집을 신호

| 전제 | 틀렸다는 신호 | 그때 바꿀 것 |
|---|---|---|
| 아리아리 로직의 85% 이상이 escape hatch 없이 표현된다 | M6 포팅에서 escape hatch 코드 줄 수가 AIP 정의의 30% 초과 | primitive 재설계, 또는 "AIP = 검증 계층 + 기존 코드" 하이브리드로 방향 전환 |
| 컴파일러가 잡는 결함이 실제로 의미 있다 | 아리아리 결함 목록 중 정적 검출 비율 50% 미만 | 분석기 투자 축소, 런타임 가드 중심으로 |
| 생성된 실행 계획이 손으로 짠 것에 크게 밀리지 않는다 | 동일 시나리오 p95 지연이 원본 Spring 대비 1.5배 초과 | planner 전략 hint를 1급으로, 필요 시 SQL escape 허용 |
| LLM이 canonical 정의를 안정적으로 생성한다 | 같은 요구사항 10회 생성 시 구조 편차가 Spring 코드 생성 대비 줄지 않음 | 문법을 더 좁히거나 IR 직접 생성으로 전환 |
| Rust 단일 런타임이 개발 속도를 감당한다 | M2 종료 시점이 계획 대비 2배 지연 | 컴파일러는 Rust 유지, 런타임 일부를 TS로 선검증 |

## 8. 비전과 단계

- **3년 비전**: AIP 정의 파일과 환경변수만으로 운영 가능한 백엔드가 뜨고, 사람과 AI가 같은 언어로 백엔드를 작성하며, 백엔드 "유지보수"의 대부분이 컴파일러 진단 해결로 바뀐다.
- **올해의 집중**: 아리아리 한 서비스를 완전히 AIP로 재구현하고 원본보다 결함이 적고 성능이 뒤지지 않음을 증명한다. 나머지는 이 증명을 위해서만 한다.
- 단계별 산출물과 종료 조건은 `07-architecture-and-roadmap.md`.
