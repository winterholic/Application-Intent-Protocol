# FlaskBB 포팅이 드러낸 AIP 제품 갭

초기 근거는 2026-10-18 실DB 재검증(`evidence/run-752-*.log`)이며, G-2·G-5·G-8은 2026-10-19 main 구현과 독립 CI 근거로 갱신했다. 갭은 "제품에 없거나 우회가 필요한 것"만 적는다. 선언 오류로 판명된 것(F-4)은 갭이 아니라 선언 수정이며 3번에 주의점만 남긴다. core 대규모 변경은 하지 않았고 아래 설계안은 제안이다.

| ID | 갭 | 근거 | 현재 처리 | 설계안(미구현) |
|---|---|---|---|---|
| G-1 | 메일 공급자 계약이 없다. SMTP는 worker 네트워크 격리(macOS `mac_net_deny`, Linux `--unshare-net`) 때문에 구조적으로 불가능하다. `workers.isolation`에는 격리를 끄는 값이 없다 | 수정 전 `AIP_FLASKBB…mail-jobs`와 동일 설정으로 SMTP worker가 `FAILED`/`WIRE.EXTENSION_ERROR`. `sandbox-exec -p '(version 1)(allow default)(deny network*)' python3 -c "socket.create_connection(...)"` → `PermissionError: Operation not permitted`, 같은 호출을 격리 없이 실행하면 연결 성공 | 이미 있는 선언형 외부 통합을 사용한다. job에 `access http.mail`·`effect managed`, 서비스 설정 `workers.integrations`의 `mail` endpoint, worker는 `ctx.http.call("mail", payload, key)`만 호출. 공급자별 요청 본문(Mailpit `POST /api/v1/send` 형태)은 앱 코드 `build_payload` 한 곳 | 메일 전용 provider preset(SES v2·Postmark·SendGrid 요청 변환, 수신 동의·템플릿 계약)을 `integrations`의 `kind`로 두면 앱이 공급자 payload를 알 필요가 없다. 이미 [capability-gap F04](../../plan-docs/backend-capability/capability-gap-2026-10-13.md)에 "템플릿·수신 동의 계약 없음"으로 기록된 항목과 같은 갭이다 |

| G-3 | `exists R where a or b`는 `a or b` 전체가 행 조건이다(문법 `set-expr = source ident? ('where' expr)?`). 행과 무관한 선택지가 뒤에 오면 그 행 집합이 비었을 때 통째로 거짓이 된다. checker가 경고하지 않는다 | F-4. `canModerateForum`·`canDeleteTopic`이 이 때문에 `user_group`이 비면 primary-group Moderator를 거부. `spikes/spike-v1-fixture/tests/exists_scope.rs` 2 passed가 파서의 현재 동작이 문법과 같음을 고정 | `exists`를 괄호로 감쌌다(`app.aip` 상단 주석). 컴파일러는 문법대로이며 결함이 아니다 | checker에 advisory: `exists` 조건 안에서 최상위 `or`의 피연산자가 집합 행 필드를 하나도 참조하지 않으면 경고. 문법 문서에 같은 예를 추가 |
| G-4 | 검색은 대소문자 구분 부분 문자열(`contains`는 `strpos`)뿐이다. Whoosh의 토큰화·어간·순위·대소문자 무시가 없고 최상위 `search` 선언은 파서가 거부한다 | `search.test.mjs`가 `discount`로 `Discount 100% off`를 못 찾음, `%`·`_`는 리터럴, 단어 순서 의존을 고정. 최상위 `search`는 `DEF.LEX_UNEXPECTED_CHAR` | 색인 없이 항상 일관(쓰기 직후 반영, 행 정책 적용, 재시작 후 동일)이라 재색인 명령이 필요 없다 | 필터 연산 `icontains`(대소문자 무시)를 먼저, 순위 검색은 PostgreSQL FTS 기반 `search` 선언을 별도 설계 |
| G-5 | core Bool 정렬은 지원된다. 포팅 선언·화면의 미연결을 보완했다 | 원본 `Forum.get_topics`의 `important desc, last_updated desc`; Topic read에 `important` sort를 추가하고 UI SDK가 동일 순서와 동률 `id asc` 요청 | 로컬 UI·메일 단위 검사 20개 통과. 실제 2+2+1 페이지·행 정책·moderation 후 정렬 변경은 새 Linux CI 대기 | core 정렬 기능은 새 설계가 필요 없다. nullable 값은 기존 정렬 계약을 따르며 Topic published 행의 날짜 제약을 유지 |
| G-6 | Forum last-post 투영은 `Post.publish`에서만 갱신된다. 삭제·숨김 뒤 "남은 가장 최근 글"로 되돌리는 재계산을 `update` 효과가 표현하지 못한다(값은 현재 행에서만 가져온다) | `Post.publish`의 `update Forum … last_post = this` | 재계산 미선언. 읽는 쪽이 `Post` 읽기로 구할 수 있다 | `update … from latest Post where … by date_created` 같은 집합식 값 |
| G-7 | 새 값이 없는 필드의 create 입력 누락이 읽기 정책에서 NULL 의미로 번진다. nullable Bool에 `default database`를 줄 수 없는 외부 schema(원본은 ORM 기본값 `default=False`)에서 `hidden`이 NULL인 행은 `hidden != true`가 거짓이라 작성자에게도 안 보이고 후속 `Post.create`가 `WIRE.MISSING_TARGET`으로 실패한다 | F-2. 원본 `HideableMixin.hidden = Column(Boolean, default=False, nullable=True)`와 `HideableQuery`의 `hidden != True`도 SQL 3값 논리에서 NULL을 제외하므로 읽기 쪽 의미는 원본과 같다 | create가 `hidden: false`를 명시한다(UI도 동일). 시험 수정 | create 입력에서 서버 상수 기본값(`default false`)을 선언하는 문법. `default database`는 DB에 기본값이 있을 때만 의미가 있다 |
