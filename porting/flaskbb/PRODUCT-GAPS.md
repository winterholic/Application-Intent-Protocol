### 저장·생성·이관 계약

1. `Post.source_order`는 NULL이면 원순서 미입증이며 UUID/date에서 만들지 않는다. `PostOrder.post`는 NOT NULL FK+UNIQUE, Post.source_order는 FK+UNIQUE와 역참조 일치 check(`source_order.post = this`)를 갖는다. 공개 create fields/patch/apply/read에 순서 조작을 노출하지 않는다. `Topic.last_post`는 파생 FK이며 `TopicFirstPost.post`와 구별한다. 기본값을 첫 글로 추측해 채우지 않는다.
2. 새 source-equivalent 저장 시점은 `Post.publish`다(포팅 draft에는 원본의 저장된 Post 대응물이 없다). 같은 트랜잭션에서 `create PostOrder { post = this }`로 id를 생략하고, 이어 Post.source_order를 `latest PostOrder … where post = this … order by id select id`로 연결한다. 이는 **선택한 구현 방향이며 아직 DSL compile 미실행**이다. UNIQUE로 한 번만 생성하며 `from published=false`, 기존 idempotency/journal/fence를 유지한다. publish·Topic.last_post·Forum projection까지 전부 commit하거나 전부 rollback한다. sequence gap은 허용하고 숫자를 commit 시각·연속 카운터로 해석하지 않는다.
3. 기존/수입 데이터는 **검증된 source namespace의 원 Post.id ↔ 현재 UUID 일대일 manifest**가 있을 때만 PostOrder.id에 그 정수를 명시 입력한다. 중복 원 ID, 중복 UUID, 소스 불일치, 누락 및 기존 pair 변경은 전체 이관 거부다. `seed/install.py`는 신규 welcome 데이터만 만들며 과거 ID mapping을 보유하지 않는다. 신규 설치 seed도 native 서버 순서를 사용한다. 기존 UUID-only 행·내용·포인터는 보존한다. 원순서가 없는 행을 조용히 후보에서 누락시키지 않는다.
4. 순서 기반 hide/delete는 해당 후보 집합의 모든 live source-equivalent 행에 mapping이 있다는 가드를 둔다. 새 publish 할당은 같은 PostOrder namespace 전체의 과거 mapping과 source high-water가 입증된 뒤에만 허용한다. unknown UUID-only가 있으면 읽기·무관 편집을 보존하고 영향받는 순서 전이는 fail-closed한다. `not exists` completeness guard가 isolation marker에 연결되는지도 검사한다. 부분 import 뒤 native allocation을 먼저 열지 않는다. 모든 importer는 writer fence/기존 승인 migration 계약을 사용하고 import 중 publish와 경합하지 않는다. source sequence high-water와 기존 PostOrder 최대값 이상으로 generator를 맞추며 실패·rollback 때 낮추지 않는다.
5. additive schema preview → 원본 manifest 검증·dry run → 쓰기 fence → mapping/포인터 migration → 검증 후 활성화 순서다. 기존 migrate preview에서 cyclic FK·새 리소스·nullable 열 분류를 먼저 확인한다. 자동 backfill·운영 apply는 이 단계 범위 밖이다. rollback은 검증된 snapshot+정의/바이너리 조합으로 하고 UUID/FK를 재작성하거나 companion을 삭제하지 않는다. 신규 글이 생긴 뒤 구 generator·구 projection writer로 돌아가지 않는다. ### 필요한 generic effect 보완·첫 구현 순서

`latest`는 scalar마다 subquery를 만든다(`spike-v2-read/src/sqlgen.rs:497`). 이전 COALESCE는 선택된 NULL과 행 부재를 구별하지 못했다. 2026-10-31 후속 source는 독립 EXISTS/CASE로 행 부재에만 fallback하고 V1 nullability도 선택값을 보존하도록 교정했다(V1 RED→GREEN 7/7·전체/Clippy exit0). 다섯 projection의 nullable 후보·부재 전체 NULL·부재 fallback을 apply/bundle/compose로 대조하는 새 PG source와 V2 MySQL 바인딩 회귀는 추가했으나 아직 실행 전이다. 현재 `id DESC` tie-break는 여전히 UUID다. `update` 효과는 match 대상이 없으면 `WIRE.EFFECT_TARGET_MISSING`이므로 `where last_post=this`를 붙이는 것만으로 no-op branch를 구현할 수 없다. `apply_op`는 to 변경 후 effect를 실행한다(physical delete만 effect 선행). 현재 sema는 같은 update target resource를 latest source로 쓰는 것도 거부한다. 이 제약을 SQL 문자열·앱 endpoint로 우회하지 않는다.

첫 코어 증분에서 V1 update effect optional `when` parser/AST/H mapping/sema 계약을 추가했고 당시 `latest_effect_values` 5/5가 통과했다. 그 뒤의 guard/read-lock source 변경은 현재 검증되지 않았다: V3에서 pre-state update guard 대상 선택 및 apply/bundle/compose 전달, `Ctx::lock_reads` 참조 잠금 정책, V1 absence marker의 update guard coverage, MySQL conditional update 전이의 fail-closed `WIRE.ADAPTER_UNSUPPORTED` gate와 회귀 source를 추가했다. MySQL gate는 조건부 update만 거부하며 일반 transition은 차단하지 않는다. 이 변경은 compile·test 결과가 아니며 과거 V1 5/5를 수정 후 현재 tree의 통과로 재사용하지 않는다.

2026-10-30 독립 review 교정 source: V3 update-target ID 비교를 정렬 의미를 유지하는 slice-to-slice 비교로 바꿨다. V4 worker는 extension `access`에 열거된 모든 transition marker의 최강 격리를 선택한다. 자체 `invoke_write`와 미사용 caller-owned transaction은 첫 SQL에서 `SET TRANSACTION`을 하고, 이미 SQL을 실행한 caller-owned transaction에서 격리를 바꾸지 못하면 worker/ctx 호출 전에 `WIRE.UNSUPPORTED_ISOLATION`으로 거부한다. V6 HTTP write-extension owner는 advisory/idempotency SQL 전에 최강 access marker를 설정하고 V4 entry는 설정값을 검증한다. V6 durable apply-job owner도 요청 marker를 guard/lease/journal SQL 전에 선택한다. V4/V6 pure selector 및 이미 시작한 shared transaction 거부 회귀 source를 추가했으며, 기존 unmarked READ COMMITTED·caller commit/rollback test source는 보존했다. root trace는 V6 ordinary apply/bundle가 이미 request marker를 tx 시작 시 선택함을 확인했다. 이 교정은 source-only다. standalone rustc의 좁은 slice 비교 검사도 temp directory 생성 `Operation not permitted`로 막혔고 우회하지 않았다. Cargo·PostgreSQL 미실행이다.

V2 `latest_effect_value`는 당시 offline dependency resolution에서 lock `ctutils 0.4.4` 부재로 실행 전 막혔다. 이후 V3 compile-only 명령 `cargo test --manifest-path spikes/spike-v3-write/Cargo.toml --target-dir target --locked --test latest_effect_values --no-run`도 컴파일 전에 보호 `~/.cargo` registry cache의 `ctutils-0.4.4.crate` open `Operation not permitted`로 차단됐다. 같은 대상을 재시도하거나 별도 cache/engine을 쓰지 않는다. 신규 Rust source와 회귀는 미컴파일·미실행이며 실제 DB DSN도 없어 DB 시도 없음. actor/fence/transaction/isolation의 실DB 경합, V2 SQL/제품 경로, 한 nullable candidate row에서 5 projection 원자 복사도 미검증이다.

다음은 보호 Cargo cache에 접근 가능한 허용 검증 환경에서 기존 lockfile/target으로 compile 및 좁은 회귀를 실행하고, 이후 PG guard/read-set/isolation·V4 caller·V6 HTTP/durable transaction-owner 경로를 대조하는 것이다. 이어 V2 SQL/실제품 호출 경로의 조건 보존을 확인한다. before 포인터와 after 후보 구분, nullable candidate 하나에서 다섯 projection 원자 복사, 행 부재와 선택 field NULL, order/null/tie 정책도 남는다. DSL을 spike contract 검증 전 공식화하지 않는다. snapshot·선택·main row·child first-post·Topic/Forum 갱신·감사·journal은 같은 actor/fence/Tx 안에 둔다.

정확한 후속 파일: `spike-v1-fixture/src/{ast,parser,sema,isolation}.rs`, `spike-v3-write/src/lib.rs`, `spike-v4-worker/src/write.rs`, `spike-v4-worker/tests/{write_isolation,write_owned_transaction}.rs`, `spike-v6-transport/src/{write_extension,durable}.rs` 및 관련 unit/PG tests; 이어 `spike-v2-read/src/sqlgen.rs`/`tests/latest_effect_value.rs`, `crates/aip-migrate/src/mysql_write.rs`, migration 검증과 `porting/flaskbb/{app.aip,seed/install.py,tests/last-post-recompute.test.mjs}`. 기존 UI/SDK 의존도 참조 검색 후 잇는다. 먼저 source 변경을 허용된 환경에서 compile/behavior 검증하고, 이후 generic contract, PostOrder 생성·mapping migration을 잇는다.
